# 구조 결함 유형

`sw-design` review 4단계에서 읽는다. 화살표 하나(결합도)나 상자 하나(응집도)가 아니라 **의존 그래프 전체의 모양**에서 생기는 문제다. 의존 행렬과 Fan-In/Fan-Out, 불안정도를 입력으로 찾는다.

## 1. 의존 행렬과 지표

행 = 의존하는 쪽(From), 열 = 의존받는 쪽(To).

```
From \ To   A   B   C   D   Fan-Out
A           –   1       1     2
B               –   1         1
C                   –   1     1
D                       –     0
Fan-In      0   1   1   2
```

- Fan-Out = 행 합계 (내가 부르는 수)
- Fan-In = 열 합계 (나를 부르는 수)
- 불안정도 `I = Fan-Out / (Fan-In + Fan-Out)`. 0 = 안정(많이 불리고 안 부름), 1 = 불안정(아무도 안 부르고 많이 부름). 둘 다 0이면 계산 불가(고립).

행렬이 **상삼각(또는 하삼각) 형태**로 정렬 가능하면 순환이 없다. 대각선 양쪽에 모두 1이 있으면 순환이 있다.

## 2. 결함 유형

### 순환 의존 (Cyclic Dependency)

**판별:** A→B와 B→A가 모두 있음. 또는 A→B→C→A 경로. 행렬을 어떻게 정렬해도 삼각 형태가 안 됨.

**왜 문제인가:** 한쪽만 수정·테스트·배포할 수 없다. A를 테스트하려면 B가 필요하고 B를 테스트하려면 A가 필요하다. 사실상 하나의 패키지인데 둘로 나뉜 척하는 것이다.

**개선:** 한쪽이 상대에게서 필요로 하는 것을 **인터페이스로 추출**해 제3 패키지에 두고 양쪽이 그것에 의존하게 한다(의존 방향 역전). 또는 양쪽이 공유하는 부분을 새 패키지로 분리한다.

### 계층 역행 (Layer Violation)

**판별:** 하위 계층(도메인·인프라)이 상위 계층(표현·응용)을 가리키는 화살표.

계층 순서: 표현(UI) → 응용(서비스) → 도메인(핵심 규칙) → 인프라(DB·외부 연동). 화살표는 위에서 아래로만.

**왜 문제인가:** 하위가 상위에 끌려간다. 도메인 규칙이 화면 때문에 바뀌고, 도메인을 다른 화면에서 재사용할 수 없다.

**개선:** 하위가 상위를 직접 부르지 않고 **이벤트·콜백·인터페이스**로 알린다. 하위가 인터페이스를 정의하고 상위가 구현한다.

### 허브 패키지 (Hub)

**판별:** Fan-In도 높고 Fan-Out도 높음. 기준: 각각 전체 상위 20% 안에 들거나, Fan-Out이 7을 넘으면서 Fan-In이 2 이상.

**왜 문제인가:** 모든 변경이 여기를 지나간다. 영향 범위(Fan-In)와 복잡도(Fan-Out)가 동시에 최대다. 이 패키지 담당자가 병목이 된다.

**개선:** 역할을 나눈다. 부르는 쪽 역할(조정)과 불리는 쪽 역할(제공)을 분리하거나, Fan-Out을 줄이기 위해 하위를 묶는 중간 패키지(퍼사드)를 둔다.

### 쓰레기통 패키지 (Garbage Bin)

**판별:** Fan-In 높음 + 응집도 논리적 이하. 이름이 `common`, `util`, `shared`, `base`, `core`인 경우가 대부분.

**왜 문제인가:** 서로 무관한 것들이 묶여 있어 하나를 고치면 그것과 무관한 모든 의존 패키지가 재컴파일·재테스트된다. 시간이 갈수록 "어디 둘지 모르는 것"이 다 여기로 들어와 커진다.

**조건부 허용:** 안의 요소들이 서로 독립적이고 거의 변경되지 않는 읽기 전용 참조 데이터(코드 테이블, 상수)뿐이면 실제 위험이 없으므로 허용한다. 단, 책임 문장에 "변경이 드문 읽기 전용 기준값만 둔다"는 제약을 적는다.

**개선:** 목적별로 분할한다. `common` → `dateutil`, `config`, `validation`, `logging`. 각각 Fan-In은 유지되지만 응집도가 올라가고, 변경 영향이 해당 목적을 쓰는 패키지로만 제한된다.

### 안정성 위반 (Stability Violation)

**판별:** 불안정도가 낮은(안정) 패키지가 불안정도가 높은(불안정) 패키지에 의존. 화살표가 I 작은 쪽 → I 큰 쪽.

**왜 문제인가:** 안정적이어야 할 패키지(많은 곳이 의존)가 자주 바뀌는 패키지 때문에 흔들린다. 흔들림이 그 패키지에 의존하는 모든 곳으로 전파된다.

**개선:** 의존 방향을 역전한다. 안정 패키지가 필요로 하는 것을 인터페이스로 정의해 안정 패키지 쪽에 두고, 불안정 패키지가 그것을 구현한다.

### 고립 패키지 (Isolated)

**판별:** Fan-In = 0 이고 Fan-Out = 0.

**왜 문제인가:** 쓰이지 않는 코드이거나, 의존도 입력에서 화살표를 빠뜨린 것이다. 입력 오류일 가능성을 먼저 확인한다.

**주의:** Fan-In = 0 이지만 Fan-Out > 0 인 패키지는 고립이 아니다. 최상위 진입점(UI, 배치 작업)이 그렇다. 정상이다.

### 정보 은닉 위반 (Information Hiding Violation)

**판별:** 내용 결합도 화살표가 1건이라도 있음.

**왜 문제인가:** 한 패키지의 내부 구현 변경이 다른 패키지로 바로 전파된다. 내부를 자유롭게 바꿀 수 없으므로 리팩터링·최적화가 불가능해진다.

**개선:** 내부 필드를 감추고 공개 메서드만 노출한다. 내부 클래스는 export하지 않는다.

## 3. 점검 순서

1. 행렬에서 순환을 찾는다(대각선 대칭 위치에 둘 다 1).
2. 계층 열을 보고 하위 → 상위 화살표를 찾는다.
3. Fan-In, Fan-Out 상위 패키지를 뽑아 허브와 쓰레기통을 본다.
4. 불안정도를 계산해 화살표 방향을 확인한다.
5. 0/0 패키지를 찾는다.
6. 결합도 판정표에서 내용 결합을 찾는다.

## 4. 결함 목록 양식

| 결함 | 관련 패키지 | 근거 화살표 | 심각도 |
|------|------------|-------------|--------|
| 순환 의존 | grade ↔ enrollment | D4, D7 | 높음 |
| 쓰레기통 | common | Fan-In 3, 응집도 논리적 | 중간 |
| 정보 은닉 위반 | grade → enrollment | D7 | 높음 |

심각도: 순환·내용 결합·공통 결합 = 높음. 계층 역행·허브·쓰레기통·안정성 위반 = 중간. 고립 = 확인 필요.

## 5. 개선 우선순위

1. **내용 결합, 공통 결합, 순환 의존** — 이 셋이 남아 있으면 다른 개선이 의미 없다. 가장 먼저 없앤다.
2. 계층 역행, 안정성 위반 — 의존 방향 문제. 인터페이스 추출로 해결.
3. 쓰레기통, 허브 — 분할.
4. 제어·스탬프 결합, 절차적·시간적 응집 — 품질 개선.

## 6. 개선 후 부작용 점검

- 패키지를 쪼갰더니 어떤 패키지의 Fan-Out이 7을 넘지 않았는가
- 새로 만든 인터페이스 패키지가 또 다른 `common`이 되지 않았는가
- 분할로 패키지 수가 두 배가 되어 전체 그림을 이해하기 어려워지지 않았는가 (분할도 한도가 있다)
- 순환을 끊으려 만든 인터페이스가 실제로는 한 구현체만 있어 불필요한 간접 계층이 되지 않았는가
