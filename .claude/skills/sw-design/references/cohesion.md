# 응집도(Cohesion) 7등급

`sw-design` review 3단계에서 읽는다. 응집도는 **한 모듈 안의 구성 요소들이 하나의 목적을 위해 얼마나 밀접하게 뭉쳐 있는가**다. 높을수록 모듈이 한 가지 역할에 집중한 좋은 설계다. 등급은 약한(나쁜) 것부터 강한(좋은) 것 순서로 우연적 → 논리적 → 시간적 → 절차적 → 통신적 → 순차적 → 기능적이다.

## 1. 등급 정의

### 우연적 응집도 (Coincidental Cohesion) — 가장 낮음, 최악

아무 관련 없는 요소들이 우연히 한 모듈에 모여 있다. 초기화 코드, 파일 읽기, 로그인 검증이 한 곳에 있는 식이다.

증상: 모듈 이름을 지을 수 없다. "기타", "misc", "helper"가 된다. 하나를 고치면 왜 다른 것이 깨지는지 알 수 없다.

### 논리적 응집도 (Logical Cohesion)

**종류가 비슷한** 기능들이 모여 있다. 출력 함수 모음(`printPDF`, `printExcel`, `printWord`), 날짜·문자열·숫자 변환이 섞인 `util`.

증상: 모듈 이름이 "~유틸", "~헬퍼", "공통". 호출하는 쪽이 어떤 기능을 쓸지 플래그로 고르는 경우가 많다(제어 결합 유발). 서로 독립적이라 하나를 고쳐도 나머지는 영향 없지만, 같은 모듈이라 함께 재컴파일·재테스트된다.

허용 예외: 변경이 거의 없는 읽기 전용 기준 데이터(코드 테이블 모음)만 모인 참조 패키지. 서로 독립적이고 거의 바뀌지 않으면 쓰레기통의 실제 위험(무관한 것이 함께 흔들림)이 없으므로 조건부로 허용한다. 단, 여기에 설정·공지·유틸 함수가 추가되는 순간 쓰레기통이 된다.

### 시간적 응집도 (Temporal Cohesion)

**같은 시점**에 실행되기 때문에 모여 있다. 시스템 시작 시 실행되는 초기화 함수들(DB 연결, 설정 로드, 캐시 준비), 종료 시 정리 함수들.

증상: 모듈 이름이 `init`, `startup`, `shutdown`. 요소들끼리 데이터를 주고받지 않는다.

개선: 각 초기화를 해당 기능 모듈로 옮기고, 시작 모듈은 호출 순서만 가진다.

### 절차적 응집도 (Procedural Cohesion)

**업무 순서상** 함께 실행되기 때문에 모여 있다. "회원 등록 → 아이디 확인 → 저장"처럼 순서는 있지만 **데이터를 공유하지는 않는다.** 앞 단계 출력이 뒤 단계 입력이 아니다.

증상: 순서도 한 장이 모듈 하나가 됨. 순서가 바뀌면 모듈이 바뀐다.

### 통신적 응집도 (Communicational Cohesion)

**같은 데이터(엔티티)** 를 다루기 때문에 모여 있다. 학생 정보를 조회·수정·삭제하는 기능들, 성적 레코드를 입력·수정·조회하는 기능들.

특징: 입력 데이터 또는 출력 데이터가 같다. 엔티티 중심 설계(테이블 하나, 클래스 하나를 책임지는 모듈)가 보통 여기에 해당한다. 실무에서 가장 흔한 "좋은" 등급이다.

### 순차적 응집도 (Sequential Cohesion)

**한 요소의 출력이 다음 요소의 입력**이 된다. 파이프라인. "성적 검증 → 등급 계산 → 저장"에서 검증 결과가 등급 계산에 들어가고, 등급 계산 결과가 저장에 들어간다.

특징: 요소 순서를 바꿀 수 없다. 전체가 하나의 변환 흐름.

### 기능적 응집도 (Functional Cohesion) — 가장 높음, 이상적

모든 요소가 **하나의 명확한 기능**만을 위해 존재한다. "등급 계산"만 하는 모듈, "결제 승인"만 하는 모듈.

특징: 모듈 이름이 동사+목적어 한 개로 정확히 설명된다. 다른 어떤 것도 섞여 있지 않다. 재사용·테스트·이해가 가장 쉽다.

## 2. 판정 질문표 (좋은 것부터)

모듈(패키지) 하나를 놓고 "안의 요소들이 왜 같이 있는가"를 위에서부터 묻는다. 먼저 "예"가 나오는 것이 등급이다.

| 순서 | 질문 | 등급 | 기본 판정 |
|------|------|------|-----------|
| 1 | 모든 요소가 **하나의 기능**만을 위해 존재하는가? | 기능적 | 허용 |
| 2 | 한 요소의 **출력이 다음 요소의 입력**으로 이어지는가? | 순차적 | 허용 |
| 3 | **같은 데이터(엔티티)** 를 다루기 때문에 모였는가? | 통신적 | 허용 |
| 4 | 업무 **순서상** 함께 실행되어서 모였는가? (데이터 공유 없음) | 절차적 | 검토 |
| 5 | **같은 시점**(초기화·종료)에 실행되어서 모였는가? | 시간적 | 검토 |
| 6 | **종류가 비슷**해서(출력 모음, 유틸 모음) 모였는가? | 논리적 | 불허 (읽기 전용 참조 데이터만 조건부 허용) |
| 7 | 아무 이유 없이 모였는가? | 우연적 | 불허 |

좋은 것부터 묻는 이유: 한 모듈이 "같은 데이터를 다루면서 순서대로 실행"되면 순차적(더 좋은 쪽)이다. 나쁜 쪽부터 물으면 절차적으로 낮게 판정한다.

## 3. 책임 문장 테스트

모듈의 책임을 한 문장으로 쓰게 하고 문장을 본다.

| 문장 모양 | 의심 등급 |
|-----------|-----------|
| "A를 한다" (동사 하나) | 기능적 |
| "A를 받아 B로 바꾸고 C에 넘긴다" | 순차적 |
| "X(엔티티)의 등록·조회·수정을 처리한다" | 통신적 |
| "A를 한 다음 B를 한다" (데이터 연결 없음) | 절차적 |
| "시작할 때 필요한 것들을 준비한다" | 시간적 |
| "A, B, C 같은 도구를 모아 둔다" | 논리적 |
| 문장을 쓸 수 없다 / "기타" | 우연적 |
| 문장에 "그리고", "및", "등"이 들어감 | 두 개 이상의 책임. 나눈다 |

이름 테스트: `common`, `util`, `misc`, `base`, `core`, `helper`, `manager`는 논리적·우연적 응집의 신호다. 이름이 그렇게밖에 안 지어진다면 안의 것들이 서로 무관하다는 뜻이다.

## 4. 잘못 배치된 요소 찾기

모듈 안의 요소(클래스, 함수, 테이블)마다 연결 수를 센다.

- 내부 연결: 같은 모듈 안의 다른 요소와의 호출·참조 수
- 외부 연결: 다른 모듈의 요소와의 호출·참조 수

**내부 연결 < 외부 연결**이면 그 요소는 지금 모듈보다 다른 모듈에 더 가깝다. 가장 많이 연결된 모듈로 옮긴다. 이 한 번의 이동이 응집도를 올리고 결합도를 동시에 내린다.

## 5. 응집도와 결합도의 관계

| 구분 | 응집도 | 결합도 |
|------|--------|--------|
| 보는 곳 | 모듈 **안** | 모듈 **사이** |
| 좋은 방향 | 높게 | 낮게 |
| 질문 | 왜 같이 있는가 | 무엇을 주고받는가 |
| 비유 | 한 사람이 한 일에 집중 | 사람끼리 서로 간섭하지 않음 |

둘은 보통 함께 움직인다. 응집도가 낮은 모듈(무관한 것이 섞임)은 그 무관한 것들이 각각 바깥과 연결되어 결합도도 높아진다. 응집도를 올리는 분할이 결합도도 내린다.

"한 모듈"에 대한 질문이면 응집도, "두 모듈"에 대한 질문이면 결합도다.

## 6. 개선 기법

| 문제 | 개선 |
|------|------|
| 논리적·우연적 | 목적별로 분할. `common` → `dateutil`, `config`, `validation` |
| 시간적 | 초기화 내용을 각 기능 모듈로 분산, 시작 모듈은 호출 순서만 |
| 절차적 | 데이터 흐름을 기준으로 다시 묶거나(순차적으로), 기능별로 분리 |
| 잘못 배치 | 가장 많이 연결된 모듈로 이동 |
| 책임 문장에 "그리고" | 접속사 앞뒤로 모듈을 나눈다 |
