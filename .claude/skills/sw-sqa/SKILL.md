## 목적

품질 보증은 소프트웨어가 처음 정한 요구사항을 만족하는지 **개발 전 단계에 걸쳐** 계획적·체계적으로 확인하는 활동이다. 개발자는 "정확하게 만들었다"고 생각하고 사용자는 "써 보니 부족하다"고 느끼는 간극이 반복되기 때문에 필요하다.

이 스킬은 세 가지를 한다.

1. **검토 회의 준비와 기록**: 정형 기술 검토(FTR), 워크스루, 인스펙션 중 상황에 맞는 것을 골라 체크리스트를 만들고 결과를 기록한다.
2. **품질 판정**: 품질 표준 11개와 요구사항 추적표로 산출물 전체를 점검하고, 코드 리뷰·테스트 결과의 추세를 본다.
3. **위험 감시**: `plan.md`의 위험 목록을 현재 시점으로 갱신하고 대응 전략을 확정한다.

결과는 `docs/sw/sqa.md`에 검토 회차별로 누적된다. 배포(제품 기준선) 결정의 근거 문서이며, `sw-maintain`이 인수 시점의 품질 상태를 참조한다.

## 입력

- `docs/sw/srs.md`: 요구사항 ID와 추적표. 없으면 `/sw-srs`를 먼저 안내하고 중단한다. 추적할 요구가 없으면 품질을 판정할 기준이 없다.
- `docs/sw/plan.md`: 위험 목록과 품질 목표. 없으면 위험 감시 절을 "계획서 부재"로 표시하고 `/sw-plan`을 안내한다. 판정은 "조건부"를 넘지 못한다.
- `docs/sw/design-oo.md` 또는 `docs/sw/design.md`, `docs/sw/design-review.md`: 설계 품질 판정에 쓴다.
- `docs/sw/code-review.md`, `docs/sw/test.md`: 일치 품질 판정에 쓴다. 없으면 해당 항목을 "미수행"으로 적고 판정에 반영한다.
- 검토 대상: 인자로 특정 산출물(예: `srs.md`)이 오면 그 산출물에 대한 검토 회의만 준비한다. `release`가 오면 전체 산출물을 대상으로 배포 판정을 한다. 인자가 없으면 사용자에게 묻는다.
- `--risk-only`: 위험 감시 절만 갱신한다.
- 사용자에게 물을 것: 검토 참석자와 역할(진행자, 기록자, 검토자, 작성자), 회의 시간, 이미 발견된 결함이 있는가.

## 절차

### 1. 검토 시점과 유형 결정

SQA는 세 시점에서 수행된다. 지금이 어느 시점인지 먼저 정한다.

| 시점 | 활동 | 대상 | 이 스킬에서 |
|------|------|------|-------------|
| 초기 | 요구사항과 품질 목표 정의 | `srs.md`, `plan.md` | 품질 목표가 측정 가능한 수치로 적혀 있는지 확인 |
| 중간 | 정형 기술 검토(FTR) | 설계서, 코드, 테스트 계획 | 검토 회의 준비·기록 |
| 최종 | 테스트와 디버깅 결과 확인 | `test.md`, `code-review.md` | 배포 판정 |

검토 유형은 `references/review-types.md`를 읽고 고른다.

| 상황 | 유형 | 인원 | 시간 |
|------|------|------|------|
| 문서·코드 초안을 조기에 훑어 오류를 빨리 찾고 싶다 | 워크스루 | 3~5명 | 2시간 이내 |
| 워크스루를 표준 절차와 체크 항목으로 수행하고 싶다 | 구조적 워크스루 | 3~5명 | 2시간 이내 |
| 산출물을 공식 승인(기준선)하려 한다 | 정형 기술 검토(FTR) | 3~10명 | 2시간 이내 |
| 전문가가 체크리스트로 결함 밀도를 측정하려 한다 | 인스펙션 | 1~4명 전문가 | 산출물 크기에 비례 |

### 2. 검토 회의 준비 (FTR 기준)

`references/ftr-checklist.md`를 읽는다. 지침 여섯 가지를 결과서 머리에 적고, 회의 중 지켰는지 사후에 체크한다.

1. **제품을 검토한다. 사람을 평가하지 않는다.** 결함 기록에 작성자 이름을 적지 않는다. 산출물 이름과 위치만 적는다.
2. **의제를 제한한다.** 검토 범위(파일, 절, 줄 범위)를 미리 정하고 결과서에 적는다. 범위 밖 지적은 "별도 검토 항목"으로 따로 모은다.
3. **논쟁과 반박을 제한한다.** 회의에서는 결함을 **확인만** 하고 해결책을 논의하지 않는다. "이렇게 고치면 된다"는 발언이 나오면 기록자가 "결함 확인, 해결은 회의 후"로 정리한다.
4. **참가자를 3~10명으로 제한한다.** 역할: 진행자(검토 주재, 작성자가 아님), 기록자, 검토자 2명 이상, 작성자(답변만).
5. **사전 준비를 강제한다.** 산출물을 최소 하루 전에 배포하고, 검토자는 회의 전에 결함 후보를 적어 온다. 준비 없이 온 검토자는 회의에서 제외한다.
6. **체크리스트로 검토한다.** 산출물 유형별 체크리스트(`references/ftr-checklist.md` 2~5절)를 쓴다. 즉흥 질문은 체크리스트 항목에 매핑한다.

준비 산출물: 검토 안내(대상·범위·일시·참석자·역할·배포한 자료), 유형별 체크리스트, 결함 기록 양식.

### 3. 검토 수행과 기록

1. 작성자가 산출물을 5분 이내로 개관한다. 변명이나 해설은 하지 않는다.
2. 진행자가 체크리스트 항목 순서대로 묻는다. 검토자가 준비해 온 결함 후보를 해당 항목에서 제시한다.
3. 기록자가 결함마다 `DF-nnn` 번호, 위치, 체크리스트 항목, 심각도(치명/중/경), 유형(누락/오류/불일치/모호/표준 위반)을 적는다.
4. 회의 종료 5분 전에 결함 수를 집계하고 판정을 내린다. 판정은 셋 중 하나다.
   - **승인**: 수정 없이 기준선 확정
   - **조건부 승인**: 지적 사항 수정 후 진행자 단독 확인으로 확정
   - **재검토**: 수정 후 회의 다시 소집
5. 회의는 2시간을 넘기지 않는다. 범위가 남으면 2차 회의를 잡는다.
6. 결함 수정은 회의 **후**에 작성자가 한다. 수정 결과는 다음 회차 결과서에서 "이전 결함 처리 현황"으로 확인한다.

### 4. 품질 표준 점검

`references/quality-attributes.md`를 읽는다. 품질을 두 측면으로 나눈다.

| 측면 | 질문 | 근거 산출물 |
|------|------|-------------|
| 설계 품질 | 설계자가 정한 기능·성능·구조 기준이 제대로 정의되었는가 | `srs.md`, `design*.md`, `design-review.md` |
| 일치 품질 | 설계서에 적힌 내용이 개발 과정에서 지켜졌는가 | `code-review.md`, `test.md` |

품질 표준 11개(정확성, 신뢰성, 효율성, 무결성, 사용 용이성, 유지보수성, 유연성, 시험 용이성, 이식성, 재사용성, 상호운용성)마다:

1. SRS에 해당 속성의 목표가 **수치**로 있는가 (없으면 "목표 미정의")
2. 측정 방법이 `test.md`에 있는가
3. 측정 결과가 목표를 만족하는가

세 질문에 예/아니오로 답하고 표로 만든다. 모든 속성이 모든 프로젝트에 필수는 아니다. SRS에 목표가 없는 속성은 "해당 없음"이 아니라 "목표 미정의"로 적어 초기 시점의 누락을 드러낸다.

### 5. 요구사항 추적과 미구현 확인

1. `srs.md`의 추적표(요구 ID ↔ 설계 모듈 ↔ TC)를 기준으로 한다. `test.md`의 추적표가 더 최신이면 그것을 쓴다.
2. 요구 ID마다 네 열을 채운다: 설계 반영(예/아니오), 구현(예/아니오/부분), 테스트 합격(예/아니오/미실행), 비고.
3. 미구현 요구, 설계에만 있고 요구에 없는 모듈(요구 없는 기능), 테스트가 없는 요구를 각각 목록으로 뽑는다.
4. "요구 없는 기능"은 결함이다. 범위 밖 작업이거나 승인 없는 변경이다.

### 6. 검증·확인·인증·시험·디버깅 구분

결과서에 아래 다섯 활동이 각각 수행되었는지, 누가 했는지 적는다. `references/review-types.md` 4절.

| 활동 | 질문 | 수행 여부 근거 |
|------|------|----------------|
| 검증 (Verification) | 설계·구현이 올바르게 만들어졌는가 | 코드 리뷰, FTR, 단위·통합 테스트 |
| 확인 (Validation) | 만들어진 것이 사용자가 원한 것인가 | 검증 단계 테스트에 사용자 참여, 프로토타입 평가 |
| 인증 (Certification) | 전문가·기관이 품질을 공식 인정했는가 | 외부 감리, 보안 인증 (해당 시) |
| 시험 (Test) | 오류를 찾기 위해 실행했는가 | `test.md` 실행 이력 |
| 디버깅 (Debugging) | 발견된 오류의 원인을 찾아 수정했는가 | 실패 TC의 수정 커밋 |

확인(Validation)에 사용자가 참여하지 않았으면 결과서에 명시한다. 개발자만으로는 "원한 것인가"에 답할 수 없다.

### 7. 위험 감시와 갱신

`references/risk-management.md`를 읽는다. `plan.md`의 위험 목록을 가져와 현재 시점으로 갱신한다.

1. **식별 갱신**: 계획 때 없던 새 위험이 생겼는가. 코드 리뷰·테스트에서 드러난 기술 위험(복잡도 초과 모듈, 성능 미달)을 추가한다.
2. **분석·평가 갱신**: 위험마다 발생 확률(높/중/낮)과 영향(파멸적/중대/경미)을 다시 매긴다. 위험 표(Risk Table)에는 위험 내용, 범주(프로젝트/기술/비즈니스), 확률, 영향, 대응을 적는다. **발생 시간은 적지 않는다.** 언제 일어날지는 예측 대상이 아니다.
3. **계획 확인**: 위험마다 대응 전략이 있는가. 회피(원인 제거) > 감시(징후 관찰) > 비상 계획(발생 시 대책) 순으로 선호한다.
4. **감시·조치**: 징후가 보이는 위험, 이미 발생한 위험을 표시하고 조치 내용을 적는다. 모니터링은 "위험 징후를 계속 인지하는 것"이다.
5. Charette 분류(알려진 위험 / 예측 가능한 위험 / 예측 불가능한 위험)를 열로 둔다. 예측 불가능한 위험은 비상 계획만 가능하다.

위험 목록에 넣지 않는 것: 유지보수(개발 이후 단계의 활동이지 개발 위험이 아니다), 소프트웨어 사용자 자체의 위험성(분석 대상은 프로젝트·기술·일정·예산이다).

### 8. 판정과 저장

1. 집계: 미해결 치명 결함 수, 미구현 FR 수, 미달 NFR 수, 목표 미정의 품질 속성 수, 발생·징후 위험 수.
2. 판정 기준(아래)에 따라 합격 / 조건부 / 불합격.
3. `docs/sw/sqa.md`가 없으면 `templates/sqa.md`로 만들고, 있으면 `## 검토 YYYY-MM-DD (대상)` 절을 추가한다. 이전 회차 결함의 처리 현황을 먼저 적는다.
4. 합격이면 제품 기준선 태그와 배포 절차를 다음 행동에 적는다.

## 판정 기준

| 판정 | 조건 (모두 만족) |
|------|------------------|
| 합격 (배포 가능) | 미해결 치명 결함 0, 미구현 FR 0, NFR 측정값 전부 합격, FTR 지침 6개 전부 준수, 확인(Validation)에 사용자 참여, 발생 상태 위험 0 |
| 조건부 | 치명 0, 미구현 FR이 있으나 발주자가 서면으로 범위 축소에 동의, 또는 NFR 1건 미달이나 개선 계획 기한 확정, 또는 `plan.md` 부재로 위험 감시 생략 |
| 불합격 | 치명 결함 1 이상, 또는 발주자 동의 없는 미구현 FR, 또는 NFR 2건 이상 미달, 또는 확인에 사용자 미참여, 또는 발생 상태 위험에 조치 없음 |

치명 결함: 요구사항과 모순되는 동작, 데이터 손실·무결성 훼손, 권한 우회, 설계 기준선과 다른 인터페이스로 구현.

## 출력

- `docs/sw/sqa.md`. 양식은 `templates/sqa.md`.
- 완성 예시는 `examples/sqa.md` (학사관리 시스템 배포 전 FTR).
- 검토 회의용 체크리스트와 결함 기록 양식은 `references/ftr-checklist.md`에서 복사해 쓴다.

## 체크리스트

- [ ] 검토 유형(워크스루/구조적 워크스루/FTR/인스펙션)을 상황에 맞게 골랐고 인원·시간 제한을 지켰다
- [ ] 결함 기록에 사람 이름이 없다
- [ ] 회의에서 해결책을 논의하지 않았고, 수정은 회의 후로 미뤘다
- [ ] 품질 표준 11개마다 목표·측정·결과 세 질문에 답했다
- [ ] 설계 품질과 일치 품질을 구분해 적었다
- [ ] 요구 없는 기능을 결함으로 잡았다
- [ ] 검증과 확인을 구분했고, 확인에 사용자가 참여했는지 적었다
- [ ] 위험 표에 발생 시간 열이 없다
- [ ] 위험 목록에 유지보수나 사용자 자체를 넣지 않았다
- [ ] 대응 전략을 회피 > 감시 > 비상 계획 순으로 검토했다
- [ ] 이전 회차 결함의 처리 현황을 먼저 적었다
- [ ] 산출물 둘째 줄 헤더를 갱신했다

## 자주 하는 실수

- 검토 회의가 설계 토론으로 변한다. 결함 확인과 해결은 분리한다. 해결책이 필요하면 회의 후 작성자가 안을 만들어 진행자 확인을 받는다.
- 테스트 합격률만 보고 배포를 결정한다. 테스트는 일치 품질의 일부다. 요구 커버리지, 미구현 목록, 위험 상태, 사용자 확인 참여를 함께 본다.
- 품질 속성을 "신뢰성 양호"처럼 형용사로 적는다. 목표 수치, 측정 방법, 측정값 세 칸이 비어 있으면 판정이 아니다.
- 위험 표에 "발생 예상 시점"을 넣는다. 예측할 수 없는 값을 적으면 표 전체의 신뢰가 떨어진다. 확률과 영향만 적는다.
- 계획 때 적은 위험을 그대로 복사한다. 코드 리뷰와 테스트가 드러낸 새 기술 위험을 추가하고, 소멸한 위험은 종료 처리한다.
- 결함을 발견한 사람이 수정 방법까지 지시한다. 작성자가 안을 내고 검토자는 수정 결과만 확인한다.
- 매 회차 결과서를 새 파일로 만든다. 한 파일에 누적해야 결함 추세와 위험 변화를 볼 수 있다.
