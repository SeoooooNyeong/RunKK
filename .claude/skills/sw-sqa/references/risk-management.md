# 위험 관리 (Risk Management)

프로젝트 추진 과정에서 예상되는 돌발 상황을 **미리 예측**하고 **대책을 세우는** 활동이다. `sw-plan`이 계획 시점의 위험 목록을 만들고, `sw-sqa`가 검토 회차마다 갱신한다. 나선형 모형에서는 매 바퀴 수행한다.

## 1. 위험의 종류

| 종류 | 내용 | 예 |
|------|------|----|
| 프로젝트 위험 | 일정·비용·자원·범위를 위협 | 일정 지연, 예산 초과, 핵심 인력 이탈, 요구사항 변경 |
| 기술적 위험 | 품질·구현 가능성을 위협 | 성능 미달, 기술 선택 실패, 외부 시스템 연동 불가, 복잡도 초과 |
| 비즈니스 위험 | 제품의 시장·전략 가치를 위협 | 시장 실패, 전략 불일치, 사용자 요구와 불일치, 발주자 조직 변화 |

가장 대표적인 위험은 **사용자 요구사항 변경**이다. 일정·비용·설계가 함께 흔들린다.

위험 목록에 넣지 않는 것:
- **유지보수**: 개발이 끝난 뒤의 활동이지 개발 단계의 위험 요소가 아니다.
- **소프트웨어 사용자 자체의 위험성**: 위험 분석의 대상은 프로젝트·기술·일정·예산이다. 사용자가 어떤 사람인가는 요구사항 분석의 입력이지 위험 분석 대상이 아니다.

## 2. Charette의 분류

| 분류 | 의미 | 예 | 가능한 대응 |
|------|------|----|-------------|
| 알려진 위험 (Known) | 지금 이미 알고 있다 | 인력 부족, 일정 촉박, 미확정 요구 | 회피, 감시, 비상 계획 모두 가능 |
| 예측 가능한 위험 (Predictable) | 과거 경험으로 예측할 수 있다 | 고객 요구 변경, 기술 경험 부족, 외부 연동 지연 | 감시 + 비상 계획 |
| 예측 불가능한 위험 (Unpredictable) | 미리 알 수 없다 | 자연재해, 갑작스러운 정책 변경, 발주 조직 개편 | 비상 계획만 |

## 3. 위험 관리 절차 (순서 고정)

```
1. 위험 식별 ─▶ 2. 위험 분석·평가 ─▶ 3. 위험 관리 계획 ─▶ 4. 위험 감시·조치
   목록화          확률·영향, Risk Table    대응 전략 문서화       징후 인지, 발생 시 대응
```

### 3.1 위험 식별

가능한 위험 요소를 목록화한다. 체크리스트를 쓴다.

| 범주 | 질문 |
|------|------|
| 요구 | 요구가 확정되었는가. 발주자 담당이 바뀔 가능성은 |
| 인력 | 핵심 기술 보유자가 1명뿐인가. 이탈 시 대체가 있는가 |
| 일정 | 임계 경로에 여유가 있는가. 외부 일정(학기 시작)에 묶여 있는가 |
| 기술 | 처음 쓰는 기술이 있는가. 성능 요구를 검증한 적이 있는가 |
| 외부 | 외부 시스템·조직에 의존하는가. 그쪽 일정을 통제할 수 있는가 |
| 비용 | 산정 근거가 과거 데이터인가 감인가 |

코드 리뷰·테스트 단계에서 추가되는 기술 위험: 순환 복잡도 10 초과 모듈, NFR 측정값 미달, 설계와 다른 의존 구조.

### 3.2 위험 분석·평가

위험마다 발생 확률과 영향을 매기고 위험 표(Risk Table)를 만든다.

| 항목 | 값 |
|------|----|
| 위험 내용 | 한 문장 |
| 범주 | 프로젝트 / 기술 / 비즈니스 |
| Charette 분류 | 알려진 / 예측 가능 / 예측 불가 |
| 발생 확률 | 높(70% 이상) / 중(30~70%) / 낮(30% 미만) |
| 영향 | 파멸적(프로젝트 중단) / 중대(일정·비용 20% 이상) / 경미(흡수 가능) |
| 우선순위 | 확률 × 영향으로 정렬 |

**위험 발생 시간은 적지 않는다.** 언제 일어날지는 예측할 수 없으므로 표에 넣으면 거짓 정밀도가 된다.

### 3.3 위험 관리 계획

위험마다 대응 전략을 정해 문서화한다. 선호 순서가 있다.

| 전략 | 내용 | 언제 |
|------|------|------|
| 회피 (Avoid) | 위험의 원인을 제거해 발생하지 않게 한다. **가장 좋은 전략** | 원인을 통제할 수 있을 때. 예: 미검증 기술 대신 검증된 기술 선택 |
| 감시 (Monitor) | 징후를 계속 관찰해 발생을 사전에 감지한다 | 회피할 수 없지만 징후가 보이는 위험. 예: 발주자 회의록에서 요구 변경 언급 추적 |
| 비상 계획 (Contingency) | 회피·감시에 실패해 발생했을 때 쓸 대비책 | 모든 위험에 하나씩. 예측 불가 위험에는 이것만 가능 |

하나의 위험에 셋을 모두 둘 수 있다. 회피 조치 + 감시 지표 + 비상 계획.

### 3.4 위험 감시·조치

- **모니터링**은 위험 요소의 **징후를 계속적으로 인지**하는 것이다. 지표와 점검 주기를 정한다.
- 징후가 보이면 상태를 "징후"로 바꾸고 회피 조치를 강화한다.
- 발생하면 상태를 "발생"으로 바꾸고 비상 계획을 실행한다. 조치 내용과 결과를 기록한다.
- 원인이 사라지면 "종료"로 바꾼다.

## 4. 위험 표 양식

| ID | 위험 | 범주 / 분류 | 확률 / 영향 | 대응 (회피 / 감시 / 비상) |
|----|------|-------------|-------------|---------------------------|
| R-01 | 교무처 담당자 교체로 요구 변경 | 프로젝트 / 예측 가능 | 중 / 중대 | 회피: SRS 서면 승인. 감시: 월례 회의록. 비상: 변경 통제 절차로 영향 분석 후 일정 재협상 |

상태 열: 열림 / 징후 / 발생 / 종료. 갱신 일자와 함께 적는다.

## 5. 위험과 생명주기 모형

나선형 모형은 위험 분석을 매 주기의 핵심 단계로 둔다. 위험 분석 결과에 따라 계속(Go) 또는 중단(No-Go)을 결정한다. 폭포수에서도 위험 관리는 하지만 단계 전환 시점에만 한다. 이 차이 때문에 대규모·고위험 프로젝트에 나선형을 권한다.

## 6. 용어 대조

| 강의 표현 | 이 문서 |
|-----------|---------|
| 프로젝트 위험 / 기술적 위험 / 비즈니스 위험 | 1절 |
| Known / Predictable / Unpredictable Risk | 2절 Charette |
| 식별 → 분석·평가 → 계획 → 감시·조치 | 3절 |
| Risk Table (발생 시간 제외) | 3.2, 4절 |
| 회피 / 모니터링 / 비상 계획 | 3.3 |
| 위험 모니터링 = 징후를 계속 인지 | 3.4 |
| 대표 위험 = 사용자 요구사항 변경 | 1절 |
| 유지보수는 위험 요소가 아님 | 1절 |
| 사용자 자체의 위험성은 분석 대상 아님 | 1절 |
