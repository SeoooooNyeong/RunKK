# 검토 유형과 품질 활동 구분

## 1. 검토 회의 유형

| 유형 | 인원 | 시간 | 형식 | 목적 | 언제 쓰는가 |
|------|------|------|------|------|-------------|
| 워크스루 (Walkthrough) | 3~5명 | 2시간 이내 | 비공식. 작성자가 산출물을 설명하며 참석자가 질문 | 소규모 문서·코드의 오류를 **조기**에 발견 | 초안 단계. 설계 초안, 모듈 코드 |
| 구조적 워크스루 | 3~5명 | 2시간 이내 | 표준화된 절차와 체크 항목으로 진행 | 워크스루의 일관성 확보 | 팀이 워크스루에 익숙해진 뒤 |
| 정형 기술 검토 (FTR) | 3~10명 | 2시간 이내 | 공식. 진행자·기록자 역할 분리, 체크리스트, 판정 기록 | 산출물 **승인**, 기준선 확정 | 단계 종료 시. SRS 승인, 설계 승인, 배포 전 |
| 인스펙션 (Inspection) | 1~4명 전문가 | 산출물 크기 비례 | 체크리스트 기반으로 전문가가 결함을 **계수** | 결함 밀도 측정, 품질 정량 평가 | 핵심 모듈, 안전·보안 중요 구간 |

공통 규칙:
- 사전 자료 배포는 필수다.
- 발견된 오류는 **회의 후**에 수정한다. 회의 중에 고치지 않는다.
- 결과를 기록으로 남긴다.

선택 순서: 초안은 워크스루 → 성숙하면 구조적 워크스루 → 승인은 FTR → 중요 구간은 인스펙션 추가.

## 2. 세 시점의 SQA 활동

| 시점 | 활동 | 핵심 질문 |
|------|------|-----------|
| 초기 | 요구사항과 품질 목표를 명확히 정의 | 무엇이 "품질이 좋다"인지 수치로 합의했는가 |
| 중간 | 개발하면서 계속 점검 (FTR) | 각 단계 산출물이 앞 단계와 일치하는가 |
| 최종 | 테스트·디버깅으로 최종 품질 확보 | 측정값이 목표를 만족하는가 |

초기 시점을 건너뛰면 최종 시점에 측정할 기준이 없다. "목표 미정의"는 최종 시점의 결함이 아니라 초기 시점의 결함이다.

## 3. 품질 관리의 범위

요구사항 → 분석 → 설계 → 구현 → 테스트 → 유지보수 모든 단계의 산출물과 작업이 대상이다.

| 단계 | 산출물 | 검토 유형 (권장) |
|------|--------|------------------|
| 계획 | `plan.md`, `estimate.md`, `schedule.md` | 워크스루 |
| 분석 | `srs.md` | FTR (승인 → 요구사항 기준선) |
| 설계 | `design*.md`, `design-review.md` | FTR (승인 → 설계 기준선) |
| 구현 | 코드, `code-review.md` | 워크스루(모듈별) + 인스펙션(핵심 모듈) |
| 테스트 | `test.md` | FTR (배포 전 → 제품 기준선) |
| 유지보수 | `maintenance/*.md` | 워크스루(변경 단위) |

## 4. 검증·확인·인증·시험·디버깅

| 용어 | 영어 | 질문 | 수행자 | 산출물 |
|------|------|------|--------|--------|
| 검증 | Verification | 설계·구현이 **올바르게** 만들어졌는가 (설계대로) | 개발자, 리뷰어, 테스터 | 코드 리뷰, FTR, 단위·통합 테스트 |
| 확인 | Validation | 만들어진 시스템이 **사용자가 원하는 것**인가 | 사용자·발주자가 참여 | 요구 기반 테스트, 프로토타입 평가, 인수 테스트 |
| 인증 | Certification | 전문가·기관이 품질을 **공식 인정**했는가 | 외부 감리, 인증 기관 | 감리 보고서, 인증서 |
| 시험 | Test | 오류를 찾기 위해 **실행**했는가 | 테스터 | `test.md` 실행 이력 |
| 디버깅 | Debugging | 발견된 오류의 **원인을 찾아 수정**했는가 | 개발자 | 수정 커밋, 재실행 결과 |

검증과 확인의 구분이 가장 자주 흐려진다. 개발자끼리 아무리 검증해도 확인은 되지 않는다. 확인에는 요구를 낸 사람이 있어야 한다.

시험과 디버깅도 구분한다. 시험은 오류를 **드러내는** 활동이고, 디버깅은 드러난 오류의 **원인을 제거하는** 활동이다. 시험 결과서에 "수정했음"만 있고 원인이 없으면 디버깅이 아니라 증상 제거다.

## 5. 검토 결과 판정

| 판정 | 의미 | 후속 |
|------|------|------|
| 승인 | 수정 없이 기준선 확정 | 다음 단계 진입 |
| 조건부 승인 | 지적 사항 수정 후 진행자 단독 확인으로 확정 | 수정 → 진행자 확인 → 다음 단계 |
| 재검토 | 수정 후 회의 재소집 | 수정 → 2차 회의 |

재검토 사유: 치명 결함 1건 이상, 또는 중 결함이 많아 수정 후 산출물의 구조가 바뀔 가능성이 있을 때.

## 6. 용어 대조

| 강의 표현 | 이 문서 |
|-----------|---------|
| Walkthrough 3~5명, 2시간, 사전 배포, 수정은 회의 후 | 1절 워크스루 |
| 구조적 Walkthrough | 1절 |
| Inspection 1~4명 전문가, 체크리스트 | 1절 |
| FTR 3~10명 | 1절, `ftr-checklist.md` |
| SQA 초기·중간·마지막 | 2절 |
| Verification / Validation / Certification / Test / Debugging | 4절 |
