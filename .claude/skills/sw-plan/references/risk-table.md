# 위험표(Risk Table) 작성법

`sw-plan` 절차 8에서 읽는다. `sw-sqa`가 같은 표를 갱신한다.

## 1. 위험의 세 범주

| 범주 | 위협하는 것 | 전형적 예 |
|------|-------------|-----------|
| 프로젝트 위험 | 일정, 비용, 인력, 자원 | 요구사항 변경, 핵심 인력 이탈, 예산 부족, 일정 촉박 |
| 기술적 위험 | 품질, 구현 가능성 | 미보유 기술, 기존 시스템 연동 불확실, 성능 목표 미달, 기술 선택 실패 |
| 비즈니스 위험 | 제품의 가치 | 발주처 조직·정책 변경, 사용자 수용 거부, 시장·전략 불일치 |

가장 대표적인 위험은 **사용자 요구사항 변경**이다. 모든 프로젝트의 위험표에 들어간다.
유지보수는 개발이 끝난 뒤의 활동이므로 개발 단계 위험으로 적지 않는다.

## 2. Charette 분류

| 분류 | 의미 | 예 |
|------|------|----|
| 알려진 위험(Known) | 지금 이미 알고 있다 | 인력 부족, 일정 촉박, 미보유 기술 |
| 예측 가능한 위험(Predictable) | 과거 경험으로 예상할 수 있다 | 고객 요구 변경, 기술 경험 부족, 연동 지연 |
| 예측 불가능한 위험(Unpredictable) | 미리 알 수 없다 | 자연재해, 발주처 조직 개편, 갑작스러운 정책 변경 |

예측 불가능한 위험은 구체적으로 열거할 수 없으므로 "비상 계획 예비비·예비 기간"으로만 대비한다.

## 3. 위험표 열

| 열 | 적을 것 |
|----|---------|
| ID | `R-001`부터 순번. 프로젝트 내내 유지 |
| 내용 | 원인 형태로 한 문장. "~해서 ~할 수 있다" |
| 범주 | 프로젝트 / 기술 / 비즈니스, Charette 분류 병기 |
| 발생 확률 | 높음(50% 이상) / 중간(20~50%) / 낮음(20% 미만) |
| 영향도 | 파멸적 / 중대 / 경미 (아래 기준) |
| 대응 전략 | 회피 / 감시 / 비상 계획 중 선택, 구체 행동 |
| 상태 | 열림 / 감시 중 / 발생 / 종료 (`sw-sqa`가 갱신) |

**발생 시간은 열에 넣지 않는다.** 언제 발생할지는 예측할 수 없다.

### 영향도 기준

| 등급 | 기준 |
|------|------|
| 파멸적 | 프로젝트 중단 또는 마감 1개월 이상 지연 또는 예산 30% 이상 초과 |
| 중대 | 마감 2주 이상 지연 또는 예산 10% 이상 초과 또는 핵심 기능 축소 |
| 경미 | 내부 조정으로 흡수 가능 |

### 우선순위

확률 × 영향도로 정렬한다. 확률 높음 + 영향 파멸적이 최상위다. 상위 3건은 반드시 대응 전략이 "감시"가 아니라 "회피" 또는 "비상 계획"이어야 한다.

## 4. 대응 전략

| 전략 | 언제 | 행동 예 |
|------|------|---------|
| 회피(Avoid) | 원천 제거가 가능할 때. 가장 좋은 전략 | 미보유 기술 → 보유 기술로 대체 설계, 요구 변경 → 프로토타입으로 조기 확정 |
| 감시(Monitor) | 제거할 수 없고 징후를 관찰할 수 있을 때 | 주간 검토에서 징후 지표 확인 (인력 이직 신호, 연동 테스트 실패율) |
| 비상 계획(Contingency) | 회피·감시가 실패했을 때 쓸 대비책 | 예비 인력 확보, 범위 축소 우선순위 목록, 예비 기간 2주 |

## 5. 위험 관리 절차 (전체 생명주기)

1. 위험 식별 — 이 문서(`sw-plan`). 체크리스트로 범주별 탐색.
2. 위험 분석·평가 — 확률·영향도 부여, 위험표 작성.
3. 위험 관리 계획 — 대응 전략과 담당자 지정.
4. 위험 감시·조치 — `sw-sqa`가 검토 때마다 상태 열 갱신. 발생 시 비상 계획 실행.

순서를 바꾸지 않는다. 계획 없이 감시만 하거나, 분석 없이 대응 전략부터 쓰지 않는다.

## 6. 위험 식별 체크리스트

프로젝트 위험
- [ ] 발주처가 요구사항을 문서로 확정했는가? 아니면 R: 요구사항 변경
- [ ] 마감이 외부 사건에 묶여 있는가? 그렇다면 R: 일정 압박
- [ ] 핵심 역할이 1명에게 집중되어 있는가? 그렇다면 R: 인력 이탈
- [ ] 예산에 예비비가 있는가? 없다면 R: 예산 초과

기술적 위험
- [ ] 처음 써 보는 언어·프레임워크·장비가 있는가? 그렇다면 R: 기술 학습
- [ ] 연동할 기존 시스템의 문서·담당자가 있는가? 없다면 R: 연동 지연
- [ ] 성능 목표를 유사 규모에서 달성한 경험이 있는가? 없다면 R: 성능 미달
- [ ] 재사용하려는 모듈의 라이선스·호환성을 확인했는가? 아니면 R: 재사용 실패

비즈니스 위험
- [ ] 발주처 담당자가 프로젝트 기간 중 바뀔 가능성이 있는가?
- [ ] 최종 사용자가 현재 방식에 강하게 익숙한가? 그렇다면 R: 수용 거부
- [ ] 관련 법·규정 개정이 예정되어 있는가?
