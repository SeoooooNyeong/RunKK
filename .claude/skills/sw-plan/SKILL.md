## 목적

"이 프로젝트를 할 가치가 있는가, 어디까지 할 것인가, 누가 무엇을 관리하는가"를 한 문서로 고정한다.
산출물 `docs/sw/plan.md`는 `sw-estimate`(규모·비용), `sw-schedule`(일정·조직), `sw-srs`(범위·이해관계자)의 입력이 되고, 위험 목록 절은 `sw-sqa`가 프로젝트 내내 갱신한다.
계획서가 모호하면 뒤의 모든 산출물이 흔들린다. 특히 범위가 정해지지 않으면 비용과 일정을 계산할 수 없다.

## 입력

- 프로젝트 개요. 구두 설명, 제안요청서(RFP), 제안서, 계약서 초안 중 하나 이상. 아무것도 없으면 아래 절차 1의 질문으로 직접 수집한다.
- 사용자에게 물어야 할 정보
  - 발주 형태: 고객이 비용을 내고 요청하는 주문형인가, 개발사가 만들어 시장에 파는 상업용인가
  - 발주처와 최종 사용자가 누구인가
  - 마감 기한이 외부 사건(학기 시작, 법 시행일 등)에 묶여 있는가
  - 연동해야 하는 기존 시스템이 있는가
- 선행 산출물 없음. 이 스킬이 체인의 첫 단계다.

## 절차

### 1. 프로젝트 성격 판별

1. 발주 형태를 정한다.

   | 구분 | 주문형(Customized) | 상업용(Commercial) |
   |------|-------------------|-------------------|
   | 비용 부담 | 고객 | 개발사 |
   | 성공 기준 | 계약서의 요구사항 충족 | 시장 반응 |
   | 핵심 문서 | RFP, 제안서, 계약서 | 시장 조사, 제품 로드맵 |
   | 범위 확정 주체 | 고객과 합의 | 개발사 자체 |

2. 주문형이면 RFP·제안서·계약서를 점검한다. 다음 표현이 있으면 모두 기록하고 수치로 바꿀 것을 요구한다.
   - "노력한다", "고려한다", "최대한", "가능한 한", "적절히", "충분히"
   - 판정 질문: 이 문장을 보고 인수 검사에서 합격/불합격을 가를 수 있는가? 없으면 모호한 표현이다.
3. 중간 결과: 발주 형태, 계약 문서 목록, 모호 표현 목록.

### 2. 타당성 검토

세 관점을 각각 "예/아니오 + 근거 한 줄"로 답한다. 하나라도 "아니오"면 프로젝트를 시작하지 않거나 범위를 줄인다.

| 관점 | 판정 질문 | 근거로 적을 것 |
|------|-----------|----------------|
| 법적 | 개인정보, 저작권, 업종 규제를 위반하지 않는가 | 해당 법령, 동의 절차 |
| 경제적 | 예상 비용이 발주처 예산과 기대 효과 안에 있는가 | 예산 상한, 유사 사례 비용 |
| 기술적 | 현재 보유 인력과 기술로 요구 기능·성능을 만들 수 있는가 | 유사 경험, 미보유 기술 목록 |

타당성은 분석 단계에서 한 번 더 확인한다. 여기서는 "시작해도 되는가"만 판정한다.

### 3. 범위(Scope) 결정

범위는 다섯 요소로만 적는다. 개발 환경과 인적 자원은 범위가 아니라 자원(절차 6)이다.

| 요소 | 적을 내용 | 예시 |
|------|-----------|------|
| 기능(Function) | 시스템이 제공하는 기능 목록. "포함"과 "제외"를 나란히 적는다 | 학적·성적·수강신청 포함, 재정·시설 제외 |
| 성능(Performance) | 응답 시간, 처리량, 동시 사용자 수 | 응답 2초 이내, 동시 접속 1,000명 |
| 제약 조건(Constraints) | OS, 하드웨어, 메모리, 예산, 기한 | 기존 서버 사용, 학기 시작 2주 전 가동 |
| 인터페이스(Interface) | 연동 대상(사용자, 하드웨어, 기존 시스템, 외부 시스템) | 기존 학적 DB, 교내 인증 서버 |
| 신뢰도(Reliability) | 허용 장애 시간, 오류율 | 월 가동률 99.5% |

- 판정 질문: "제외" 목록이 비어 있는가? 비어 있으면 범위를 정하지 않은 것이다. 발주처가 당연히 기대할 만한 인접 기능을 최소 2개 이상 명시적으로 제외하거나 포함시킨다.
- 상세 기준과 품질 목표 정의는 `references/scope-and-quality.md`를 읽는다.

### 4. 이해관계자와 3P

1. 이해관계자를 역할별로 나열한다. 발주자, 최종 사용자(여러 유형이면 각각), 운영자, 기존 시스템 담당자, 외부 연동 담당자, 개발사.
2. 프로젝트 관리 3요소를 채운다.

   | 요소 | 질문 | 적을 내용 |
   |------|------|-----------|
   | 사람(People) | 누가 만드는가 | 필요한 역할과 인원 규모(정확한 수는 `sw-estimate` 이후 확정) |
   | 문제(Problem) | 무엇을 해결하는가 | 발주처의 현재 업무 문제 한 문단 |
   | 프로세스(Process) | 어떤 절차로 푸는가 | 생명주기 모형(`/sw-sdlc model`로 선택), 업무 흐름(Task Framework) |

3. 중간 결과: 이해관계자 표, 3P 표.

### 5. 관리 대상과 전개 단계

1. 관리 대상 여섯 개를 각각 "누가, 무엇을 기준으로, 어느 산출물로" 관리하는지 적는다.

   | 관리 대상 | 기준 | 산출물 |
   |-----------|------|--------|
   | 계획 관리 | 이 계획서 | `plan.md` |
   | 비용 관리 | 산정 대비 실적 | `estimate.md` |
   | 일정 관리 | 임계 경로 준수 | `schedule.md` |
   | 조직 관리 | 역할과 책임 | `schedule.md` 조직 절 |
   | 품질 관리 | 품질 목표 | `sqa.md` |
   | 위험 관리 | 위험 목록 | `plan.md` 위험 절, `sqa.md` 갱신 |

   고객 관리는 프로젝트 관리 대상이 아니다. 고객은 이해관계자로 다룬다.

2. 전개 5단계(계획 수립 → 가동 → 실행 → 통제 → 종료)마다 이 프로젝트에서의 시작 조건과 종료 조건을 한 줄씩 적는다.

### 6. 자원 식별

중요한 순서대로 적는다. 인적 자원 → 재사용 가능한 소프트웨어 자원 → 환경 자원.

| 자원 | 적을 내용 | 판정 질문 |
|------|-----------|-----------|
| 인적 | 필요한 역할(분석가, 설계자, 개발자, 테스터, 관리자)과 보유 여부 | 미보유 역할이 있으면 채용·외주 계획이 있는가 |
| 재사용 SW | 쓸 수 있는 기존 모듈, 라이브러리, 컴포넌트 | 라이선스와 호환성을 확인했는가 |
| 환경 | 서버, PC, 네트워크, IDE, 테스트 도구 | 프로젝트 가동 시점에 준비되는가 |

### 7. 품질 목표 설정

품질 목표를 "속성 + 측정 방법 + 목표 수치"로 적는다. 측정 방법이 없는 목표는 쓰지 않는다. 속성 정의와 측정 예는 `references/scope-and-quality.md`에 있다.
최소 포함: 정확성, 신뢰성, 효율성, 사용성. 환경이 여럿이면 이식성, 외부 연동이 있으면 상호운용성을 추가한다.

### 8. 초기 위험 식별

1. 위험을 세 범주로 나눠 찾는다. 범주별로 최소 1건.
   - 프로젝트 위험: 일정, 비용, 인력, 요구사항 변경
   - 기술적 위험: 미보유 기술, 기존 시스템 연동, 성능 목표 달성 가능성
   - 비즈니스 위험: 발주처 조직 변화, 시장·정책 변화, 사용자 수용성
2. 각 위험을 Charette 분류(알려진 위험 / 예측 가능한 위험 / 예측 불가능한 위험)로 표시한다.
3. 위험표(Risk Table)를 작성한다. 열은 내용, 범주, 발생 확률, 영향도, 대응 전략(회피/감시/비상 계획). 발생 시간은 예측할 수 없으므로 열에 넣지 않는다. 작성법과 등급 기준은 `references/risk-table.md`를 읽는다.
4. 이 절은 `sw-sqa`가 검토 때마다 상태를 갱신한다. 위험 ID(`R-001`부터)를 붙여 추적할 수 있게 한다.

### 9. 저장

`templates/plan.md` 양식에 채워 `docs/sw/plan.md`로 저장한다. 둘째 줄 헤더를 반드시 쓴다.

## 판정 기준

- 타당성 세 관점 모두 "예"일 때만 계획서를 확정한다. "아니오"가 있으면 문서 상단에 "보류: <관점>"을 적고 범위 재조정 항목을 남긴다.
- 범위 기능 목록에 "제외" 항목이 2개 이상 있다.
- 성능, 신뢰도 항목에 수치가 하나 이상 있다.
- 계약 문서의 모호 표현이 0건이거나, 남은 것마다 "수치화 요청 중"으로 표시되어 있다.
- 품질 목표 4개 이상, 각각 측정 방법이 있다.
- 위험 3건 이상, 세 범주 각 1건 이상, 모두 확률·영향·대응 전략이 채워져 있다.
- 이해관계자에 발주자와 최종 사용자가 별도 행으로 있다(같은 조직이라도 역할이 다르면 분리).

## 출력

- `docs/sw/plan.md`. 양식은 `templates/plan.md`.
- 완성 예시는 `examples/plan.md` (학사관리 시스템).
- 다음 단계: `/sw-estimate`. 계획서의 범위 기능 목록이 규모 산정의 입력이 된다.
- 협업 모드: `docs/sw/OWNERS.md`가 있으면 저장 전에 그 규칙을 따른다. `git config user.name`으로 작성자를 찾아 그 사람 담당 파일만 고친다. 새 번호는 `[임시:FR-<이니셜>-1]` 형식으로 쓰고 산출물 버전은 올리지 않는다(변경 표시는 "(다음 판 변경)"). 목차 파일의 머리 헤더·문서 상태·목차, `docs/sw/README.md`, 공용 조각(추적표, 자료사전 등)에 들어갈 내용과 남의 파일에 고칠 것은 `docs/sw/pending/<브랜치 이름의 / 를 - 로>.md`에 적는다. 정식 번호와 버전은 공용 담당이 `/sw-sdlc merge`로 매긴다. 규칙 전문은 `docs/sw/OWNERS.md` 3절이다.

## 체크리스트

- [ ] 발주 형태(주문형/상업용)를 명시했다
- [ ] 계약 문서에 "노력한다", "고려한다" 같은 표현이 남아 있지 않거나 수치화 요청으로 표시했다
- [ ] 범위에 개발 환경이나 인적 자원을 넣지 않았다 (자원 절에 있다)
- [ ] 관리 대상에 고객 관리를 넣지 않았다
- [ ] 3P가 People, Problem, Process다 (Power 같은 다른 항목이 아니다)
- [ ] 자원을 인적 → 재사용 SW → 환경 순으로 적었다
- [ ] 비용 추정이 계획 단계에 포함된다는 전제로 `sw-estimate`를 다음 단계로 지정했다
- [ ] 위험표에 발생 시간 열이 없다
- [ ] 위험에 "유지보수"를 넣지 않았다 (개발 단계 위험이 아니다)
- [ ] 사용자 요구사항 변경을 위험으로 포함했다 (가장 대표적인 위험이다)
- [ ] 품질 목표에 측정 불가능한 항목이 없다
- [ ] 둘째 줄 헤더 형식을 지켰다

## 자주 하는 실수

- 범위를 기능 목록으로만 쓴다. 성능·제약·인터페이스·신뢰도가 빠지면 `sw-srs`에서 비기능 요구사항을 처음부터 다시 캐야 한다.
- "제외" 목록을 쓰지 않는다. 발주처는 적혀 있지 않은 인접 기능도 당연히 포함이라고 생각한다. 분쟁은 대부분 여기서 생긴다.
- 타당성 검토를 형식적으로 "예"로 채운다. 기술적 타당성에서 미보유 기술을 숨기면 위험 목록도 비게 되고, 나중에 비용 산정이 틀어진다.
- 위험을 "일정 지연"처럼 결과로 쓴다. 위험은 원인으로 쓴다. "기존 학적 DB 스키마 문서가 없어 연동 설계가 늦어질 수 있다"처럼 쓴다.
- 품질 목표를 "사용하기 쉬워야 한다"로 쓴다. "신규 사용자가 교육 없이 10분 안에 성적 입력을 완료한다"처럼 측정 방법을 붙인다.
- 계획 단계에서 인원 수를 확정한다. 인원은 `sw-estimate`의 노력(인월)이 나온 뒤 `sw-schedule`에서 정한다. 여기서는 역할만 적는다.
