# 요구사항 도출 기법과 분석가의 자질

`sw-srs` 1~2단계에서 읽는다.

## 1. 도출 기법

| 기법 | 진행 방법 | 강점 | 약점 |
|------|-----------|------|------|
| 인터뷰 | 핵심 사용자와 1:1 또는 소그룹 대화. 질문지를 준비하되 답에 따라 파고든다 | 숨은 요구와 업무 맥락을 가장 잘 찾음 | 시간이 많이 들고 답변자의 관점에 치우침 |
| 설문조사 | 표준화된 질문을 다수에게 배포 | 사용자가 많을 때 효율적, 수치화 가능 | 깊이가 얕고 질문에 없는 요구는 못 찾음 |
| 시나리오 작성 | 실제 사용 상황을 이야기로 쓴다. 정상 흐름 + 예외 흐름 | 예외 상황과 순서 요구를 발견 | 작성자의 상상에 의존 |
| 현행 업무 분석 | 기존 업무 흐름, 양식, 보고서, 시스템 화면을 관찰·수집 | 사용자가 말하지 않는 암묵적 요구를 찾음 | 기존 방식을 그대로 옮기려는 함정 |
| 프로토타이핑 | 화면 중심 시제품을 만들어 조작하게 하고 피드백 수집 | 사용자가 원하는 것을 모를 때 유일한 방법 | 시제품이 기대치가 되는 위험, 시간 증가 |
| 벤치마킹 | 유사 시스템을 비교·분석 | 빠르게 기능 목록 확보 | 우리 업무와 다른 점을 놓침 |
| 브레인스토밍 | 이해관계자가 모여 아이디어를 제한 없이 수집 | 새로운 서비스에서 폭넓은 후보 확보 | 정리하지 않으면 요구가 아닌 희망 사항이 섞임 |

도출 기법이 **아닌 것**: 통제 분석, 보안 분석, 성능 비교, 코드 리뷰. 이들은 설계·테스트·평가 단계의 활동이다.

## 2. 인터뷰 진행 요령

1. 질문지를 만든다. "현재 어떻게 하고 있는가" → "무엇이 불편한가" → "어떻게 되면 좋겠는가" → "그것이 안 되면 어떤 일이 생기는가" 순서로.
2. 업무 담당자별로 따로 한다. 교무처 직원과 교수를 한자리에 두면 한쪽 요구가 묻힌다.
3. 측정 불가 표현은 그 자리에서 되묻는다.

   | 사용자 표현 | 되묻기 |
   |------------|--------|
   | 빠르게 | 몇 초 안에 결과가 나와야 하는가 |
   | 편리하게 | 지금은 몇 단계인데 몇 단계면 되는가 |
   | 많은 사용자 | 동시에 몇 명, 하루 몇 명인가 |
   | 안전하게 | 누가 보면 안 되는가, 유출되면 어떤 피해인가 |
   | 가끔 | 한 달에 몇 번인가 |

4. 기록은 원문 그대로 남기고, 해석은 따로 적는다. 나중에 "그런 말 한 적 없다"에 대비한다.
5. 끝나기 전에 요약을 읽어 주고 확인받는다.

## 3. 도출이 어려운 이유와 대응

| 이유 | 증상 | 대응 |
|------|------|------|
| 업무 범위 불명확 | 인터뷰마다 범위가 늘어남 | `plan.md` 범위를 인터뷰 시작에 보여 주고 "이 밖의 것"은 따로 적는다 |
| 사용자의 모호한 표현 | "알아서 잘", "지금처럼" | 되묻기 표로 수치화. 현행 업무 분석으로 "지금처럼"의 실체를 확인 |
| 요구사항의 잦은 변경 | 지난주 말과 다름 | 확정/가변 표시, 변경 이력 기록, 기준선 승인 후 변경 통제 |
| 개발자와 사용자의 지식 차이 | 같은 단어를 다르게 씀 | 용어 사전 먼저, 그림(DFD, 화면 시제품)으로 대화 |
| 시스템 복잡성 | 아무도 전체를 모름 | 하향식 분해(배경도 → Level 1 → Level 2), 부서별 인터뷰 후 통합 |

이 다섯 가지 때문에 요구사항은 **원래 모호하고, 부정확하고, 불완전하다.** 그것이 정상이며, 분석 단계는 그것을 줄이는 과정이다. "사용자 요구는 예외가 적어 열거하기 쉽다"는 가정으로 일정을 잡으면 분석 기간이 반드시 초과된다.

## 4. 분석가의 자질

| 자질 | 왜 필요한가 |
|------|------------|
| 개발 경험 | 요구가 구현 가능한지, 비용이 얼마나 드는지 감각이 있어야 협의가 된다 |
| 거시적 관점 | 시스템 전체 구조와 부서 간 흐름을 한눈에 봐야 누락을 찾는다 |
| 세부 관찰력 | 입력 양식의 칸 하나, 예외 처리 하나까지 논리적으로 파악한다 |
| 의사소통 능력 | 사용자의 말을 개발자의 언어로, 개발자의 제약을 사용자의 언어로 옮긴다 |
| 기술 지식 | 하드웨어·소프트웨어·네트워크 제약을 이해한다 |
| 사용자 중심 사고 | 개발자 입장의 편의가 아니라 사용자 입장의 필요로 판단한다 |

가장 중요한 하나를 꼽으면 **거시적 관점에서 세부 요소를 관찰하는 능력**이다. 전체를 보면서 세부를 놓치지 않는 것.

## 5. 시나리오 양식

```
시나리오 S-03: 교수가 성적을 입력한다
  전제: 교수가 로그인했고 담당 과목이 1개 이상 있다
  정상 흐름:
    1. 교수가 과목을 선택한다
    2. 시스템이 수강생 목록을 보여 준다
    3. 교수가 학생별 점수를 입력한다
    4. 시스템이 0~100 범위를 검증하고 등급을 계산해 보여 준다
    5. 교수가 확인하면 시스템이 저장하고 완료 메시지를 보여 준다
  예외 흐름:
    3a. 점수가 범위 밖이면 해당 칸을 표시하고 저장하지 않는다
    3b. 결시 학생은 비고에 사유를 쓰고 0점으로 처리한다
    5a. 성적 입력 기간이 지났으면 저장을 거부하고 교무처 연락처를 보여 준다
  출처: 교수 인터뷰 (10/02, 컴퓨터공학과 A교수)
```

정상 흐름 하나에 예외 흐름이 하나도 없으면 시나리오가 덜 쓰인 것이다.
