## 목적

사용자가 말로 전한 추상적인 요구를 설계·구현·테스트·검수의 공식 기준이 되는 문서로 바꾼다.
산출물 `docs/sw/srs.md`는 `sw-design-oo`와 `sw-design`이 "무엇을 만들어야 하는가"의 입력으로 읽고, `sw-test`가 테스트 케이스의 출처로, `sw-sqa`가 검증(Validation)의 기준으로, `sw-maintain`이 변경 영향 분석의 기준선으로 읽는다.
요구사항은 계약의 근거다. 이 문서에 없는 기능은 인수 대상이 아니고, 이 문서에 있는데 안 만든 기능은 분쟁 대상이다.

## 입력

- `docs/sw/plan.md` (범위 정의, 이해관계자 목록). 없으면 `/sw-plan`을 먼저 안내하고 중단한다. 사용자가 "계획 없이 바로 요구사항만"이라고 하면 범위와 이해관계자를 즉석에서 묻고 진행하되, 산출물 헤더의 입력란에 "plan.md 없음"이라고 적는다.
- 인터뷰 기록, 회의록, 설문 결과, 현행 업무 문서(입력 양식, 출력 보고서, 기존 화면), 제안요청서(RFP). 있는 것만 받는다.
- 사용자에게 물어야 할 것:
  - 요구사항이 얼마나 확정되어 있는가 (명확 / 대략 / 사용자도 모름). "사용자도 모름"이면 `prototype` 인자 흐름을 권한다.
  - 기존 시스템이 있는가. 있으면 현행 업무 분석을 도출 기법에 넣는다.
  - 외부 연동 시스템이 있는가. 있으면 DFD 단말과 외부 인터페이스 요구사항에 넣는다.

## 절차

전체 흐름은 **도출 → 분석 → 모델링 → 명세화 → 확인 → 승인**이다. 모델링은 분석의 일부지만 산출물이 뚜렷해서 따로 둔다.

### 1단계. 준비

1. `plan.md`에서 범위(하는 일 / 하지 않는 일)와 이해관계자를 옮겨 적는다. 범위가 "학적·성적·수강신청, 재정·시설 제외"처럼 **제외 항목까지** 적혀 있어야 한다. 제외 항목이 없으면 사용자에게 물어 채운다.
2. 용어 사전 초안을 만든다. 사용자와 개발자가 다르게 쓰는 단어(예: "수강 취소"와 "수강 철회")를 먼저 맞춘다. 이 사전은 뒤에서 자료사전의 이름 규칙이 된다.
3. 분석 담당자의 관점을 고정한다. 개발자 입장이 아니라 **사용자 입장**에서 "무엇이 필요한가"를 묻는다. 분석가에게 필요한 자질은 `references/elicitation.md`의 분석가 항목을 본다.

판정 질문: 범위에 "하지 않는 일"이 한 줄 이상 있는가? 이해관계자에 최종 사용자·발주자·운영자가 모두 있는가?

### 2단계. 도출 (Elicitation)

1. 상황에 맞는 도출 기법을 고른다. 선택 기준은 아래 표를 따르고, 기법별 진행 방법은 `references/elicitation.md`를 읽는다.

   | 상황 | 1순위 기법 | 보조 기법 |
   |------|-----------|-----------|
   | 핵심 사용자가 소수이고 접근 가능 | 인터뷰 | 시나리오 작성 |
   | 사용자가 많고 질문이 표준화 가능 | 설문조사 | 인터뷰(대표자) |
   | 기존 시스템·수작업 업무가 있음 | 현행 업무 분석 | 인터뷰 |
   | 사용자가 원하는 것을 말로 못 함 | 프로토타이핑 | 시나리오 작성 |
   | 유사 시스템이 시장에 있음 | 벤치마킹 | 브레인스토밍 |
   | 새로운 서비스라 참고할 것이 없음 | 브레인스토밍 | 프로토타이핑 |

   통제 분석, 보안 분석, 성능 비교는 도출 기법이 아니다. 그것은 설계·평가 단계의 일이다.

2. 인터뷰·설문의 답에서 측정할 수 없는 표현을 찾아 **되묻는다**. "빠르게" → "몇 초 이내인가", "편리하게" → "클릭 몇 번 이내인가, 어떤 화면에서 시작하는가", "많은 사용자" → "동시 접속 몇 명인가". 되물은 결과를 원문 옆에 적는다.
3. 시나리오를 쓴다. 정상 흐름 하나마다 예외 흐름(입력 오류, 취소, 권한 없음, 외부 시스템 장애)을 최소 하나 붙인다. 예외 흐름에서 요구사항의 절반이 나온다.
4. 원시 요구 목록을 만든다. 한 줄에 요구 하나, 출처(누가·언제·어떤 자료)를 반드시 적는다. 번호는 `R-001`부터 임시로 붙인다.

판정 질문: 원시 요구 중 수치 없는 품질 표현("빠르게", "안정적으로")이 남아 있는가? 남아 있으면 되묻기 전에는 다음 단계로 가지 않는다.

도출이 어려운 이유는 다섯 가지로 정해져 있다. 업무 범위 불명확, 사용자의 모호한 표현, 잦은 변경, 개발자와 사용자의 지식 차이, 시스템 복잡성. 각각의 대응은 `references/elicitation.md`에 있다. "사용자 요구는 예외가 적어 열거하기 쉽다"는 전제로 일정을 잡지 않는다.

### 3단계. 분석 (Analysis)

1. **기능적 / 비기능적** 으로 나눈다.
   - 기능적 요구사항: 시스템이 **무엇을** 하는가. 입력 → 처리 → 출력이 있는 동작. 예: 교수가 담당 과목 성적을 입력할 수 있다.
   - 비기능적 요구사항: **어떻게** 해야 하는가. 성능(응답 시간, 처리량), 가용성, 보안, 사용성, 유지보수성, 이식성, 데이터 품질, 법규·표준 준수.
2. **확정 / 가변** 을 표시한다. 바뀔 가능성이 큰 요구(정책, 기간, 외부 연동 규격)는 "가변"으로 두고 변경 통제 대상임을 미리 알린다.
3. 중복을 합친다. 표현만 다른 같은 요구는 하나로 두고 출처를 모두 남긴다.
4. 모순을 푼다. 충돌하는 요구(예: "성적은 즉시 공개" vs "이의신청 기간 동안 비공개")는 이해관계자와 협의해 하나로 정하거나 조건을 붙여 둘 다 살린다. 협의 결과와 결정자를 적는다.
5. 누락을 점검한다. 다음 항목이 빠져 있으면 사용자에게 묻는다.
   - 시나리오의 예외 흐름마다 대응 요구가 있는가
   - 관리자 기능(계정, 권한, 기준값 변경)이 있는가
   - 외부 시스템 연동(기존 DB, 인증, 결제)이 있는가
   - 데이터 백업·복구, 로그, 감사 추적이 있는가
   - 운영 환경 제약(OS, 브라우저, 네트워크)이 있는가
6. 우선순위를 매긴다. 필수(Must) / 권장(Should) / 선택(Could). 필수는 "없으면 인수 거부"인 것만 둔다. 전체의 절반 이상이 필수면 우선순위를 다시 본다.
7. 정식 ID를 부여한다. 기능은 `FR-001`, 비기능은 `NFR-001`. 번호는 한 번 붙이면 바꾸지 않는다. 삭제된 요구는 번호를 비워 두고 "삭제됨(사유)"으로 남긴다. 이 번호가 설계서·테스트 케이스·유지보수 분석까지 이어지는 추적의 열쇠다.

판정 질문: 모든 요구에 ID, 유형, 우선순위, 출처가 있는가? 모순으로 표시된 쌍이 0개인가?

### 4단계. 구조적 분석 모델링

구조적 분석은 **하향식(Top-down)**, **처리 중심(Process-oriented)**, **그림 중심**이다. 큰 그림에서 시작해 점점 쪼개고, 사용자와 개발자가 같은 그림을 보게 한다. 표기법은 `references/dfd-notation.md`, 자료사전 기호는 `references/data-dictionary.md`를 읽는다.

1. **배경도(Context Diagram, Level 0)** 를 그린다. 시스템 전체를 **원 하나**로 그리고, 단말(□)과 주고받는 자료 흐름(→)만 표시한다. 내부 프로세스나 저장소는 그리지 않는다. 단말은 `plan.md`의 이해관계자와 외부 시스템에서 나온다.
2. **DFD Level 1** 을 그린다. 배경도의 원을 3~7개 프로세스로 나눈다. 배경도에 있던 입출력 흐름이 Level 1에서도 빠짐없이 나타나야 한다(균형 규칙). 이 단계에서 자료 저장소(║)가 처음 등장한다.
3. **Level 2 이상** 으로 세분화한다. 프로세스 하나가 "한 문장으로 설명되는 단일 처리"가 될 때까지 쪼갠다. 보통 Level 2~3에서 끝난다.
4. 다음 규칙을 지킨다.
   - 자료가 프로세스를 거치면 **새 이름**을 붙인다. "성적 입력값"이 검증을 거치면 "검증된 성적"이 된다.
   - DFD에는 **시간·순서 개념이 없다.** 어느 흐름이 먼저인지 표현하지 않는다. 순서가 중요하면 소단위 명세서나 상태전이도에 쓴다.
   - 자료 저장소는 입력 흐름만 있을 수 있다(로그, 이력). 출력 흐름이 반드시 짝으로 있어야 하는 것은 아니다.
   - 단말끼리, 저장소끼리, 단말과 저장소 사이에 직접 흐름을 긋지 않는다. 반드시 프로세스를 거친다.
   - 프로세스 이름은 "동사 + 목적어"(성적을 검증한다 → "성적 검증")로, 자료 흐름 이름은 명사로 쓴다.
5. **자료사전(Data Dictionary)** 을 쓴다. DFD에 등장한 모든 자료 흐름과 저장소를 정의한다.
   - 기호: `=` 구성, `+` 연결, `{ }` 반복, `( )` 생략 가능, `|` 선택, `* *` 주석
   - 예: `성적입력 = 학번 + 과목코드 + 점수 + (비고)` , `성적표 = 학번 + 성명 + {과목코드 + 과목명 + 학점 + 등급}`
   - **이름 중복 금지.** 같은 이름이 두 번 정의되면 어느 쪽이 맞는지 알 수 없다. 1단계 용어 사전과 이름을 맞춘다.
   - 각 항목은 정의와 설명 두 부분으로 쓴다. 갱신하기 쉽게 한 항목이 한 줄 또는 한 블록을 넘지 않게 한다.
6. **소단위 명세서(Mini-spec)** 를 쓴다. 더 이상 쪼개지 않은 최하위 프로세스마다 처리 논리를 서술한다. 구조적 언어(IF-THEN-ELSE, 반복), 의사결정표, 의사결정도 중 고른다. 조건이 3개 이상 조합되면 의사결정표를 쓴다. 프로그램 명세서(코드 수준 설계)가 아니다. "무엇을 판단하고 무엇을 내보내는가"까지만 쓴다.
7. 필요하면 보조 모델을 붙인다.
   - **개체 관계도(ERD)**: 자료 저장소가 3개 이상이고 저장소 간 관계가 있을 때.
   - **상태전이도(STD)**: 수강신청·결제처럼 상태가 바뀌는 대상이 있을 때. 상태·사건·전이를 그린다.

판정 질문: 배경도의 모든 입출력이 Level 1에 있는가? 자료사전에 이름 중복이 0개인가? DFD의 모든 자료 흐름 이름이 자료사전에 있는가? 최하위 프로세스마다 소단위 명세서가 있는가?

### 5단계. 명세화 (Specification)

1. `templates/srs.md` 목차대로 문서를 채운다. 목차의 각 절이 무엇을 담는지는 `references/srs-outline.md`에 있다.
2. 요구 항목 하나는 다음 규칙으로 쓴다.
   - **한 항목에 한 요구.** "그리고", "및"으로 두 가지를 묶지 않는다. 묶여 있으면 번호를 나눈다.
   - **"~해야 한다(shall)"** 로 끝낸다. "~하면 좋겠다", "~할 수 있으면" 은 요구가 아니다.
   - **수치로 쓸 수 있는 것은 수치로.** "빠르게" 대신 "응답 2초 이내", "많은" 대신 "동시 1,000명".
   - **설계 내용을 쓰지 않는다.** 어떤 DB, 어떤 언어, 어떤 화면 구조는 설계 단계의 결정이다. 사용자가 명시적으로 제약으로 요구한 것(예: "기존 Oracle DB와 연동해야 한다")만 제약 조건 절에 쓴다.
   - 항목 구성: ID, 명칭, 설명, 입력, 처리(규칙·예외), 출력, 우선순위, 출처, 관련 DFD 프로세스 번호.
3. 비기능 요구는 측정 방법까지 쓴다. "응답 2초 이내"라면 "어떤 조건(동시 접속 수, 네트워크)에서, 어떤 기능을, 몇 회 측정해 95% 이상이 2초 이내"처럼 쓴다. 측정 방법이 없으면 검증 가능성 요건에 걸린다.
4. **추적표**를 만든다. 열: 요구 ID, 출처, DFD 프로세스, (설계 요소), (테스트 케이스). 뒤의 두 열은 비워 두고 `sw-design-oo`·`sw-test`가 채운다.
5. 용어·이름을 맞춘다. 본문의 자료 이름, 자료사전의 이름, DFD의 흐름 이름이 같은지 전수 확인한다.

### 6단계. 확인 (Validation)

1. 6대 요건을 체크리스트로 점검한다. 각 요건의 점검 질문은 아래 판정 기준 절에 있다.
2. 이해관계자와 **요구사항 검토 회의**를 연다. 명세서를 함께 읽고 지적 사항을 번호와 함께 기록한다. 회의에서 해결책을 토론하지 않고 지적만 모은다(해결은 회의 후).
3. **DFD 워크스루**를 한다. 2단계의 시나리오를 하나씩 골라 DFD 위에서 단말 → 프로세스 → 저장소 경로를 손가락으로 따라간다. 지나갈 프로세스가 없거나 저장소가 없으면 모델 누락이다.
4. 요구가 불명확했던 부분은 **프로토타입으로 확인**한다. 인자 `prototype`이면 아래 반복 루프를 돈다.
5. 지적 사항을 반영하고 **수정된 항목만** 다시 검토한다. 전체를 다시 읽지 않는다.

#### 프로토타입 평가 루프 (`prototype` 인자 또는 요구가 불명확할 때)

폭포수처럼 한 번에 확정할 수 없을 때 쓴다. 사용자가 원하는 것을 정확히 모르거나, 요구가 자주 바뀌거나, 개발자가 사용자의 업무를 불완전하게 이해할 때 특히 유효하다.

1. 시제품 범위를 정한다. **사용자 인터페이스**(화면 흐름, 메뉴, 입력 양식)에 집중하고 성능·오류 처리는 최소화한다. 빨리 만드는 것이 목적이다.
2. 시제품을 사용자에게 보여 주고 직접 조작하게 한다. 불편한 점, 빠진 기능, 불필요한 기능을 기록한다.
3. 피드백을 요구 항목의 추가·수정·삭제로 반영한다. 반영마다 `srs.md` 버전을 올린다(v0.1 → v0.2 …).
4. 두 회 연속으로 필수 요구의 변경이 0건이면 루프를 멈춘다. 멈추지 않으면 범위 정의가 흔들리고 있는 것이므로 `plan.md`로 돌아간다.
5. 시제품 코드는 버린다고 가정한다. 시제품이 최종 제품의 기대치가 되지 않도록 사용자에게 "완성품은 이와 다를 수 있다"를 매 회 말한다.

### 7단계. 승인과 관리

1. 발주자·프로젝트 관리자·분석 담당이 승인한다. 승인 시점의 문서가 **기준선(Baseline) v1.0** 이다.
2. 이후 변경은 절차를 거친다: 변경 요청서 → 영향·비용 분석(어느 FR이 영향받는지 추적표로 확인) → 승인/기각 → 반영 → 버전 갱신(v1.1, v1.2 …). 인자 `revise`는 이 흐름이다.
3. 요구사항 관리 도구를 쓴다면 그 역할은 변경 이력, 요구 간 의존 관계, 변경 영향·비용 분석, 추적성, 협업 검토다. 기존 시스템과 신규 시스템의 성능 비교는 요구사항 관리 도구의 일이 아니다.
4. 확정된 `srs.md`를 설계 단계 입력으로 넘긴다. 객체지향으로 갈지 구조적으로 갈지는 사용자에게 묻되, 대화식·사용자 중심 시스템(화면이 많고 상호작용이 많음)이면 `sw-design-oo`를 권한다.

## 판정 기준

### 요구 항목 수준

| 기준 | 합격 조건 |
|------|-----------|
| 단일성 | 한 항목에 동사가 하나. "및/그리고"로 묶인 요구 0건 |
| 의무 표현 | 모든 항목이 "~해야 한다"로 끝남 |
| 측정 가능 | 비기능 항목 100%에 수치와 측정 조건이 있음 |
| 설계 비침범 | DB·언어·프레임워크 이름이 제약 조건 절 밖에 0건 |
| 추적성 | 모든 항목에 출처와 DFD 프로세스 번호가 있음 |

### 문서 수준 (6대 요건)

| 요건 | 점검 질문 | 합격 조건 |
|------|-----------|-----------|
| 이해 가능성 | 사용자와 개발자가 모두 읽고 같은 뜻으로 이해하는가 | 검토 회의에서 "무슨 뜻인가" 질문 0건 |
| 명확성 | 두 가지로 해석되는 문장이 없는가 | 모호 표현("적절히", "가능한 한", "등") 0건 |
| 완전성 | 필요한 기능·예외·비기능이 빠짐없이 있는가 | 시나리오의 모든 예외 흐름에 대응 FR 존재. 누락 점검 5항목 모두 확인 |
| 일관성 | 서로 모순되는 요구가 없는가. 자료사전과 본문 이름이 같은가 | 모순 쌍 0건. 이름 불일치 0건 |
| 검증 가능성 | 각 요구를 테스트로 확인할 수 있는가 | 모든 FR에 입력·기대 출력이 있고, 모든 NFR에 측정 방법이 있음 |
| 추적 가능성 | 각 요구의 출처와 구현 위치를 따라갈 수 있는가 | 추적표에 빈 출처 0건 |

### 모델 수준

| 항목 | 합격 조건 |
|------|-----------|
| 배경도 | 프로세스 1개, 단말 1개 이상, 저장소 0개 |
| 균형 | 상위 레벨의 모든 입출력 흐름이 하위 레벨에 존재 |
| 자료사전 | 이름 중복 0건. DFD의 모든 흐름·저장소 이름이 정의됨 |
| 소단위 명세서 | 최하위 프로세스 수 = 소단위 명세서 수 |
| 금지 흐름 | 단말↔단말, 단말↔저장소, 저장소↔저장소 직접 흐름 0건 |

## 출력

- `docs/sw/srs.md`. 양식은 `templates/srs.md`. 하나의 파일 안에 SRS 본문, DFD(배경도·Level 1·Level 2), 자료사전, 소단위 명세서, 추적표를 모두 담는다.
- 완성 예시는 `examples/srs.md` (학사관리 시스템).
- 첫 두 줄: `# <프로젝트명> 요구사항 명세서` / `> 작성: YYYY-MM-DD | 버전: v1.0 | 입력: plan.md, 인터뷰 기록(날짜)`
- 다음 단계: `/sw-design-oo` (객체지향) 또는 `/sw-design design` (구조적). 사용자가 정하지 않았으면 `sw-sdlc`가 아닌 이 스킬이 바로 묻는다.
- 협업 모드: `docs/sw/OWNERS.md`가 있으면 저장 전에 그 규칙을 따른다. `git config user.name`으로 작성자를 찾아 그 사람 담당 파일만 고친다. 새 번호는 `[임시:FR-<이니셜>-1]` 형식으로 쓰고 산출물 버전은 올리지 않는다(변경 표시는 "(다음 판 변경)"). 목차 파일의 머리 헤더·문서 상태·목차, `docs/sw/README.md`, 공용 조각(추적표, 자료사전 등)에 들어갈 내용과 남의 파일에 고칠 것은 `docs/sw/pending/<브랜치 이름의 / 를 - 로>.md`에 적는다. 정식 번호와 버전은 공용 담당이 `/sw-sdlc merge`로 매긴다. 규칙 전문은 `docs/sw/OWNERS.md` 3절이다.

## 체크리스트

저장 전에 모두 확인한다.

- [ ] 범위에 "하지 않는 일"이 적혀 있다
- [ ] 모든 요구에 ID(FR-/NFR-), 유형, 우선순위, 출처가 있다
- [ ] "빠르게", "편리하게", "많은", "적절히" 같은 측정 불가 표현이 0건이다
- [ ] 한 항목에 "및/그리고"로 묶인 두 요구가 없다
- [ ] 제약 조건 절 밖에 DB·언어·프레임워크 이름이 없다
- [ ] 배경도는 원 하나와 단말, 입출력 흐름만으로 되어 있다 (저장소 없음)
- [ ] DFD에 시간·순서를 뜻하는 표현(먼저, 다음에, 번호 순서로 실행)이 없다
- [ ] 단말은 사각형, 프로세스는 원, 저장소는 평행선으로 그렸다
- [ ] 자료가 프로세스를 지날 때 새 이름을 받았다
- [ ] 자료사전에 이름 중복이 없고, `=`, `+`, `{ }`, `( )`, `|`, `* *` 기호만 썼다
- [ ] 자료사전의 "정의"가 DFD 구성 요소로 잘못 들어가 있지 않다 (정의는 자료사전의 것이다)
- [ ] 최하위 프로세스마다 소단위 명세서가 있다. 프로그램 명세서(코드)가 아니다
- [ ] 6대 요건 표를 채웠고 불합격 항목이 0건이다
- [ ] 검토 회의 지적 사항과 반영 결과가 변경 이력에 있다
- [ ] 추적표의 설계·테스트 열은 비워 두었다 (뒤 스킬이 채운다)
- [ ] 승인자와 승인일이 적혀 있다 (초안이면 "미승인"으로 명시)
- [ ] 요구사항 관리 도구의 역할에 "성능 비교"를 넣지 않았다

## 자주 하는 실수

- **설계를 요구사항에 섞는다.** "MySQL에 저장한다", "React로 만든다"는 요구가 아니다. 사용자가 계약 조건으로 못 박은 경우에만 제약 조건에 쓴다.
- **정상 흐름만 쓴다.** 예외·오류·취소 흐름을 빼면 구현 단계에서 개발자가 임의로 정하고, 테스트 단계에서 분쟁이 난다.
- **수치 없는 비기능 요구를 그대로 둔다.** "안정적으로"는 검증할 수 없고 인수 기준이 되지 못한다.
- **DFD에 순서를 그린다.** 화살표에 번호를 매기거나 "먼저 로그인 후"라고 쓰는 것은 흐름도(Flowchart)이지 DFD가 아니다.
- **자료사전 이름이 DFD와 다르다.** DFD에는 "성적정보", 자료사전에는 "성적데이터"로 쓰면 둘을 연결할 수 없다.
- **배경도에 저장소를 그린다.** 배경도는 시스템을 블랙박스로 본다. 저장소는 Level 1부터다.
- **프로토타입을 완성품으로 착각하게 둔다.** 시제품의 성능과 완성도가 최종 기대치가 되면 인수 때 실망과 분쟁이 생긴다.
- **승인 없이 요구를 바꾼다.** 구두로 바꾸면 설계·테스트와 명세서가 어긋나고, 어느 쪽이 맞는지 아무도 모르게 된다.
- **ID를 다시 매긴다.** 중간에 번호를 밀면 설계서·테스트 케이스의 참조가 모두 깨진다. 삭제는 번호를 비워 둔다.
