# 소프트웨어 재사용(Reusability)

## 1. 정의

기존에 잘 만들어진 코드·모듈·라이브러리·설계·문서·테스트 등을 **다른 소프트웨어 개발에 활용**하는 것이다. 개선 보수나 재공학에서 새 코드를 쓰기 전에 재사용할 수 있는 요소가 있는지 먼저 본다.

## 2. 무엇이 재사용되는가

| 요소 | 재사용 빈도 | 비고 |
|------|-------------|------|
| **소스 코드** | 가장 많음 | 함수, 클래스, 라이브러리, 패키지 |
| 설계 | 많음 | 아키텍처 패턴, 클래스 구조, 인터페이스 |
| 테스트 케이스 | 중간 | 같은 요구에 대한 TC |
| 문서 | 중간 | 명세 양식, 매뉴얼 구조 |
| 데이터 | 중간 | 코드 테이블, 기준 데이터 |
| 지식 | 낮음 (측정 어려움) | 도메인 지식, 실패 경험 |

## 3. 재사용 유형

| 유형 | 방식 | 예 | 적합한 경우 |
|------|------|----|-------------|
| 합성 중심 (Composition-based) | 미리 만들어진 부품(모듈·컴포넌트)을 **조립**한다. 블록 쌓기 | 라이브러리 호출, 컴포넌트 연결, 마이크로서비스 조합 | 부품이 표준화되어 있고 인터페이스가 명확할 때 |
| 생성 중심 (Generation-based) | 명세·패턴에서 코드를 **자동 생성**한다 | 코드 생성기, 템플릿, 4세대 언어, ORM 매핑 | 반복 구조가 많고 명세가 정형화되어 있을 때 |

## 4. 부품 크기와 재사용률

**부품이 작을수록 재사용률이 높다.** 작은 함수는 어디서나 쓸 수 있지만, 큰 서브시스템은 특정 맥락에 묶여 있다. 재사용을 목표로 설계하면 모듈을 작고 기능적 응집으로 만들게 되고, 그것은 유지보수성에도 좋다.

반대로 "재사용 가능하게" 만든다며 모듈을 범용으로 키우면 응집도가 떨어지고(논리적 응집의 유틸 모음) 재사용률은 오히려 낮아진다.

## 5. 장점

| 장점 | 설명 |
|------|------|
| 개발 시간 단축 | 이미 있는 것을 다시 만들지 않는다 |
| 품질 향상 | 검증된 부품은 새 코드보다 결함이 적다 |
| 생산성 상승 | 같은 인월로 더 많은 기능 |
| 문서·지식 공유 | 부품과 함께 문서·테스트가 온다 |
| 실패 위험 감소 | 검증된 설계를 따른다 |
| 비용 절감 | 위 모두의 결과 |

## 6. 단점

| 단점 | 설명 | 대응 |
|------|------|------|
| 새 개발 방법론 도입 어려움 | 기존 부품이 옛 방법론에 묶여 있어 새 방법론으로 바꾸기 어렵다 | 부품의 인터페이스만 유지하고 내부를 점진적으로 교체 |
| 기존 시스템에 끼워 넣기 어려움 | 재사용 부품의 가정이 기존 시스템과 다를 수 있다 | 어댑터 계층 |
| 언어 종속성 증가 | 특정 언어·런타임의 부품은 그 언어를 강제한다 | 언어 중립 인터페이스(HTTP, 메시지) |
| 재사용 요소 선정 어려움 | 무엇이 재사용할 만한지 판단에 경험이 필요 | Fan-In이 높고 기능적 응집인 모듈부터 |
| 표준화 부족 | 부품 간 인터페이스·명명·오류 처리가 제각각 | 팀 표준 정의 |

"새로운 개발 방법론 도입이 용이하다"는 재사용의 효과가 아니다. 오히려 어려워진다.

## 7. 객체지향과 재사용

클래스·객체·상속·캡슐화는 재사용성을 크게 향상시켰다.
- 캡슐화: 내부를 몰라도 인터페이스만으로 쓸 수 있다
- 상속: 기존 클래스를 물려받아 차이만 추가한다
- 다형성: 같은 인터페이스로 여러 구현을 바꿔 끼운다

단, 상속은 결합을 만든다. 코드 재사용만을 위한 상속은 합성으로 바꾼다.

## 8. 재사용 검토 양식 (개선 보수·재공학 시)

| 필요 기능 | 재사용 후보 | 출처 | 유형 | 적합성 | 결정 |
|-----------|-------------|------|------|--------|------|
| 모바일 인증 | 기존 LoginService | academic 패키지 | 합성 | 인터페이스 그대로 사용 가능 | 재사용 |
| 모바일 성적 화면 | 없음 | | | | 신규 |
| PDF 생성 | 기존 GradeReportPrinter | grade 패키지 | 합성 | 폰트 종속 코드 분리 필요 | 재구성 후 재사용 |

## 9. 재사용과 무관한 것

- 사용자에게 책임·권한을 부여하는 것은 재사용의 효과가 아니다 (조직 관리의 영역)
- 재사용은 재공학의 활동이 아니다 (재공학의 결과로 재사용성이 높아질 수는 있다)

## 10. 용어 대조

| 강의 표현 | 이 문서 |
|-----------|---------|
| 소프트웨어 재사용 정의 | 1절 |
| 합성 중심 / 생성 중심 | 3절 |
| 재사용이 가장 많이 되는 요소 = 소스 코드 | 2절 |
| 부품이 작을수록 재사용률 높음 | 4절 |
| 장점: 시간 단축·품질·생산성·문서 공유·위험 감소 | 5절 |
| 단점: 새 방법론 도입 어려움·기존 시스템 추가 어려움·언어 종속·선정 어려움·표준화 부족 | 6절 |
| OOP가 재사용성을 크게 향상 | 7절 |
| 재사용 효과와 거리가 먼 것: 사용자 책임·권한 부여 | 9절 |
