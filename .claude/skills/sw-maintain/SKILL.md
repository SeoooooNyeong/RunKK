## 목적

유지보수는 소프트웨어가 인수·설치된 뒤에 수행되는 **모든 공학적 수정 작업**이다. 생명주기에서 가장 긴 단계이고, 비용도 개발보다 더 든다. 이 스킬은 변경 요청 하나가 들어왔을 때 다음을 한다.

1. 요청을 네 유형(수정·적응·개선·예방) 중 하나로 **분류**해 절차와 비용 규모를 정한다.
2. 기존 산출물로 **영향 범위**를 잡는다. 어느 요구 ID, 어느 모듈, 어느 테스트 케이스가 바뀌는가.
3. 수정 절차(요구 확인 → 기존 시스템 이해 → 수정 → 수정 후 테스트)와 **부작용 점검**(코딩·자료·문서화)을 적는다.
4. 개선 보수(기능 추가·변경)이면 `sw-srs`로 **회귀**시킨다. 요구사항 없이 기능을 덧붙이면 추적표가 끊긴다.
5. 문서 없이 오래된 코드(외계인 코드)나 반복되는 수정 비용이 발견되면 **재공학 계획**을 세운다.

결과는 요청마다 `docs/sw/maintenance/YYYY-MM-DD_요청명.md` 한 파일이고, 재공학 계획은 `docs/sw/maintenance/reengineering.md`다. `sw-sdlc`가 이 폴더를 보고 "운영·유지보수 중"으로 판정한다.

## 입력

- **변경 요청**: 인자 또는 사용자 설명. 누가, 언제, 무엇이 안 되거나 무엇을 원하는지. 재현 조건이 있으면 함께.
- `docs/sw/srs.md`: 요구 ID와 추적표. 없으면 `/sw-srs`를 먼저 안내한다. 단, 운영 중인 시스템에 SRS가 아예 없는 경우(인수받은 레거시)는 중단하지 않고 "SRS 부재"를 적은 뒤 재공학(역공학) 절차로 간다.
- `docs/sw/design-oo.md` 또는 `docs/sw/design.md`, `docs/sw/design-review.md`: 영향 모듈 식별과 결합도 기준.
- `docs/sw/test.md`: 회귀 테스트 범위 선정.
- `docs/sw/sqa.md`: 인수 시점 품질 상태, 열려 있던 결함과 위험.
- `docs/sw/code-review.md`: 형상 관리 규칙(브랜치·커밋·버전).
- 이전 `docs/sw/maintenance/*.md`: 같은 모듈에 반복되는 요청이 있는지. 재공학 판단 근거.
- `--reengineering`: 개별 요청 없이 재공학 계획만 세운다.
- 사용자에게 물을 것: 요청자와 긴급도, 재현 절차, 운영 환경 변화(OS·DB·브라우저 버전), 비슷한 요청이 전에 있었는가.

## 절차

### 1. 요청 접수와 기록

1. 변경 요청 ID `CR-nnn`을 부여한다. 번호는 `maintenance/` 폴더의 기존 파일에서 이어 간다.
2. 접수 정보를 적는다: 요청자(역할), 접수일, 긴급도(즉시/이번 주/다음 릴리스), 증상 또는 요구, 재현 절차, 영향받는 사용자 수.
3. 요청자의 표현을 그대로 한 번 인용한 뒤, 측정 가능한 문장으로 다시 쓴다. "출력이 깨진다"는 "Windows 11 + Edge 120에서 성적표 PDF의 한글이 네모로 표시된다"로.

### 2. 유형 분류

`references/maintenance-types.md`의 분류 질문표를 위에서부터 묻는다. 먼저 걸리는 것이 유형이다.

| 순서 | 질문 | 예이면 | 비용 규모 |
|------|------|--------|-----------|
| 1 | 요구사항은 그대로인데 동작이 명세와 다른가 (테스트에서 못 잡은 오류) | **수정 보수** (Corrective) | 낮음 |
| 2 | 요구사항은 그대로인데 운영 환경(OS, DB, 브라우저, 하드웨어, 연동 시스템)이 바뀌어 안 되는가 | **적응 보수** (Adaptive) | 중간 |
| 3 | 새 기능, 기능 변경, 성능 향상, 사용성 개선처럼 **요구사항이 바뀌는가** | **개선 보수** (Perfective) | 가장 높음. 유지보수 비용의 약 50% |
| 4 | 지금은 문제가 없지만 장래 오류·비용을 줄이기 위한 구조 개선, 문서화, 재공학인가 | **예방 보수** (Preventive) | 중간, 장기 회수 |

분류 결과에 따라 다음 절차가 갈린다.

| 유형 | 절차 |
|------|------|
| 수정 | 3 → 4 → 5 → 6. SRS 변경 없음. 버전 PATCH |
| 적응 | 3 → 4 → 5 → 6. SRS 운영 환경 절(2.3)만 갱신. 버전 PATCH 또는 MINOR |
| 개선 | 3(영향 범위 개략) → **`/sw-srs` 회귀** → 설계·구현·테스트 재수행. 버전 MINOR 이상. 별도 견적(`/sw-estimate`) |
| 예방 | 7 재공학 계획. 기능 불변을 비교 검사로 증명. 버전 PATCH |

하나의 요청에 두 유형이 섞여 있으면 둘로 나눈다. "윈도우 11에서 깨지는 것도 고치고 모바일도 되게" 는 CR 두 개다.

### 3. 기존 시스템 이해 (영향 범위)

유지보수 비용의 대부분은 수정이 아니라 **이해**에 든다. 산출물이 있으면 여기서 회수된다.

1. **요구 ID 식별**: 증상·요구가 어느 FR/NFR에 해당하는지 `srs.md`에서 찾는다. 해당 요구가 없으면 (a) 개선 보수이거나 (b) SRS 누락이다. (b)면 SRS 보완 항목으로 적는다.
2. **모듈 식별**: 추적표로 요구 ID → 설계 모듈 → 코드 파일을 따라간다. 추적표가 없으면 코드를 직접 뒤져야 하고, 이 비용을 결과서에 기록한다 (재공학 근거가 된다).
3. **의존 모듈 식별**: `design-review.md`의 의존 행렬에서 수정 대상 모듈의 Fan-In(이 모듈을 쓰는 쪽)을 본다. Fan-In이 높을수록 회귀 범위가 넓다.
4. **파생 데이터 식별**: 수정 대상이 저장하는 데이터를 다른 모듈이 복사·계산해 쓰는지 본다. 자료 부작용의 원인이다.
5. **테스트 케이스 식별**: `test.md` 추적표에서 요구 ID에 연결된 TC와, 의존 모듈의 TC를 모아 회귀 테스트 목록을 만든다.
6. **외계인 코드 판정**: 수정 대상 코드가 다음 셋 중 둘 이상이면 외계인 코드다. 설계 문서 없음 / 작성자 불명 또는 퇴사 / 장기간(수년) 미수정. 외계인 코드면 수정 전에 역공학(7절)으로 최소한의 설계 정보를 복원한다.

### 4. 수정 계획

1. **변경 통제**: `code-review.md`의 형상 관리 규칙대로 브랜치(`fix/CR-nnn-…`)를 만들고 커밋에 CR 번호를 단다. 승인 없이 `main`을 고치지 않는다.
2. **수정 범위 최소화**: 증상의 원인만 고친다. "하는 김에" 주변 코드를 손대면 회귀 범위가 통제 밖으로 나간다. 주변의 문제는 별도 CR(예방 보수)로 적는다.
3. **설계 기준 준수**: 수정이 결합도·응집도 기준(`design-review.md`)을 깨지 않는지 본다. 급한 수정에서 전역 플래그나 다른 모듈 내부 접근이 들어오는 일이 잦다. `sw-code-review`를 수정 후 호출한다.
4. **적응 보수 특유 항목**: 환경 종속 코드가 한 곳에 모여 있는가. 흩어져 있으면 이번 수정으로 한 곳(인프라 계층)에 모으는 것까지를 범위로 할지 결정한다. 모으면 예방 보수 성격이 추가된다.

### 5. 수정 후 테스트

1. **원인 확인 테스트**: 증상을 재현하는 TC를 먼저 만들고 수정 전에 실패함을 확인한다. 수정 후 합격해야 "고쳤다"고 쓸 수 있다. 이 TC는 `test.md`에 영구 추가한다.
2. **회귀 테스트**: 3절 5번 목록을 `/sw-test`로 실행한다. 수정 전 버전의 출력과 비교(비교 검사)해 의도한 변화 외에 달라진 것이 없는지 본다.
3. **적응 보수**: 새 환경과 이전 환경 **둘 다**에서 실행한다. 이전 환경 사용자가 남아 있는 동안은 둘 다 지원 대상이다.
4. 실패하면 4절로 돌아간다. 3회 이상 반복되면 원인 분석이 틀린 것이므로 3절부터 다시 한다.

### 6. 부작용 점검과 문서 갱신

`references/maintenance-types.md` 6절. 수정이 끝났다고 CR을 닫지 않는다. 세 가지 부작용을 점검하고 문서를 갱신해야 닫는다.

| 부작용 | 질문 | 점검 방법 |
|--------|------|-----------|
| 코딩 부작용 | 고친 코드가 다른 코드의 동작을 바꿨는가 | 회귀 테스트, Fan-In 모듈 TC |
| 자료 부작용 | 자료 구조·형식·파생 데이터가 바뀌어 다른 모듈이 깨지는가 | 파생 데이터 목록, 자료사전 대조 |
| 문서화 부작용 | 코드는 바뀌었는데 SRS·설계서·매뉴얼·주석이 그대로인가 | 아래 갱신 체크리스트 |

문서 갱신 체크리스트:
- [ ] `srs.md`: 적응 보수면 운영 환경 절, 개선 보수면 요구 항목과 추적표 (버전 올림)
- [ ] `design*.md`: 모듈·인터페이스·의존이 바뀌었으면 갱신. `design-review.md` 재검증
- [ ] `test.md`: 원인 확인 TC 추가, 회귀 실행 이력 기록
- [ ] 사용자·운영자 매뉴얼: 화면·절차·지원 환경이 바뀌었으면
- [ ] 코드 주석: 수정 이유를 "왜"로
- [ ] 변경 이력(CHANGELOG), 버전 태그
- [ ] 이 CR 파일: 상태를 "완료"로, 수정 커밋과 배포일 기록

문서화 부작용이 쌓이면 다음 유지보수 때 "기존 시스템 이해" 비용이 커지고 결국 외계인 코드가 된다. **외계인 코드의 유일한 방지책은 문서화**다.

### 7. 재공학 계획 (예방 보수, 또는 `--reengineering`)

`references/reengineering.md`를 읽는다. 다음 중 하나면 재공학을 검토한다.

- 같은 모듈에 수정 보수 CR이 분기당 3건 이상 반복된다
- 외계인 코드 판정 모듈이 있다
- 적응 보수 때마다 환경 종속 코드를 여러 파일에서 찾아 고친다
- `maintenance/` 파일들의 "기존 시스템 이해" 소요가 수정 소요보다 크다

재공학은 기존 시스템을 **버리지 않고** 개선·강화해 유지보수성을 높이고 수명을 연장하는 활동이다. 목적은 유지보수 생산성이지 개발 생산성이 아니다. 활동은 넷이고 순서가 있다.

| 순서 | 활동 | 내용 | 산출물 |
|------|------|------|--------|
| 1 | 분석 | 기존 시스템의 동작·명세를 파악하고 재공학 대상을 정한다 | 대상 모듈 목록, 현재 지표 |
| 2 | 재구성 (Restructuring) | **기능은 그대로 두고** 내부 구조만 개선한다. 코드 정리, 함수 분리, 이름 정리, 결합도 낮추기 | 재구성된 코드, 비교 검사 결과 (출력 동일) |
| 3 | 이식 (Migration) | OS·하드웨어·DB·언어 버전 등 **환경을 옮긴다** | 새 환경 실행 결과 |
| 4 | 역공학 (Reverse Engineering) | 코드에서 설계·명세 정보를 **거꾸로 복원**한다. 가장 오래된 형태는 재문서화 | 복원된 설계서, 자료사전, 추적표 |

재사용(Reuse)은 재공학 활동이 아니다. 재공학의 **결과**로 재사용 가능성이 높아질 수는 있다. 기존 시스템의 보안 취약점을 찾아 침입하는 것도 재공학의 목표가 아니다.

역공학 절차 (외계인 코드일 때 수정 전에 최소 수행):
1. 코드에서 모듈·클래스 목록과 호출 관계를 뽑아 의존 행렬을 만든다 (`sw-design` 1단계 형식)
2. 각 모듈의 공개 인터페이스(입력·출력)를 적는다
3. 데이터 구조와 저장소를 자료사전 형식으로 적는다
4. 동작을 관찰해 "현재 이렇게 동작한다"를 요구 항목 형식(FR-R-nnn, R은 recovered)으로 적는다. 이것이 **맞는** 동작인지는 사용자가 확인해야 한다
5. 복원된 문서를 `design-oo.md`(또는 `design.md`)와 `srs.md`에 "역공학 복원" 표시와 함께 넣는다

재공학 계획서에는 대상, 활동별 범위, 기능 불변 증명 방법(비교 검사 TC 목록), 전후 지표(결합도·응집도·복잡도·수정 소요), 비용·기간, 위험을 적는다. 재공학은 장기 전략이며 비용·시간·자원이 많이 든다. 한 번에 전부 하지 않고 수정 CR이 몰리는 모듈부터 한다.

### 8. 재사용 검토

개선 보수나 재공학에서 새 코드를 쓸 때 `references/reuse.md`로 재사용 가능한 요소가 있는지 본다. 가장 많이 재사용되는 요소는 소스 코드이고, 부품이 **작을수록** 재사용률이 높다. 재사용 유형은 합성 중심(기존 부품을 조립)과 생성 중심(명세에서 생성)이다. 재사용의 단점(언어 종속, 기존 시스템에 끼워 넣기 어려움, 새 방법론 도입 어려움)도 적는다.

### 9. 저장

- 요청마다 `docs/sw/maintenance/YYYY-MM-DD_요청명.md`. 양식은 `templates/request.md`. 요청명은 한글 10자 이내, 공백 없이.
- 재공학 계획은 `docs/sw/maintenance/reengineering.md`. 양식은 `templates/reengineering.md`.
- 개선 보수로 `/sw-srs`에 회귀할 때는 CR 파일에 "회귀: srs.md vX.Y → vX.Y+1"을 적고, SRS 승인 후 설계·구현·테스트 스킬을 순서대로 다시 호출한다. CR 파일은 그 전체 과정의 추적 지점이 된다.

## 판정 기준

| 항목 | 완료 조건 |
|------|-----------|
| 분류 | 네 유형 중 하나. 혼합이면 CR 분리 |
| 영향 범위 | 요구 ID, 모듈, 의존 모듈(Fan-In), TC 목록이 모두 적혀 있음. "전체"는 허용하지 않음 |
| 원인 확인 TC | 수정 전 실패, 수정 후 합격이 실행 이력에 있음 |
| 회귀 테스트 | 영향 범위의 TC 100% 실행, 의도하지 않은 변화 0건 |
| 적응 보수 | 이전 환경과 새 환경 둘 다 합격 |
| 개선 보수 | `srs.md` 버전이 올랐고 추적표에 새 요구 ID가 있음. 없으면 완료 불가 |
| 부작용 점검 | 코딩·자료·문서화 세 항목 모두 점검 기록 |
| 문서 갱신 | 체크리스트 전 항목 완료. 하나라도 미완이면 CR 상태 "문서 미갱신" |
| 재공학 | 재구성 전후 비교 검사 출력 100% 동일. 전후 지표 기록 |

## 출력

- `docs/sw/maintenance/YYYY-MM-DD_요청명.md`. 양식은 `templates/request.md`.
- `docs/sw/maintenance/reengineering.md`. 양식은 `templates/reengineering.md`.
- 완성 예시: `examples/2026-05-12_윈도우11출력깨짐.md` (적응 보수), `examples/2026-05-12_모바일성적조회.md` (개선 보수, SRS 회귀), `examples/reengineering.md` (재공학 계획).
- 다음 단계:
  - 수정·적응: `/sw-code-review` (수정 코드) → `/sw-test` (원인 확인 + 회귀) → 이 CR 파일 완료 처리
  - 개선: `/sw-estimate` (별도 견적) → `/sw-srs` (요구 갱신) → `/sw-design-oo` → `/sw-code-review` → `/sw-test` → `/sw-sqa`
  - 예방·재공학: `/sw-design` (역공학 결과 검증) → `/sw-code-review` → `/sw-test` (비교 검사)
- 협업 모드: `docs/sw/OWNERS.md`가 있으면 저장 전에 그 규칙을 따른다. `git config user.name`으로 작성자를 찾아 그 사람 담당 파일만 고친다. 새 번호는 `[임시:FR-<이니셜>-1]` 형식으로 쓰고 산출물 버전은 올리지 않는다(변경 표시는 "(다음 판 변경)"). 목차 파일의 머리 헤더·문서 상태·목차, `docs/sw/README.md`, 공용 조각(추적표, 자료사전 등)에 들어갈 내용과 남의 파일에 고칠 것은 `docs/sw/pending/<브랜치 이름의 / 를 - 로>.md`에 적는다. 정식 번호와 버전은 공용 담당이 `/sw-sdlc merge`로 매긴다. 규칙 전문은 CONVENTIONS 8절과 OWNERS.md 3절이다.

## 체크리스트

- [ ] 요청을 측정 가능한 문장으로 다시 썼다
- [ ] 분류 질문을 순서대로 물었고, 혼합 요청은 CR을 나눴다
- [ ] 개선 보수를 "간단한 수정"으로 처리하지 않고 `sw-srs` 회귀를 적었다
- [ ] 영향 범위에 Fan-In 의존 모듈과 파생 데이터를 포함했다
- [ ] 외계인 코드 판정 기준 세 가지를 적용했다
- [ ] 원인 확인 TC가 수정 전에 실패하는 것을 확인했다
- [ ] 회귀 테스트 목록이 "전체"가 아니라 구체적 TC 목록이다
- [ ] 적응 보수에서 이전 환경도 테스트했다
- [ ] 부작용 세 종류(코딩·자료·문서화)를 각각 점검했다
- [ ] 문서 갱신 체크리스트를 다 채우기 전에 CR을 닫지 않았다
- [ ] 재공학 활동에 재사용을 넣지 않았다
- [ ] 재구성에서 기능이 바뀌지 않았음을 비교 검사로 증명했다
- [ ] 유지보수를 "설계를 다시 하는 활동"으로 쓰지 않았다 (설계 변경은 개선 보수로 SRS부터)
- [ ] 산출물 둘째 줄 헤더를 썼다

## 자주 하는 실수

- 기능 추가 요청을 "작으니까" 수정 보수처럼 코드부터 고친다. 요구 ID 없는 기능은 추적표 밖에 있어 다음 유지보수 때 누구도 왜 있는지 모른다. 개선 보수는 반드시 SRS부터다.
- 증상을 재현하는 테스트 없이 고친다. 고쳐졌는지 알 수 없고, 같은 버그가 다시 와도 모른다. 원인 확인 TC가 먼저다.
- 회귀 테스트를 "전체 다 돌림"으로 적는다. 전체를 돌릴 수 있으면 좋지만, 영향 범위를 적지 않으면 왜 그 테스트가 충분한지 설명할 수 없다. Fan-In 기준으로 범위를 적고, 그 위에 전체를 돌리는 것은 자유다.
- 적응 보수에서 새 환경만 테스트한다. 이전 환경 사용자가 깨진다.
- 코드만 고치고 문서를 안 고친다. 문서화 부작용은 당장 보이지 않지만 다음 담당자의 "기존 시스템 이해" 비용으로 반드시 청구된다.
- 재구성하면서 "이 참에" 동작도 바꾼다. 기능이 바뀌면 재구성이 아니라 개선 보수이고, 비교 검사로 검증할 수 없게 된다. 둘을 섞지 않는다.
- 재공학을 "새로 만들기"로 이해한다. 재공학은 기존 시스템을 살려서 개선하는 것이다. 완전 교체는 새 시스템이 더 낫다는 보장이 없고, 사용자 경험·호환성·비용 부담이 크다.
- 모델링(의존도, 클래스 다이어그램)을 유지보수 단계에서만 쓰는 것으로 안다. 모델링은 분석·설계·구현 전반에 쓰이며, 유지보수에서는 그것을 **읽는** 단계다. 읽을 모델이 없으면 역공학으로 만든다.
