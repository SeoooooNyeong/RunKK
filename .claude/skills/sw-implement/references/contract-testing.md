# 단위 사이 계약 고정

`sw-implement` 5단계. 설계서는 이름과 흐름을 정하지만 enum 상수 이름, 응답 항목, 시각 형식까지 고정하지 않는 경우가 많다. 병렬로 만든 단위는 각자 그럴듯한 값을 고르고, 통합에서 400·해석 실패로 드러난다. 계약은 파일로 고정하고 **양쪽 시험이 같은 파일을 읽게** 한다.

## 1. 계약 종류와 고정 방법

| 계약 | 기준을 만드는 쪽 | 고정 형태 | 시험 |
|------|------------------|-----------|------|
| 실시간 메시지 | 받는 쪽(앱) | 메시지 종류별 표본 JSON | 서버: 직렬화 결과 = 표본 / 앱: 표본 해석 |
| 내부 서비스 응답(ai 등) | 응답하는 쪽 | 상태 코드별 표본 JSON + 부르는 쪽 기대 결과 | 부르는 쪽: 표본마다 기대 결과 |
| REST enum 상수 | 서버 | enum별 상수 목록 파일 | 앱 상수 ⊂ 서버 목록 / 서버 목록 = 기준 파일 |
| REST 요청·응답 항목 | 서버 | record 구조(항목·필수 여부·중첩) 파일 | 앱이 보내는 항목 ⊂ 서버 요청, 앱 필수 항목 ⊂ 서버 응답 |
| 계산 공식(앱·서버 공용) | 먼저 만든 쪽 | 입력·출력 표(CSV) | 양쪽이 같은 표로 같은 출력 |

## 2. 공통 형식 규칙 (먼저 정해 둔다)

- 시각: 오프셋 포함 ISO-8601(예: `+09:00`). 오프셋 없는 값은 받을 때만 허용한다.
- 날짜: `yyyy-MM-dd`. 거리: 미터 정수. 시간: 초 정수. 페이스: km당 초.
- 오류 응답: 모든 실패가 같은 본문(`{code, message}`)과 상태 코드 규칙(400 형식, 401 인증, 403 권한, 409 업무 규칙, 429 시도 제한, 5xx 서버)을 쓴다. 실패인데 200, 한글 문구만 담은 본문 같은 예외 형식을 만들지 않는다.
- 페이지 나누기를 나중에 넣을 때는 선택 파라미터(`cursor`·`size`)와 선택 항목(`nextCursor`)으로 기존 형식을 깨지 않는다.

## 3. 갱신 절차

1. 서버 계약이 바뀌면 서버 쪽 계약 시험이 실패한다. 실패 메시지에 기준 파일 갱신 명령을 적어 둔다.
2. 기준 파일을 갱신하고 같은 내용을 앱 시험 자료로 다시 뽑는다(추출 스크립트 하나를 양쪽이 쓴다).
3. 앱 계약 시험이 실패하면 앱을 고친다. 화면 라벨은 그대로 두고 서버로 가는 값만 바꾼다.
4. 두 기준 파일이 같은지(줄바꿈 차이 제외) 확인하고 함께 커밋한다.

## 4. 계약 전에 만든 화면

화면이 서버보다 먼저 만들어지면 값을 가정할 수밖에 없다. 그때는

- 결정 목록에 "가정"으로 적고(어느 enum·항목인지),
- 서버 단계가 끝나면 앱이 서버로 보내는 모든 값과 앱이 필수로 읽는 모든 항목을 전수 대조한다.
- 대조 중 실제 서버에 요청을 보내 재현한다. Windows 셸에서 한글을 보내면 인코딩이 깨져 거짓 400이 나므로 영문 값으로 확인한다.
