# 기능 점수(Function Point)와 Putnam 모형

`sw-estimate` 절차 3(규모)과 절차 4(노력)에서 읽는다.

## 1. 기능 점수 (Function Point, FP)

Allan Albrecht가 IBM에서 1979년 제안했다. 코드 라인이 아니라 **사용자 관점에서 시스템이 제공하는 기능의 수**로 규모를 잰다.

### 왜 쓰는가

- LOC는 언어마다 다르다. 같은 기능을 Python 10줄, C 50줄로 짤 수 있다.
- 고객은 코드 줄 수가 아니라 기능에 관심이 있다.
- 언어를 정하기 전에도 셀 수 있다.
- 단점: 세는 과정이 복잡하고, 기능 정의가 불명확하면 측정이 흔들린다.

### 다섯 가지 기능 요소

| 요소 | 정의 | 세는 기준 | 예 |
|------|------|-----------|----|
| 외부 입력(EI) | 시스템 밖에서 들어와 내부 파일을 바꾸는 트랜잭션 | 입력 트랜잭션 수. 화면 수가 아니다 | 성적 입력, 수강신청, 학생 등록 |
| 외부 출력(EO) | 계산·가공을 거쳐 밖으로 나가는 결과 | 보고서·출력 화면 수 | 성적표, 수강 인원 통계 |
| 외부 질의(EQ) | 입력 → 조회 → 출력. 계산 없이 저장된 값을 그대로 보여줌 | 조회 기능 수 | 성적 조회, 학생 검색 |
| 내부 논리 파일(ILF) | 시스템이 유지·관리하는 데이터 집합 | 논리적 파일(엔티티 그룹) 수 | 학생, 과목, 수강, 성적 |
| 외부 인터페이스 파일(EIF) | 다른 시스템이 유지하고 이 시스템은 참조만 하는 데이터 | 참조 외부 파일 수 | 기존 학적 DB, 인증 서버 사용자 |

입력과 질의 구분: 저장 데이터를 바꾸면 입력, 바꾸지 않고 보여주기만 하면 질의. 계산·집계가 들어가면 출력.

### 복잡도별 가중치

| 요소 | 단순 | 보통 | 복잡 |
|------|------|------|------|
| 외부 입력 | 3 | 4 | 6 |
| 외부 출력 | 4 | 5 | 7 |
| 외부 질의 | 3 | 4 | 6 |
| 내부 논리 파일 | 7 | 10 | 15 |
| 외부 인터페이스 파일 | 5 | 7 | 10 |

복잡도는 다루는 데이터 항목 수와 참조 파일 수로 정한다. 대략 기준: 데이터 항목 5개 이하·참조 파일 1개면 단순, 데이터 항목 16개 이상 또는 참조 파일 3개 이상이면 복잡, 그 사이가 보통.

### 계산 절차

1. 기능 목록을 5요소로 분해하고 각각 복잡도를 매긴다.
2. 요소별 개수 × 가중치를 합산한다 → 미조정 기능 점수(UFP).
3. 영향도 보정 계수(VAF)를 구한다. 14개 시스템 특성(데이터 통신, 분산 처리, 성능, 사용 빈도, 트랜잭션 비율, 온라인 입력, 사용 편의성, 온라인 갱신, 복잡한 처리, 재사용성, 설치 용이성, 운영 용이성, 다중 사이트, 변경 용이성)에 0 ~ 5점을 매겨 합(ΣF)을 구한다.
   ```
   VAF = 0.65 + 0.01 × ΣF        (범위 0.65 ~ 1.35)
   ```
4. 조정 기능 점수 `FP = UFP × VAF`.
5. 언어별 환산 계수로 LOC를 구한다.

### 언어별 LOC/FP 환산 참고치

| 언어 | LOC/FP |
|------|--------|
| C | 128 |
| COBOL | 107 |
| C++ | 53 |
| Java | 53 |
| C# | 54 |
| Python | 27 |
| SQL | 13 |
| 4세대 언어 | 20 |

조직 실측이 있으면 그것을 쓴다. 혼합 언어는 비율로 가중 평균한다.

### 자동화 도구

기능 점수 기반 비용 예측 자동화 도구는 **ESTIMACS**다. 프로젝트 유형과 개발자 수준 차이를 반영해 계산한다.

### 흔한 오류

- 화면 수를 입력 수로 센다.
- 클래스 인터페이스, 모듈 수, 테이블 컬럼 수를 요소로 센다. 요소는 다섯 가지뿐이다.
- 영향도 보정을 빼먹고 UFP를 그대로 쓴다.
- LOC 환산 없이 기능 점수를 COCOMO에 넣는다. COCOMO 입력은 KLOC다.

## 2. Putnam 모형

Larry Putnam이 제안한 **소프트웨어 생명주기 예측 모형**이다. 프로젝트 기간 동안 인력 투입이 일정하지 않다는 관찰에서 출발한다.

### Rayleigh-Norden 곡선

인력 투입은 초반(계획·요구분석)에 적고, 중반(설계·코딩)에 최대가 되었다가, 후반(테스트·인수)에 다시 줄어든다. 이 분포를 종 모양 곡선으로 표현한 것이 Rayleigh-Norden 곡선이다.

```
인력
 |            . .
 |         .       .
 |       .           .
 |     .               .
 |   .                   .
 | .                       . .
 +------------------------------ 시간
   계획  분석  설계  코딩  테스트  인수
```

### 핵심 관계

규모(Size)는 노력(Effort), 생산성(Productivity), 기간(Time)의 함수다.

```
Size = C × Effort^(1/3) × Time^(4/3)      (C: 기술 상수, 조직 생산성 수준)
```

의미
- 규모가 클수록 노력이 늘어난다.
- **기간을 줄이면 노력이 급격히(4제곱에 가깝게) 늘어난다.** 기간 단축이 비용을 크게 올리는 이유를 수식으로 보여 준다.
- 같은 규모를 더 긴 기간에 하면 총 노력은 줄어든다 (한계 있음).

### 언제 쓰는가

- 대규모·장기 프로젝트에서 **시기별 인력 투입 계획**이 필요할 때
- 기간 압축이 노력에 미치는 영향을 정량화하고 싶을 때
- 소규모·단기 프로젝트에는 과하다

### 자동화 도구

Putnam 모형 기반 자동화 추정 도구는 **SLIM**(Software Life-cycle Management)이다.
