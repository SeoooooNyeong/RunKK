## 목적

테스트는 소프트웨어가 요구사항을 충족하는지 확인하기 위해 **오류를 찾아내는** 과정이다. 오류가 없음을 증명하는 활동이 아니라 아직 발견되지 않은 오류를 드러내는 활동이다. 이 스킬은 두 가지를 만든다.

1. **테스트 계획**: 어느 수준(단위·통합·검증·시스템)에서 무엇을 어떤 기법으로 검사할지, 합격 기준은 무엇인지
2. **테스트 케이스**: 입력값, 실행 조건, 기대 결과가 적힌 검사 데이터 집합. 요구사항 ID와 1:1 이상으로 연결된다

결과는 `docs/sw/test.md`에 저장되고, `sw-sqa`가 요구사항 추적표 대비 테스트 커버리지와 결함 추세를 볼 때 읽는다. `sw-maintain`은 수정 후 회귀 테스트 범위를 고를 때 이 파일의 케이스 목록을 쓴다.

## 입력

- `docs/sw/srs.md`: 기능 요구(FR-nnn)와 비기능 요구(NFR-nnn) ID. 없으면 `/sw-srs`를 먼저 안내하고 중단한다. 요구사항 없이 만든 테스트는 "무엇이 맞는 동작인지"의 근거가 없다.
- `docs/sw/design-oo.md` 또는 `docs/sw/design.md`: 클래스·모듈 경계. 단위 테스트의 단위를 정하고 통합 순서를 잡는 데 쓴다. 없으면 코드의 패키지 구조로 대신하되 결과서에 "설계서 부재"를 적는다.
- `docs/sw/code-review.md`: "우선 테스트 대상" 절. 있으면 순환 복잡도 상위 함수를 기초 경로 검사 대상으로 먼저 잡는다.
- 코드. 화이트박스 기법은 코드가 있어야 가능하다. 코드가 아직 없으면(V-모델에서 설계 직후 호출) `--plan-only`로 간주해 테스트 계획과 블랙박스 케이스만 만들고, 화이트박스 절은 "구현 후 작성"으로 비워 둔다.
- 사용자에게 물을 것: 테스트 대상 범위(함수 하나인가, 모듈인가, 전체인가), 테스트 프레임워크(JUnit 등. 케이스를 코드로도 뽑을지), 성능 요구 검증 환경이 있는가.

## 절차

### 1. 테스트 계획 수립

1. **수준별 대상과 기법을 정한다.** `references/test-levels.md`를 읽는다.

   | 수준 | 대상 | 주 기법 | 합격 기준 |
   |------|------|---------|-----------|
   | 단위 | 클래스·함수 하나 | 화이트박스 + 블랙박스 | 기초 경로 100%, 경곗값 전부 |
   | 통합 | 클래스 묶음 (스레드 기반 / 사용 기반) | 블랙박스, 인터페이스 검사 | 설계서의 모든 메시지 1회 이상 |
   | 검증 | 전체 기능 | 요구사항 기반 블랙박스 | FR 커버 100% |
   | 시스템 | 운영 환경의 전체 | 성능·보안·장애·시나리오 | NFR 전부 측정값으로 확인 |

2. **V-모델 대응을 적는다.** 요구분석 ↔ 시스템 테스트, 시스템 설계 ↔ 통합 테스트, 상세 설계 ↔ 단위 테스트. 각 테스트 수준이 어느 산출물을 기준 문서로 삼는지 표에 적는다. 이 대응이 있어야 "이 케이스가 왜 이 기대 결과를 갖는가"를 문서로 답할 수 있다.
3. **통합 전략을 고른다.**
   - 스레드 기반: 하나의 입력·이벤트에 응답하는 클래스들을 한 스레드로 묶어 테스트. 사용자 시나리오 단위로 빨리 돌릴 수 있다. 사용자 중심 시스템에 우선.
   - 사용 기반: 다른 클래스에 의존하지 않는 독립 클래스부터 테스트하고, 그것을 사용하는 종속 클래스로 올라간다. 기반 라이브러리·도메인 계층에 우선.
   - 보통 둘을 섞는다. 도메인 계층은 사용 기반, 응용 계층은 스레드 기반.
4. **테스트 순서를 고정한다.** 단위 → 통합 → 검증 → 시스템. 앞 수준이 합격해야 다음으로 간다. 순서를 바꾸면 시스템 테스트에서 발견한 결함의 원인을 클래스 수준까지 추적하는 비용이 커진다.
5. **범위에서 뺄 것을 명시한다.** 외부 시스템(기존 학적 DB 등)은 스텁·목으로 대체하고 실제 연동은 시스템 테스트에서만 한다고 적는다.

### 2. 테스트 케이스 구성 규칙

케이스 하나는 반드시 다음 다섯 칸을 가진다.

| 칸 | 내용 | 예 |
|----|------|----|
| ID | `TC-nnn` | TC-014 |
| 요구 ID | 연결되는 FR/NFR | FR-012 |
| 입력 | 값과 상태 | score = 100, 학생 상태 = 재학 |
| 실행 조건 | 사전 조건, 환경 | 교수 권한으로 로그인 |
| 기대 결과 | 관찰 가능한 결과 | 등급 "A" 반환, 저장 1건 |

기대 결과가 "정상 동작"이면 케이스가 아니다. 무엇이 반환되고 무엇이 저장되고 무엇이 표시되는지 쓴다. 기대 결과는 SRS 또는 설계서에서 나온다. 코드가 지금 내는 결과를 기대 결과로 적지 않는다. 그러면 버그를 정답으로 고정하게 된다.

### 3. 화이트박스 테스트 설계 (코드가 있을 때)

`references/white-box.md`를 읽는다. 함수 단위로 수행한다. `code-review.md`의 우선 대상부터.

1. **제어 흐름도(CFG) 작성**
   - 노드: 명령문 하나 또는 분기 없이 이어지는 명령문 묶음
   - 간선: 제어가 이동하는 화살표
   - 영역: 간선과 노드로 둘러싸인 면. 그래프 바깥도 영역 하나로 센다
   - 순차 / if-else / while / do-while / for / switch 의 그래프 모양은 references의 그림을 따른다
2. **순환 복잡도 V(G) 계산** — 세 가지로 계산해 서로 맞는지 확인한다.
   - V(G) = E − N + 2 (E 간선 수, N 노드 수)
   - V(G) = 영역 수
   - V(G) = 단순 조건(if, while, for, case, &&, ||) 수 + 1
   - 세 값이 다르면 CFG를 잘못 그린 것이다. 다시 그린다.
3. **독립 경로 집합 도출** — V(G)개의 경로를 고른다. 각 경로는 이전 경로에 없던 간선을 적어도 하나 포함해야 한다. 시작 노드에서 끝 노드까지 적는다.
4. **경로별 테스트 케이스** — 각 경로를 지나가게 만드는 입력값을 정한다. 어떤 경로는 입력으로 도달할 수 없을 수 있다(죽은 코드 또는 모순 조건). 그 경로는 "도달 불가"로 표시하고 `sw-code-review`에 넘긴다.
5. **보조 기법 적용**
   - 조건 검사: 복합 조건(`a > 10 && b < 5`)의 각 단순 조건이 참·거짓을 독립적으로 결정하는 조합
   - 루프 검사: 단순 루프는 0회·1회·2회·n−1회·n회·n+1회. 중첩 루프는 안쪽부터 최소값으로 고정하고 바깥을 변화. 연결 루프는 독립이면 단순 루프로, 종속이면 중첩으로. 비구조적 루프는 테스트하지 말고 재구성을 요구한다
   - 데이터 흐름 검사: 변수마다 정의(define) 지점과 사용(use) 지점을 짝지어 모든 정의-사용 경로를 1회 이상
6. **복잡도 10 초과 함수**는 테스트 케이스를 만들되 결과서에 "리팩터링 권고"를 적고 `sw-code-review`에 전달한다. 테스트로 복잡도를 줄일 수는 없다.

### 4. 블랙박스 테스트 설계

`references/black-box.md`를 읽는다. 요구사항 단위로 수행한다. 코드 없이도 가능하다.

1. **동치 분할** — 입력 조건마다 유효 동치 클래스와 무효 동치 클래스를 나누고 각 클래스에서 대표값 하나를 고른다.
   - 범위 조건(0~100): 유효 1개(범위 안), 무효 2개(미만, 초과)
   - 특정 값 조건(학년 = 1,2,3,4): 유효 4개(각 값), 무효 1개(그 외)
   - 집합 조건(권한 ∈ {교수, 조교}): 유효 1개(집합 안), 무효 1개(밖)
   - 불리언 조건: 유효 1개(참), 무효 1개(거짓)
   - 형식 조건(학번 10자리 숫자): 유효 1개, 무효는 형식 위반 유형별 1개(길이, 문자 포함, 빈 값)
2. **경곗값 분석** — 범위 조건마다 min−1, min, min+1, max−1, max, max+1 여섯 값. 오류는 경계에서 가장 많이 난다. 동치 분할 대표값이 경계를 포함하지 않으면 경곗값 케이스를 추가한다.
3. **원인-효과 그래프** — 입력(원인) 여러 개가 조합되어 출력(효과)을 결정할 때. 원인·효과를 나열하고 관계(AND, OR, NOT)를 그린 뒤 결정표로 바꿔 각 열을 케이스로 만든다. 입력 조건이 3개 이상 조합되는 기능에만 쓴다. 그 이하는 동치 분할로 충분하다.
4. **오류 예측** — 경험상 틀리기 쉬운 입력: 빈 값, null, 0, 음수, 최대 길이 초과, 특수 문자, 중복 제출, 동시 수정. 기법이라기보다 체크리스트다. 각 기능에 한 번씩 돌린다.
5. **비교 검사** — 같은 요구로 만든 다른 버전(이전 릴리스, 기존 시스템)이 있을 때 같은 입력에 같은 출력이 나오는지. 유지보수 단계의 회귀 테스트에서 주로 쓴다.

기법 선택 기준:

| 상황 | 기법 |
|------|------|
| 입력이 숫자·날짜 범위 | 동치 분할 + 경곗값 |
| 입력이 열거형·집합 | 동치 분할 |
| 입력 조건 3개 이상이 조합되어 결과 결정 | 원인-효과 그래프 |
| 기존 버전이 있는 수정·이식 | 비교 검사 |
| 모든 기능 | 오류 예측 체크리스트 1회 |

### 5. 통합 테스트 케이스

1. 설계서의 시퀀스 다이어그램(또는 DFD 프로세스 간 자료 흐름) 하나가 스레드 하나다. 스레드마다 참여 클래스를 나열한다.
2. 스레드의 입력(사용자 요청)과 최종 출력(응답·저장)으로 블랙박스 케이스를 만든다. 내부 클래스 사이의 메시지는 설계서의 시퀀스대로 호출되는지 확인 항목으로 둔다.
3. 사용 기반으로 올라갈 순서를 적는다. 의존하지 않는 클래스(엔티티, 계산기) → 저장소 → 서비스 → 컨트롤러.
4. 외부 시스템은 스텁으로 대체한다. 스텁이 반환하는 값도 케이스 입력에 적는다.

### 6. 검증·시스템 테스트 케이스

1. **검증**: SRS의 FR 목록을 위에서부터 훑으며 각 FR에 연결된 TC가 1개 이상인지 확인한다. 없는 FR은 케이스를 추가한다. 이 단계의 질문은 "사용자가 원한 그것인가"다.
2. **시스템**: NFR마다 측정 방법과 합격 수치를 적는다. "응답 2초 이내"는 "동시 1,000 세션에서 성적 조회 95퍼센타일 응답 2.0초 이하"처럼 측정 가능하게 쓴다. 장애 시나리오(DB 연결 끊김, 디스크 가득 참)와 보안(권한 없는 성적 수정 시도)을 포함한다.

### 7. 요구사항 추적표 갱신

FR/NFR ID ↔ TC ID 표를 만든다. 커버되지 않은 요구 0건이 목표다. 설계서가 있으면 FR ↔ 설계 모듈 ↔ TC 세 열로 만든다. 이 표는 `sw-sqa`의 FTR 입력이 된다.

### 8. 저장

`docs/sw/test.md`. 양식은 `templates/test.md`. 이미 있으면 케이스를 추가하고 버전을 올린다. 실행 결과(합격·실패)는 케이스 표의 "결과" 열에 날짜와 함께 기록한다. 결과서를 새로 만들지 않는다.

## 판정 기준

| 항목 | 합격 조건 |
|------|-----------|
| 기초 경로 커버리지 | 우선 대상 함수마다 독립 경로 V(G)개 모두에 케이스 1개 이상 |
| 경곗값 | 모든 범위 조건에 여섯 값 전부 |
| 동치 분할 | 모든 입력 조건에 유효·무효 클래스 대표값 전부 |
| 요구 커버리지 | FR 100%에 TC 1개 이상. NFR 100%에 측정 방법과 합격 수치 |
| 통합 | 설계서의 시퀀스 다이어그램 100%에 스레드 케이스 1개 이상 |
| 케이스 형식 | 모든 TC에 입력·실행 조건·기대 결과가 비어 있지 않음 |

하나라도 미달이면 결과서 판정은 "미완성"이다. 실행 결과의 합격률은 별도로 적는다. 계획 완성도와 실행 합격률을 섞지 않는다.

## 출력

- `docs/sw/test.md`. 양식은 `templates/test.md`.
- 완성 예시는 `examples/test.md` (학사관리 시스템 성적 모듈: `calculateGrade` 기초 경로 검사, 점수 입력 동치·경곗값, "성적 입력" 스레드 통합 테스트).
- 요청이 있으면 케이스를 JUnit 등 프레임워크 코드로도 뽑는다. 단, 문서가 원본이고 코드는 파생물이다.
- 다음 단계: `/sw-sqa`. 추적표와 실행 결과를 입력으로 넘긴다.
- 복잡도 10 초과 함수가 있으면 `/sw-code-review` 재호출을 함께 안내한다.
- 협업 모드: `docs/sw/OWNERS.md`가 있으면 저장 전에 그 규칙을 따른다. `git config user.name`으로 작성자를 찾아 그 사람 담당 파일만 고친다. 새 번호는 `[임시:FR-<이니셜>-1]` 형식으로 쓰고 산출물 버전은 올리지 않는다(변경 표시는 "(다음 판 변경)"). 목차 파일의 머리 헤더·문서 상태·목차, `docs/sw/README.md`, 공용 조각(추적표, 자료사전 등)에 들어갈 내용과 남의 파일에 고칠 것은 `docs/sw/pending/<브랜치 이름의 / 를 - 로>.md`에 적는다. 정식 번호와 버전은 공용 담당이 `/sw-sdlc merge`로 매긴다. 규칙 전문은 CONVENTIONS 8절과 OWNERS.md 3절이다.

## 체크리스트

- [ ] 모든 케이스에 요구 ID가 붙어 있다
- [ ] 기대 결과를 코드의 현재 출력이 아니라 SRS·설계서에서 가져왔다
- [ ] 순환 복잡도를 세 방법으로 계산해 값이 일치했다
- [ ] 독립 경로 수가 V(G)와 같고, 각 경로가 새 간선을 하나 이상 포함한다
- [ ] 범위 조건마다 경곗값 여섯 개가 있다
- [ ] 무효 동치 클래스를 빠뜨리지 않았다 (유효만 테스트하는 것이 가장 흔한 누락)
- [ ] 테스트 순서가 단위 → 통합 → 검증 → 시스템이다
- [ ] 단위 테스트의 단위가 클래스(또는 함수)다. 패키지 전체를 단위로 잡지 않았다
- [ ] 통합 테스트에서 스레드 기반·사용 기반 중 무엇을 어디에 썼는지 적었다
- [ ] NFR마다 측정 방법과 합격 수치가 있다
- [ ] 테스트 목적을 "오류가 없음을 보이는 것"으로 쓰지 않았다
- [ ] 산출물 둘째 줄 헤더를 갱신했다

## 자주 하는 실수

- 정상 입력만 테스트한다. 무효 동치 클래스와 경곗값 바깥(min−1, max+1)이 결함의 절반 이상을 잡는다.
- 코드를 돌려 본 출력을 기대 결과로 적는다. 테스트가 현재 동작을 승인하는 도구가 되어 버린다. 기대 결과는 요구사항에서 온다.
- 순환 복잡도를 "if 개수"로만 센다. `&&`, `||`, `case`, `while`, `for`도 각각 +1이다. 세 가지 계산법으로 교차 검증한다.
- 블랙박스와 화이트박스를 택일로 본다. 단위 테스트는 둘 다 쓴다. 화이트박스는 경로를, 블랙박스는 값을 고른다.
- 통합 테스트를 "다 붙여서 한 번 돌려 보기"로 한다. 스레드(시나리오) 단위 또는 의존 순서 단위로 쪼개야 실패 원인을 찾을 수 있다.
- 시스템 테스트에서 처음으로 외부 DB를 연결한다. 연동 인터페이스는 통합 테스트에서 스텁으로 미리 검증하고, 시스템 테스트는 실제 연동의 성능·장애만 본다.
- 테스트 결과를 새 파일로 만든다. 한 파일에 케이스와 실행 이력을 함께 두어야 회귀 테스트 범위를 고를 수 있다.
