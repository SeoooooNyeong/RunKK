# 구조적 프로그래밍 점검표

구조적 프로그래밍은 신뢰성과 유지보수성을 높이기 위해 프로그램의 제어 흐름을 세 가지 기본 구조만으로 제한하는 코딩 방법론이다. 제어 흐름이 제한되면 코드를 위에서 아래로 읽을 수 있고, 각 블록의 입구와 출구가 하나라서 테스트와 증명이 쉬워진다.

## 1. 기본 제어 구조 세 가지

| 구조 | 의미 | 언어 구문 |
|------|------|-----------|
| 순차(Sequence) | 위에서 아래로 차례대로 실행 | 문장 나열 |
| 선택(Selection) | 조건에 따라 둘 이상의 경로 중 하나 | `if`, `if-else`, `switch` |
| 반복(Iteration) | 조건이 유지되는 동안 되풀이 | `while`, `do-while`, `for` |

**함수 호출(call)은 기본 제어 구조가 아니다.** 호출은 코드를 추상화하고 재사용하는 수단이며, 호출된 함수 내부도 결국 위 세 구조로 이루어진다. 점검 시 "이 함수는 호출로 구성되어 있으니 구조적이다"라고 판단하지 않는다. 호출 안쪽을 본다.

## 2. 원칙

| 원칙 | 판정 질문 | 위반 시 |
|------|-----------|---------|
| 세 구조만 사용 | 세 구조 외의 흐름 제어(goto, 다중 레벨 탈출, 예외를 분기로 사용)가 있는가 | 치명 |
| 단일 입구 | 함수나 블록의 중간으로 뛰어드는 진입점이 있는가 | 치명 |
| 단일 출구 | 반복문 한가운데 `return`, `break`가 흩어져 있는가 | 중 |
| 직선 흐름 | 뒤로 점프하는 흐름이 반복문 외에 있는가 | 중 |
| 블록 명확성 | 한 줄 if에 중괄호를 생략해 다음 문장이 블록에 들어가는지 모호한가 | 경 |

## 3. goto의 등가물

현대 언어에는 goto가 없거나 쓰지 않지만, 같은 효과를 내는 패턴이 있다. 모두 goto와 같이 판정한다.

| 패턴 | 왜 goto와 같은가 | 교정 |
|------|------------------|------|
| 라벨 붙은 `break outer;` / `continue outer;` | 블록 경계를 넘어 점프 | 내부 반복을 함수로 뽑아 `return` |
| 예외(`throw`)로 정상 흐름을 분기 | 호출 스택을 가로질러 점프 | 반환값 또는 결과 객체로 분기 |
| `while(true)` 안의 조건부 `break` 여러 개 | 종료 조건이 헤더에 없음 | 종료 조건을 `while` 조건으로 올림 |
| 재귀로 반복을 흉내 내며 상태를 전역에 저장 | 흐름이 코드 순서와 무관 | 반복문과 지역 변수로 |
| `switch` fallthrough로 여러 case 연속 실행 | 암묵적 점프 | 공통 처리를 함수로 뽑고 각 case에서 호출 |

## 4. 단일 출구의 허용 예외: 가드 절

```java
public String calculateGrade(int score) {
    if (score < 0 || score > 100) return "INVALID";   // 가드 절
    if (score >= 90) return "A";
    if (score >= 80) return "B";
    return "F";
}
```

함수 시작부에서 전제 조건을 검사하고 즉시 반환하는 가드 절은 출구가 여러 개지만 허용한다. 이유: 모든 return이 **최상위 수준**에 있어 흐름이 위에서 아래로 읽히고, 중첩이 생기지 않기 때문이다. 다음은 허용하지 않는다.

```java
for (Student s : students) {
    if (s.getId() == target) {
        return s;          // 반복문 한가운데의 출구
    }
}
```

교정: 찾으면 반복 변수를 저장하고 반복을 종료하는 조건을 `for` 헤더에 두거나, 이 검색 자체를 `findById()`로 뽑아 그 함수에서는 유일한 일로 만든다. 후자가 보통 더 낫다. 검색 함수에서는 반복 중 return이 "찾았다"는 유일한 의미이므로 허용 범위로 본다. 판정 기준은 "반복문 안의 return이 그 함수의 유일한 책임인가"다.

## 5. 제어 흐름도와의 관계

구조적 프로그래밍을 지키면 제어 흐름도(Control Flow Graph)가 중첩된 블록의 조합으로 그려진다. 모든 분기가 다시 합류하고, 반복은 한 노드로 돌아오는 간선 하나로 표현된다. goto가 있으면 그래프에 임의 간선이 생겨 독립 경로 수가 급증하고 `sw-test`의 기초 경로 검사가 어려워진다. 즉 이 점검은 테스트 가능성 점검이기도 하다.

## 6. 점검 절차

1. 함수마다 제어 구문을 나열한다 (if, switch, for, while, do, break, continue, return, throw, 라벨).
2. 3절의 등가물 표에 해당하는 것을 찾는다. 하나라도 있으면 치명.
3. return 위치를 본다. 모두 최상위 가드 절이거나 함수 끝이면 통과. 반복문·깊은 중첩 안에 있으면 중.
4. 중첩 깊이를 센다. 4 이상이면 `coding-style.md`의 제어 구조 단순화 항목으로 넘긴다.
5. 결과를 함수별 표로 정리한다: 함수명, 조건문 수, 반복문 수, 약산 복잡도(조건+반복+1), 위반 항목.
