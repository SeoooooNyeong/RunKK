## 24. v0.27 검증 (워치 v2 R11~R15 반영, 2026-11-03)

이 장은 **design-oo.md v0.27**의 새 조각 `05-20-설계-결정-v0.27.md`(D-461~D-471)를 입력으로 review 0~6단계를 적용한 결과다. v0.27은 워치 v2 R11~R15 구현(거부 기록 보존·다시 보내기, 정지 구간 정밀도, 서버 판정의 빈 도달 시간, 폰 동행 표시 통일, 화면 모션)을 설계에 옮긴 판이고, 05-20은 "구조 수치 그대로"(D-471)라고 주장한다. 그러므로 이 장은 설계서 본문과 **코드 S15P31A207-watch feature/runkk-watch-v2 cc8c138b**(읽기만 함)를 함께 대조한다. 워치·폰 전체의 `com.a207.runkk` import를 소스에서 직접 셌고(테스트 소스 제외, 5.1.2 모듈 대응은 Konsist `moduleOf`와 같은 규칙), 23.8의 기준 코드 3ca3fef1을 git archive 사본으로 같은 방법으로 세어 비교했다. Gradle은 돌리지 않았다. 구조 시험 통과 여부는 구현 기록을 따른다.

기준은 23장과 같다: 0.1 기본값(결합도 상한 스탬프, 응집도 하한 통신적, Fan-Out 7, 순환 0), core.model은 폰·워치 모두 화살표로 센다(05-18 D-415), 화살표로 세지 않는 것은 자기 모듈 리소스 R(watch.ui.R, api.core.R, data.phone.R)뿐이다, 클래스 협력 객체는 Clock·CoroutineScope·그 클래스만 여는 저장소 핸들을 빼고 상한 7이다(05-18 D-419).

판정 대상은 넷이다.

1. D-471 주장(새 화살표 없음, 폰 154·워치 37, 순환 0, 역행 0, Fan-Out 7 이하)이 코드 import와 맞는가
2. `ResendRejectedRunsUseCase`의 domain.account 배치(D-463, 05-20 11절): (가) 그대로, (나) ui.me → domain.run 허용(폰 155)
3. 결합도·응집도: Data Layer 경로 13개·항목 경로 넷, WatchResendRequester 두 연산, WatchResultHeadline 매개변수 3, RejectedResendReceiver의 같은 시각 비교
4. 상태도(05-20 3.3 보관 기록 전송 상태, 3.4 Countdown 하위 상태)의 사건과 연산 대응, UploadState.SENDING

범위 밖: 05-19(v0.26, ai 서버 연결 D-434~D-455)는 이 장에서 보지 않는다. cc8c138b의 Konsist 허용 표에는 domain.coach·domain.runbody가 없으므로(ArchitectureTest.kt:385-430) 폰 154는 D-455의 화살표를 더하기 전 값이다. 05-19의 수치는 ai 구현 뒤 따로 센다.

**Data Layer 경로 13개와 항목 경로 넷.** WearPaths는 START_REQUEST, WATCH_DISPLAY, HEART_RATE_BATCH, END_REQUEST, PAUSE_REQUEST, PROXIMITY, LEAD_CHANGE, SESSION_REQUEST, WATCH_SESSION, SESSION_REVOKED, WATCH_MEASURING, RESEND_REJECTED, REJECTED_COUNT로 13개다(능력 이름 WATCH_CAPABILITY는 경로가 아니다). `DATA_ITEM_PATHS`는 HEART_RATE_BATCH·SESSION_REVOKED·RESEND_REJECTED·REJECTED_COUNT 넷이다(WearPaths.kt:67). D-464와 같다. 경로는 더하기만 했고 옛 폰의 MessageClient 요청도 받는다(PhoneMessageService.kt:38). 판정: DataClient 항목은 두 기기가 나눠 쓰는 저장소지만 경로마다 쓰는 쪽이 하나(RESEND_REJECTED는 WatchLink.kt:251, REJECTED_COUNT는 RejectedCountReporter.kt:44)이고 형식은 wear.contract 한 곳이 정한다. 메시지 큐 주제와 같은 계약 통신이므로 **외부 결합이 아니라 데이터 결합 + 숨은 의존**으로 본다(22장 H-55와 같은 판단). 숨은 의존은 H-60이다.

**WatchResendRequester 두 연산.** `requestResend()`(명령)와 `observeWatchRejectedCount()`(조회)는 둘 다 "연결된 워치의 거부 기록"이라는 같은 데이터를 다루고, 부르는 쪽은 ResendRejectedRunsUseCase 하나다(WatchResendRequester.kt:6). 통신적 응집이고 인터페이스 분리 원칙에도 어긋나지 않는다(쓰지 않는 연산을 강요받는 클라이언트 없음). 허용. 구현 WatchLink는 WatchGateway와 이 포트를 함께 구현한다. 둘 다 폰–워치 연결이라 같은 데이터이고, 생성자 협력 객체는 3으로 그대로다.

**RejectedResendReceiver의 같은 시각 비교.** 요청 시각(폰 시계 밀리초)을 요청의 **식별자**로 쓰고 직전 값과 같은지만 본다(RejectedResendReceiver.kt:42-48). 질문: 같은 요청이 두 번 오는 경로는 항목 재동기화와 (옛 폰) 메시지뿐이고 둘 다 같은 시각을 싣는다. 새 요청은 시각이 다르므로 폰 시계가 거꾸로 가도 놓치지 않는다. 크기 비교(>)였다면 시계가 되감긴 뒤의 새 요청을 버렸을 것이다. 그러므로 사건(요청)의 중복 제거로는 같음 비교가 맞다. 남는 위험은 둘이다. (1) lastRequestedAt은 메모리 값이라 프로세스가 새로 뜬 뒤 같은 항목이 다시 오면 한 번 더 되돌린다. 되돌리기는 REJECTED만 바꾸므로 결과는 "한 번 더 보내 보기"이고 서버가 다시 거부하면 REJECTED로 돌아온다(멱등에 가까움, 6절 지침과 맞음). (2) 같은 밀리초 두 요청은 화면 조작으로 생기지 않는다. **허용.** 반대로 폰의 건수 쪽은 워치 시계 크기 비교(`atEpochMillis >`)로 늦게 온 옛 값을 버린다(WatchLink.kt:265-267). 건수는 사건이 아니라 "마지막 값"이라 순서가 필요하므로 크기 비교가 맞지만, 워치 시계가 되감기면 새 건수가 다음 변화까지 버려진다. 영향은 설정 줄의 건수가 잠시 낡는 것뿐이다(누르면 워치가 되돌릴 것이 없어 아무 일도 없다). 숨은 의존 H-61로 등록한다.

**3.3 보관 기록 전송 상태.** 사건과 연산 대응은 맞다: 보관 → `save`, 거부 → `markRejected`(UploadPendingRunsUseCase.kt:56-58 → RoomPendingRunRepository.kt:117 `markState`), 다시 보내기 → `resetRejected`(:122 `replaceState(REJECTED, NOT_SENT)`), 성공 → `remove`(UploadPendingRunsUseCase.kt:51), 정리 → `clear`. 상태를 바꾸는 규칙이 UploadPendingRunsUseCase 한 곳(6절 지침)이고 워커·화면은 읽기만 한다는 것도 코드와 같다. 결함은 02 2.4.8과 어긋난 점이다(M88).

**UploadState.SENDING.** SENDING은 들어오는 전이도 나가는 전이도 없는 **도달할 수 없는 상태**다. 코드에서도 선언(UploadState.kt:12) 말고 쓰는 곳이 없고, 첫 커밋(685b8ff3)부터 한 번도 저장된 적이 없다. 상태도 원칙(모든 상태는 들어오는 전이가 있다)에 어긋나지만 결합도·응집도 등급에는 걸리지 않는다. 남겨 두면 읽는 사람이 "전송 중" 상태가 있다고 오해하고, 상태를 `when`으로 가르는 코드가 생기면 오지 않는 가지를 다뤄야 한다. 판정: **권고 R81, 지운다.** Room은 이름 문자열로 저장하고(PendingRunMapper.kt:44, :66) SENDING을 쓴 행이 없으므로 이전 없이 지울 수 있다. 02 2.4.8의 SENDING은 "UploadPendingRunsUseCase 실행 중(저장하지 않는 활동)"으로 바꿔 적는다(M88과 함께).

**3.4 Countdown 하위 상태.** 대응 확인: startRecord[온라인] → `Countdown(isConnecting = true)`(WatchFlowViewModel.kt:562), 서버 대결 열림 → BattleStep.Countdown → `countdownTo`가 `isConnecting` 기본값 false로 3부터(:663-671), 1초 → `secondsUntil(startAt)` 폴링, 0 → `onBattleRunning`의 Countdown(0) 뒤 Running(:676-683). 오프라인·자유런은 처음부터 Counting(:483, :563-566). 어긋난 곳은 실패 전이다(M89): 시간 초과를 포함한 네트워크 실패는 오프라인 대결로 Counting에 들어가고, 그 밖의 실패만 Countdown을 떠난다. "다시 고르기" 전이는 이 장에서 코드로 확인하지 않았다.
