## 23. v0.23 검증 (워치 v2 구현 반영, 2026-11-01)

이 장은 **design-oo.md v0.23**(05-17 D-395~D-414, v0.23 보정 포함)을 입력으로 review 0~6단계를 적용한 결과다. v0.23은 워치 v2 구현(MR !57)과 12차 리뷰·수정 반복을 설계서에 옮긴 판이다. 원칙은 "코드가 옳고 설계가 낡은 것은 설계서를 코드에 맞춘다"이다. 그러므로 이 장은 설계서 본문과 **코드 S15P31A207-watch feature/runkk-watch-v2 807d744a**를 함께 대조한다(읽기만 함). 워치·data.watch·data.guide의 import는 소스에서 직접 셌다. 폰 나머지와 서버는 Konsist(app ArchitectureTest)와 ArchUnit(backend ArchitectureTest)의 허용 표, 새 클래스의 import로 확인했다. 구조 시험을 실행한 결과는 이 장의 대상이 아니다. 시험 통과 여부는 구현 기록(implementation.md 14장)을 따른다.

설계 담당이 넘긴 판정 대상은 여섯이다.

1. 폰 154·워치 29 화살표. 새 화살표 넷(watch.cache → domain.live, watch.link → domain.live, watch.session → domain.settings, data.watch → core.model)의 근거와 Fan-Out(watch.ui 7, watch.link 6, data.watch 5)
2. 협력 객체 세는 규칙 변경(Clock·CoroutineScope·플랫폼 저장소 핸들 제외). WatchSessionStore 8 → 6, WatchBattleFlow 6 → 5, 최대 7
3. 서버 세대 폐기 구조. TokenIssuer 연산 4개, RefreshGrant의 Optional 값이 제어 결합인지, WatchSessionWithdrawalListener 의존 방향
4. W26 AccessGrant.watch·AuthFilter.WATCH_CLIENT
5. 머리말 팩토리 넷(forRecordVerdict)과 매개변수 3개
6. 8절 보류 결함

**R74 RefreshGrant의 Optional은 제어 결합인가.** 질문표 4번("flag·mode를 넘겨 상대 내부 분기를 정하는가")에 비춰 보았다. reissue는 Optional이 있으면 워치 쌍, 없으면 폰 쌍을 낸다(M84). 그러나 이 값을 **만드는 쪽이 TokenIssuer 자신**이다(redeemRefreshToken이 토큰 클레임 client·wgen을 읽어 만든다). AuthService는 값을 고르지 않고 받은 그대로 돌려준다. 호출자가 피호출자의 행동을 고르는 제어 신호가 아니다. 피호출자가 자기 토큰 종류를 기억하는 왕복 값이다. 그러므로 **스탬프 결합, 허용**으로 판정한다. 다만 설계 6절의 "분기하지 않는다"는 사실이 아니어서 고친다(M84). 권고: 같은 의미를 형식으로 드러내려면 RefreshGrant를 sealed(Phone, Watch(generation))로 바꿔 쓰지 않는 isWatch()(M86)를 없앤다. 행동은 바뀌지 않는다.

**R73 머리말 팩토리의 kind (검토).** R67로 `of(…, mode)`의 mode는 없어졌다. 그런데 `forRecord(kind, gapSeconds, opponentName)`와 `forRecordVerdict(kind, result, opponentName)`의 `kind: RecordBattleKind`가 여전히 함수 안 분기를 정한다. SELF면 BEST·GOOD, CELEBRITY면 WIN·LOSE와 셀럽 이름이다. 호출자(WatchFlowViewModel)는 이미 셀프인지 셀럽인지 안다. R67과 같은 종류의 **제어 결합(같은 패키지 안 연산), 검토**다. 매개변수 3개는 상한 4 안이라 허용이다.
- 개선 (가): 기록 대결 팩토리를 `forSelf(gapSeconds)`·`forCeleb(gapSeconds, name)`·`forSelfVerdict(result)`·`forCelebVerdict(result, name)`으로 나눈다. 팩토리가 여섯이 되고 매개변수가 최대 2로 준다.
- 개선 (나): kind를 결과 값의 일부로 본다. RecordBattleKind는 사용자에게 보이는 결과 종류를 정하는 도메인 값이고, 분기가 문구 선택 하나뿐이라는 근거를 설계에 적고 허용으로 둔다.
- 22장 R67과 같은 기준을 지키려면 (가)가 맞다. 화면 문구만 바뀌는 작은 수정이라 구현을 막지 않는다.

**협력 객체 세는 규칙 변경 (판정 대상 2).** v0.23은 Clock에 더해 CoroutineScope와 SharedPreferences·DataStore 같은 플랫폼 저장소 핸들을 뺀다. 셋 다 행동을 맡기는 협력자가 아니라 실행 환경(시간, 실행 문맥, 저장 위치)이다. 클래스 책임 판단에 쓰는 "협력 객체 수"의 뜻과 맞으므로 **받아들인다**. 조건은 둘이다. (1) 이 규칙을 12.4(구조 합격 조건)와 0.1에 함께 적어 폰 클래스에도 같게 쓴다. 21장의 DeviceCopySync 7도 다시 센다. (2) 저장소 핸들을 빼는 것은 그 파일을 그 클래스만 열 때로 한정한다. 두 클래스가 같은 파일을 열면 외부 결합이라 협력 객체 이전에 불허다. 코드 확인:
- WatchSessionStore: 생성자 tokens, accounts, pendingRuns, cache, uploads, settings, prefs, scope. 새 규칙으로 6
- WatchBattleFlow: coordinator, battleRepository, cache, waiter, pendingRuns, clock. 새 규칙으로 5
- WatchFlowViewModel: runTracker, battleFlow, sessionStore, phoneLink, connectivity, guidance, accounts. 7
- 최대 7로 설계와 같다

**판정 대상 5 매개변수.** forFree 2, forBattle 2, forRecord 3, forRecordVerdict 3. 상한 4 안이다(허용). 6절 "최대 3"과 같다. 분기 문제는 R73이다.
