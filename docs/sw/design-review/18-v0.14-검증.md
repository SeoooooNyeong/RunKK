## 18. v0.12~v0.14 검증 (2026-10-29)

이 장은 **design-oo.md v0.14**를 입력으로 review 0~6단계를 v0.12·v0.13·v0.14 변경 범위에 적용한 결과다. 17장은 v0.11 설계까지만 판정했으므로, v0.12(구현 반영 D-190~D-199, 05-04), v0.13(배틀런 QA 반영·계약 정정 D-200~D-217, 05-05, 02-02), v0.14(피그마 반영 서버 D-218~D-249·앱 D-250~D-289·통합 D-290~D-293, 05-06~05-09, 02-03)를 한 번에 본다. 기준선은 17장 검증 반영본(서버 64개·174개, 폰 145개, 조건부 합격)이다. **세 판에서 새로 생기거나 내용이 바뀐 화살표·패키지·모듈·클래스만 새로 판정**하고 나머지는 17장 판정을 이어 쓴다.

구현 저장소 S15P31A207-fig origin/develop 7c42b0fe의 코드와 구조 시험을 읽기만 했다. 서버 ArchitectureTest.java(PACKAGES 64, ALLOWED, 규칙 (1)~(12))와 앱 Konsist ArchitectureTest.kt(5.1.2 허용 표, TC-6583·TC-6584 등)를 v0.14 본문과 대조해, 본문대로 구현하면 깨지는 규칙을 찾았다(18.0.6). 2026-10-29 사용자 위임("10번까지 너가 전부 알아서 진행하고 MR 올려둬")에 따라 남은 결정 두 건과 개선안을 묻지 않고 정했다. 개선안은 design-oo 조각에 직접 반영했고(고친 문장 끝 `(v0.14 검증, D-xxx)`), 새 결정은 D-294~D-300이다.

#### 18.5.2 남은 결정 두 건 (위임, 기본값)

**a. evaluation에 validRuns를 더하는가 → 더한다 (D-294, R48).** 앱 D-284의 평가 화면 "유효 러닝 [n]회 달성"과 Routes.Evaluation(tier, validRuns, runimalType)은 평가가 일어난 순번을 요구한다. 서버는 평가 때 그 값을 이미 안다. running이 저장 때 유효 러닝 순번(validRunOrdinal)을 계산해 RunScoreInput에 실어 recordValidRun으로 넘기고, member의 TierProgress가 그 순번으로 평가 시점을 정한다(코드 Member.recordValidRun, TierProgress.validRunCount). 앱이 따로 세면 미전송 기록·재판정(v0.12 D-191) 때 서버 순번과 어긋난다.

| 비교 | 더함 (결정) | 더하지 않음 |
|------|-----------|------------|
| 앱이 n을 얻는 길 | 응답 그대로 | 대시보드·프로필의 runCount로 추정(평가 뒤 다른 기록이 오면 틀린다) 또는 새 조회 |
| 화살표 | 0 (D3 위의 반환 값) | 0 |
| DB | run_record.evaluation_valid_runs INTEGER 하나 | 없음 |

같은 결정으로 H-36 복제도 없앤다. D-291 원문은 running.TierApplier가 "순번이 3이면 FIRST_PLACEMENT"를 정하는데, 평가 시점 규칙의 주인은 member.TierProgress다. 그래서 member가 TierChange에 `Optional<TierEvaluation> evaluation()`(member 값 record TierEvaluation(EvaluationKind kind, int validRuns), kind는 FIRST_PLACEMENT·REEVALUATION, 평가가 없으면 비어 있다)을 담아 돌려주고 running은 그대로 저장한다. 결정 내용:

- 응답 `evaluation{kind, tier, validRuns, runimalType}`. validRuns는 평가를 일으킨 유효 러닝 순번(첫 배치는 3, 재평가는 10의 배수).
- TierChange + evaluation(), TierProgress.addValidRun이 평가할 때 kind를 정한다. TierApplier는 `markTierApplied(recordId, Optional<TierEvaluation>, Tier)`로 반영 표시와 같은 조건부 UPDATE에 kind·tier·valid_runs를 쓴다. running에 상수 3이 없다.
- V30 run_record: evaluation_kind VARCHAR(20), evaluation_tier VARCHAR(10), evaluation_valid_runs INTEGER, evaluation_runimal_type VARCHAR(20). CHECK(evaluation_kind·evaluation_tier·evaluation_valid_runs가 모두 NULL이거나 모두 NOT NULL), CHECK(evaluation_valid_runs IS NULL OR evaluation_valid_runs >= 3).
- RunEvaluationNote.noteRunimalType은 evaluation_runimal_type 한 열만 고치는 UPDATE라 TierApplier와 순서가 바뀌어도 된다(Runimal 판정은 비동기). evaluationOf는 evaluation_kind가 NULL이면 비어 있다(유형만 있는 행은 평가 화면을 띄우지 않는다).

**b. 기록 목록 newRecords 이름 → 코드의 기존 이름 체계로 맞춘다 (D-295, R49).** 코드를 확인한 결과(7c42b0fe) 기록 상세 응답의 newRecords는 enum 이름이 아니라 화면 문구 문자열 목록이다("최장 거리 신기록 · 직전 4.20 km", "5 km 신기록", RecordQueryService.newRecordLabels). 그 근원인 도메인 값은 running.NewRecordMark(kind: Kind{LONGEST, BASE_DISTANCE}, distance: StandardDistance, previous)이고 기록 행에 그 형식 그대로 저장된다(RunRecord.newRecordsData = "LONGEST;;…", "BASE_DISTANCE;KM5;…"). 거리 이름 KM1·KM3·KM5·KM10·HALF·FULL은 GET /growth 최고 기록 키와도 같다. 앱 요청 R-2의 LONGEST_DISTANCE·BEST_AT과 D-292의 LONGEST·BEST_1K…는 둘 다 코드에 없는 이름이다.

| 비교 | NewRecordMark 이름 (결정) | D-292 평면 enum(BEST_1K…) |
|------|---------------------|--------------------------|
| 서버 변환 | 저장된 NewRecordMark의 kind·distance를 그대로 싣는다 | 거리 → BEST_xK 대응표가 새로 생긴다(StandardDistance가 바뀌면 함께 고쳐야 하는 숨은 의존) |

결정: 목록 행 `newRecords: [{kind: LONGEST | BASE_DISTANCE, distance: KM1 | KM3 | KM5 | KM10 | HALF | FULL | null}]`(LONGEST면 distance null, DTO NewRecordDto). previous는 목록에 싣지 않는다. 상세의 문구 목록 newRecords(List\<String\>)는 이미 배포된 앱이 읽으므로 그대로 둔다. newRecord 불리언은 D-292대로 남긴다. 앱 RecordTag는 BASE_DISTANCE + 거리 이름으로 "n km 최고", HALF는 "하프 최고", FULL은 "풀 최고"를 붙인다.

- D-299로 BattleStartService의 책임이 "대결 시작 알림과 출발"에서 "친구 대결 생성 + 시작 알림"으로 넓어진다. 랜덤 대결은 Matchmaker가 Battle을 만들고 announceMatch만 부르므로 두 경로의 공통 부분은 announceMatch 그대로다. 협력 객체 수는 늘지 않는다.
- W5로 running Fan-In이 13이 되어 running → member 여유가 0.045로 정방향 쌍 가운데 가장 작다. 표현 패키지가 running을 더 읽을 때마다 0.01 안팎 줄어든다. 다음 표현 화살표는 analysis 경유로 해결할 수 있는지 먼저 본다.
