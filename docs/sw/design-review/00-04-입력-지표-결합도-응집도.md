## 0. 입력 정리

### 0.1 검증 기준

설계서에 별도 합의된 기준이 없어 스킬 기본값을 쓴다.

| 항목 | 기준 |
|------|------|
| 결합도 상한 | 스탬프 (제어는 검토, 외부·공통·내용 불허). 스탬프 중 받는 쪽이 쓰는 필드가 절반 미만이면 검토 |
| 응집도 하한 | 통신적 (절차적·시간적 검토, 논리적·우연적 불허. 변경이 드문 읽기 전용 기준 형식만 모인 패키지는 논리적이라도 조건부 허용) |
| Fan-Out 상한 | 7 |
| 순환 의존 | 0 |
| 계층 역행 | 0 (표현·구동 → 조립 → 응용+도메인 → 도메인 공통. 인프라는 인터페이스 구현으로만 위를 가리킨다) |

검증 범위: 서버 패키지 19개(design-oo.md 5.1.1)를 본 검증 대상으로 하고, 앱 모듈 11개(5.1.2)는 8장에서 따로 본다. 워치·ai 서버는 앱·서버와 네트워크 계약(5.7)으로만 연결되고 내부 모듈이 2~3개라 검증에서 뺐다.

- A01: `changeSetting`은 item이 동의 항목이면 Member.changeConsent → 감사 → ConsentWithdrawn 발행, 아니면 MemberSettings.apply로 처리 방식이 갈라진다. 호출자가 넘긴 값이 처리 경로를 고르므로 제어다. `withdraw(memberId, boolean confirmed)`의 confirmed도 "취소 / 진행"을 고르는 플래그다(불리언 매개변수는 거의 항상 제어, coupling.md 3절).
- A03: `ranking(memberId, RankingKind, period)`는 PERSONAL이면 회원 자신의 줄을, CREW면 회원의 크루를 찾아 크루 줄을 찾는다. kind가 처리 경로를 고른다.
- A05: `candidates(memberId, BattleType, filter)`는 SELF면 PersonalRecordBook을, CELEBRITY면 CelebrityRecordRepository를 읽는다. 두 경로가 공유하는 처리가 없다.
- A06: `decide(…, boolean approve)`, `delete(…, boolean confirmed)`, `lobby(…, LobbyAction)` 세 연산이 플래그·모드로 내부 분기를 고른다.
- A23, A25, A37, A38, A51, A57, A58, A62: 엔티티 전체를 받아 절반 미만의 필드만 쓴다. 엔티티에 필드가 추가·변경되면(예: RunRecord에 새 측정 항목) 쓰지도 않는 패키지가 함께 재컴파일·재시험된다. 특히 A38·A51·A58은 running의 저장소 인터페이스(RunRecordRepository)를 다른 패키지가 직접 써서, running이 저장 방식(경로 압축 열, E-11)을 바꾸면 세 패키지가 영향을 받는다.
- A39: analysis가 crew의 WeeklyRaceRepository를 직접 읽는다(design-oo.md 6.1.4 DashboardService 의존). crew가 공개한 WeeklyRaceService·CrewMembershipReader를 두고 저장소를 직접 쓴다.
- **A44**: SQ-03에서 MatchingService가 `member.getSettings().rememberBattleDistance(KM5)`를 부른 뒤 `MemberRepository.save(member)`를 한다. MemberSettings는 Member에 합성된 내부 부품이고(1.3.1), 6.1.2는 `getSettings()`를 "읽기 전용 뷰"로 정했다. battle이 member의 내부 부품을 꺼내 상태를 바꾸고 member의 응용 서비스를 거치지 않고 저장하므로, member는 자기 설정이 언제 어떻게 바뀌는지 통제하지 못한다. 상대의 내부 구현을 직접 고치는 것이므로 내용 결합이다. 설계서 안에서도 6.1.2(읽기 전용)와 SQ-03(수정)이 서로 모순된다.
- A45: RunRecordOpponent가 경로(누적 거리 표본), 거리, 경과 시간, 구간을 쓰므로 필드 절반 이상을 쓴다. 허용.
- A94·A95: design-oo.md 5.1.1이 "실시간 메시지 DTO"를 realtime 패키지에 두었다. 그런데 이 메시지를 만드는 쪽은 battle(BattleStartService, LiveBattleSession)과 crew(CrewRunService, CrewRunLiveSession)다. 메시지 클래스가 realtime에 있으면 도메인이 표현 계층을 import한다.
- A96·A97: Java의 sealed 인터페이스는 허용 하위 형식을 permits 절에 적어야 하고, 이름 없는 모듈에서는 같은 패키지에 있어야 한다. common의 sealed LiveMessage가 battle·crew의 메시지를 허용하려면 common이 그 클래스를 알아야 하거나 컴파일되지 않는다.
- 공통 결합 의심을 점검한 곳: OperationPolicy는 실행 중 바뀌는 캐시(가변 상태)를 가진 싱글턴이고 7개 패키지가 읽는다. 그러나 (1) 읽는 쪽은 메서드로 불변 값 객체만 받고 필드를 직접 읽지 않으며, (2) 쓰는 경로가 SettingAdminService.change 하나뿐이고 감사 기록이 남는다. 누가 언제 바꿨는지 추적할 수 있으므로 공통 결합으로 보지 않았다. 단, 요청 하나 안에서 같은 기준을 두 번 읽으면 그 사이 값이 바뀔 수 있다(2.3 숨은 의존 H-09).

근거:
- P1·P3·P16·P17·P18: 질문 1~5에 모두 "아니오", 질문 6("종류가 비슷해서")에 "예". 예를 들어 infra.persistence에서 크루 저장소 매핑을 바꾸면 회원·러닝·대결 저장소 구현과 같은 패키지라 함께 재시험 대상이 된다. 계층별 패키지(web, infra)를 기능별로 나누지 않은 것이 원인이다.
- **P10 character**: 안의 요소가 세 묶음이다. (1) Runimal 판정(RunimalProfile, AxisEvaluator 4개, RunSample, RunimalJudge, CourseSimilarityJudge, CourseVerdict, RunimalService, CourseSimilarityService), (2) 아바타 외형(Avatar, Face 3개, SdFaceParts, AppearanceCalculator, AvatarService, AppearanceService), (3) 리워드 경제(RewardWallet, RewardAccrual, OwnedItem, RewardService, ShopService). (1)과 (2)·(3) 사이에는 호출도 공유 데이터도 없다. 설계서 1.5.3이 캐릭터레코드를 RunimalProfile과 Avatar로 이미 나눴기 때문에 "같은 데이터"(통신적) 이유도 사라졌다. 남은 이유는 DFD 프로세스 6 "캐릭터 관리"라는 묶음 이름뿐이다. (2)와 (3)은 Avatar.equip이 RewardWallet.owns를 묻는 연결 하나가 있다.
- **P11 admin**: 유명인 기록 관리, 기준값 변경, 감사 조회, 운영자 인증이 "운영자가 쓴다"는 이유로 모였다. 앞의 세 서비스는 각각 battle·policy·audit의 데이터를 다루고 admin 안에서 서로 부르지 않는다(공유하는 것은 ensureOperator 호출 하나).
- **P15 common**: 세 가지 목적이 섞였다. (1) 불변 기본 형식(Distance, Pace, GeoPoint, Week, DateRange, TagSet, DisplayName, 열거형 8개) — 거의 바뀌지 않는다. (2) 도메인 사건 4개 — 기능이 바뀔 때마다 바뀐다(H-12). (3) 실시간 송신 포트(LiveMessenger, LiveMessage, ProgressReport) — battle·crew만 쓴다. (1)만 있으면 "변경이 드문 읽기 전용 기준 형식" 조건부 허용이 가능하지만, (2)·(3)이 섞여 Fan-In 17 전체가 사건·메시지 변경에 흔들린다.
- P6 analysis: 책임 문장에 접속사가 없고 서비스 7개가 모두 RunRecord를 입력으로 읽는다(대시보드, 기록 조회, 성장, 리포트, 랭킹, 코치 계획 이행). 통신적으로 판정했다. CoachService의 RunningGoal은 analysis 안에서 DashboardService(주간 목표 달성률)와 CoachService 두 곳이 써서, 내부 연결이 외부 연결(notification 1)보다 많다.
- P9 crew: 40개 안팎으로 가장 크지만 모든 요소가 crewId 하나에 매달려 있다. 크루 삭제가 소속·신청·게시글·크루런·주간 거리를 한꺼번에 지우는 것(FR-116)이 같은 데이터에 묶여 있다는 증거다. 크기 때문에 나누면 crewrun → crew, crew → crewrun(삭제) 양방향이 생기므로 나누지 않는 것이 낫다.
- P19 config: SecurityConfig·WebSocketConfig·SchedulerConfig·AsyncConfig·DomainEventConfig는 서로 데이터를 주고받지 않고 시작 시점에 함께 읽힌다는 이유로만 모였다.
