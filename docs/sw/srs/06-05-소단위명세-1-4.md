### 6.3 소단위 명세서

최하위 프로세스 70개마다 하나씩 쓴다. 처리 논리는 구조적 언어(IF-THEN-ELSE, 반복)로 쓰고, 조건 3개 이상이 조합되는 곳은 의사결정표로 쓴다. 의사결정표의 Y는 참, N은 거짓, -는 상관없음, X는 수행이다. "무엇을 판단하고 무엇을 내보내는가"까지만 쓰며 자료 구조·알고리즘·화면은 설계 단계의 일이다. 입력·출력 이름은 6.1 흐름 목록, 6.2 자료사전과 같다. v0.2에서 2026-10-19 결정(7.10)을 반영했고, v0.3에서 랭킹 제외로 3.6·5.5.2를 지웠다가 v0.4에서 되살렸고, v0.5에서 Q-60~Q-74 결정과 7.5를 넣었고, v0.6에서 Q-75~Q-87 결정과 5.7을 넣었고, v0.8에서 와이어프레임 결정(7.10.3)으로 5.6.1·5.7·6.1을 빼고 5.7.1~5.7.4·7.6을 넣었다. v0.10에서 변경 요청 CR-01~CR-09(7.13)를 반영해 5.1.5·5.4.1~5.4.5·5.6.1(되살림)·5.8·6.8·7.7을 넣고, 5.2.2를 지우고(번호 비움), 5.4를 Level 3로 나눴다. 바꾼 곳에는 `(v0.10 추가, CR-0x)` 또는 `(v0.10 변경, CR-0x)`를 붙였다.

#### 1.1 로그인 인증
입력: 로그인요청, 로그아웃요청, 계정연동요청, 인증결과, 회원레코드 / 출력: 인증요청, 로그인결과, 신규계정정보, 계정연동결과, 회원레코드, 회원삭제지시 / 관련 FR: FR-001, FR-002, FR-198, FR-199
```
요청이 로그인요청이면
    제공자종류(C-007의 두 제공자 중 하나)로 인증요청을 소셜 로그인 제공자에 보낸다
    IF 제공자 응답이 없으면
        로그인결과 ← 로그인실패 + "로그인 제공자 연결 실패"
    ELSE IF 인증결과가 인증실패이면
        로그인결과 ← 로그인실패 + 실패사유
    ELSE IF 같은 제공자종류·제공자계정ID를 가진 회원레코드가 있으면
        로그인 상태를 만들고 로그인결과 ← 로그인완료 + 회원ID
    ELSE
        신규계정정보 ← 제공자종류 + 제공자계정ID + (제공자제공이름), 1.2로 보낸다
        로그인결과 ← 가입필요 + 동의 화면(1.2)으로 바로 가입하거나 게스트로 시작(FR-197)할 수 있다는 안내
            * (v0.10 변경, CR-09, FR-001) *
요청이 계정연동요청(회원ID, 제공자종류)이고 그 회원의 계정유형 = 게스트 이면      * (v0.10 추가, CR-09, FR-198) *
    인증요청을 소셜 로그인 제공자에 보낸다
    IF 제공자 응답이 없거나 인증결과가 인증실패이면
        계정연동결과 ← 거부 + 거부사유("로그인 제공자 연결 실패" 또는 인증결과의 실패사유)
    ELSE IF 같은 제공자종류·제공자계정ID를 가진 다른 회원레코드가 있으면
        계정연동결과 ← 거부 + "이미 가입된 계정"            * 두 계정을 합치지 않는다 (제안) *
    ELSE
        회원레코드의 제공자종류·제공자계정ID ← 인증결과 값, 계정유형 ← 연동회원
        계정연동결과 ← 완료 + 제공자종류                    * 같은 회원ID를 유지하므로 모든 자료가 그대로 남는다 *
    * 결과 이름을 자료사전의 계정연동결과(처리상태 + (제공자종류) + (거부사유))로 맞췄다 (v0.10 변경, CR-09) *
요청이 로그아웃요청이면
    IF 계정유형 = 게스트 이고 유실확인여부 ≠ 예 이면       * (v0.10 추가, CR-09, FR-002, FR-199) *
        로그인결과 ← 유실확인필요 + 자료 유실 고지(FR-199) + 소셜 계정 연동 안내
    ELSE IF 계정유형 = 게스트 이면
        회원삭제지시를 ║D15║에 보내 기기의 미전송 기록을 지우고, 로그인 상태를 지우고 로그인결과 ← 로그아웃완료
        * 이름을 자료사전의 유실확인여부·유실확인필요·회원삭제지시로 맞췄다 (v0.10 변경, CR-09) *
    ELSE
        로그인 상태를 해제하고 로그인결과 ← 로그아웃완료
        * 기기의 미전송 기록은 지우지 않는다 *
로그인 상태로 앱이 서버에 접속할 때마다
    회원레코드의 마지막접속일시 ← 지금        * 미이용 게스트 파기(1.5, FR-200)의 기준. (v0.10 추가, CR-09) *
```

#### 1.2 회원 가입
입력: 회원가입요청, 게스트시작요청, 신규계정정보, 가상기록 / 출력: 회원가입결과, 회원레코드, 감사기록 / 관련 FR: FR-003, FR-004, FR-017, FR-197, FR-199 (FR-028 삭제됨)

가입 단계는 동의 화면 하나다(필수 3종 + 만 14세 확인 + 선택 2종). 프로필·기록 공개 범위·성향 태그·아바타 단계는 없다 (v0.10 변경, CR-03·CR-04, FR-003). 동의 화면에는 "전체 동의"를 두어 필수 동의와 선택 동의를 한꺼번에 켜게 하고 선택 동의는 따로 끌 수 있다. 기록 공개 범위 고지 문구는 두지 않는다 (v0.13 변경, CR-39, FR-003, FR-197. v0.10의 고지 문구 FR-028은 삭제됨). 소셜 로그인으로 온 회원가입요청(신규계정정보 있음)과 게스트시작요청(FR-197)에 같은 표를 쓴다 (v0.10 변경, CR-09, FR-004). 닉네임 입력 단계가 없어져 v0.9의 닉네임 오류 규칙은 1.3으로만 남는다.

| 조건 \ 규칙 | 1 | 2 | 3 |
|-------------|---|---|---|
| 필수 동의 3종(이용약관, 개인정보수집, 위치수집)에 모두 동의 | N | Y | Y |
| 만14세이상확인에 동의했고 출생연도가 있으면 만 14세 이상((기준 연도 − 출생연도) 15 이상, v0.9 추가, test.md TC-1105) | - | N | Y |
| 동작: 가입거부 "필수동의누락" + 빠진 동의항목 | X | | |
| 동작: 가입거부 "만 14세 이상만 가입할 수 있음" (FR-004) | | X | |
| 동작: 아래 가입 수행, 가입완료 + 회원ID | | | X |

```
가입 수행
    IF 회원가입요청이면 (소셜 로그인으로 온 가입)
        계정유형 ← 연동회원, 제공자종류·제공자계정ID ← 신규계정정보의 값
        닉네임 ← 제공자제공이름, 없으면 "러너" + 숫자 4자리 (FR-197 규칙)    * (v0.10 변경, CR-03, FR-003) *
            IF 제공자제공이름이 2자 미만이면 닉네임 ← "러너" + 숫자 4자리, 20자를 넘으면 닉네임 ← 앞 20자 (가입을 거부하지 않는다)   * (v0.10 보완, test.md v0.6 TF-VA-32), FR-003 *
    ELSE (게스트시작요청)                                               * (v0.10 추가, CR-09, FR-197) *
        IF 같은 접속지에서 최근 1시간 안에 만든 게스트가 10명(제안) 이상이면 회원가입결과 ← 가입거부 "시도 한도 초과", 끝   * (v0.10 보완, test.md v0.6 TF-VA-34), FR-197 *
        계정유형 ← 게스트, 제공자종류·제공자계정ID는 비운다
        닉네임 ← "러너" + 숫자 4자리 (제안)
    IF 같은 닉네임의 회원이 있거나 같은 가상닉네임(║D16║)이 있으면 겹치지 않는 숫자 4자리를 쓴다 (Q-75)
    회원레코드를 만든다. 마지막접속일시 ← 지금 (v0.10 추가, CR-09). 설정 기본값:
        기록공개범위 ← 전체공개 (FR-010 기본값. 가입 중 선택 단계도 고지 문구도 없고 러너는 가입 뒤 설정에서 바꾼다, v0.13 변경, CR-39)
        코스지도공유 ← 꺼짐, 단위 ← km
        알림수신 ← 모든 알림종류 예 (제안), 개인정보공개 ← 나이대·성별 각각 비공개(Q-69, v0.13 변경, CR-29), 가이드확인여부 ← 아니오 (v0.13 변경, CR-51)
        선택 동의 2종(마케팅수신, LLM전송) ← 요청 값, 없으면 아니오 (게스트도 같은 화면에서 기본 꺼짐으로 받는다, FR-197)
        심박수집·얼굴변환전송 동의 ← 아니오 (사용 시점에 받는다, N-23)
        러닝설정 ← 목표 자유·음성 켬·진동 켬·코치 계획 꺼짐
        대결설정 ← 5km·음성 켬·진동 켬·1km·근접알림 켬 (제안, 근접알림은 v0.10 추가, CR-02, FR-109)
        화면테마 ← 기기설정따름 (제안, v0.10 추가, CR-07, FR-203)
        티어 ← 언랭, 레벨 ← 1
    동의이력 기록, 감사기록 ← 행위종류 "가입동의"
    IF 게스트시작요청이면
        회원가입결과에 자료 유실 고지(FR-199)와 소셜 계정 연동(1.1) 안내를 붙이고 바로 홈으로 간다   * (v0.10 추가, CR-09) *
* 출생연도·성별·프로필소개는 가입 뒤 프로필 편집(1.3)에서 받는다. 러너 성향 태그는 받지 않는다 (v0.10 변경, CR-03·CR-04) *
* 아바타 얼굴은 가입 뒤 아바타 화면(6.3)에서 고르며, 고르기 전에는 기본 캐릭터 얼굴 1번을 쓴다 (v0.10 변경, CR-03, FR-155, FR-158) *
* 게스트 회원은 대결·크루·랭킹·프로필을 연동 회원과 똑같이 쓴다 (FR-197) *
```

#### 1.3 프로필 관리
입력: 프로필조회요청, 프로필변경요청, 회원레코드, 캐릭터레코드, 러닝기록, 가상기록 / 출력: 프로필, 회원레코드 / 관련 FR: FR-005, FR-006, FR-007, FR-076, FR-199, FR-202
```
요청이 프로필조회요청이면
    대상회원ID의 회원레코드와 캐릭터레코드(Runimal 유형, 얼굴구성, 선택배경)를 읽는다
        * 아바타 얼굴은 선택배경(6.6)과 함께 보인다. 얼굴구성이 없으면 기본 캐릭터 얼굴 1번이다 (v0.10 변경, CR-03·CR-06, FR-158, FR-202) *
    IF 대상 회원레코드가 없으면 (탈퇴)
        프로필 ← 표시명 "탈퇴한사용자"
    ELSE IF 요청자ID = 대상회원ID 이면 (마이페이지)
        최장거리기록 ← 본인 유효 러닝 중 거리가 가장 긴 기록
        누적거리 ← 본인 유효 러닝 거리의 합, 러닝횟수 ← 본인 유효 러닝 수          * (v0.13 변경, CR-29, FR-005) *
        프로필 ← 아바타 + 닉네임 + 레벨 + 티어 + Runimal유형 + 누적거리 + 최장거리기록 + 러닝횟수 + 공개 설정 + 설정   * 프로필 사진은 없고 아바타만 쓴다 (v0.13 변경, CR-29) *
        IF 계정유형 = 게스트 이면                                    * (v0.10 추가, CR-09, FR-199) *
            설정 화면에 자료 유실 고지(FR-199)와 소셜 계정 연동(1.1) 안내를 붙인다
    ELSE (다른 러너의 프로필, v0.13 변경, CR-29, FR-006)
        프로필 ← 표시명 + 아바타 + 레벨 + 티어 + Runimal유형 + 누적거리 + 최장거리기록 + 러닝횟수 (늘 보인다)
        IF 프로필소개가 있으면 프로필 ← 프로필소개 (한줄 소개는 쓰면 항상 공개)
        IF 대상의 개인정보공개의 나이대 = 공개 이면 프로필 ← 나이대 (기본 비공개, Q-69)
        IF 대상의 개인정보공개의 성별 = 공개 이면 프로필 ← 성별 ("여성 / 남성 / 밝히지 않음")
        최근러닝 ← 대상의 최근 유효 러닝 3건(종류·날짜·거리) 중 대상의 기록공개범위(FR-060)가 요청자에게 허용하는 것
        * 소속 크루명은 2차 배포 때부터 보이고 1차 배포 앱에는 보이지 않는다 (v0.13 변경, CR-24) *
    * 계정유형(게스트/연동회원)은 다른 러너의 프로필에 보이지 않는다 (제안, v0.10 변경, CR-09, FR-006) *
요청이 프로필변경요청이면
    IF 닉네임이 2~20자가 아니거나 다른 회원 닉네임 또는 가상닉네임과 겹치면 프로필 ← 거부사유 "닉네임 오류"
    ELSE IF 프로필소개가 40자를 넘으면 프로필 ← 거부사유 "소개 길이 초과"
    ELSE
        회원레코드의 바뀐 항목을 저장한다 (닉네임 변경 횟수 제한 없음)
        프로필 ← 바뀐 본인 프로필
    * 편집 항목에서 성향 태그를 뺐다. 러너는 성향 태그를 고르지 않는다 (v0.10 변경, CR-04, FR-007) *
    * 가입 단계에서 뺀 출생연도·성별·프로필소개는 여기서 받는다. 프로필 사진은 없앴다 (v0.10 변경, CR-03, FR-003. v0.13 변경, CR-29) *
    * 입력한 출생연도는 화면에 나이대로 보인다. 나이대·성별의 공개 여부는 항목마다 이 화면에서 정하며 설정변경요청으로 1.4가 저장한다 (v0.13 변경, CR-29, FR-012) *
```

#### 1.4 설정·동의 관리
입력: 설정변경요청, 고지문서요청, 회원레코드 / 출력: 설정결과, 고지문서, 회원레코드, 감사기록, 경로파기지시, 심박파기지시 / 관련 FR: FR-008~FR-019, FR-025, FR-026, FR-029, FR-048, FR-109, FR-203, FR-231, FR-237, FR-238(기기 안 처리, v0.17 추가)
```
요청이 고지문서요청이면
    고지문서 ← 문서종류 + 그 문서의 공개 주소
요청이 설정변경요청이면

#### 4.4 상대 진행도 생성
입력: 러닝진행값, 대결상대기록, 대결레코드, 캐릭터레코드, 회원레코드 / 출력: 상대진행도, 대결레코드, 알림사건, 종료카운트다운신호, 근접알림 / 관련 FR: FR-088~FR-091, FR-098, FR-099, FR-102, FR-107, FR-109, FR-188, FR-189, FR-196
```

    대결레코드를 읽는다. IF 대결상태 ≠ 진행 이면 무시한다
    IF 대결종류 = 랜덤 이면

        IF 대결종류 = 유명인 이면 러너 아바타(캐릭터레코드)와 유명인 SD 캐릭터의 화면 간격을 거리차에 비례하게 정한다 (2단계)
    * 상대 마커 위치는 앱이 거리차로 정한다. 뒤처지면 내 경로 위에서 거리차만큼 뒤, 앞서면 내 진행 방향으로 늘인 선 위에서 거리차만큼 앞, 출발 뒤 내 누적거리가 20m가 되기 전에는 그리지 않는다 (v0.15 변경, CR-63, FR-088) *

        앞서게 된 참가자에게 대결안내 ← 추월, 뒤처지게 된 참가자에게 대결안내 ← 역전당함
        회원 설정 대결설정의 진동안내여부 = 예 이면 안내방식 ← 진동 (음성은 음성안내여부를 따른다)
        앞서게 된 참가자의 추월횟수 ← 추월횟수 + 1 을 대결레코드에 남긴다
        참가자마다 아래 근접 알림 표의 규칙 4·5에 들면 그 참가자의 근접알림에 추월진동여부 ← 예 (워치 1초 긴 진동 1회, v0.10 추가, CR-02, FR-188, FR-196)

            모든 참가자에게 종료카운트다운신호(대결ID, 도착자표시명, 종료일시)를 보낸다 (FR-107)
