##### 7.13.25.1 도출 기록 (되묻기와 시나리오)

| 원문(사용자 결정) | 되물은 결과 | 반영 |
|-------------------|-------------|------|

수신 동의와 야간 규칙 판단(설계 D-623): 공지는 응모한 러너 개인에게 그 응모 결과(당첨)를 알리는 운영 안내이고 광고가 아니다. 자료사전 알림종류 주석도 「마케팅 알림은 범위에 없다」고 적고 있다. 마케팅 수신 동의(FR-025)는 기본 미동의라 대부분의 당첨자가 동의하지 않았을 것이고, 동의를 따르면 당첨자 대부분이 푸시를 받지 못한다. 홈 알림함 단추의 점은 새 이벤트만 표시하고 안 읽은 알림을 표시하지 않으므로 알림함만으로는 당첨자가 알아채기 어렵다. 그래서 공지는 마케팅 동의를 보지 않고, 러너가 끄는 수신 설정 단위로도 두지 않는다(끄면 당첨 안내를 놓친다). 대신 공지를 광고에 쓰지 않도록 받는 사람을 회원ID로 고르게 하고 한 번에 100명으로 묶는다. 야간 발송 규칙은 프로젝트에 없고, 법의 야간 제한은 광고성 정보에만 걸리므로 시스템 규칙으로 막지 않고 운영 절차(08:00~21:00 발송)로 둔다. 이 판단은 PM 확인 대상이다(메모 N1).

시나리오 S-NT-1 당첨 안내(정상): 11/17 운영자가 응모자 명단(FR-319)에서 코치님별 1명, 베타 10명을 추첨한다 → 관리 기능으로 회원ID 12명, 제목 「이벤트 당첨을 축하해요」, 본문, 구글 폼 짧은 주소를 보낸다 → 결과에 요청 12, 저장 12, 건너뜀 없음이 나온다 → 감사기록(기준값변경, NOTICE:제목)이 남는다 → 당첨자 기기에 제목 「이벤트 당첨을 축하해요」 알림이 뜬다 → 앱 알림함 맨 위 묶음에 그 제목과 본문이 보인다 → 누르면 바깥 브라우저에서 구글 폼이 열린다.

- 예외 S-NT-1a: 회원ID에 탈퇴한 회원이나 없는 번호가 섞였다 → 그 회원만 건너뛰고 결과의 건너뜀 목록에 적는다. 나머지는 보낸다.
- 예외 S-NT-1b: 링크가 http이거나 구글 폼이 아니다 → 「값이 올바르지 않음」으로 거부하고 아무에게도 보내지 않는다.
- 예외 S-NT-1c: 회원ID가 비었거나 100개를 넘는다, 제목이나 본문이 비었다 → 형식 오류로 거부한다.
- 예외 S-NT-1d: 당첨자 기기 토큰이 없거나 푸시 알림 서비스가 실패한다 → 알림함에는 남는다. 다시 보내지 않는다(FR-175).
- 예외 S-NT-1e: 당첨자가 앱을 0.11.4로 올리지 않았다 → 알림함에 제목 「알림」과 본문이 보이고 눌러도 링크가 열리지 않는다. 본문에 구글 폼 짧은 주소를 글로 함께 적는 운영 절차로 보완한다(메모 N2).
- 예외 S-NT-1f: 화이트리스트에 없는 계정 → 거부(FR-173).

##### 7.13.25.4 모델 반영 (DFD, 소단위 명세, 자료사전)

새 프로세스 7.12 「공지 발송」을 Level 2 프로세스 7 아래에 더한다(7.11 다음 번호). 그림과 흐름은 v0.30 병합에서 06-02b, 06-01, 02 배경도(L0-54)에 옮겼다. 새 저장소는 없다.

배경도 균형: 단말을 더하지 않는다. 운영자 → 시스템에 공지발송요청을 더하고, 운영자로 나가는 공지발송결과는 기존 복합 흐름 운영결과의 구성이다. 러너로 나가는 흐름(알림함, 푸시 알림)은 그대로다. 바깥 브라우저로 링크를 여는 일은 앱 기기 안의 일이라 흐름으로 그리지 않는다. 자료 이름 바뀜: 공지발송요청 → 알림사건 → 알림레코드, 푸시요청.

소단위 명세서

```
7.12 공지 발송
  운영자ID가 운영기준의 운영자 목록에 없으면 거부한다 (FR-173)
  수신회원ID목록이 비었거나 100개를 넘거나, 공지제목, 공지본문이 비었거나 길이를 넘으면 거부한다
  공지링크가 있고 구글 폼 https 주소가 아니면 「값이 올바르지 않음」으로 거부한다(아무에게도 보내지 않는다)
  수신회원ID목록에서 겹친 ID를 뺀다
  수신회원ID마다:
    IF 회원레코드가 없거나 탈퇴 상태 THEN 건너뜀 목록에 넣는다
    ELSE 알림사건(공지, 알림제목 = 공지제목, 알림내용 = 공지본문, 이동대상 = 외부링크 + 공지링크)을 7.3으로 보낸다
  감사기록(기준값변경, 「NOTICE:공지제목」, 변경후값 = 요청과 결과)을 남긴다
  공지발송결과(수신요청수, 저장수, 건너뛴회원ID목록)를 보낸다
```

7.3 알림 발송 소단위 명세(06-06)의 보충: 알림종류가 공지면 수신 설정을 보지 않고(공지는 수신 설정 단위가 아님) 푸시요청에 알림제목을 싣는다. v0.30 병합에서 06-06 7.3에 옮겼고, 7.12 소단위 명세도 06-06에 옮겼다.

```

    * 운영자 → 7.12 (FR-320) *

    * 7.12 → 운영자. 운영결과의 구성. 건너뛴회원ID는 없거나 탈퇴한 회원이다 *
```

##### 7.13.25.5 구현 대조와 모르는 알림 종류 처리 (2026-11-08)

모르는 알림 종류를 받은 지금 앱(main 0.11.3, 핫픽스 전 코드)의 동작을 코드로 확인했다.

| 위치 | 지금 동작 | 공지에서의 결과 |
|------|-----------|-----------------|
| 응답 해석 `InboxResponse`(type은 문자열, Json `ignoreUnknownKeys = true`) | 모르는 type 값과 새 항목(title)을 오류 없이 받는다 | 알림함이 깨지지 않는다 |
| 제목 `NotificationRepositoryImpl.titleOf`(TITLES 표) | 모르는 type은 `inbox_title_default` 「알림」 | 제목 「알림」 |
| 라벨 `InboxLabels.of` | 모르는 type은 null이고 줄 위 글은 제목 | 「알림」 위에 본문 |
| 닫힌 기능 판정 `GatedFeature.of` | 모르는 type은 null(숨기지 않음) | 알림함과 기기 알림에 보인다 |
| 이동 `inboxDestination` | 모르는 화면(EXTERNAL_LINK)은 null, 알림함에 머문다. 읽음 처리는 한다 | 눌러도 링크를 열지 못한다 |
| 기기 알림 `RunkkMessagingService`와 OS | FCM notification 메시지의 제목, 본문을 그대로 띄우고 누르면 앱을 연다 | 제목은 공지제목으로 보인다 |
| 알림 설정 `NotificationTypes` | 서버 설정 응답의 알림 목록에 공지가 없다(서버 설정 목록 밖) | 영향 없음 |

결론: 옛 앱도 공지를 받아 본문까지 읽을 수 있고 깨지지 않는다. 링크만 열 수 없다. 핫픽스 0.11.4가 공지를 알아보게 고쳤다(FR-321).

구현(같은 핫픽스 브랜치, 커밋 b26b3317): 서버 `NotificationType.NOTICE`, `Screen.EXTERNAL_LINK`, notification.title 열, `NoticeService`, `POST /api/v1/admin/notifications/notices`, V35_3. 앱 알림함 공지 제목, 링크 열기, 설정 계약. 설계는 [05-27](../design-oo/05-27-설계-공지알림-성.md). 검증(2026-11-08): 서버 `./gradlew build` 시험 1,970건 통과(Docker PostgreSQL 마이그레이션 시험 포함, PlacementMigrationIntegrationTest의 develop 순서 모의에서 35.1, 35.2, 35.3이 V36, V37 뒤 순서 밖으로 한 번씩 적용됨을 확인), 앱 ktlintCheck, lintLocalDebug, testLocalDebugUnitTest(모듈 합계 2,078건), assembleLocalDebug 통과.
