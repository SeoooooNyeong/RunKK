##### 7.13.27.1 도출 기록 (사실 확인과 되묻기)

| 원문(사용자 결정, 확인 사실) | 되물은 결과 | 반영 |
|------------------------------|-------------|------|
| 서버가 쓰는 시각은 한국 시각이다 | 어디서 정하는가: Clock 빈이 `Clock.system(Asia/Seoul)`이라 `LocalDateTime.now(clock)`은 한국 시각이다. 그러나 API 컨테이너 JVM은 UTC(TZ 없음)이고 `hibernate.jdbc.time_zone`이 Asia/Seoul이라 저장할 때 9시간 더해진다(실제 14:29에 쓴 last_access_at가 23:26으로 저장). 읽을 때 9시간 빠져 앱에서는 맞게 보인다 | [임시:NFR-성-1] |
| DB에서 now()는 한국 시각이다 | 어느 연결에서: psql로 들어가면 postgres 컨테이너의 TZ, PGTZ가 Asia/Seoul이라 한국 시각이다. 서버 연결(JDBC)은 JVM 시간대(UTC)를 세션 시간대로 보내므로, 서버 연결에서 도는 Flyway 시드의 now()는 UTC 벽시계 값이다(운영 V35_2 이벤트 created_at과 flyway_schema_history.installed_on이 같은 UTC 값으로 확인) | [임시:C-성-1] |
| SQL로 직접 넣은 값이 틀어진다 | 어떤 값: 마이그레이션 시드 리터럴(이벤트 기간, 유명인 기록 등록 시각), 운영자 SQL(코치님 유명인 기록 11, 12번, develop 공지 시험 행), dev-seed 더미 자료. 서버는 이 값들을 9시간 이르게 읽는다 | [임시:NFR-성-1] |
| 서버 시간대 자체를 고친다 | 무엇을 고치는가: 실행 환경(JVM 기본 시간대)과 저장 규칙. 기존 자료는 「서버가 쓴 값」만 되돌리고, SQL로 넣은 한국 시각 값은 그대로 둔다(열과 행을 나눠야 한다, 설계 05-28 4절) | [임시:CR-성-1] |
| develop 먼저, 운영은 백업 뒤 따로 | 운영 적용 시점: develop 확인 뒤 사용자가 정한다. 운영 DB와 443에는 이 브랜치에서 아무것도 쓰지 않는다(읽기 전용 조회만) | [임시:CR-성-1] |

##### 7.13.27.2 바뀐 요구

| ID | 종류 | 요구 | 측정(확인 방법) | 우선순위 |
|----|------|------|-----------------|----------|
| [임시:NFR-성-1] | 정확성(자료 일관성) | 서버가 다루는 일시는 한국 시각(Asia/Seoul) 기준이다. 서버가 DB에 쓴 일시는 한국 시각 벽시계 값 그대로 저장되고, SQL로 넣은 한국 시각 일시는 서버가 같은 시각으로 읽는다. 서버가 쓴 값과 그 순간의 DB now()(psql) 차이는 1분 안이다 | (1) 저장 계약 통합 시험: JPA로 쓴 14:29가 DB 문자열 「14:29:00」이고 SQL로 넣은 14:29를 서버가 14:29로 읽는다(JVM 시간대가 UTC여도). (2) develop 적용 뒤 확인 쿼리: 방금 접속한 계정의 last_access_at과 DB now() 차이 1분 안, now()보다 미래인 서버 시각 열 0건 | 필수 |
| [임시:C-성-1] | 제약(운영 환경) | API 서버의 JVM 기본 시간대, 서버 연결의 DB 세션 시간대, 서버 시계(Clock), postgres 컨테이너 시간대는 모두 Asia/Seoul이다. DB 일시 열은 timestamp without time zone에 한국 시각을 저장한다(ai 서버의 analytics 스키마와 토큰 기록처럼 시점을 저장하는 timestamp with time zone 열은 예외). hibernate.jdbc.time_zone처럼 저장 때 시간대를 옮기는 설정을 두지 않는다 | 배포 뒤 `docker exec runkk-<환경>-api-1 date`가 KST, 서버 연결의 `SHOW TimeZone`이 Asia/Seoul(통합 시험), application.yml에 jdbc.time_zone 없음 | 필수 |

기존 자료 이전 요구(이번 변경에 한함): 적용 시점에 저장되어 있던 일시 중 서버가 쓴 값은 9시간 빼서 실제 한국 시각으로 바꾼다. SQL로 넣은 한국 시각 값(시드 리터럴, 운영자 SQL)은 바꾸지 않는다. 이벤트 기간은 임시 보정을 되돌려 11/08 00:00~11/16 23:59:59로 돌아간다. 열과 행 분류는 설계 05-28 4절이 정한다.

##### 7.13.27.3 시나리오

- S-TZ-1 운영자 SQL(정상, 적용 뒤): 운영자가 psql로 공지 행이나 이벤트 기간을 한국 시각 그대로(예: `now()`, `TIMESTAMP '2026-11-17 10:00'`) 넣는다 → 서버와 앱이 같은 시각으로 보인다(「방금」, 11/17 10:00). 9시간을 더하거나 빼지 않는다.
- S-TZ-2 서버 저장(정상, 적용 뒤): 러너가 14:29에 앱을 연다 → member.last_access_at이 DB에 14:29로 저장된다 → 운영자가 DB에서 바로 읽어도 14:29다.
- S-TZ-3 배포(기존 자료 이전): develop에 새 이미지가 뜬다 → Flyway가 서버가 쓴 일시를 9시간 빼고 이벤트 기간 보정을 되돌린다 → 앱의 기존 기록 시각, 대결 시각, 크루런 일정은 배포 전과 같게 보이고, 이벤트 기간은 11/08 00:00~11/16 23:59:59 그대로 보인다. 코치님 유명인 기록(11, 12)의 등록 시각은 바뀌지 않는다.
- 예외 S-TZ-3a: 새 설정 없이 옛 이미지가 다시 뜬다(되돌림) → 옛 이미지는 다시 9시간 앞선 값을 쓴다. 되돌릴 때는 배포 직전 덤프로 복구한다(설계 05-28 7절).
- 예외 S-TZ-3b: 운영 적용 전(운영 443은 옛 설정)에는 운영 DB에서 서버가 쓴 시각을 읽을 때 9시간을 빼고, SQL로 시각을 넣을 때 9시간을 더한다(infra/README.md 운영 주의).

##### 7.13.27.4 확인 기준

1. 저장 계약 통합 시험과 V48 마이그레이션 통합 시험 합격, backend `./gradlew build` 통과(test/서버시간대-성).
2. develop 배포 뒤 확인 쿼리(설계 05-28 7절) 합격: now()보다 미래인 서버 시각 열 0건, 이벤트 기간 11/08 00:00~11/16 23:59:59, 유명인 기록 11, 12 등록 시각 그대로, 새로 쓴 last_access_at과 now() 차이 1분 안.
3. develop 앱에서 기존 러닝 기록, 대결, 크루런 일정, 알림 시각이 배포 전과 같게 보인다.
4. 운영 적용은 별도 결정(백업, 같은 확인 쿼리). 운영 적용이 끝나야 DF-073을 닫는다.
