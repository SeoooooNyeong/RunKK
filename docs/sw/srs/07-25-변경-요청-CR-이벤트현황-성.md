##### 7.13.30.1 도출 기록 (사실 확인과 되묻기)

| 원문(사용자 결정, 확인 사실) | 되물은 결과 | 반영 |
|------------------------------|-------------|------|
| 관리 웹 대신 기존 Grafana | 무엇이 이미 있는가: 에지 스택에 Grafana 13.2.4가 한 벌 있고 nginx `/grafana/`(443)로만 밖에 보이며 관리자 계정 하나로 로그인한다(익명, 가입 꺼짐). 데이터소스는 Prometheus 하나뿐이고 DB에는 닿지 않는다(postgres는 환경별 프로젝트 망에만 있다) | FR-345, NFR-065 |
| 이벤트별 응모자 수 | 어떤 정의인가: 응모는 저장하지 않고 읽을 때 센다(FR-310, FR-319). 셀럽 승리 이벤트는 기간 안에 지정 셀럽 기록을 한 번 이상 이긴 회원(셀럽마다 첫 판정 시각), 기록 거리 이벤트는 기간 안에 시작한 유효 기록 중 응모기준거리 이상이 있는 회원이다. 기간은 양 끝을 포함하고 탈퇴 회원은 뺀다. 공개 여부와 관계없이 센다(FR-319와 같음) | FR-345 처리 |
| 코치별 대결과 승리 수 | 무엇을 세는가: 코치는 셀럽 승리 이벤트에 지정된 셀럽 기록(베타는 11, 12번)이다. 기간 안에 판정된 끝난 셀럽 대결 수, 그 가운데 회원이 이긴 수, 첫 승리 회원 수(응모 항목 달성 수)를 셀럽마다 센다. 대결과 승리는 같은 회원이 여러 번 해도 모두 센다 | FR-345 출력 |
| 1km 응모자 수 | 베타 이벤트 beta-1km(응모기준거리 1000m)의 응모자 수다. 기준 거리는 이벤트설정에서 읽으므로 다른 거리 이벤트도 같은 패널로 센다 | FR-345 |
| 이벤트 포인트 지급 건수와 합계 | 어디서 읽는가: 포인트 지급 이력(event_point_grant, (회원, 이벤트, 대상)마다 한 번)이다. 지급은 이미 일어난 일이라 탈퇴 회원 몫도 센다 | FR-345 |
| 일별 추이 | 무엇의 일별인가: 새 응모자(그날 처음 조건을 채운 회원), 코치 대결과 회원 승리, 포인트 지급 건수와 합계를 한국 날짜로 나눈다 | FR-345, 시각 주의(아래) |
| 운영 DB 읽기 전용 | 무엇까지 읽는가: 대시보드가 쓰는 표와 열만이다. 회원은 ID, 닉네임, 상태만 읽고 계정 연결 정보(소셜 계정 ID 등), 러닝 경로와 심박은 읽지 않는다. 쓰기는 권한으로 막는다 | NFR-064 |
| 망 노출을 가장 작게 | 어떻게 닿는가: postgres를 호스트 포트로 열지 않는다. Grafana만 각 환경 postgres에 닿고 그 환경의 api, redis, ai에는 닿지 않는다. 두 환경 postgres는 서로 닿지 않는다 | NFR-065 |
| 비밀번호는 사용자가 CI 변수로 넣는다 | 누가 무엇을 하는가: 사용자가 GitLab CI 변수(masked)에 넣는다. 배포가 그 값으로 운영과 develop DB에 계정을 만들거나 비밀번호를 맞추고 Grafana 데이터소스에 넣는다. 저장소, 명령줄, 로그에 값이 남지 않는다. 값이 없으면 데이터소스만 빠지고 배포는 계속된다 | NFR-064 |
| 운영 DB 시각은 아직 +9시간 | 집계가 틀어지지 않는가: 운영은 2차 배포(V48) 전까지 서버가 쓴 시각(대결 판정, 기록 시작, 포인트 지급)과 이벤트 기간(임시 보정)이 모두 9시간 앞서 저장되어 있다(NFR-058, 7.13.27). 저장 값끼리 비교하면 두 상태 모두 맞게 센다. 화면에 보이는 시각과 일별 날짜만 보정이 필요하다 | FR-345 처리 |

##### 7.13.30.3 시나리오

- S-EV-DASH-1 현황 보기(정상): 운영자가 `https://<도메인>/grafana/`에 로그인해 **런크크 › 런크크 이벤트 현황**을 연다 → 위쪽 DB에서 `runkk-db-prod`, 이벤트 전부, 시각 보정 `자동`이 골라져 있다 → 코치 대결 응모자 수, 1km 응모자 수, 포인트 지급 건수와 합계, 이벤트별 표, 코치별 표, 일별 막대, 응모자 닉네임 명단이 보인다. 숫자는 관리 API 응모자 명단(FR-319)의 전체 응모자 수와 같다.
- S-EV-DASH-2 운영 V48 전(시각 +9시간): 운영 DB에 V48이 없다 → 자동 보정이 화면 시각과 일별 날짜에서 9시간을 뺀다 → 이벤트 기간이 11/08 00:00~11/16 23:59:59로 보인다. 개수는 보정과 관계없이 같다. 2차 배포로 V48이 들어가면 자동 보정이 저절로 0시간이 된다.
- S-EV-DASH-3 비밀번호 없음(예외): CI 변수가 비어 있다 → 배포는 성공하고 두 DB 데이터소스가 없다 → 대시보드는 남지만 패널이 데이터소스 없음으로 보인다. 다른 대시보드(API, 서버 호스트)와 장애 알림은 그대로다.
- S-EV-DASH-4 한 환경만 배포(예외): 비밀번호를 넣은 뒤 develop만 배포했다 → develop DB에는 계정이 생기고 운영 DB에는 아직 없다 → `runkk-db-prod` 패널이 인증 오류로 보인다 → 운영 배포 뒤 붙는다.
- S-EV-DASH-5 Grafana 침해(위협): 공격자가 Grafana 관리자 권한이나 컨테이너를 얻는다 → 두 환경 DB를 읽기 전용 계정의 표와 열 범위만큼 읽을 수 있다(쓰기 불가, 닉네임까지). 대응은 비밀번호 교체(CI 변수 변경 뒤 두 환경 배포)와 Grafana 관리자 비밀번호 교체다.

| DFD | 7.9(이벤트 관리)에 운영자의 이벤트현황요청 → 모니터링 화면이 ║D6║ 대결레코드, ║D2║ 러닝기록, ║D1║ 회원레코드(닉네임, 상태), 이벤트, 포인트 지급 이력을 직접 읽는 흐름이 더해진다. 서버(API)를 거치지 않는다. 글자 그림과 자료사전(이벤트현황)은 공용 정리 때 반영한다(병합 대기 파일) |
| ERD | 바뀌지 않는다(표를 더하지 않는다). DB 계정 하나가 생긴다 |
| 비기능 | NFR-025(권한 우회 0건)의 대상에 모니터링 DB 계정이 더해지는 것은 NFR-064가 따로 정한다 |
| 운영(infra) | 에지 스택 grafana에 DB 전용 망 두 개, 환경 스택 postgres에 그 망 하나, 배포 스크립트에 계정 맞추기, CI 변수 하나가 더해진다(설계 05-29) |
| 계획(위험) | 새 위험 후보: Grafana 침해 시 두 환경 DB 일부 읽기 노출(완화: 열 권한, 관리자 하나, 비밀번호 교체 절차). 대시보드 SQL과 서버 판정이 나중에 어긋날 수 있음(완화: 판정 규칙을 바꾸는 CR은 대시보드 SQL도 함께 고친다) |

##### 7.13.30.5 확인 기준

1. 로컬 시험 DB(Flyway 전체 적용, develop 상태와 운영 V48 전 상태 두 벌)에서 대시보드 쿼리를 읽기 전용 계정으로 실행해 기대값(경계값 포함)과 같고, 두 상태의 결과가 같다(설계 05-29 8절).
2. 같은 쿼리를 Grafana 13.2.4에 provisioning한 데이터소스로 실행해(매크로 포함) 같은 결과가 나온다.
3. NFR-064 측정 (1)~(3), NFR-065 compose 설정 확인 합격.
4. develop 배포 뒤 Grafana의 `runkk-db-develop` 연결 확인이 `Database Connection OK`이고, 이벤트별 응모자 수가 관리 API 응모자 명단(FR-319)의 전체 응모자 수와 같다. 운영은 운영 배포 뒤 같은 확인을 한다.
