## 1. 테스트 계획

테스트는 런크크가 요구사항을 충족하는지 확인하려고 **오류를 찾아내는** 활동이다. 오류가 없음을 증명하지 않는다. 좋은 케이스는 아직 드러나지 않은 오류를 찾을 확률이 높은 케이스이므로, 정상 입력보다 무효 동치 클래스·경계 바깥값·동시 요청·연결 끊김을 먼저 고른다.

|-----------|---------|------------------------------------------------------|------------------------|

이번 판의 범위 결정(사용자, 2026-10-21):

- 블랙박스 케이스, 요구사항 추적표, NFR 측정 계획은 **FR·NFR 전체**로 만든다. 미구현 FR도 케이스를 먼저 만들고 `구현` 열에 미구현 단계를 적는다. 구현이 들어오면 그 케이스를 그대로 실행한다
- 화이트박스(기초 경로)는 code-review.md 9절 우선 대상 중 **통합 브랜치에 구현된 함수만** 만든다. 미구현 함수는 각 단위 조각의 "구현 후 작성" 표에 남긴다
- 시험 코드는 만들지 않는다. 문서가 원본이고, 시험 코드는 이 문서에서 파생한다. 이미 있는 시험(서버 91개 파일, 앱·워치 78개 파일, ai 10개 파일)이 같은 것을 검사하면 케이스의 `대응 시험` 열에 적는다
- 이번 판은 계획·케이스만 만들었고 실행하지 않았다. 모든 케이스의 `결과`는 `미실행`이다

### 1.2 수준별 계획 (V-모델 대응)

왼쪽 산출물이 오른쪽 테스트의 기대 결과를 정한다. 케이스의 기대 결과가 왜 그 값인지는 이 표의 기준 문서로 답한다.

```
srs.md 3장 FR  ─────────────────────────  4장 검증 테스트
srs.md 4장 NFR ─────────────────────────  5장 시스템 테스트
    design-oo.md 5장 서브시스템·계층, 2.2 시퀀스, 5.7 계약 ──  3장 통합 테스트
        design-oo.md 6장 클래스, 6.7 알고리즘, 2.4 상태도 ──  2장 단위 테스트
            코드 (통합 브랜치 18442f7) ────────┘
```

### 1.3 통합 전략

혼합 전략을 쓴다. 바닥(도메인·인프라)은 사용 기반으로 다지고, 위(응용·표현)는 스레드 기반으로 시나리오를 돌린다.

- **사용 기반**: 의존하지 않는 클래스부터 한 층씩 올라간다. 서버는 design-oo.md 12.3 의존 행렬 정렬 순서(common → audit → policy → member → notification → running → runimal → battle → reward → avatar → crew → analysis → profile·operator → infra.\* → realtime·batch.\* → web.\*), 앱은 5.1.2 정렬 순서(core.model·wear.contract → domain.\* → api.core → api.\*·data.\* → ui.\* → app), ai는 라우터 → 서비스 → 추상 클라이언트의 역순(클라이언트 가짜부터). 층마다 아래는 실제 구현, 위는 드라이버다. 이유: 서버 도메인 패키지가 12개이고 순환이 없도록 설계되어(design-review.md) 결함 위치를 층으로 좁힐 수 있다
- **스레드 기반**: 시퀀스 다이어그램 하나가 스레드 하나다. design-oo.md 14장의 T-1~T-17을 쓰고, 그 목록에 없는 시퀀스는 스레드를 더해 SQ-01~SQ-17 17개를 모두 덮는다(3.2). 이유: 런크크는 러너·크루장과 주고받는 대화식 시스템이라 사용자 시나리오 단위 결과가 먼저 필요하다
- **스텁**: 1.1 "제외와 대체" 표. 스텁이 돌려주는 값은 각 케이스의 입력 칸에 적는다. 미통합 패키지(B4·B5, 앱 A3b)는 위층 드라이버나 아래층 스텁으로 대신하지 않고, 해당 층·스레드를 "미구현"으로 표시한 채 케이스만 둔다

### 1.4 순서와 진입 조건

단위 → 통합 → 검증 → 시스템 순서로 한다. 순서를 바꾸면 시스템 테스트에서 찾은 결함을 클래스까지 추적하는 비용이 커진다.

| 수준 | 진입 조건 | 시점 (schedule.md) |
|------|-----------|--------------------|
| 단위 | 해당 단계 코드가 통합 브랜치에 병합됨. 코드 리뷰 치명 결함 0 | 구현 단계마다 (B1~B5, A1~A4) |
| 통합 | 단위 합격률 100%. 사용 기반은 아래 층 단위 합격 뒤 한 층씩 | 1단계 통합 테스트 10/26~11/09 |
| 검증 | 통합 치명 결함 0. 대상 FR의 서버·앱이 모두 통합됨 | 2단계 통합 테스트(4.8) |
| 시스템 | 검증 FR 합격 100%. 운영과 같은 서버 구성과 부하 도구 준비 | 동결 후 측정 11/17~11/20 |

실기기 측정(거리 정확도 NFR-007, 배터리 NFR-011, 백그라운드 연속성 NFR-008)은 기능 동결과 무관하게 측정 일정(10/29 배터리 기준 측정 등)이 SRS에 정해져 있어 5장 측정 일정 표를 따른다.
