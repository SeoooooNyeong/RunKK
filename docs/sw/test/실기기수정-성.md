## 1. 테스트 계획

### 1.1 범위와 환경

대상은 크루 얼굴, 기록 시점 모습 저장과 표시, 대결과 크루런 트랙, 보기 선호, 자유런 지도, 매칭 대기 확인, 결과 무대와 기록 카드, 가이드, 크루 초대다. 오류를 찾기 위해 null과 옛 응답, 읽기 실패, 경계, 상태 경쟁, 글자 확대를 함께 본다.

앱은 JUnit 4, Robolectric, Compose UI, kotlinx-coroutines-test, MockWebServer를 쓴다. 서버는 JUnit 5, AssertJ, Mockito와 실제 PostgreSQL 통합 시험을 쓴다. 앱 단위 시험의 Rive는 실제 기기 렌더를 보장하지 않는다. 카카오 지도와 공유 SDK, App Links 검증, 미설치 스토어 이동, 여러 계정의 실시간 러닝은 실기기 범위다. 기존 스냅숏은 시각 참고이며 별도 Roborazzi 대조 명령 통과로 쓰지 않는다.

### 1.3 통합 전략과 순서

사용 기반은 값과 계산 → 저장소와 매퍼 → 서비스와 조정자 → ViewModel → 화면 순서다. 서버 실패 격리는 목만으로 판정하지 않고 PostgreSQL의 실패 뒤 바깥 쓰기를 확인한다. 응용 계층은 3절의 사용자 사건별 스레드로 묶는다.

단위 → 통합 → 검증 → 시스템 순서로 확인한다. 앞 수준의 실행 시험 실패 0을 진입 조건으로 삼는다. 보고된 자동 검증은 통과했으나 미자동화와 실기기 공백이 남아 전체 완료로 판정하지 않는다. MockWebServer는 얼굴 키와 모습이 든 JSON 또는 그 필드가 없는 옛 JSON을 준다. 매칭 대역은 WAITING과 MatchFound를, 초대 대역은 정상, INVALID_CODE, TOO_MANY_ATTEMPTS와 연결 실패를 준다. 기기 확인은 Galaxy S22와 로컬 서버이며 세부 환경은 구현 기록 7절을 인용한다.

## 2. 단위 테스트

### 2.1 화이트박스: `TrackLayout.finishOf`

코드: `android/core/ui/src/main/java/com/a207/runkk/app/core/designsystem/TrackLayout.kt`. 리뷰가 넘긴 남은 18m 경계를 먼저 본다. 제어 흐름은 그림 대신 노드와 간선 목록으로 적는다.

노드는 N1 `remaining <= 0`, N2 `Finish(MY_X)` 반환, N3 `xOf(remaining)` 계산, N4 `x <= 1f`, N5 `Finish(x)` 반환, N6 null 반환, N7 종료다. 간선은 1→2, 1→3, 2→7, 3→4, 4→5, 4→6, 5→7, 6→7이다.

| 계산 | 값 |
|------|----|
| N, E | 7, 8 |
| E − N + 2 | 8 − 7 + 2 = 3 |
| 단순 조건 + 1 | 2 + 1 = 3 |
| 영역 수 | 두 분기 안쪽 2와 바깥 1 = 3 |

| 독립 경로 | 입력 | 대응 |
|-----------|------|------|
| 1→2→7 | 남은 0m, -3m | TC-10433, `TrackLayoutTest::남은 거리 18 m 이내에서 결승선이 보인다` |
| 1→3→4→5→7 | 남은 9m, 18m | 같은 시험 |
| 1→3→4→6→7 | 남은 18.5m, 30m | 같은 TC, `TrackLayoutTest::결승선이 화면 밖이면 그리지 않는다` |

이 함수의 세 경로는 기존 시험에 있다. 루프는 없다. `x`는 N3에서 정의돼 N4와 N5에서 쓰이며 양쪽 분기에 시험이 있다. null은 호출 `of`의 별도 분기이고 같은 TC에 연결한다. 이 결과를 다른 함수의 경로 충족으로 확대하지 않는다.

원인과 효과는 「대결이 RUNNING이고, 상대 위치가 트랙 안이고, 모습이 준비됨 → 달리는 상대와 그림자, 이름표 표시」로 나눈다. 준비 중이면 상대 묶음을 숨기고, 밖이면 칩과 미리 그리기, 실패면 기본 정지 그림이다. 단계와 모습 준비의 개별 시험은 있으나 이 세 조건의 모든 결합을 확인하는 시험은 없다(TC-10435, TC-10436).

오류 예측은 null과 빈 목록(얼굴과 모습), 0과 음수(거리), 잘못된 값(성별과 속도), 중복(초대 열기와 업로드), 상태 경쟁(대기 확인 중 성사), 지연(공유와 다시 보기), 글자 확대를 적용했다. 카카오 중복 탭과 저장된 보기의 늦은 읽기 덮어쓰기는 구현 L-9로 남아 있다.

### 10.2 경로와 입력 분할

`lobbySeatCharacter`는 본인 여부 조건 하나다. 텍스트 CFG의 노드는 진입, 본인 조건, 내 성별 선택, 표시 성별 선택, 반환의 5개다. 간선은 진입→조건, 조건→두 선택 각각, 각 선택→반환으로 5개다. `E−N+2=2`, 조건 1+1=2, 바깥 포함 영역 2로 일치한다. 독립 경로는 본인 참과 거짓 두 개이며 TC-11006의 기존 시험 두 메서드에 대응한다. 다른 우선 함수의 전체 CFG와 경로 전수 대응은 6.1절, 리뷰 28 4절과 같이 미완성이다.

### 11.3 NFR-066 기기 측정 절차

**조정자 측정 예정.** 자동 시험 통과나 셀프런 결과를 20회 측정으로 세지 않는다.

1. Galaxy S22에 측정 대상 local debug 빌드를 설치하고 실제 상대와 랜덤 대결을 시작한다. 빌드 커밋/작업 트리, OS, 화면 주사율, 테마, 망 상태와 상대 계정을 기록한다. 트랙 보기에서 상대 위치와 진행 막대가 모두 보여야 한다.
2. `adb logcat -v monotonic -s RunkkNfr7:D '*:S'`를 저장하고 화면 녹화와 프레임 시각 자료(Perfetto FrameTimeline)를 함께 수집한다. 수신 로그는 `recv ahead=... at=...`, 카드 구성 로그는 `draw ahead=... at=...`다. `at`은 같은 기기의 uptimeMillis다.
3. 서로 구분되는 ahead 값이 도착한 연속 20건을 고른다. 같은 값의 recv 뒤 대응 draw를 순서대로 연결하고 `draw.at-recv.at`을 계산한다. 값이 겹치거나 화면/로그가 누락된 표본은 이유를 기록하고 추가 수집한다. 유리한 20건만 고르지 않는다.
4. `draw`는 SideEffect의 구성 시각이므로 실제 표시 완료와 구별한다. 수신 뒤 상대 위치와 진행 막대가 모두 새 값에 도달한 화면 프레임을 녹화/FrameTimeline과 대조해 표시 지연도 잰다. 두 요소 중 늦은 완료를 표본의 완료 시각으로 쓴다.
5. 표에 표본 번호, ahead, recv, draw, 구성 지연, 화면 완료 시각, 표시 지연, 1초 이내 여부를 남긴다. 20건 중 19건 이상 표시 지연 ≤1000ms면 합격이다. 로그/녹화/trace와 원본 표를 연결하고 DF-096을 재판정한다. 현재 측정값은 없다.
