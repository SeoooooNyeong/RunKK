### 최종 API/메시지 경계와 다른 담당에게 요청

최종 경로/요청/응답/오류와 JSON 표본의 원본은 05-32 5절이다. 이번 pending에서는 해당 계약을 다르게 정의하지 않는다.

- 서버/크루 제공자 이성현: 기존 /ws와 조건부 GET /api/v1/live/poll, POST /live/progress 재사용. 신규 GET lobby, 멱등 PUT ready, POST start/join. COUNTDOWN 최초 후보 고정/취소자 제외/늦은 입장자 join. GET settlement 신설은 **삭제됨(사유: U-34)**. 목록 order/activeOnly, 커밋 뒤 Changed/Departure의 최종 후보 검토.
- 기록/홈/집계 소비자 박재영: 기존 POST /api/v1/runs의 200 recordId/status(STORED 또는 ALREADY_STORED)/valid 재사용. domain.run의 내 recordId별 저장/업로드 상태 포트와 RunStartSpec 개인 시작시각 경계 검토. pending 부재로 성공 추정 금지. 홈은 본인 유효 거리, 레이스는 기존 공개 API의 현재 확정분만 조회. 타인 소유 원본은 이번에 수정하지 않음.
- 앱 소비자: 결과 확인은 내 성공 즉시 복귀, race/ranking 탭 재진입 강제 읽기. 복귀 값은 내 성공 자료만, 참가자 정산 맵 없음. 강조는 각 최신 렌더부터2초, 같은 기록/스냅숏 중복 금지. 신규3초/표식 상태/공유 dirty 없음. 결과 기존 최대60초/종료 후 최대10회 폴링은 유지.
- 시험 담당: 설계8절의 TC11016~11050 중 삭제2개를 제외한33개를 서버/앱으로 나눠 실행. U-33 후보0명/1명과 늦은 join, U-34 타인 진행/오프라인/지연 도착/집계 실패를 포함. 원인 정적 근거를 실행 증거로 확대하지 않음.
- PM: Q1~6은 U-31~36으로 해소. 정책 재질문 없음. CREW_RELEASED 운영 설정은 다음 이슈이며 이번 CR 인수 선행 조건이 아님.

원인 E1~E5는 그대로다: 비동기 내 기록 저장/업로드보다 결과 복귀가 빠를 수 있음, 확인은 기존 back, 레이스 캐시 재사용, 결과 임시 거리와 유효 집계의 차이, AFTER_COMMIT 동기 합산의 실패 흡수 경로. U-34는 모든 집계를 기다려 해결하는 가정을 폐기하고 내 전송 완료와 확정 원본 재조회를 연결한다. 제품 수정/시험/배포/CR 종료는 아직 하지 않았다.
