## 0. 개요

### 0.1 설계 방식

객체지향 분석·설계로 진행한다. 분석은 럼바우 기법(객체 모델 → 동적 모델 → 기능 모델)으로, 설계는 시스템 설계 → 객체 설계 순서로 한다. 표기는 UML이고 다이어그램은 모두 mermaid로 그린다.

| 실행 단위 | 구현 언어·프레임워크 | 근거 | 이 문서에서의 이름 |
|-----------|---------------------|------|-------------------|
| api 서버 | Java 21, Spring Boot 3.x, Spring WebSocket, Spring Data JPA, PostgreSQL, Redis | C-003, C-004, plan.md 7.2 (Spring Boot 전원 보유) | 서버 |
| 스마트폰 앱 | Kotlin, Jetpack Compose, FusedLocationProvider, 포그라운드 서비스, Room | C-001, C-010 | 앱 |
| 워치 앱 | Kotlin, Wear OS, Health Services, Wearable Data Layer | C-002 | 워치 |
| ai 서버 | Python 3.12, FastAPI | C-003, plan.md 3.4 (ai 범위: 아바타 생성·크루 추천·AI 코멘트). 크루 추천은 부록 E E-03 결정 전까지 api 서버의 TagOverlapRecommender가 하고 ai 서버에는 엔드포인트가 없다(v0.8, CR-U40) | ai 서버 |

- 서버 언어는 문서에 "Spring Boot"만 있고 Java·Kotlin이 정해져 있지 않다. 이 설계서는 Java로 가정하고 시그니처를 Java 문법으로 적는다. **(가정, 부록 E E-01)** Kotlin으로 정하면 문법만 바뀌고 클래스·메소드 이름과 관계는 그대로다.
- 기존 클래스·라이브러리 제약: 위치 수집은 1주차 스파이크 코드와 공식 샘플을 공통 기반으로 쓴다(C-010). 지도는 앱에서 Kakao 지도 SDK로 그린다(C-005). 푸시는 FCM(C-008), 크래시 수집은 Crashlytics(C-009)다. 서버 측 AGPL 컴포넌트는 팀 합의 뒤에만 쓴다(C-019). Redis 8.x의 라이선스 합의가 끝나지 않았으므로 Redis를 쓰는 클래스는 모두 인터페이스 뒤에 두고 PostgreSQL 구현을 대안으로 둔다(5.6 D-07).
- 서버 기본 패키지 이름은 `com.a207.runkk`로 둔다 **(제안)**. 앱은 `com.a207.runkk.app`, 워치는 `com.a207.runkk.watch`, ai 서버는 `runkk_ai` 모듈이다.
- 구조 수치 세는 기준(v0.24, 05-18 D-415·D-419): 패키지 화살표는 core.model을 포함해 폰·워치 모두 센다(W30). 자기 모듈 리소스 R(:wear `watch.ui.R`, :data `api.core.R`)만 세지 않는다. 클래스 협력 객체는 생성자로 받는 협력 객체에서 Clock, CoroutineScope, 그 클래스만 여는 플랫폼 저장소 핸들(SharedPreferences·DataStore)을 빼고 세며 상한은 7이다.

### 0.3 이 시스템이 객체지향에 적합한 이유

런크크는 화면 30종 안팎(srs.md 5.1)에서 러너·크루장·운영자가 시스템과 계속 주고받는 **대화식·사용자 중심** 시스템이다. 화면에 보이는 것(러닝 기록, 대결, 크루, 크루런, 아바타, 알림)이 그대로 객체가 되고, 그중 대결·크루런·가입 신청·러닝 기록 전송·Runimal 유형·체형은 **생애주기(상태 변화)** 를 가진다. 같은 메시지에 대상마다 다르게 반응해야 하는 곳(고스트·가상·유명인 상대 기록, 두 소셜 로그인 제공자, AI·규칙 코멘트, Runimal 4축 판정, 공유 방식 3종, 실시간 채널과 폴링 대체)이 많아 다형성이 바로 쓰인다.

배치 처리는 시각에 따라 도는 작업 14종(매일 0시 랭킹·외형·알림 보관 기한(v0.8 D-67), 0시 30분 주간 거리 재합산(v0.10 D-88), 20시 계획 미이행 알림, 1초 간격 매칭·대결 시계·연결 확인, 크루런 시계, 매일 3시 7일 파기·가입 신청 만료·탈퇴 7일 정리·6개월 감사 정리)이 있다. 모두 객체의 상태 전이를 시각 사건으로 일으키는 것이라 구조적 설계(`/sw-design design`)로 따로 나눌 필요가 없다.

### 0.4 문서 구성

1부는 분석(객체·동적·기능 모델과 검증), 2부는 설계(시스템 설계, 객체 설계), 3부는 UML 모음, 4부는 패키지 의존도, 5부는 구현 지침과 테스트 순서다. 부록 A는 추적표, B는 변경 이력, C는 자료사전 전체 대응, D는 클래스 색인, E는 가정과 확인 필요 사항이다.
