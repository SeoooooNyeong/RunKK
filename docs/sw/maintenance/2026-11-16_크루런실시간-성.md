### 3.2 모집 알림, 대기실, 출발의 근거

- 모집 알림 호출은 이미 있다(`CrewPostService.java:106~125`). `NotificationType.java:17`의 CREW_RUN_RECRUIT는 크루 공개 스위치 대상이다. `SettingKey.java:200`의 CREW_RELEASED 기본값은 false이고 `NotificationService.java:73~75,140~154`는 알림함 저장 후 푸시를 생략할 수 있다. **현재 배포 DB 설정값, 수신 설정, 푸시 토큰은 미조회이므로 푸시 누락 원인 확정 불가**다. **삭제됨(사유: U-36): 이번 운영값 점검/켜기/푸시 인수**. 다음 이슈로 넘기며 포그라운드 변경 신호는 별도 구현한다.
- 입장 재호출은 안전한 조회가 아니다. `CrewRunPost.java:261` → `CrewRunParticipation.java:74~75`가 READY를 ENTERING으로 바꾼다. 읽기 전용 GET이 필요하다.
- 기존 depart는 예약 시각에 READY만 runner로 표시한다(`CrewRunPost.java:312~325`). `CrewRunAnnouncer.java:73~82`는 그 runner에게만 보낸다. 중간 참가 등록 연산도 없다.
- 서버 startAt은 예약 시각+3초(`CrewRunPost.java:323`)이고 앱은 다시 +3초한다(`CrewRunCoordinator.kt:175`, DTO 변환 `CrewRunStartJson.kt:35~36`은 단순 시각 파싱). 요청의 3초 조건에 맞춰 **실제 측정 시작 절대시각 하나**로 통일해야 한다(TC-11043). 이번 문서에서 코드를 수정하지 않는다.

이해 소요는 미계측이며 3절은 이번 코드 읽기로 보완했다. 설계 존재: 예, 작성자 불명/퇴사 근거: 없음, 장기간 미수정: 아니오. 외계인 코드로 판정할 근거가 없다. 이전 요청은 2026-11-14 실기기수정의 진행/결과 표시 변경이며, 이번 것은 동기화와 출발 정책 변경이다. 재공학 별도 착수 근거는 부족하다.

## 4. 수정 계획과 간단 견적

문서 작업은 현 브랜치 `impl/S15P31A207-306-realtime`에서만 한다. 기존 pending 파일은 PM이 지정한 이름에 누적한다. 브랜치 변경, 코드 편집, 커밋, push, MR 작업은 하지 않는다.

| 단계 | 예상 공수(인일, 1일 8시간) | 산정 근거 |
|------|--------------------------|-----------|
| 요구와 경계 계약 조정 | 0.5~1 | PM 답변 반영 완료, 남은 러닝 저장/홈 담당 경계 검토 |
| 서버 정책과 읽기/신호 | 2~3 | 고정 후보/출발 직렬화, 중간 참여, 안전한 대기실 읽기, 커밋 뒤 신호. settlement 신설은 삭제됨(사유: U-34) |
| 앱 화면 수명과 결과 복귀 | 2~3 | 세 화면 재조회, 기존 채널 임대, 두 집계 읽기, 강조 |
| 원인 확인, 통합/회귀, 문서 보정 | 1.5~2 | 지연 업로드, 2대 동시 실행, 주 경계, 장애 |
| 합계 | 6~9 | 기존 개략 범위 유지, 확정 견적 아님. U-31~36에 따라 신규 전송/3초 타이머/전체 정산/표식/운영 푸시를 제외하고 내 완료 관찰 포트를 추가해 구현 전 재견적 |

일정/금액 확정 견적이 아니다. 실제 담당 투입과 기한은 미정이다. 재사용은 합성 중심이다: CrewRunMessenger, AfterCommit, CrewTransactions, LiveChannelProvider 임대, UploadScheduler, 기존 목표/집계 API를 활용한다. 한계는 Java/Kotlin에 묶인 구현과 결과 finalDistance를 유효 기록으로 대체할 수 없다는 점이다.
