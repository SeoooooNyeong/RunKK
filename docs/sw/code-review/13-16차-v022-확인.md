### 3. 설계 일치와 구조

- **구조 시험 허용 표.** `ArchitectureTest.kt`는 이번 범위에서 바뀌지 않았다(폰 154, 워치 37, Fan-Out 상한 7). 새 import를 표와 대조했다: `domain.account → domain.run`(ResendRejectedRunsUseCase), `data.watch → domain.run·wear.contract`(WatchLink의 WatchResendRequester·ResendRejectedMessage), `watch.link → domain.run·core.model·wear.contract`(RejectedResendReceiver), `ui.me → domain.account`(SettingsViewModel), `watch.ui → watch.link`(PhoneLeadChange)는 모두 이미 있는 화살표다. `WatchMotion.kt`는 Compose와 안드로이드 플랫폼만 import한다. 설계에 없는 화살표는 없다. 구조 시험을 돌려 154·37이 그대로인지는 이번에 확인하지 않았다.
- **Fan-Out.** `SettingsViewModel` 협력 객체가 6에서 7(`ResendRejectedRunsUseCase` 추가, `ioDispatcher`는 세지 않음)로 상한에 닿았다. 다음 설정 기능은 UseCase를 묶어야 한다. `PhoneMessageService` 3, `RejectedResendReceiver` 2, `ResendRejectedRunsUseCase` 3, `ResetRejectedRunsUseCase` 2다.
- **결합도.** 다시 보내기 경로는 `ui.me` → `ResendRejectedRunsUseCase` → (`ResetRejectedRunsUseCase` → `PendingRunRepository`·`UploadScheduler`) + `WatchResendRequester`(포트) → `WatchLink` → 메시지 → 워치 `PhoneMessageService` → `RejectedResendReceiver` → `ResetRejectedRunsUseCase`로 한 방향이다. 주고받는 값은 건수(Int)와 요청 시각 하나라 자료 결합이다. `WatchLink`가 포트 둘(`WatchGateway`, `WatchResendRequester`)을 구현하는 것은 인터페이스 분리라 결합도를 올리지 않는다.
- **응집도.** `ResendRejectedRunsUseCase`가 기록 전송 일을 하는데 `domain.account`에 있다. KDoc이 밝힌 사유는 `ui.me`가 `domain.run`을 모른다는 허용 표 제약이다. 패키지 응집이 논리적 쪽으로 기우나 클래스 자체는 한 가지 일(거부 기록 다시 보내기)만 해 기능적이다. 결함으로 세지 않고 배치를 설계서가 정하도록 U16-3에 넣었다.

### 4. R12·W40 기록 전송(정합성)

**R12 기록 끝 하나.** `RunSession`이 시작·정지·재개 시각을 밀리초로 자르고(`atMillis`), 종료 때 `max(now, 열린 정지 시작, 마지막 닫힌 정지 끝)` 하나로 열린 정지를 닫고 운동 시간을 계산한다. 보관(epoch 밀리초)과 전송(밀리초 세 자리)에서 값이 바뀌지 않으므로 서버가 다시 만든 `endedAt`과 정지 끝이 1ms 어긋나 400이 나던 원인이 없어진다. 길이 0 정지는 남기지 않는다(서버는 `from < to`). 옛 판이 보관함에 남긴 넘친 기록은 `withPausesInRange`가 전송 직전에 잘라 보낸다. 기록 끝은 그대로 두고 잘린 만큼 운동 시간을 늘린다. 공용 `RunSession`이라 폰도 같이 고쳐진다. 시험 7개(밀리초 아래 시각, 다른 스레드의 늦은 정지, 같은 밀리초 정지·재개, 달리는 중 종료, 1ms 넘친 옛 기록, 자르기 합치기, 고칠 것 없음)가 경계를 덮는다.

**REJECTED 상태 전이.** `NOT_SENT --4xx(AppError.Rejected)--> REJECTED`(사유 코드와 함께, `markState`는 상태·사유 칸만 UPDATE해 전송 중 덧붙은 늦은 심박을 덮지 않는다) `--다시 보내기(resetRejected)--> NOT_SENT --성공 또는 ALREADY_STORED--> 삭제`, `--다시 4xx--> REJECTED`. 네트워크·인증·5xx·408·사유 없는 429는 `Server`라 REJECTED가 되지 않고 재전송된다(ApiErrorMapper). 거부 표시를 남기지 못하면 저장 실패로 돌려 `UploadWorker`가 재전송을 예약한다. `UploadWorker`의 `retryable = outcomes == null || failures.size > rejected.size`도 맞다.

**중복 저장(recordId 멱등).** REJECTED 기록은 서버가 저장하지 않은 기록이다. 되돌려 다시 보낼 때 같은 `recordId`가 이미 있으면 서버가 200 `ALREADY_STORED`를 주고(RunController.upload, D-11) 앱은 보관함에서 지운다. 거듭 누름은 `isResending`과 화면 쪽 가드 둘이 막고, 되돌리기는 `UPDATE … WHERE uploadState = 'REJECTED' AND sentAtMillis IS NULL`이라 두 번 불러도 결과가 같다(멱등). 업로드 작업이 도는 중에 되돌려도 `WorkManagerUploadScheduler.requestUpload`가 `APPEND_OR_REPLACE`로 다음 실행을 이어 붙여 되돌린 기록이 다음 실행에 실린다.

**워치 쪽.** 결함 AN16-1(워치에만 거부 기록이 있으면 요청할 길이 없음)과 AN16-2(워치 미연결이면 요청이 조용히 버려짐). 워치 수신은 바인더 스레드에서 해독만 하고 앱 범위 코루틴에서 되돌린다(`WatchSessionReceiver`와 같은 방식). 해독 실패는 버린다.

### 5. M1 모션·W42·f4dd2a68(Compose)

**잘된 점.**
- 값 읽기 단계: 측정 고리(`EdgeRing(fraction: () -> Float, color: () -> Color)`, `rememberRingFraction`)·등장(`revealLayer`의 `graphicsLayer`)·카운트다운 둘레 원(`drawBehind`)·매칭 숨쉬기(`graphicsLayer { alpha }`)·측정 거리 숫자(`RollingNumber`의 `graphicsLayer`)가 모두 그리기 단계에서 값을 읽는다. 카운트다운은 "다 찼는가"만 `derivedStateOf`로 구성 단계에 올려 차오름 시작과 끝에만 다시 구성하고, 연결 중 점은 점 수가 바뀔 때만 다시 구성한다. 측정 1초 갱신마다 시간·페이스·심박을 움직이지 않는 것도 배터리 쪽으로 맞다.
- 움직임 줄이기: 범위 안의 애니메이션 호출(`AnimatedContent` 4곳, `animate*AsState` 3곳, `Animatable.animateTo` 6곳, `rememberInfiniteTransition` 2곳)이 모두 `LocalMotionStill` 또는 `motionSpec`을 거친다(grep으로 전수 확인). 저전력 표시는 `WatchRoot`가 `isAmbient`로 `LocalMotionStill`을 참으로 만든다. 값이 드물게 바뀌므로 `staticCompositionLocalOf`가 맞다.
- 무한 애니메이션 정리: 매칭 숨쉬기와 연결 중 점은 `rememberInfiniteTransition`이라 화면이 구성에서 빠지면 함께 멈춘다. 움직임 줄이기면 아예 만들지 않는다. 카운트다운 `fill`은 `LaunchedEffect(secondsLeft, isConnecting, still)` 키로 숫자마다 다시 시작하는 유한 애니메이션이다.
- 화면 전환: `screenKey`가 같은 종류 상태를 한 화면으로 보아 값 변화로는 전환하지 않는다. 사라지는 화면은 마지막 값으로 그린다. 전환 220ms 동안 옛 화면이 아래에 남아 누름이 새 화면에 받는 곳이 없으면 옛 화면으로 내려갈 수 있으나, `onPause`·`onResume`·`onResultClosed`·`onEndLongPressed`가 모두 지금 흐름 종류를 먼저 보아 무시하고 종료 길게 누름(1초)은 전환보다 길어 해가 없다. 쓸어 뒤로 가기는 겹치지 않고 바로 바뀐다(시험 있음).

### 7. 단계별 점검 결과

**구조적 프로그래밍.** goto 등가물 없음. `withPausesInRange`는 `for` 하나 안에 `continue` 하나와 `if/else` 하나(중첩 2)다. `verdict`의 `?: return Stop`, `RollingNumber`·`rememberRingFraction`의 `return@LaunchedEffect`는 맨 앞 가드다. 반복문 한가운데 return 없음.
**순환 복잡도·길이.** 10 초과·50줄 초과는 아래 "우선 테스트 대상"에 적었다. 대부분 Composable 안의 `if (isHighlighted) … else …` 식 분기라 실제 경로 수보다 약산 값이 크다. 결함 번호는 주지 않는다(중 기준에 해당하지 않음). `DialPicker`(101줄)·`DistanceRow`(61줄)·`WatchCountdownScreen`(73줄)은 다음 화면 정리 때 숫자·고리·버튼 부품으로 나누기를 권한다.
**객체지향.** 새 클래스는 모두 불변 `data class`(`PhoneLeadChange`, `ResendRejectedMessage`) 또는 협력 객체를 `private val`로 받는 UseCase·수신기다. `RecordBattleMemory`처럼 외부가 필드를 직접 바꾸는 곳 없음. `PendingRunRepository`의 새 기본 구현(`markRejected`, `resetRejected`)은 시험 가짜용이고 Room 구현이 상태 칸만 바꾸도록 덮어쓴다(늦은 심박 보존, 시험 있음).
**코딩 스타일.** 이름이 역할을 드러낸다(`withPausesInRange`, `localLeadSeconds`, `screenFadeMillis`, `isLapWrap`). 피그마 수치는 상수로 모으고 주석에 원본 px과 배율(×0.64)을 적었다. `DissolvingFlow`가 구성 중에 `remember`한 `HashMap`에 마지막 값을 쓰는 것(WatchRoot.kt:96-97)은 구성 단계의 부수 효과지만 같은 값을 다시 쓰는 캐시라 버려진 구성에도 해가 없고 키는 화면 종류 수(약 15)로 한정된다. 지적만 한다.
**글꼴(W37).** Barlow Condensed Bold·ExtraBold 정적 ttf 두 개와 OFL 1.1 사본(`assets/licenses/OFL-BarlowCondensed.txt`)이 함께 들어왔다. 글꼴 가족에 두 굵기만 있어 다른 굵기를 요청하면 가까운 것으로 대체된다(지금 호출은 Bold·ExtraBold뿐).
