### 5. 쟁점 판정

**조건 1. 탈퇴한 초대자의 토큰이 INVITE_NOT_FOUND인 것(r8be c3ad7bf7)은 결함이 아니라 설계서 갱신 요청이다(U9-1).**
- 변경 내용: BattleWithdrawalListener가 탈퇴 때 `cancelOpenOf`(PENDING 취소) 다음에 `eraseOf`를 불러 그 회원이 보낸·참가한 friend_invite 행을 모두 지운다(대결 행은 남는다). 그래서 받는 사람이 탈퇴한 초대자의 링크를 열면 INVITE_CANCELLED가 아니라 INVITE_NOT_FOUND다.
- 설계와의 차이: D-223은 탈퇴 때 "그 회원의 PENDING 초대를 취소한다"만 정한다. 취소 상태 행이 남고 by-token은 INVITE_CANCELLED를 돌려주는 흐름이다. 반면 8차 서버 U8-8이 이미 "탈퇴 때 friend_invite 끝난 행(회원 ID 두 열)의 보관·익명화"를 파기 대상 표에 넣으라고 요청해 두었고, 코드는 그 결정을 "지운다"로 풀었다.
- 결함이 아닌 이유: (1) 회원 ID를 담은 행을 남기지 않는 쪽이 파기 원칙(D-156 계열)에 맞고 U8-8의 미결정을 닫는다. (2) 사용자가 보는 것이 같다. 앱 `joinNotice`는 INVITE_NOT_FOUND·INVITE_EXPIRED·INVITE_CANCELLED를 모두 `battle_join_ended`로 보인다(MatchViewModel.kt:719). 앱이 코드를 가르지 않는다는 점은 직접 읽어 확인했다. (3) 참가가 이미 끝난 대결(ACCEPTED)은 행을 지워도 대결·결과가 그대로다(by-token 호출은 참가 전에만 있다). (4) 시험이 있다(withdrawalErasesNewTables, eraseOf_deletesInvitesOfMember).
- 설계서에 적을 것: D-223에 "탈퇴하면 취소한 뒤 그 회원의 초대 행을 지운다", 05-08 오류표에 "INVITE_NOT_FOUND = 없는 토큰 또는 초대한 사람이 탈퇴한 토큰", INVITE_CANCELLED는 "초대한 사람이 취소한 초대"로 좁힌다. 코드가 기준이다.
- 남는 한계: 탈퇴 정리는 AFTER_COMMIT 수신자라 정리가 실패하면 로그만 남고 보정이 없다. 다른 탈퇴 수신자와 같은 정책이고 BE8-8(보류)과 같은 묶음이다.

**조건 2. BE8-2 필수 변수로 인한 배포 위험은 코드 결함이 아니라 병합·배포 전 조건이다.**
- 사실: compose가 `${FRIEND_INVITE_LINK_BASE:?…}`를 쓰므로 `.env`에 값이 없으면 compose 파일을 읽는 단계에서 실패한다. 배포 잡은 CI File 변수 `INFRA_ENV`(develop·release 8443)와 `INFRA_ENV_PROD`(main 443)를 `infra/.env`로 쓴다(.gitlab-ci.yml 239행). 이 두 변수에 키가 없으면 deploy.sh 133행 `app_compose up -d --no-deps postgres backup`이 실패해 배포가 막힌다. 이 지점은 백업·마이그레이션·컨테이너 교체보다 앞이라 실행 중인 스택은 건드리지 않는다(코드 읽기 기준, 실행은 확인하지 않았다). develop은 병합 즉시 자동 배포이므로 변수 등록 전에 병합하면 develop 배포 잡이 실패한다.
- 판정: 같은 방식인 RUNKK_INTERNAL_TOKEN `:?`와 일관되고 오류 문구가 "set FRIEND_INVITE_LINK_BASE in .env"로 분명해 안전장치가 의도대로 작동한다. 결함이 아니고 병합 전 조건으로 적는다. 등록할 값은 develop·release `https://k15a207.p.ssafy.io:8443/invite/battle`, prod `https://k15a207.p.ssafy.io/invite/battle`(README 10절)이다.
- 남는 결정(앱·서버 U8-4): 8443 링크가 App Links로 열리는지(포트를 구분하지 않는다는 전제), `.dev`·`.local` 패키지와 디버그 키 지문을 운영 도메인 assetlinks.json에 둘지. 코드 결함이 아니라 설계 결정이다.

**조건 3. BE8-1(V29 병합 순서)은 보류가 합리적이다.** 규칙은 implementation.md F-2에 적혀 있다. MR !49를 먼저 병합하면 문제가 없고, 이 MR이 먼저 적용되면 !49가 V29를 들고 들어올 때 Flyway 검증이 실패한다. MR !53 본문이 이 규칙을 적고 있는지는 이 저장소에서 확인하지 못했다.
