### 2. 영역별 점검

**POST /auth/watch-session (FR-240, D-372)**

- 게스트·탈퇴: 게스트는 `anyRequest().authenticated()`로 통과하고(시험 `guest_isIssued` 2곳), 탈퇴 회원은 AuthFilter가 401로 막으며 그 사이 탈퇴한 경우는 `requireActive` → `AuthFailureException` → 401 본문 없음이다(refresh와 같은 처리). `refresh`에서 `requireActive`를 뽑아 낸 리팩터링은 동작이 같다(순서도 requireActive → recordAccess → issue 그대로).
- 폰 토큰 유지: `issueWatchSession`은 `redeemRefreshToken`·`revoke`를 부르지 않고 `issue`만 부른다. 마지막 접속 시각도 기록하지 않아 폰의 갱신 판정에 영향이 없다. 시험 `issuesNewPair_phoneTokensStayValid`가 이를 확인한다.
- 발급 한도: `admitWatchSession`이 접속지 요청 수(1분 30회)와 회원별 한도(1시간 20회, 설정 `runkk.auth.attempts.watch-sessions`·`watch-session-window`)를 센다. 한도는 `tryAcquire`로 확인과 기록을 한 번에 해 동시 요청이 넘지 못한다. 넘으면 `TOO_MANY_ATTEMPTS` → 429이다. 키는 회원 ID 문자열이고 `AttemptLimiter`가 1만 키마다 만료 키를 치운다(메모리 상한). 재시작하면 비워지는 단일 인스턴스 가정은 5.4와 같다. 시험 `watchSessionLimits`가 접속지를 바꿔도 회원 한도가 걸리는 것과 접속지 상한을 함께 본다.
- `admit(http, null)`의 자격 키는 빈 문자열의 해시다. 이 키에 실패를 쌓는 경로는 없다(`failed(attempt)`는 모두 자격이 있는 경로: AuthController 70·100·137·160행, SignUpController 59행). 따라서 다른 경로 때문에 watch-session이 전체 차단되지 않는다.
- 로그: `watch_session_issued memberId={}`만 남기고 토큰·접속지는 남기지 않는다. 한도 초과는 ApiExceptionHandler의 기존 경로(개인정보 없음)다. NFR-050의 "앱 로그에 평문 로그인 정보 0건"을 서버 쪽에서도 지킨다.
- 남는 위험(결함으로 세지 않음): 유출된 접근 토큰(1시간)으로 갱신 토큰(14일)을 시간당 20개까지 만들 수 있다. 갱신 토큰은 jti 단위로만 폐기되므로(`JwtTokenIssuer.revoke`) 폰이 로그아웃해도 워치용 쌍은 서버에서 끊기지 않는다. 한도(20)가 위험을 줄였고(I14-5), 폐기 방식은 D-372가 정한 설계다. 허용 여부를 U12-6으로 설계서에 올린다.

**GET /battles/record-tracks (FR-258~FR-260, D-377)**

- SELF·CELEBRITY만: 컨트롤러가 `@RequestParam BattleType kind`로 받고 서비스 `switch`의 `default`가 `IllegalArgumentException`이다(RANDOM 등은 400). kind 없음도 `MissingServletRequestParameterException` → 400이다. 시험 `badKind_andUnauthorized`, `otherKinds_areRejected`.
- 정렬: `TRACK_ORDER`(거리 → 완주 시간)를 마지막에 한 번 적용한다. 같은 거리·같은 시간이면 순서는 입력 순서(셀럽은 `findAll` 등록 최신순)가 유지되는 안정 정렬이다. 응답의 `finishSeconds`는 초 버림이라 밀리초가 다른 두 기록이 같은 초로 보일 수 있으나 순서는 밀리초 기준이라 계약(finishSeconds 오름차순)과 어긋나지 않는다.
- estimated: `CelebrityRecord.isEstimated()`(구간 기록 없음)를 그대로 싣고, 균등 페이스 표는 `OpponentTrack.uniform`이다. SELF는 false 고정이다. 후보 목록(`celebrityCandidates`)과 같은 필드를 쓴다.
- 읽기 전용: `battleRepository`·`matchQueue`를 호출하지 않고 `@Transactional(readOnly = true)`다. `hasCurve`를 둔 이유(읽기 트랜잭션 안에서 업무 예외를 잡으면 rollback-only)는 합당하다. 규칙 복제 문제는 BE12-5이다.
- 상대 표: SELF는 `selfOpponent`(POST /battles/self와 같은 코드)와 `RunQueryService.curve`, 셀럽은 `CelebrityRecord.track(distance)`를 쓴다. 표가 대결 거리에 닿지 않으면 `arrivalTime`이 비어 건너뛴다(`RecordBattleSpec.of`와 같은 조건, I14-4). 시험 `self_trackMatchesStartSelfBattle`, `celebrity_trackMatchesStartCelebrityBattle`이 시작 응답과 같은지 확인한다.
- 개인정보: 응답에는 SELF의 "MM/dd의 나"와 셀럽의 가린 이름(`anonymousName`)·출처·그림 키뿐이다. 다른 회원의 정보는 없다. 로그는 recordId·거리·사유만 남긴다(BE12-6은 양이 문제).
- 위치 동의를 보지 않는 것은 시작이 아니라 읽기라는 판단(I14-4)이고 후보 목록 API와 같은 수준이다. 설계서 갱신으로 올린다(U12-2).

**startDevice (W23, D-378)**

- V33: `ADD COLUMN start_device VARCHAR(5) NOT NULL DEFAULT 'PHONE'` + `CHECK (start_device IN ('PHONE','WATCH'))`. 상수 기본값이라 PostgreSQL 11 이상에서 행을 다시 쓰지 않는다. 기존 기록은 PHONE이 된다. 엔티티 `length = 5`가 'PHONE'·'WATCH' 5자와 맞는다. CHECK 제약의 잠금은 BE12-2이다.
- 엔티티: `@Column(nullable = false, updatable = false)`, 필드 초기값 PHONE, setter 없음, getter 하나. `RunRecord.receive`에서 `upload.startDevice()`로 한 번만 정한다. 불변이다(`receive_keepsStartDevice`).
- `RunUpload`: canonical 생성자가 null → PHONE으로 바꾼다(옛 앱 호환). 요청 DTO는 `StartDevice` enum으로 받아 모르는 값은 `HttpMessageNotReadableException` → 400이다(`upload_startDevice`). `withPoints` 같은 복사 메소드(168행)도 startDevice를 넘긴다.
- 신고 값이므로 판정·보상에 쓰지 않는다는 I14-23의 선언대로 `judgeValidity` 등 판정 코드에 startDevice 참조가 없다(grep 0).
- 계약 자료: `dto-records.json`에 `BattleDtos.RecordTrackResponse`·`RecordTracksResponse`와 `RunController.RunUploadRequest.startDevice` 한 항목이 더해졌고, `enums/StartDevice.txt`는 PHONE·WATCH이며 `sync_from_server.py`의 `ENUMS['running']`에 `StartDevice`가 들어 있다. 서버 시험 자원(`backend/src/test/resources/contract/app/enums/StartDevice.txt`)은 android 쪽과 diff 0이다. `AppContractSnapshotTest`가 바뀌어 서버 record가 계약 자료와 달라지면 실패한다.

**보안·응답 크기**

- 토큰 남용: 위 한도와 단일 인스턴스 메모리 값. 접속지 요청 상한은 같은 NAT의 폰·워치가 함께 센다(1분 30회라 정상 사용에는 충분).
- 응답 크기: 셀럽 `track`은 1초에 1점이다(`OpponentTrack.uniform`·`wholeSeconds`). 점 하나가 `{"elapsedSeconds":3600,"distanceMeters":21097}` 약 47바이트라 10km 30분은 약 85KB, 하프 1시간은 약 170KB, 풀 2시간은 약 340KB다. 개수 제한이 없고 압축 설정이 없다(BE12-1).

#### 경으로도 올리지 않은 확인 사항

- `selfTracks`가 `StandardDistance`마다 `runQueryService.best`를 불러 최대 5번 읽는다. 후보 목록(`selfCandidates`)도 같은 방식이라 규모가 같다.
- `recordTrack`의 `log.info`가 `static` 메소드 안에서 쓰이는 것은 클래스 로거가 static이라 문제 없다.
- `AuthController.watchSession`이 `admitWatchSession` 뒤에 `try`로 `AuthFailureException`만 잡는다. 필터가 먼저 막으므로 이 분기는 경합 때만 닿는다(BE12-7에서 시험 추가).
- 발급 실패(탈퇴)도 한도 자리를 돌려주지 않는다는 javadoc 선언은 `tryAcquire`가 먼저 자리를 잡는 구조와 일치한다. 탈퇴 회원은 어차피 필터에서 막힌다.
- `RecordTrack` 정의의 생성자가 `Objects.requireNonNull`로 필수 값을 검사해 생성 직후 유효하다. record 컴포넌트가 9개지만 값 객체라 매개변수 기준에 넣지 않았다(응답 DTO도 같다).
- `RunUploadRequest`의 `startDevice` 검증은 enum 변환에 맡긴다. 대소문자(`watch`)는 400이고 계약은 대문자 상수만 허용하므로 일치한다.

### 4. 구조적 프로그래밍

goto 등가물(다중 레벨 break 남용, 예외를 흐름 제어로 씀) 없음. `recordTracks`의 `switch default → IllegalArgumentException`은 입력 거부이고 흐름 제어가 아니다. 반복문 한가운데 return 없음(`selfTracks`의 `for` 안은 `ifPresent` 한 문장). 중첩 깊이 3 초과 새 함수 없음(`selfTracks` 최대 2). 가드 절만 쓴다(`selfTrack`, `recordTrack`, `selfTracks`의 `bests.isEmpty()`).

### 5. 객체지향 구현

- 캡슐화: 새 public 가변 필드 없음. `RunRecord.startDevice`는 private, `updatable = false`, getter 하나. `RecordTrack`은 record(불변). `AuthAttemptGuard.Limits`는 `final` 필드와 패키지 전용 접근자다.
- 전역 상태: `watchSessions`는 `AuthAttemptGuard` 인스턴스 안에 갇힌 메모리 값이고 `AttemptLimiter`가 동기화한다. 공통 결합 없음.
- 절차적 스타일: 새 static 메소드는 `recordTrack`(BE12-3의 매개변수 문제뿐)과 `RecordTracksResponse.of`·`RecordTrackResponse.of` 정적 팩터리뿐이다. 데이터와 처리가 분리된 새 클래스 없음.
- 다형성: `switch (kind)` 두 갈래(SELF·CELEBRITY)는 두 가지만이고 값이 달라(경로 만들기 방식) 오버라이딩 대상으로 보지 않았다. `OpponentRecord` 인터페이스로 이미 한 경로를 쓴다.
- 상속: 새 상속 없음.
