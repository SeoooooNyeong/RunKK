### 4. W48 셈·홈 띠·R81 문자열 경로

**경계와 셈.** `needsReminder`(RoomPendingRunRepository.kt:146)는 `countNotIn("REJECTED") > 20 || (oldest != null && oldest < now − 7일)`이다. 20건째는 거짓, 21건째부터 참이고, 가장 오래된 저장 시각이 정확히 7일 전이면 `<`가 거짓이라 W48 "20건째와 7일 정각은 아님"과 맞다. REJECTED는 COUNT와 MIN 모두에서 빠진다. 보낸 머리 정보(`sentAtMillis` 있음)도 둘 다 뺀다. 전체 행을 읽던 `dao.pending()` 대신 COUNT·MIN 두 쿼리라 경로·심박 칸을 풀지 않는다. 시험(실제 Room)이 19·20·21건, 6일 23시간·7일 정각·7일+1ms·7일 1시간, 거부 3건 + 미전송 18건, 8일 된 기록이 거부뿐일 때와 되돌린 뒤를 모두 단언한다.

**홈 띠 다시 세기.** `HomeViewModel`은 `init`에서 `pendingRuns.observePending()`을 구독해 보관함이 바뀔 때마다, `refresh()` 맨 앞에서 홈이 다시 보일 때(`LifecycleResumeEffect` → `onResumed` → `refresh`)마다 `clock.instant()`로 `needsReminder`를 부른다. 결과가 거짓이면 `isResendReminderVisible = false`라 조건이 풀리면(전송 성공으로 행이 지워지거나 거부로 바뀜) 띠가 내려간다. 보관함을 읽지 못하면 띠를 보이지 않는다. 띠는 `Top`(HomeScreen.kt:258)에 있고 대시보드 오류 표시(`RunkkErrorState`)는 `Room` 안이라 오프라인으로 대시보드를 못 읽어도 띠는 보인다. 홈이 계속 떠 있는 동안 7일 경계를 넘으면 다음 재표시까지 늦게 뜨는데, W49가 정한 "보관함 변화와 재표시"의 범위 안이라 결함으로 세지 않는다. 구독 대상이 전체 목록인 점은 AN17-1이다.

**R81 SENDING 삭제의 안전성.** 칼럼은 문자열이고 읽는 길은 `PendingRunEntity.toDomain`의 `uploadStateOf`(PendingRunMapper.kt:66, 146) 하나다. `UploadState.valueOf`는 저장소에서 사라졌다(grep 0건). 모르는 문자열(옛 SENDING 등)은 NOT_SENT가 되어 다음 업로드에 실리고, 성공하면 지워지며 4xx면 `markState`가 REJECTED로 다시 쓴다. SQL 쪽도 같은 규칙이다: 거부 건수는 `= 'REJECTED'`만, 재전송 안내는 `!= 'REJECTED'`로 모르는 문자열을 미전송으로 센다, 되돌리기는 `WHERE uploadState = 'REJECTED'`라 모르는 문자열을 건드리지 않는다. 다른 곳에 UploadState를 직렬화하는 경로(계약·DataStore)는 없다. 시험 `R81 모르는 전송 상태 문자열(옛 SENDING)은 미전송으로 읽는다`가 DAO로 "SENDING"을 써 넣고 NOT_SENT를 단언한다.

### 5. 시험 품질

WR16-1 시험은 실제 방송·리스너를 거친다.
- 약한 점(결함 아님): `HomeViewModelTest`의 W48 시험 다섯은 `needsReminder` 결과를 가짜가 정해 "언제 다시 세는가"만 본다. 셈 자체는 Room 시험이 맡아 두 반쪽이 나뉘어 있다. 도메인 `FakePendingRunRepository.needsReminder`는 7일 조건 없이 건수만 본다(쓰는 시험이 건수만 본다). `WatchScreenshotTest` 새 둘은 기준 이미지 비교만 한다.

### 7. 단계별 점검 결과

**구조적 프로그래밍.** goto 등가물 없음. `Top`의 `return`과 `RejectedResendReceiver.onRequest`의 해독 실패 `return`·`if (!isNew) return`은 맨 앞 가드다. `PhoneMessageService.onDataEvents`의 `return@forEach`는 람다 안 가드다.
**순환 복잡도·길이.** 이번 범위의 새·바뀐 본 코드 함수는 모두 약산 10 이하, 50줄 이하다(`rememberMotionReduced` 약 4·30줄, `needsReminder` 3, `onDataEvents` 4). 우선 테스트 대상에 새로 더할 함수는 없다. 16차 표는 그대로 유효하다.
**객체지향.** 새 클래스 `RejectedCountReporter`는 협력 객체를 `private val`로 받고 시작 여부를 `lock` 안에서만 바꾼다. `WatchLink.watchRejected`는 `MutableStateFlow.update`로 원자적으로 바꾼다. `RejectedCountMessage`는 불변 `data class`다. `WatchResendRequester`는 연산 둘의 포트로 커졌으나 둘 다 "워치 거부 기록"이라 응집이 유지된다(설계 검증 24장 허용).
**코딩 스타일.** 이름이 역할을 드러낸다(`isForwardedItem`, `isConsumedItem`, `countNotIn`, `oldestSavedAtNotIn`, `uploadStateOf`). `RejectedCountReporter`의 `.distinctUntilChanged()`는 Room 구현이 이미 같은 일을 해 겹치지만 포트 기본 구현에도 붙어 있어 해가 없다. 지적하지 않는다.
