- 크루런 종료 두 경우: `shouldClose`가 진행 참가자 전원 `hasEnded()` 또는 `now ≥ departedAt + 거리 × km당 분`. 시간 초과 마감은 `close(now, lastProgress)`가 끝내지 않은 사람만 마지막 중계 값으로 마감하고 이미 끝낸 사람의 값은 덮지 않는다(`end`가 처음만 true). 목표 거리 자동 종료 코드는 앱·서버 모두 지워졌다(CrewRunCoordinatorTest "크루런 거리에 닿아도 측정을 끝내지 않고").
- 일시정지·재개: 정지 경과와 진행값 경과가 같은 초 단위(앱 `elapsed.seconds`, 실시간 `elapsedSeconds`)라 같은 초의 늦은 진행값이 재개로 잘못 읽히지 않는다. 정지 보고가 재시도로 늦게 도착해도 다음 진행값(경과 증가)이 바로 재개로 되돌린다. 정지 중 참가자는 `detectTimeouts`가 CHECKING으로 바꾸지 않는다. 끝낸 사람의 늦은 진행값은 무시한다.
- 크루런 동시성: 세션 변경은 줄무늬 잠금 64개 안에서 load → 변경 → save → 중계. 끝내기는 모집글 행 잠금(`findCrewRunByIdForUpdate`) + 낙관적 잠금 재시도 안에서 `end` 뒤 커밋 후 `markEnded`. 1초 시계 `step`은 행 잠금 → `lastProgress`(줄무늬 잠금)이고 줄무늬 잠금 안에서는 DB 잠금을 잡지 않아 잠금 순서 역전이 없다.
- V39·V40: 크루 탭이 1차 배포에서 잠겨 운영 자료 손실이 없다는 전제(mr-body 마이그레이션 표)와 맞다. V40 뒤 `ended` NOT NULL 유지, 엔티티와 열 대응 일치. Redis 세션 형식 변경도 진행 중 크루런이 없어 영향 없다.
- 런바디 작업 상태 전이: PENDING → (submitted) ANALYZING → DONE/FAILED, 실패는 30초 뒤 재제출, 3회째 FAILED, 연결 실패는 세지 않고 하루 뒤 FAILED, 409·413·422는 바로 FAILED. 상태 위반 전이는 `requireStatus`의 IllegalStateException을 `update`가 잡아 다음 pollDue에 맡긴다. ai `claim`은 같은 회원·같은 세션이면 기존 기록을 돌려주고 실패 기록만 바꿔 계산하므로 재제출이 중복 계산을 만들지 않는다(ai repository.py:66-72).
- 런바디 폴링 중복: 커밋 뒤 비동기 제출과 pollDue는 PENDING 작업의 `nextPollAt = createdAt + 1분`(SUBMIT_GRACE)으로 갈라진다. 제출 읽기 10초 + 연결 시간 초과보다 길어 둘이 같은 작업을 동시에 내지 않는다. 겹쳐도 ai가 같은 회원 재제출을 202로 받고 `@Version`이 두 번째 갱신을 막는다. pollDue는 fixedDelay라 자기끼리 겹치지 않는다. 앱 폴링은 `sessionJob?.cancel()` 뒤 새로 시작해 한 기록에 하나다.
- 런바디 결과 회원 확인: `sessionOf`는 작업 주인(404 RUNBODY_NOT_FOUND로 존재도 숨김)과 ai 결과 userId를 둘 다 보고, 점수 저장도 userId가 같을 때만 한다. 월간은 경로가 본인 회원 ID이고 userId가 다르면 503. 목록 커서도 본인 작업만 받는다.
- 점수·커서: 0.5 올림 공식, 커서 `(created_at, record_id)` 내림차순 비교와 V42 색인 순서가 같다. 쪽 경계의 변화량은 `previousScore(쪽 마지막)`에서 시작해 위로 올라가며 이어진다.
