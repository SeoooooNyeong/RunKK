### 6. 응모자 명단 관리 API (2026-11-08 사용자 결정, [임시:FR-성-14], [임시:D-성-18])

사용자 결정: (1) 추첨 명단은 관리 API로 제공한다. (2) 당첨자 연락은 앱 알림과 구글 폼(앱 변경 없음). 결정 (1)로 설계 R6, srs 메모 E1의 「명단 뽑는 기능 없음」을 해소했다.

- `GET /api/v1/admin/events/{id}/entrants?celebrityId=&cursor=&size=`(운영자 전용, OperatorCheckInterceptor). size 기본 30, 1~100 밖이면 400. 없는 이벤트 404 EVENT_NOT_FOUND, COACH_CELEB이 아니거나 이벤트 셀럽이 아닌 celebrityId는 400.
- 응답 `{eventId, slug, kind, celebrityId, total, entrants:[{memberId, nickname, entryCount, items:[{key, label, done, doneAt, distanceMeters}]}], nextCursor}`. 회원 ID 내림차순 커서 쪽(PageCursor, 신고 관리와 같은 방식). COACH_CELEB은 코치마다 첫 승리 판정 시각, `celebrityId`로 코치별 추첨 대상만 거른다. RUN_DISTANCE는 기준 거리 이상 첫 유효 기록의 시작 시각과 거리.
- 탈퇴 회원 제외(ACTIVE 닉네임만), 개인정보는 회원 ID와 닉네임만. 조회는 감사하지 않는다(다른 관리 조회와 같다. 명단을 내려받아 보관하는 운영 절차는 srs E1에 남김).
- 질의: 이벤트 1, 승리 집계 1((회원, 기록)별 min) 또는 기록 1, 셀럽 이름 셀럽 수만큼, 닉네임 1. 회원 수만큼 늘지 않는다.
- 새 경계 계약: battle `BattleHistoryService.celebrityWinners`, `celebrityNames`, `BattleRepository.findCelebrityWinners`, 새 값 `CelebrityWin`, running `RunQueryService.earliestValidRunsAtLeast`, `RunRecordRepository.validSummariesAtLeast`(박재영 승인 대기), member `MemberQueryService.activeNicknames`, `MemberRepository.activeNicknames`. 허용 쌍 event → member 추가.
