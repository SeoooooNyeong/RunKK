인터페이스는 기존 응답에 nullable 필드를 추가하는 형태다. `AvatarLookSource.currentLookOf(long): Optional<AvatarLook>`, `RunQueryService.lookOf(String): Optional<AvatarLook>`, `AvatarQuery.looksOf(Collection<Long>)`에서 서비스, DTO, 앱 슬롯까지 값을 대조했다. 서버와 앱 `dto-records.json`은 들여쓰기와 줄 수가 다르지만 JSON을 파싱해 객체 키 순서를 정규화하면 의미상 동일하다. 바이트 해시 차이는 결함으로 세지 않았다.

의존 방향은 `avatar → running.AvatarLookSource` 구현, `battle → running` 포트 사용, `crew.chat → avatar.AvatarQuery`, `web.crew → avatar` 조합이다. 새 `crew.chat → avatar`는 설계 허용표에 들어 있고 역방향은 발견하지 못했다. 자료 값/스탬프 결합이며 다른 모듈 엔티티의 내부 필드를 조작하지 않는다. 앱의 `core.navigation`은 원시 슬롯 값만 받고 `core.designsystem`이 렌더러 모듈을 import하지 않는다. 가이드 싱글턴 공유는 없고 경로 값으로 전달한다. 기존 얼굴 캐시는 저장소 인터페이스를 통해 읽는다.

응집도는 기록의 저장/조회, 상대 모습 선택, 채팅 작성자 정보 조합, 배치 계산, 공유 전송으로 나뉘어 기존 설계 책임을 유지한다. `AvatarLook`의 방어적 맵 복사와 `RunRecord`의 private 열, 엔티티 동작 메서드 사용을 확인했다. 새 일반 가변 public 필드, 설계에 없는 양방향 패키지 의존, 정상 분기용 throw/goto 등가 흐름은 발견하지 못했다. 오류를 잡고 기본값을 주는 I-4는 합의된 예외 처리이며 구조 결함으로 다시 세지 않았다. 새 보조 함수의 매개변수 위반은 AR-99로 따로 적는다.

V66은 기존 행을 채우지 않고 일곱 nullable 열을 추가한다. 성별, 체형, 러닝량의 동시 존재와 모습 없는 행의 의상/얼굴 null을 CHECK로 묶고, JPA SMALLINT 매핑과 맞는다. 얼굴 키 255자와 평면 저장은 I-2다. 업로드 전에 모습을 읽고 기존 저장 트랜잭션으로 기록을 저장하며, 탈퇴 때 기록 행 삭제를 통해 같이 삭제된다. 이 범위에서 별도 마이그레이션 결함은 발견하지 못했다.

### 3. 새 결함

모든 항목은 **미해소**다. 다음 재현은 소스와 상태 전이를 따라 확인한 조건이며, 새 회귀 시험이나 실기기 재현을 실행한 것으로 읽으면 안 된다. 각 항목에 제안 시험을 붙였다.

#### 3.1 코드 결함

##### AR-93 높음, 실제 성별 조회가 업무 트랜잭션을 다시 오염시킴

- 위치: `backend/src/main/java/com/a207/runkk/battle/OpponentLooks.java:122`, 연결 `:65`, `:115`; `backend/src/main/java/com/a207/runkk/member/MemberQueryService.java:85`(클래스의 `:21` REQUIRED 트랜잭션).
- 재현 조건: 저장된 모습이 있는 본인 최고 기록으로 `selfCandidates` 또는 SELF `active`를 조회한다. 모습/기록 조회는 성공시키고, 마지막 `ownGenderOf`의 회원 조회만 SQL 오류나 statement timeout으로 실패시킨다. `AvatarLookFailureIntegrationTest`의 `select 1/0` 주입 위치를 이 추가 조회로 옮기면 격리를 확인할 수 있다.
- 현재 코드: `return ownGender.apply(memberId);`를 바깥 try/catch로만 감싼다. 이 함수는 `MemberQueryService` 프록시의 기본 REQUIRED 트랜잭션에 들어가므로 호출자의 읽기/쓰기 트랜잭션에 참여한다. 예외가 프록시를 빠져나올 때 rollback-only가 되고, PostgreSQL SQL 오류면 연결의 트랜잭션도 실패 상태다. catch 뒤 Optional.empty를 반환해도 원래 응답이 커밋 단계나 다음 SQL에서 실패한다. 기존 모습 읽기 두 경로의 REQUIRES_NEW 격리가 이 조회에는 없다.
- 영향: 없어도 되는 성별 보정 실패로 후보/진행 대결 응답이 5xx가 될 수 있다. I-15의 실제 성별 선택 자체를 반대하는 지적이 아니라, I-4의 실패 격리를 새 조회에도 적용하지 않은 결함이다.
- 교정: 이 보정도 별도 읽기 트랜잭션 안에서 실행하고 그 트랜잭션 바깥에서 예외를 잡는다. 추가 연결에 대한 기존 읽기 상한도 함께 적용한다. 예시: `isolatedRead("own_gender", memberId, () -> memberQuery.ownGenderOf(memberId))`. 단순히 같은 클래스 private 메서드에 `@Transactional`을 붙이는 방식은 프록시를 거치지 않아 해결되지 않는다.
- 확인 시험: 실제 PostgreSQL에서 이 조회만 실패시켜 후보/active 응답이 정상이고 저장된 모습의 성별로 대체되는지, 바깥 트랜잭션에서 뒤이은 쓰기가 성공하는지 확인한다. 기존 실패 통합 시험은 `RunnerService.runner`와 `RunQueryService.lookOf`만 주입해 이 경로를 덮지 않는다.

- 확인 시험: 시간 초과 대체 그림 → 늦은 Ready → 정지 비트맵 준비의 세 시점을 분리하고, 각 시점의 캡처에 그림이 있거나 공유가 잠기는지 확인한다.

##### AR-97 중간, 고정 60% 그림 칸이 글자 확대 때 지표 줄을 밀어냄

- 위치: `android/feature/record/src/main/java/com/a207/runkk/app/ui/record/RecordCardFront.kt:70`, `:95`, `:118`.

##### AR-98 중간, 채팅 얼굴의 묶음 API가 실제로는 회원별 조회임

- 확인 시험: 작성자 1명과 정원만큼의 서로 다른 작성자에서 얼굴 조회 SQL이 동일한 1회인지 JPA 통계/쿼리 수로 검증한다. 준비를 위한 쿼리와 검증 쿼리는 카운트에서 분리한다.
