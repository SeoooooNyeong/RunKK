## 2. 원인 (메커니즘과 증거)

옛 설정: JVM 기본 시간대 UTC(컨테이너 TZ 없음), Clock Asia/Seoul, `hibernate.jdbc.time_zone: Asia/Seoul`, postgres 컨테이너 TZ와 PGTZ Asia/Seoul(서버 기본 timezone도 Asia/Seoul).

| 경로 | 저장 | 서버가 읽을 때 | 결과 |
|------|------|----------------|------|
| 서버 JPA 쓰기(엔티티, JPQL과 네이티브 쿼리 매개변수) | 한국 시각 14:29 → UTC 시점 14:29Z로 해석 → Asia/Seoul로 바꿔 23:29 저장 | 23:29 → Asia/Seoul로 해석 → UTC 14:29 | 앱은 맞고 DB 값은 9시간 앞섬 |
| psql로 넣은 값(운영자 SQL, dev-seed, now()) | 한국 시각 그대로(세션 Asia/Seoul) | 9시간 빠짐 | 앱에 9시간 이르게 보임(공지 「어제」) |
| Flyway 시드 리터럴(V32 유명인, V35_2 이벤트 기간) | 리터럴 그대로(의도는 한국 시각) | 9시간 빠짐 | 이벤트가 11/07 15:00~11/16 14:59:59로 동작 |
| Flyway 시드 now()(V35_2 created_at), flyway_schema_history | 서버 연결(세션 UTC)의 UTC 벽시계 값 | 9시간 빠짐 | 한국 시각보다 18시간 이르게 보임(표시에 쓰지 않음) |
| JdbcTemplate `Timestamp.valueOf`(match_ticket.waiting_since)와 SQL LOCALTIMESTAMP(assigned_at) | 각각 한국 시각 그대로, UTC 벽시계 | JdbcTemplate는 그대로 읽음 | 대기열 안에서만 쓰고 몇 분 뒤 지운다 |

증거(2026-11-09 14:58 KST, BEGIN READ ONLY): DB now()보다 미래인 서버 시각 행이 develop member.last_access_at 2건, run_record 4건, 운영 member.last_access_at 12건(최대 23:26), member_consent 18건 등이다. 운영 event.created_at(2026-11-08 16:35:55)과 flyway V35_2 installed_on(16:35:54)이 같은 UTC 값이고, develop V47 installed_on 04:54(UTC)는 api 컨테이너 기동 13:54 KST와 맞는다.

새 설정: JVM Asia/Seoul, jdbc.time_zone 없음. 모든 경로가 한국 시각 벽시계 값을 그대로 저장하고 읽는다.

## 3. 클래스와 설정 명세

##### ServerZone (common, 고침)
`useAsJvmDefault()`를 더한다. `TimeZone.setDefault(TimeZone.getTimeZone(ID))`. 서버 시간대의 단일 출처라는 기존 책임 안이다.

##### RunkkApplication (bootstrap, 고침)
`main`이 `SpringApplication.run` 전에 `ServerZone.useAsJvmDefault()`를 부른다. 연결 풀과 Flyway가 세션 시간대를 정하기 전이어야 한다. Clock 빈은 그대로 `Clock.system(ServerZone.ID)`다.

##### application.yml (고침)
`spring.jpa.properties.hibernate.jdbc.time_zone` 삭제. 이유는 주석으로 남긴다.

##### backend/Dockerfile, infra/docker-compose.yml (고침)
`ENV TZ=Asia/Seoul`, `ENTRYPOINT ["java", "-Duser.timezone=Asia/Seoul", "-jar", "/app/app.jar"]`. compose api 서비스 environment에 `TZ: Asia/Seoul`. JAVA_TOOL_OPTIONS(API_JAVA_OPTS)는 건드리지 않는다.

##### 시험 환경
build.gradle.kts의 시험 작업은 이미 `systemProperty("user.timezone", "Asia/Seoul")`다(크루런 예약 시험 때문에 넣은 것). 그래서 시험은 처음부터 새 설정과 같은 조건이었고, 운영 컨테이너만 달랐다. H2 시험 문맥과 Testcontainers 시험은 바뀌는 것이 없다. CI(GitLab 러너 컨테이너, UTC)도 같은 시스템 속성으로 Asia/Seoul이다.

### 4.4 알고 받아들이는 것

- develop의 dev-seed 더미 자료(더미러너 01~18, 더미 크루, 대상 계정의 시드 러닝과 런바디 작업)는 psql로 한국 시각을 넣었으므로 V48 뒤 9시간 이르게 된다. 더미라 받아들인다(필요하면 dev:seed를 다시 돌리지 않고 그대로 쓴다. 다시 돌려도 이미 있는 회원과 크루는 만들지 않는다).
- V17이 develop 대결 closed_at을 LOCALTIMESTAMP(당시 UTC)로 채운 행은 지금 두 환경에 없다(closed_at develop 0행).
- 운영 적용 전에 운영자가 SQL로 「9시간 더해」 넣은 값은 V48이 다루는 표(공지 등)면 같이 되돌아가고, 다루지 않는 표(유명인 기록)면 9시간 앞선 채 남는다. 운영 적용 전에 7절의 확인 쿼리로 찾는다.

|-----------|-----------|------|
| ai 서버(FastAPI) | `datetime.now(UTC)`, 한국 날짜는 고정 +09:00으로 계산(coach, runbody, comment). analytics 열은 timestamp with time zone. public 표는 읽기만 하고 서버가 런바디 요청에 `startedAt.atZone(Asia/Seoul)` 오프셋을 붙여 보낸다 | 없음. 컨테이너 TZ는 그대로(로그만 UTC) |
| avatar(Node), writer(llama.cpp) | DB를 쓰지 않는다 | 없음 |
| nginx | 접근 로그 시각만(컨테이너 UTC) | 없음 |
| backup(pg-backup.sh), restore-check, offsite | 컨테이너 TZ Asia/Seoul, 덤프 파일 이름과 BACKUP_TIME이 한국 시각. pg_dump는 저장 값을 그대로 옮긴다 | 없음 |
| Grafana, Prometheus | Prometheus 지표는 시점(epoch), 대시보드는 브라우저 시간대 | 없음 |
| 스케줄 작업 | CronTrigger와 `@Scheduled(zone = "Asia/Seoul")`이 시간대를 명시한다 | 없음 |
| API 응답, 실시간 메시지 | LocalDateTime 값 또는 ServerZone 오프셋(+09:00)을 붙인 값 | 서버가 읽는 값이 배포 전과 같으므로 앱 표시는 그대로 |
| Redis(대결 세션, 대기열) | 서버 시계 값 문자열 | 없음 |
| 앱, 워치 | 서버 응답을 기기 시간대로 보인다 | 없음 |
| 운영 문서(infra/README.md 운영 주의) | 지금은 「9시간 더하고 빼라」 | 운영까지 적용한 뒤 「한국 시각 그대로」로 바꾼다(병합 대기 파일) |

## 6. 마이그레이션 번호와 운영 적용 경로

- 번호: develop 최신 V47 다음 V48. develop 프로필은 out-of-order가 켜져 있지만 V48은 가장 높은 번호라 차례대로 적용된다.
- 운영(main, V35_3까지 적용)의 기본 경로: 2차 배포(release → main)에 V36~V48이 함께 들어가 차례대로 적용된다. 이 이미지는 새 시간대 설정을 갖고 있으므로 자료 이전과 설정 변경이 한 배포에서 함께 일어난다. 이벤트 기간 임시 보정도 이때 되돌아간다.
- 운영에 2차 배포보다 먼저 넣어야 하는 경우: V48 파일을 main에 그대로 넣을 수 없다(V36~V47이 만드는 표를 고친다). 운영 전용 이전 파일(예: V35_4)을 만들면, 역병합 뒤 develop이 그것을 순서 밖으로 적용해 두 번 뺀다. 이 경로를 고르면 (1) 운영 전용 파일과 V48이 함께 쓰는 표시(예: operation_setting의 키나 별도 한 줄 표)를 두고 이미 적용된 쪽을 건너뛰게 고치거나, (2) 역병합 전에 develop flyway_schema_history에 그 버전을 수동 기록하는 절차를 정한다. 어느 쪽이든 따로 설계 검토를 받는다.
- 옛 설정의 api가 V48 뒤에 다시 뜨면 안 된다. V48과 시간대 설정은 같은 이미지에만 있으므로 이 브랜치를 쪼개 병합하지 않는다.

## 7. 배포 순서와 확인 (develop 8443)

1. 백업: 병합 직전에 develop 수동 덤프를 하나 뜬다. `docker exec runkk-develop-backup-1 sh /opt/runkk-backup/pg-backup.sh now before-tz`. 배포 잡의 deploy.sh도 배포 직전 덤프(`-predeploy-`)를 뜬다.
2. 배포: MR을 develop에 병합하면 CI가 develop을 배포한다. api가 뜰 때 Flyway가 V48을 적용한다(한 트랜잭션).
3. 확인 쿼리(psql, `BEGIN READ ONLY`):
   - `SELECT version, success FROM flyway_schema_history WHERE version = '48';` → 1행, true
   - `SELECT id, slug, starts_at, ends_at FROM event ORDER BY id;` → 2026-11-08 00:00:00 ~ 2026-11-16 23:59:59
   - `SELECT id, registered_at, real_name_consented_at FROM celebrity_record WHERE id IN (11, 12);` → 배포 전 값 그대로(develop 2026-11-08 21:59:16.549619 등)
   - 미래 행 0건: `SELECT 'member', count(*) FROM member WHERE last_access_at > now() UNION ALL SELECT 'run_record', count(*) FROM run_record WHERE ended_at > now() UNION ALL SELECT 'audit', count(*) FROM audit_record WHERE recorded_at > now();` → 모두 0
   - 앱으로 develop에 한 번 들어간 뒤 `SELECT max(last_access_at), now()::timestamp(0) FROM member;` → 차이 1분 안
   - `docker exec runkk-develop-api-1 date` → KST, `SELECT pg_trigger.tgenabled FROM pg_trigger WHERE tgname = 'trg_audit_record_reject_update';` → O
4. 앱 확인: develop 앱에서 기록 목록, 대결 결과, 크루런 일정, 알림함 시각, 이벤트 목록 기간 표시가 배포 전과 같다.
5. 되돌림: 확인이 틀리면 develop을 이전 이미지로 돌리기 전에 1의 덤프로 DB를 복구한다(infra/README.md 7절 「실제 복구」). V48만 되돌리는 역 SQL(같은 열에 9시간 더함, 4.2절 조건 반대, flyway_schema_history V48 행 삭제)은 쓰지 않는 것을 기본으로 한다.

시험 리허설(2026-11-09): develop DB를 그 순간 pg_dump로 떠서 서버 안 일회용 컨테이너(망 없음)에 복원하고 V48을 psql로 돌렸다. 4.1절 열은 값 있는 행 전부 평균 -9.0000시간, celebrity_record 0, flyway 0, event created_at, updated_at +9, 이벤트 기간 11/08 00:00~11/16 23:59:59, 트리거 다시 켜짐을 확인하고 컨테이너를 지웠다(test/서버시간대-성 3절).

## 8. 운영 적용 때 주의

- 운영 적용은 이 MR 범위가 아니다. 적용 전 백업(`pg-backup.sh now before-tz`)과 같은 확인 쿼리를 쓴다. 운영 DB 덤프로 같은 리허설을 서버 안 일회용 컨테이너에서 먼저 돌린다.
- 운영 적용 전까지 운영 SQL은 옛 규칙(읽을 때 9시간 빼고 넣을 때 9시간 더함)을 지킨다. 적용 뒤 바로 규칙이 바뀐다. 11/16 이벤트 종료와 11/17 당첨 공지 전후에 적용하면 명단 조회 기간 조건을 어느 규칙으로 쓰는지 확인한다.
- 운영 적용 전에 운영자가 SQL로 9시간 더해 넣은 유명인 기록이 있으면 V48이 되돌리지 않으므로 따로 고친다(4.4절).
- 앱(0.11.x)은 바뀌지 않는다. 서버 응답 값이 같기 때문이다.
- 적용 뒤 infra/README.md 운영 주의와 메모를 「한국 시각 그대로」로 바꾸고 DF-073을 닫는다.

## 9. 구현 지침과 테스트 순서

1. ServerZoneTest(단위): `useAsJvmDefault`가 JVM 기본 시간대를 Asia/Seoul로 바꾼다.
2. ServerTimeZoneStorageIntegrationTest(Testcontainers, 스프링 문맥): JPA로 쓴 14:29가 DB 문자열 그대로, JVM을 UTC로 바꿔도 그대로, SQL 14:29를 서버가 14:29로 읽음, 서버 연결 `SHOW TimeZone` Asia/Seoul.
3. ServerTimeZoneMigrationIntegrationTest(Testcontainers, Flyway V47 → V48): 서버 값 -9시간과 NULL 유지, 감사 -9시간과 트리거 유지, 유명인 시드와 운영자 행 유지와 관리 API 행 -9시간, 이벤트 기간 복원과 시드 만든 시각 +9시간, 대기열과 Flyway 기록 유지, V47의 모든 timestamp 열이 목록에 있음.
4. 기존 시계 관련 시험(크루런 예약, 배치 Clock, 감사 저장소, 이벤트 기간)은 고치지 않고 통과해야 한다. `./gradlew build`(spotlessCheck, ArchUnit 포함).
