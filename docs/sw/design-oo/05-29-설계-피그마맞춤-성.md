이 조각은 피그마 맞춤 여덟 묶음(W1~W8)의 설계다. 묶음별로 나눠 병렬로 구현하므로 묶음 사이 경계(누가 어느 클래스·응답을 고치는가)를 먼저 고정한다.

- **W1~W3**은 앱만 바뀐다. 이 조각이 클래스·상태·경로를 글자 그대로 정한다.
- **W4~W8**은 서버까지 바뀐다. 이 조각은 묶음마다 목적, 바뀌는 클래스·화면, 앱 경로(Route)·화면 상태(UiState)·저장소 메소드 이름, 설계 결정만 둔다. **REST 엔드포인트, 요청·응답 record와 필드, enum 상수, 오류 코드, DB 열과 Flyway 파일은 묶음 작업자가 `../maintenance/2026-11-09_피그마맞춤-성/contract-Wn.md`에 먼저 쓰고 서버 구현과 함께 확정한다.** 확정 뒤 공용 담당이 05-03(API 계약)과 06-04·06-05(클래스 명세)로 옮긴다. 계약 표본(서버 응답 JSON)도 그 파일에 둔다.
- (다음 판 보완 2026-11-10) 계약은 구현으로 확정되었고 5절에 엔드포인트·Flyway·앱 이름을 옮겼다. 계약 파일은 부록으로 남는다. 앱 Rive 렌더러 W9(Jira S15P31A207-300)를 5.6절로 더했다.
- 새 결정 번호는 임시다([임시:D-성-7]~[임시:D-성-40], 구현 뒤 [임시:D-성-41]~[임시:D-성-77]과 코드 리뷰 뒤 [임시:D-성-78]~[임시:D-성-85]는 1.3절). [임시:D-성-1]~[임시:D-성-6]은 서버 시간대 브랜치(05-28)가 먼저 썼다.

### 5.6 W9 아바타 Rive 렌더러 (Jira S15P31A207-300, 앱·avatar-ai)

- 목적: 아바타 PoC(근거: `AVATAR_POC_ONBOARDING.md` 3·4·5절, 저장소 `avatar-ai/INTEGRATION.md`)의 남녀 Rive 몸체(정면 = 서기, 오른쪽 옆모습 = 달리기)와 셀카 머리 레이어 합성을 앱 공용 모듈로 옮기고, W8 화면(내 러너, 꾸미기 미리보기)이 쓴다. 묶음 브랜치는 W9a `feature/S15P31A207-300-avatar-rive`(앱 `:core:avatar`)와 W9s `feature/S15P31A207-300-avatar-ai-port`(avatar-ai 수정 포팅) 둘이다. 서버 쪽 머리 레이어 전달은 W8(39d85330)이 했다.
- 모듈: 새 `:core:avatar`(패키지 `com.a207.runkk.app.core.avatar`). 의존은 Compose UI, lifecycle-runtime-compose, `rive-android`, kotlinx-serialization-json뿐이고 앱의 다른 core·domain 모듈에 의존하지 않는다. `:feature:avatar`만 이 모듈을 쓴다([임시:D-성-75]).

공개 API:

```kotlin
@Composable
fun RunkkRiveAvatar(
    gender: AvatarGender,          // FEMALE, MALE
    motion: AvatarMotion,          // STAND(정면 서기), RUN(옆모습 달리기)
    outfit: AvatarOutfit,          // top·bottom·shoes 각 0..6, 0 = 기본(흰 반팔티, 검은 반바지, 흰 신발)
    bodyShape: AvatarBodyShape,    // BASE(0), CHANGE_1(1), CHANGE_2(2) → Rive body_shape 0·50·100
    runningAmount: Int,            // 0..100(밖이면 자름), 높을수록 피부가 어둡다. 피부에만 적용
    headLayers: GeneratedHeadLayers?, // 셀카 머리(GeneratedHeadLayers.fromHeadJson), null이면 내장 기본 머리
    modifier: Modifier = Modifier,
    onError: (Throwable) -> Unit = {}  // Rive 파일·자산을 읽지 못했거나 합성 실패. 앞 그림은 그대로 둔다
)
```

남녀나 머리가 바뀌면 파일을 다시 읽고(다음 판 보완: 자산 바이트는 IO에서 남녀마다 한 번 미리 읽은 `PreparedRiveAssets`를 쓰고, 네이티브 초기화는 첫 render에서 한 번, [임시:D-성-84]), 의상·체형·러닝량이 바뀌면 백그라운드에서 텍스처만 다시 만든다. 새 그림이 준비될 때까지 그 동작의 기본 그림을 보이지 않는다. 화면이 멈추면(ON_PAUSE) 재생도 멈춘다. 그 밖의 공개 보조: `skinToneAmountFrom(toneIndex, toneCount)`(톤 순번 → 0~100, 지금 화면은 쓰지 않고 서버 `runAmount`를 쓴다, [임시:D-성-62]), `MIN_RUNNING_AMOUNT = 0`, `MAX_RUNNING_AMOUNT = 100`, `AvatarOutfit.MAX_ID = 6`.

Rive 파일과 상태 머신 입력(`RiveAvatarScene`, Rive 원본의 계약이라 이름 그대로):

| 화면 | `res/raw` | 아트보드 | 상태 머신 | 입력 |

- 의상·피부는 Rive 입력이 아니라 앱이 합성한 텍스처로 바꾼다(그리는 순서: 몸 피부(톤 적용) → 의상 → 얼굴 → 눈 → 헤어, 피부톤 필터는 눈·헤어·안경·옷에 적용하지 않음). 서기 몸 기본 텍스처 `avatar_legacy_standing_body.png`와 남녀 내장 머리 레이어 12장씩(`assets/avatars/{female,male}/`, 1024×1024)은 승인본 그대로다(시험 `ApprovedAvatarAssetsTest`).
- 렌더러 입력 출처(W8 화면): 성별 = 회원 프로필 성별(`LocalAvatarCharacter`, 여성이면 여 몸체, 그 밖 남 몸체), 체형 = `AvatarRunner.bodyVariant`(꾸미기는 `bodyShape` 4단계를 같은 규칙으로 접는다, [임시:D-성-58]), 러닝량 = `AvatarRunner.runAmount`([임시:D-성-59]), 의상 = 착용 아이템의 `assetKey` → 앱 대응표([임시:D-성-76]), 머리 = ~~`AvatarRepository.headJson(faceKey)`~~ `SelfieHeads`(LRU 3) → `AvatarRepository.selfieHead(faceKey)` → `GeneratedHeadLayers.fromHeadJson`(얼굴 키마다 한 번, 실패·옆모습 없음이면 null, 다음 판 정정 [임시:D-성-83]). 남의 아바타는 체형 0·러닝량 0이다(이번에 Rive로 그리는 곳은 내 러너 카드와 꾸미기 미리보기뿐).
- 셀카 응답(`GeneratedHead`): PNG Data URL 8장 = 정면 `faceImage`·`eyesImage`·`hairImage`(기존) + `frontImage`·`rightImage`(완성 원본) + `rightFaceImage`·`rightEyesImage`·`rightHairImage`(옆모습 레이어), 모두 1024×1024 공통 좌표. 새 5장과 `rightLayerLayout`은 값이 없으면 JSON에서 빠진다. `mobile`(canvas, anchor, renderFaceImage, displayHeight, neckRemoved, skinColor, neckMask, scene …)은 ai가 준 객체를 그대로 넘기고 `mobile`·`mobile.neckMask`·`mobile.skinColor`는 null이거나 없을 수 있다(없으면 알파에서 목을 찾고 턱 위 피부 중앙값을 쓴다). 서버는 저장하지 않고 전달만 하며 `Cache-Control: no-store`다([임시:D-성-77]).

## 8. 구현 지침과 테스트 순서

- (다음 판 보완) 실제 순서: W9s → W9a → W8·W7·W5·W1·W4 서버와 계약(A단계, 2026-11-09) → W3 → W2 → W8 앱 → W4 앱 → W6(서버와 앱) → W5 앱(2026-11-10). W7 앱은 통합 전이다. 구현 기록 18장. (다음 판 보완) 그 뒤 W7 앱(3313274c) → 코드 리뷰 결함 수정(e5fec330~c6570511, [임시:D-성-78]~[임시:D-성-85]) → 최종 게이트.
- 묶음 순서: W1을 먼저 병합하고 W2~W8은 W1 위에서 마무리한다. W4와 W7은 크루 상세 응답을 같이 보므로 W4를 먼저 병합한다. W6과 W7은 「지난 크루런」 진입만 겹친다(W7 경로가 없으면 W6은 링크를 숨긴 채 병합해도 된다).
- 서버 마이그레이션은 4.1(유지보수 기록)의 번호 대역 안에서만 만든다. 빈 번호는 남겨 둔다.
- 화면 문구는 srs 문구 그대로 strings.xml에 둔다. 가운뎃점을 넣지 않고 `MetaRow`를 쓴다([임시:D-성-10]).
- 테스트 순서: (1) 서버 단위(크루명 12자 경계 12·13자와 기존 13자 이름 수정 통과, 거리 다섯 선택지와 1km 거부, 반복 작업 멱등·규칙 종료, 초대 코드 7일 경계 자동 재발급, 시스템 메시지 유효·무효·크루 없음·두 번 저장), (2) 서버 통합(채팅 시스템 메시지 전송, 반응한 사람 권한, 운영진 자료 이전), (3) 앱 ViewModel(대기실 얼굴 키마다 한 번, 축하 팝업 주마다 한 번, 쿨타임 남은 시간 0에서 단추 바뀜, 쓰기 isValid, 상점 선택·구매 바, 배경 해금 처음 실행 무팝업), (4) 화면 스냅샷(W1 공통 부품, 각 묶음 화면), (5) 피그마 비교 검사.
