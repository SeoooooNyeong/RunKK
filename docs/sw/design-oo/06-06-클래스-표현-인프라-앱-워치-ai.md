#### 6.1.13 표현·인프라 계층

표현·인프라 클래스는 업무 규칙을 갖지 않는다. 책임과 주요 연산만 적는다.

| 클래스 | 패키지 | 책임 | 주요 연산 |
|--------|--------|------|-----------|
| AuthFilter | web.auth | JWT에서 회원ID를 꺼내 요청에 붙인다 | doFilter(): member.TokenIssuer.verify(접근 토큰) → memberId. 만료·위조면 401. 서명이 맞아도 ActiveMembers.isActive(memberId)가 거짓(탈퇴 회원)이면 401이다 (v0.11, CR34-09). /admin/*은 회원 JWT를 검사하지 않고 web.admin의 OperatorCheckInterceptor가 관리툴 토큰을 확인한다(D-42, D-50) |
| SecurityConfig | web.auth | 인증 필터의 적용 경로를 설정한다 | 로그인·가입 경로만 공개하고 /admin/*을 회원 인증 필터에서 뺀다. 공개 경로에 POST /members/guest, POST /auth/guest/session을 더한다(AuthFilter 제외 목록도 같다) (v0.11, FR-197, D-89) |
| AuthAttemptGuard | web.auth | 공개 인증 경로의 시도 횟수를 제한한다 | `admit(http, credential): Attempt`(접속지별 요청 수, 자격(제공자 토큰·갱신 토큰·가입 티켓·게스트 자격 증명)별 실패 수를 확인, 넘으면 429 TOO_MANY_ATTEMPTS), `failed(attempt)`(접속지·자격 실패 수 +1). 자격은 SHA-256 앞부분만 키로 남긴다. 접속지는 X-Real-IP(L25 신뢰 프록시 설정화는 보류). 창과 접속지 판정은 web.attempt의 AttemptLimiter·ClientAddress다 (v0.11 검증, D-132). 메모리 값이라 재시작하면 비워진다(5.4 인스턴스 1개). AuthController·SignUpController가 부른다. v0.11 게스트 생성(POST /members/guest)에 접속지별 한도(제안 시간당 10회)를 더하고, POST /auth/guest/session에도 같은 제한을 건다 (v0.11, CR34-09, CR2-U7, D-89). 게스트 생성은 `admitGuestStart(http): Attempt`가 admit 뒤 생성 한도 자리를 AttemptLimiter.tryAcquire로 미리 잡고(넘으면 429), 받아들인 요청이 입력 거부(동의 누락 409, 받지 않는 동의 400, 닉네임 경합)로 끝나면 SignUpController가 `guestRejected(attempt)`로 자리를 돌려준다(release). 시스템 장애(503)는 돌려주지 않는다. 한도 설정은 `runkk.auth.attempts.guest-starts`(기본 10)·`guest-start-window`(기본 1h) (v0.11 구현 반영, U5-A-4, D-177) |
| ActiveMembers | web.auth | 접근 토큰 주인이 탈퇴하지 않았는지 답한다 | `isActive(memberId): boolean`(회원 상태를 30초 캐시, 탈퇴 표시 1시간), `onMemberWithdrawn(MemberWithdrawn)`(탈퇴 즉시 거부 표시). AuthFilter가 부른다. 접근 토큰 수명(1시간) 안의 탈퇴 회원 요청을 막는다 (v0.11, CR34-09, CR2-U7) |
| OperatorCheckInterceptor | web.admin | 관리툴 요청을 보낸 운영자를 확인한다 | preHandle(): Authorization 헤더의 관리툴 토큰 → operator.OperatorAuthorizer.ensureOperator → request.setAttribute("actorId", id.actorId()). 실패면 403. 업무 규칙을 갖지 않는다(D-50) |
| AdminWebConfig | web.admin | 인터셉터 적용 경로를 설정한다 | /admin/** 에 OperatorCheckInterceptor 등록, /admin/login 제외 |
| ApiExceptionHandler | web.error | 예외를 응답 코드와 화면 문구로 바꾼다 | BusinessRuleException → 409 + 사유 코드, PermissionDeniedException → 403 "권한 없음", IllegalArgumentException·요청 형식 오류(Bean Validation 실패, 형식 오류, 필수값 누락) → 400 "잘못된 요청", IllegalStateException → 409 "처리할 수 없는 상태", 같은 행을 동시에 바꾼 충돌(낙관적 잠금·고유 제약 경합) → 409 "다시 시도해 주세요". 셀카가 1MB를 넘으면 413 TOO_LARGE, 지원하지 않는 형식이면 415 UNSUPPORTED_IMAGE. 응답 본문은 ErrorResponse(code, message)이고 내부 예외 문구는 싣지 않는다 (v0.8, CR-U06). 사유 코드별 상태는 STATUS_BY_REASON 한 표에만 적고 나머지는 409다: AUTH_FAILED 401, PROVIDER_UNAVAILABLE 503(소셜 제공자 무응답 전용), TEMPORARILY_UNAVAILABLE 503("잠시 후 다시 시도해 주세요", 갱신·로그아웃 때 폐기 목록 저장소 장애), TOO_MANY_ATTEMPTS 429 (v0.11, CR34-25). v0.11의 새 사유 코드 16개(F.2.3)는 모두 기본 409라 표에 더하지 않는다. 게시글 사진(POST /crews/{id}/board-posts)은 파일 1MB·요청 6MB를 넘으면 413 TOO_LARGE(MaxUploadSizeExceededException, multipart 한도 D-100), JPEG 머리가 아니면 422 UNSUPPORTED_IMAGE다(F.2.0). PhotoUpload는 BusinessRuleException(UNSUPPORTED_IMAGE·TOO_LARGE)을 던지고 STATUS_BY_REASON에 UNSUPPORTED_IMAGE → 422, TOO_LARGE → 413을 더한다(MaxUploadSizeExceededException도 413 TOO_LARGE) (v0.11, FR-211, D-100) |

#### 6.1.14 앱 (Kotlin)

계층별로 적는다(5.1.2, D-56). 도메인(domain.\*)은 순수 Kotlin이고, 포트 구현과 Android 어댑터는 데이터(api.\*, data.\*), 화면은 표현(ui.\*)에 있다. 시각은 모두 매개변수(Instant)로 받는다.

v0.11 공통 규칙 셋을 이 절 전체에 적용한다 (v0.11, D-111, D-112, CR34-13, CR34-19):
- 문구 키화: domain.\*은 사용자에게 보일 문구를 갖지 않고 enum 키(GuidanceMessage, WatchNotice)와 인자만 갖는다. 문자열로 바꾸는 일은 데이터 계층이 strings.xml로 한다(data.device GuidanceTexts, data.watch의 `WatchNotice.textRes()`). 화면 문구는 strings.xml과 core.ui `UiText`(Res·Plain)로 다룬다. v0.11의 새 키(PAUSED, RESUMED, PAUSE_AUTO_END_SOON, PAUSE_AUTO_ENDED, AUTO_END_SOON, AUTO_ENDED)도 같다 (v0.11, D-111, CR34-13)
- Boolean 이름: domain의 Boolean은 is·has·can 접두어만 쓴다(should 불허). GuidanceSettings.shouldFollowCoachPlan → isFollowingCoachPlan, 설정 필드 locationConsented → isLocationConsented, runVoice → isRunVoiceOn 등, UploadReceipt.isAlreadySaved. 직렬화 이름이 걸린 곳은 @SerialName으로 JSON 키를 지킨다(D-97) (v0.11, D-111, U4-10)
- 한 파일 규칙: 타입마다 한 파일이 원칙이다. 예외는 sealed 계층(부모와 하위 타입, 예 domain.live.ServerMessage·ClientMessage)과 private 함수를 공유하는 짝 UseCase(예 LoginUseCase·SignUpUseCase) 둘이다. 그 밖에 한 파일에 최상위 타입을 여럿 두면 경 결함이다. 앱 Konsist ArchitectureTest가 지킨다 (v0.11, D-112, CR34-19). 적용 범위는 domain·api·data·core·app·ui.\* 전부와 6.1.15 워치(:wear)다(watch.alert의 AlertPorts.kt 세 타입, WatchUiState.kt의 PauseControl은 나눈다, AN5-C-14) (v0.11 구현 반영, U5-C8, D-183)

PAUSED_LOCKED에서는 폰 버튼(재개·정지)을 받지 않고 정지 한도는 PAUSED와 같다 (v0.11, D-93, D-120). 워치 요청은 pauseFromWatch·resumeFromWatch가 받고(LOCKED ⇄ PAUSED_LOCKED 포함), "정지 중"은 isPaused(PAUSED 또는 PAUSED_LOCKED) 하나로 판정한다(D-157) (v0.11, test.md v0.6 TF-AN-23)

###### ProximityAlertRule, ProximityAlert
ProximityAlert(data class, domain.run): gapMeters(Int, 절댓값), interval(Duration), isAhead(Boolean) (v0.11, FR-196). ProximityAlertRule(domain.run): 격차·설정·연결로 근접 알림을 만든다(규칙 한 곳, D-96). 상수: 켜는 거리 100m, 간격 최대 2.0초·최소 0.3초, 간격 기준 거리 5~100m, 다시 보내는 간격 변화 100ms, 유지 신호 2초(모두 SRS (제안) 값이라 이 클래스의 상수, D-113). 연산 `evaluate(gapMeters: Int?, isAlertOn: Boolean, isWatchConnected: Boolean): ProximityAlert?`(v0.11 검증, D-137에서 mode 매개변수 삭제): isProximityAlertOn, 워치 연결, 격차 값 있음(대결 4종에서만 RunSession.updateGap이 채운다), |격차| ≤ 100m를 모두 만족하면 ProximityAlert, 아니면 null. 간격 = 300 + (2000 − 300) × (clamp(|격차|, 5, 100) − 5) ÷ 95 ms(앞서든 뒤처지든 같다). isAhead = 격차 > 0(격차 0은 거짓, D-124). 보내는 때는 `shouldSend(previous: ProximityAlert?, next: ProximityAlert?, sinceLastSent: Duration?): Boolean`(켜짐·꺼짐 변화, 간격 100ms 이상 변화, 그 밖에는 2초마다 유지 신호)이 판정한다(F.4.3). 두 연산 모두 상태가 없고 마지막으로 보낸 값·시각은 RunWatchBridge가 갖는다(D-119) (v0.11, FR-196, D-96, F.4.3, A-23)

###### CoachingJudge, GuidanceRule

###### LiveChannel, LiveChannelProvider
LiveChannel: `suspend fun connect(): Outcome<Unit>`(핸드셰이크 거부·네트워크 실패는 예외가 아니라 Failure, CR-U11), `fun send(m: ClientMessage)`, `val messages: Flow<ServerMessage>`, `fun close()`, `val state: StateFlow<LiveState>`(CONNECTING·CONNECTED·POLLING·CLOSED, 재연결·폴링 전환을 알린다, v0.11 정리 D-131). LiveChannelProvider: `fun open(): LiveChannel`. ServerMessage(sealed interface)와 하위 메시지 11종(5.7.2, v0.8 MatchFailed 추가, v0.8 검증, R39), 앱 ProgressReport(channel, channelId, 거리, 경과, 보낸 시각 — 서버 InboundProgress와 같은 JSON 항목)는 domain.live의 값이다.

v0.11 변경 (v0.11, D-103, F.3): 서버는 회원마다 연결 하나만 두고 새 연결이 이전 연결을 닫으므로 앱은 대결·크루런·채팅이 연결 하나를 함께 쓴다. `LiveChannelProvider.open()`은 그 연결 하나에 대한 **임대**를 돌려주고, 임대의 `close()`는 자기 임대만 반납한다. 참조 수가 0이 될 때만 실제 연결을 닫는다(data.live FallbackLiveChannelProvider). 받기 Flow(messages)는 임대들이 공유하고 쓰는 쪽(조정자, ChatRoom)이 필요한 메시지만 거른다. 보내기는 `send(m: ClientMessage)`이고 ClientMessage(sealed interface)의 하위 타입은 ProgressReport(JSON type "Progress")와 ChatPresence(crewId, isPresent → JSON `present`) 둘이다. ServerMessage에 CrewChatPosted(crewId, messageId, authorId?, authorName, content, sentAt, clientMessageId), CrewChatRemoved(crewId, messageId, reason: DELETED / HIDDEN), CrewChatReactionChanged(crewId, messageId, reactions)를 더해 14종이다 (v0.11, FR-208~FR-210). ServerMessage·ClientMessage는 sealed 계층이라 한 파일에 둘 수 있다(D-112). ChatPresence의 Kotlin 이름 isPresent는 @SerialName("present")로 F.3.2의 JSON 키 present에 대응한다(D-111·D-97). | ClaudeClient, OpenAiClient | runkk_ai.comment | 제공자 하나를 부른다 | 비동기 SDK(AsyncAnthropic / AsyncOpenAI)를 `max_retries=0`, `timeout=anthropic.Timeout(2.5, connect=0.5)`(OpenAiClient는 `openai.Timeout`)로 만든다. 시간 제한 형식은 각 SDK가 다시 내보내는 Timeout이라 httpx를 직접 import하지 않는다 (v0.8, CR-U33). 생성자 `(api_key, model, max_tokens, timeout_s)`로 값만 받고 Settings를 import하지 않는다. 2.5초 안에 짧은 문장을 받아야 하므로 가장 빠른 등급 모델을 쓰고 확장 추론(thinking)은 끈다 **(제안, C-006 선정 때 확정)**. 어느 쪽을 쓸지는 환경 설정(C-006). 제공자 상용 API 약관의 입력 데이터 사용·보존 조건을 C-006 선정 기준에 넣는다(부록 E E-21) |
| FaceRouter | runkk_ai.face | POST /faces를 받는다 | `async def create(request: Request, service = Depends(get_face_service)) -> FaceOut`. 본문은 `application/octet-stream`(multipart 아님)이고 메모리에서만 읽는다. `request.stream()`으로 조각을 모으며 누적 크기가 service.max_image_bytes를 넘는 순간 읽기를 멈추고 413 TOO_LARGE를 낸다(Content-Length가 이미 넘어도 413, CR-U34). Content-Type이 octet-stream이 아니거나 본문이 JPEG(FF D8 FF)·PNG(89 50 4E 47 0D 0A 1A 0A) 시그니처로 시작하지 않으면 415 UNSUPPORTED_IMAGE(CR-U35). 입력 관문은 이어서 이미지를 디코드하지 않고 머리 정보만 읽어, 머리가 깨졌으면 422 UNSUPPORTED_IMAGE, 가로 × 세로가 service.max_image_pixels(Settings.max_image_pixels, 기본 4096 × 4096)를 넘으면 422 TOO_LARGE를 낸다(변환기에 넘기기 전, L28) (v0.11, CR34-26). 413·415와 머리 정보의 422는 입력 관문이 내고, 그 밖의 422(NO_FACE, MULTIPLE_FACES 등)·503(UPSTREAM_FAILED)·504(TIMEOUT)는 변환기 결과로 낸다(CR-U36) (v0.11, CR34-26). 실패 응답은 413/415/422/503/504 + reason ∈ {NO_FACE, MULTIPLE_FACES, UNSUPPORTED_IMAGE, TOO_LARGE, UPSTREAM_FAILED, TIMEOUT} |
| FaceOut | runkk_ai.face | 변환 결과 형식을 정한다 | parts: dict[FacePart, str(base64 PNG)]. 저장 키는 ai 서버가 만들지 않는다 |
| FaceTransformService | runkk_ai.face | 변환을 조정한다 | 생성자 `FaceTransformService(transformer: FaceTransformer, timeout_s: float, max_image_bytes: int, max_image_pixels: int)`(max_image_pixels 읽기 속성은 FaceRouter 입력 관문이 쓴다) (v0.11, CR34-26). `async def transform(image: bytes) -> FaceResult`(images 또는 reason 하나): FaceTransformer.convert를 timeout_s로 감싼다. FaceTransformError(reason)는 그 reason으로, TimeoutError는 TIMEOUT으로, 그 밖의 예외는 UPSTREAM_FAILED로 바꾼다. 성공 결과도 검증한다: 부위 5개(EYES, NOSE, MOUTH, EARS, HAIR)가 모두 있고 각각 PNG 시그니처로 시작해야 하며, 아니면 UPSTREAM_FAILED다 (v0.8, CR-U39). 원본 bytes는 지역 변수로만 다루고 디스크·로그에 쓰지 않으며 반환 뒤 참조를 버린다(FR-156) |
| FaceTransformer (추상, ABC) | runkk_ai.face | 얼굴 변환 계약 | `async def convert(image: bytes) -> SdFacePartImages`(부위별 PNG bytes. api의 avatar.SdFaceParts(저장 키)와 이름을 나눴다). 실패는 FaceTransformError(reason)(reason은 응답의 reason 6종 중 하나)로, 시간 초과는 TimeoutError로 알린다 (v0.8, CR-U29). 연결을 닫는 `async def aclose()`를 가진다(기본은 아무 일도 하지 않음, CR-U30) |
| ExternalFaceApi, LocalSdModel | runkk_ai.face | 외부 API 또는 팀 운영 모델로 변환한다 | ExternalFaceApi는 httpx.AsyncClient(재시도 없음). LocalSdModel은 lifespan에서 모델을 한 번 적재하고 `anyio.to_thread.run_sync` + `asyncio.Semaphore(1)`로 돌려 이벤트 루프와 코멘트 요청을 막지 않는다. 10/24 선정 결과(C-011)에 따라 하나를 쓴다. ExternalFaceApi는 선정 전 임시 계약을 쓴다: POST face_api_url, 본문 application/octet-stream, Authorization: Bearer face_api_key, 응답 200 `{"parts": {부위: base64 PNG}}`, 4xx `{"reason": ...}`(NO_FACE, MULTIPLE_FACES, UNSUPPORTED_IMAGE, TOO_LARGE만 받아들이고 그 밖의 응답은 UPSTREAM_FAILED). 선정 결과에 따라 이 계약을 고친다 (v0.8, CR-U37). C-011에서 팀 운영 모델을 정하기 전에는 face_impl=local로 기동하면 거부한다 (v0.8, CR-U38). LocalSdModel을 고르면 A-003에 따라 DFD를 고치고 ai-face 컨테이너를 따로 둔다(부록 E E-04). 외부 API면 원본 보존 정책(보존하지 않음 또는 N시간 안 삭제)을 선정 기준에 넣는다(E-21) |

프롬프트 캐싱과 응답 캐시는 쓰지 않는다. 요약이 러닝마다 바뀌고 회원당 하루 1회라 같은 요청이 거의 없고, 시스템 프롬프트도 짧다. 전체 하루 200회 한도는 비용보다 남용을 막기 위한 것이다(D-58). ai 서버의 하루 상한 240은 이 한도에서 계산하지 않는 고정 값이고, 운영자는 관리툴에서 전체 한도를 200보다 크게 바꿀 수 없다(D-62).
