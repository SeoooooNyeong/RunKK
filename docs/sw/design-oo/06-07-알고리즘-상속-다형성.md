### 6.2 알고리즘

연산마다 입력·처리·출력을 의사코드로 적었다. srs.md 6.3 소단위 명세서가 "무엇을 판단하는가"였다면 여기는 "어떤 자료 구조로 어떻게 계산하는가"다.

#### A-01 RunningScore.of / paceFor (러닝 점수, D-12)
```
of(distance, elapsed):
    v ← distance.meters ÷ elapsed.minutes            -- 분당 미터
    t ← elapsed.minutes
    vo2 ← -4.60 + 0.182258 × v + 0.000104 × v²
    pctMax ← 0.8 + 0.1894393 × e^(-0.012778 × t) + 0.2989558 × e^(-0.1932605 × t)
    RETURN RunningScore(vo2 ÷ pctMax)                 -- 예: 5km 25:00 → 약 38.3

paceFor(distance):                                   -- 같은 점수로 distance를 달리는 페이스
    lo ← 2분, hi ← 600분                              -- 점수는 시간이 길수록 작아진다(단조 감소)
    REPEAT 50번
        mid ← (lo + hi) ÷ 2
        IF of(distance, mid).value > this.value THEN lo ← mid ELSE hi ← mid
    RETURN Pace.of(hi, distance)
```

#### A-03 RunTrack.maxSegmentSpeedKmh / overspeedSegments / pathLength / timeToReach, RunRecord.judgeValidity (FR-047, FR-063) (v0.11, D-94, CR34-08) (v0.12 구현 반영, CR-11, D-190)
```
maxSegmentSpeedKmh(pauses):                          -- 인자 없는 옛 연산은 maxSegmentSpeedKmh([])로 위임 (v0.11, D-94)
    max ← 0
    FOR i IN 1 .. points.size − 1
        a ← points[i−1], b ← points[i]
        IF b가 불안정 구간 끝 포인트 THEN CONTINUE     -- 신호 공백을 건너뛴 직선 거리는 속도 계산에서 뺀다
        IF ∃ p ∈ pauses: p.straddles(a.at, b.at) THEN CONTINUE   -- 정지 경계 구간(정지 앞 마지막 포인트 ~ 재개 뒤 첫 포인트)은 뺀다. straddles = a < p.to AND b > p.from(경계 비포함, D-163 (v0.11, test.md v0.6 TF-BE-33)) (v0.11, D-93 (7))
        dt ← b.at − a.at (초); IF dt = 0 THEN CONTINUE
        speed ← a.point.distanceTo(b.point) ÷ dt × 3.6
        max ← MAX(max, speed)
    RETURN max
    -- v0.12: 판정에 쓰지 않는다. GPS 튐·차량 이동은 넘는 쌍만 overspeedSegments가 뺀다(쌍 단위 제외로 E-10 닫음, D-190)

overspeedSegments(pauses, rule):                    -- (v0.12 구현 반영, CR-11, D-190)
    intervals ← [], meters ← 0, elapsed ← 0
    FOR i IN 1 .. points.size − 1
        a ← points[i−1], b ← points[i]
        IF b가 불안정 구간 끝 포인트 OR ∃ p ∈ pauses: p.straddles(a.at, b.at) THEN CONTINUE   -- maxSegmentSpeedKmh와 같은 쌍
        dt ← b.at − a.at (ms); IF dt ≤ 0 THEN CONTINUE
        seg ← a.point.distanceTo(b.point)
        IF rule.isOverspeed(seg ÷ (dt/1000) × 3.6)        -- 시속 > 25. 같으면 넘지 않는다
            intervals.add([a.at, b.at]); meters ← meters + seg; elapsed ← elapsed + dt
    RETURN intervals 비었으면 NONE, 아니면 ExcludedSegments(intervals, round(meters), elapsed)

countedLength(stops):                               -- stops = 정지 구간 + 제외 구간 (D-190)
    RETURN 불안정 구간 끝 쌍과 stops에 걸친 쌍을 뺀 이웃 포인트 거리의 합(반올림 m)   -- 앱이 달리는 중에 세는 쌍과 같다

pathLength(pauses):                                  -- 인자 없는 옛 연산은 pathLength([])로 위임 (v0.11, D-94)
    acc ← 0
    FOR i IN 1 .. points.size − 1
        a ← points[i−1], b ← points[i]
        IF ∃ p ∈ pauses: p.straddles(a.at, b.at) THEN CONTINUE   -- 정지 경계 구간은 경로 길이에서도 뺀다
        acc ← acc + a.point.distanceTo(b.point)
    RETURN Distance(acc)

RunRecord.judgeValidity(rule):                       -- 저장 때 한 번(이미 판정했으면 IllegalStateException). 경로 파기 뒤 다시 하지 않는다 (v0.11, D-94)
    judge(rule); RETURN valid                         -- 재판정(rejudgeInvalid, A-29)도 같은 judge를 쓴다 (v0.12, D-190, D-191)

RunRecord.judge(rule):                               -- (v0.12 구현 반영, CR-11, D-190)
    excluded ← track.overspeedSegments(pauses, rule)
    counted ← distance(보낸 값), countedElapsed ← elapsed(보낸 운동 시간)
    IF excluded 있음
        counted ← MIN(track.countedLength(excluded.withPauses(pauses)), counted)   -- 옛 앱은 초과 쌍을 더해 보내고 새 앱은 빼고 보낸다. 어느 쪽이든 두 번 빼지 않는다
        countedElapsed ← countedElapsed − excluded.elapsed                          -- 시간은 서버만 뺀다(앱은 거리만 뺀다)
    excludedMeters ← excluded.distance, excludedMillis ← excluded.elapsed
    IF counted ≤ 0 OR countedElapsed ≤ 0 THEN valid ← false; score ← null; RETURN   -- 저장 값은 보낸 값 그대로(거리·시간 > 0 제약)
    path ← track.pathLength(pauses) − excluded.distance
    declaredElapsed ← elapsed(보낸 값); wall ← Duration.between(startedAt, endedAt) − pausedTotal()
    distance ← counted; elapsed ← countedElapsed; averagePace ← elapsed ÷ distance
    valid ← rule.isSatisfiedBy(distance, elapsed, averagePace)                    -- 세 조건. 남은 값 기준(FR-047 v0.10)
            AND rule.isBackedBy(distance, path, declaredElapsed, wall)              -- 다섯째 조건
    IF valid THEN score ← RunningScore.of(distance, elapsed)

ValidityRule.isBackedBy(declared, path, elapsed, wall):               -- (v0.11, CR-10, CR34-08)
    RETURN declared ≤ path × MAX_DECLARED_TO_PATH_RATIO(2.0)            -- 선언 거리 ≤ 경로 길이 × 2
           AND elapsed ≤ wall + WALL_CLOCK_TOLERANCE(1초)              -- 선언 운동 시간 ≤ 벽시계 − 정지 + 1초

timeToReach(target, pauses):                         -- pauses 매개변수(D-163) (v0.11, test.md v0.6 TF-BE-33)
    acc ← 0
    FOR i IN 1 .. points.size − 1 (불안정 구간 건너뜀은 누적에서 뺀다)
        IF 정지 구간이 points[i−1].at와 points[i].at 사이에 있으면 CONTINUE   -- 재개 뒤 첫 쌍은 거리를 더하지 않는다(D-93 (1))
        seg ← points[i−1].distanceTo(points[i])
        IF acc + seg ≥ target
            ratio ← (target − acc) ÷ seg
            reachedAt ← points[i−1].at + ratio × (points[i].at − points[i−1].at)
            RETURN reachedAt − start − pausedBetween(start, reachedAt)   -- 정지 시간을 뺀 경과 시간(FR-034·FR-063, D-122)
        acc ← acc + seg
    RETURN empty
```

#### A-06 Matchmaker.tick (srs.md 6.3 4.2, FR-081~FR-083)
v0.10에서 한 연산이던 tick을 넷으로 나눴다(D-79, TF-BE-21). v0.9 의사코드를 한 연산으로 두면 V(G) 11로 기준 10을 넘었다. 동작은 v0.9와 같다.

```
tick(now):                                                              -- V(G) 4: 반복, 짝지음 검사, pairUp 결과
    cond ← policy.matchCondition()
    waiting ← queue.waitingOldestFirst()
    paired ← {}
    FOR a IN waiting
        IF a.memberId ∈ paired THEN CONTINUE
        b ← partnerOf(a, waiting, paired, cond)
        IF pairUp(a, b, now) THEN paired ← paired ∪ {a, b}
        ELSE resolveUnpaired(a, cond, now)

partnerOf(a, waiting, paired, cond):                                    -- V(G) 4. 후보가 없으면 null
    FOR b IN waiting에서 a 뒤의 표 (가장 오래 기다린 순)
        IF a.canPairWith(b, cond) AND b.memberId ∉ paired THEN RETURN b
    RETURN null

pairUp(a, b, now):                                                      -- V(G) 4. 배정했으면 true
    IF b = null OR NOT queue.tryAssignPair(a.memberId, b.memberId) THEN RETURN false   -- 원자적(5.3)
    ok ← TRANSACTION(새 트랜잭션)                                        -- 대결 저장 + 통지 예약. 통지는 커밋 뒤 나간다
             battle ← battleRepo.save(Battle.random(a, b, now)); battleStartService.announceMatch(battle)
    IF ok THEN queue.remove(a.memberId); queue.remove(b.memberId)
    ELSE queue.release(a.memberId); queue.release(b.memberId)          -- ASSIGNED → WAITING, waitingSince 유지. 다음 tick에 다시 (v0.8, TF-BE-11, D-64)
         로그 random_match_failed(두 회원 ID)
    RETURN true

resolveUnpaired(a, cond, now):                                          -- V(G) 6
    -- 후보가 없었거나, 후보는 있었지만 tryAssignPair가 실패한 경우 모두 여기로 온다(FR-083 15초 규칙, v0.8, TF-BE-12)
    IF a.isExpired(now, cond.ghostAfter + GIVE_UP_MARGIN)                -- 대기 30초(15 + 15초)를 넘음: 대결을 만들지 못한 채 포기 (v0.8, D-64). 30초 정각은 유지 (v0.10, TF-VB-15)
        IF queue.remove(a.memberId)
            battleMessenger.send(a.memberId, MatchFailed("MATCH_FAILED", ReasonCode.MATCH_FAILED.message()))   -- 러너는 "대결을 만들지 못했어요. 다시 시도해 주세요" 안내를 받는다 (v0.13 정정 D-210)
    ELSE IF a.isExpired(now, cond.ghostAfter)
        IF queue.tryAssign(a.memberId)                                   -- WAITING → ASSIGNED. 그 사이 취소·배정됐으면 false
            ok ← TRANSACTION(새 트랜잭션) ghostMatcher.match(a, now)
            IF ok THEN queue.remove(a.memberId)
            ELSE queue.release(a.memberId)                               -- 다음 tick에 고스트 매칭을 다시 한다 (v0.8, TF-BE-11, TF-BE-16, D-64)
                 로그 ghost_match_failed(회원 ID)
```

GIVE_UP_MARGIN은 Matchmaker 상수 15초다. 정상 경로에서 고스트 매칭은 3초 안에 끝나므로(FR-083, TC-2147) 포기는 저장소·Redis 장애나 가상 기록 0개처럼 다시 해도 실패하는 경우에만 일어난다. 어떤 경로도 러너가 MatchFound도 MatchFailed도 받지 못한 채 대기열에서 사라지지 않는다 (v0.8, D-64).

```
    ELSE

        second ← arrivedInTime 중 first 다음의 유효한 첫 번째
```

BattleResultService는 corrected가 참인 판정마다 두 참가자에게 BATTLE_CORRECTED 알림을 보낸다(기록 대결은 참가자 한 명). 정정 알림의 유무는 판정 횟수가 아니라 규칙 3 적용 여부로 정해진다(v0.8, D-63). 다만 규칙 3으로 이미 FINISHED인 대결에 늦은 기록(카운트다운 밖 도착)이 와서 다시 판정할 때는 판정이 바뀐 경우만 정정이다. 같은 판정이면 BATTLE_CORRECTED를 다시 보내지 않는다(FR-103 "결과가 정정될 때", v0.10, TF-BE-20, D-82).

표시가 선 기록은 다시 고르지 않고, markTierApplied가 조건부 UPDATE라 리스너와 보정이 겹쳐도 한쪽만 참이다(진 쪽은 IllegalStateException으로 그 회원 트랜잭션을 되돌린다). 리스너(TierUpdateListener)는 일시 오류 3회 재시도 뒤 로그만 남기고 이 보정이 다음 날 채운다(M4 결정과 같은 꼴). 대상 고르기는 부분 색인 idx_run_record_tier_pending (saved_at) WHERE valid AND NOT tier_applied를, 순번 세기는 idx_run_record_member_valid_saved를 쓴다(V21). 구멍(앞 순번이 늦게 옴)은 recordLateValidRun이 판정 없이 점수·거리만 더하므로 판정 지점이 구멍이면 다음 판정 지점까지 티어가 늦다. 방향은 running → member(D3) 그대로다 (v0.11 구현 반영, U5-A-1, D-169).

#### A-28 CrewPostService.remindClosingPolls (투표 마감 임박 알림, FR-218) (v0.11, D-106)
```
remindClosingPolls(now):                                         -- PollReminderJob 1분. 반환: 알린 투표 수
    polls ← post_kind = POLL, 삭제·숨김되지 않음(D-125), reminded = false, now ≤ poll_closes_at ≤ now + 1시간 인 투표   -- idx_crew_post_poll_closing

        커밋 뒤 crewNewsNotifier.remindClosing(poll, targets)    -- POLL_CLOSING_SOON, 수신 설정(PushDecision)으로 거른다
```

reminded 칼럼은 크루런 CREW_RUN_SOON과 같은 칼럼이다. 1시간 전 알림은 1분 정밀도면 충분해 1초 시계(CrewRunTickJob)에 얹지 않는다(D-106). 숨김(hidden) 투표는 알림 대상에서 뺀다(크루원이 열 수 없는 투표다, D-125).

#### A-29 RunRejudgeService.run (기존 무효 기록의 일회성 재판정, FR-047, FR-043 예외) (v0.12 구현 반영, CR-11, D-191)
```
run():                                                -- batch.running.RunRejudgeJob이 ApplicationReadyEvent에 한 번 부른다(기동 스레드 밖, 상한 1,000개·60초, D-199 구현 대기)
    drain(PENDING, rejudgeOne); drain(VALID, applyOne)
    RETURN Result(nowValid, stillInvalid, skipped, applied, failed)   -- 처리한 것이 있으면 run_rejudged 로그

drain(state, step):
    LOOP
        ids ← repo.rejudgeCandidates(state, 100 + |failed|)에서 failed 뺀 앞 100개   -- idx_run_record_rejudge
        IF ids 비었음 THEN RETURN
        FOR id IN ids: 새 트랜잭션(REQUIRES_NEW)에서 step(id), 예외면 failed에 넣고 로그(표시는 그대로, 다음 기동이 다시)

rejudgeOne(id):                                      -- 1단계
    r ← repo.findForUpdate(id)                        -- 행 잠금. 다른 인스턴스와 겹쳐도 한쪽만
    IF r 없음 OR r.rejudgeState ≠ PENDING THEN RETURN NONE
    IF NOT r.hasRoute() OR r.valid THEN repo.moveRejudgeState(id, PENDING, SKIPPED); RETURN SKIPPED   -- 경로 파기·미수집
    valid ← r.rejudgeInvalid(ValidityRule.STANDARD)    -- judge(A-03) 재적용
    IF valid THEN book ← bookRepo.findOrCreateForUpdate(r.memberId); book.apply(r); bookRepo.save(book)   -- 신기록 표시는 붙이지 않는다
    repo.storeRejudgement(r, PENDING, valid ? VALID : DONE)   -- 무효 그대로여도 남은 거리·시간·제외 값은 남긴다

applyOne(id):                                        -- 2단계
    r ← repo.findForUpdate(id); IF r 없음 OR r.rejudgeState ≠ VALID THEN RETURN NONE
    active ← memberQuery.isActive(r.memberId)
    IF active AND NOT r.tierApplied THEN tierApplier.apply(r.memberId, id, RunScoreInput(validRunScoreOf(id)))   -- 늦은 반영 포함(D-169)
    repo.moveRejudgeState(id, VALID, DONE)
    IF active THEN publish(RunRecordRejudged(id, r.memberId, r.distance, r.savedAt))   -- 커밋 뒤 리워드 적립·배경 해금(알림 없음)
```

표시가 바뀐 행은 다시 고르지 않으므로 몇 번 돌려도 결과가 같고, 남은 일이 없으면 색인 조회 두 번으로 끝난다. 리워드는 (회원, 사유, 근거) 고유 제약으로 한 번만 적립하고 하루 상한은 원래 저장일로 센다. 배경은 BackgroundService.unlockReachedQuietly(누적 유효 거리 전체, 알림 없음)가 이미 해금한 것을 다시 넣지 않는다. 대시보드·달력·이번 주 크루 레이스는 기록을 읽어 다시 세므로 할 일이 없고, 랭킹(RankingSnapshot)은 다음 0시 집계(RankingRebuildJob)부터 반영된다(BE7-5). run은 기동 스레드 밖에서 돌고 한 번에 기록 1,000개 또는 60초까지만 처리한다(D-199, 구현 대기. 지금 코드는 기동 스레드에서 전부 동기 처리) (v0.12, U7-2).

남은 `type ==` 분기 점검: 같은 종류 분기가 3곳 이상 반복되는 곳 0개. 2곳 이하로 남긴 것은 RunMode(서버 RunRecord 일관성 검사 1곳, 앱 RunSession 시작 방식 1곳)다. v0.11에서 앱의 RunMode 분기가 늘었다: RunSession.pause(FREE만), RunWatchBridge.publish의 isPausable(FREE만), ProximityAlertRule.evaluate(BATTLE만). 시작 방식까지 4곳이라 기준(3곳 이상이면 다형성 후보)에 걸린다. 앞의 둘은 같은 질문("정지할 수 있는 모드인가")이므로 RunMode 상수 연산 하나로 모으면 3곳이 된다. design-review.md 17장(R-6) 판정으로 모았다: 일시정지 가능 여부는 domain.run의 `RunMode.isPausable` 한 곳에서 답하고(RunSession.pause와 워치 표시가 읽는다), ProximityAlertRule.evaluate는 mode를 받지 않는다(격차 없음 = 대결 아님). 남은 모드 비교는 isPausable 정의와 RunSession 시작 방식 2곳이다 (v0.11, D-93, D-96) (v0.11 검증, D-137).
