### 5.7 API·실시간 메시지 계약 (객체 수준)

10/21 API 계약(schedule.md 2.1)에서 필드 이름·형식을 고정한다. 여기서는 어떤 엔드포인트가 어떤 서비스 연산으로 가는지만 정한다. 모든 엔드포인트는 `/api/v1` 아래에 있고 AuthFilter가 회원 JWT로 memberId를 정한다(로그인·가입·운영자 로그인 제외). /admin/* 요청의 관리툴 토큰은 AuthFilter가 아니라 web.admin의 OperatorCheckInterceptor가 OperatorAuthorizer.ensureOperator로 확인하고, 확인한 운영자 계정을 요청 속성 actorId로 붙인다(D-42, D-50).

v0.11 공통 규칙(부록 F F.2.0): 공개 경로(SecurityConfig와 AuthFilter의 제외 목록)는 POST /auth/login, POST /auth/refresh, POST /members, GET /legal/\*\*, POST /admin/login에 게스트 시작 POST /members/guest와 게스트 세션 재개 POST /auth/guest/session을 더한다. 오류 본문은 `ErrorResponse{code: String, message: String}`(web.error) 그대로이고 상태는 기존 규칙을 따른다: BusinessRuleException(ReasonCode)은 409(ApiExceptionHandler.STATUS_BY_REASON에 적은 것만 다른 상태), PermissionDeniedException은 403 PERMISSION_DENIED, 입력 검증 실패(Bean Validation, IllegalArgumentException)는 400 BAD_REQUEST, 크기 초과 413 TOO_LARGE, 이미지 형식 422 UNSUPPORTED_IMAGE, 시도 제한 429 TOO_MANY_ATTEMPTS. ReasonCode.TEMPORARILY_UNAVAILABLE은 503("잠시 후 다시 시도해 주세요")이고 토큰 갱신·로그아웃의 폐기 목록 저장소 장애에만 쓴다. PROVIDER_UNAVAILABLE은 소셜 제공자 무응답 전용이다(CR34-25). web.auth의 AuthAttemptGuard가 접속지별 요청 수·실패·자격 실패를 제한하고(게스트 생성 한도 포함, 429 TOO_MANY_ATTEMPTS), ActiveMembers가 탈퇴 회원의 접근 토큰을 거부한다(CR34-09). 새로 만들거나 바꾸는 REST 항목의 시각은 D-84 형식(ISO-8601, `+09:00` 오프셋 포함)의 OffsetDateTime이고(v0.13 정정, D-213: web.battle의 GET /battles/history playedAt과 GET /battles/active startAt은 예외로 오프셋 없는 LocalDateTime이다. 그 밖의 web.* 전송 형식 시각은 OffsetDateTime이다), 이번에 다시 만드는 web.crew 전송 형식은 기존 LocalDateTime 항목도 모두 OffsetDateTime으로 바꾼다. 앱 api.crew 매퍼는 A2에서 오프셋 있는 값과 없는 값을 모두 읽게 먼저 고친다(D-114). 목록 페이지는 common.PageCursor(cursor, size)와 같은 방식(size+1 읽기, nextCursor)이다. 요청·응답 본문은 부록 F F.2.2, 새 사유 코드 16개는 F.2.3, 앱 계약(android/contract)이 깨지는 곳은 F.2.4에 있다([F-v0.11-변경-명세](F-v0.11-변경-명세.md)) (v0.11, D-114, CR34-09, CR34-25) 크루 밖 러너의 크루 전용 요청(srs.md 3.0.3)은 거부하고 자료를 바꾸지 않는다. srs v0.10 보완이 3.0.4에서 이 응답 코드를 설계(5.7)에 맡겼다 (v0.11, 7.13.5 TF-VB-24, TF-SY-26). 응답 코드는 두 경로다(D-167): (1) 권한표(3.0.3) 행위로 판정하는 크루 게시·관리 쓰기(응원·일정·공지·투표·게시글 쓰기, 참석·투표 응답, 고정, 공동 목표, 운영진 지정·강퇴·정보 변경, 크루 안 조회 VIEW_CREW_INTERNAL, 사진 조회)는 CrewPermissionPolicy.check가 PermissionDeniedException → 403 PERMISSION_DENIED. (2) 크루 소속이 전제인 자원(크루 채팅 보내기·읽기·삭제·리액션·채팅방 입장, 신고 대상 조회·신고 접수)은 BusinessRuleException(NOT_CREW_MEMBER) → 409. 권한표의 "이 관계에게 허용되지 않은 행위"는 403, "그 크루에 속하지 않아 대상 자원이 없는 것과 같음"은 409로 가른다. 사용자 결정에 따라 한쪽으로 합칠 수 있다(부록 E E-34) (v0.11 구현 반영, U5-8, D-167)

#### 5.7.2 실시간 메시지

WebSocket 경로 하나(`/ws`)에 메시지 종류(type) 필드로 나눈다. 앱은 연결 때 접근 토큰을 핸드셰이크 Authorization 헤더로 보내고 TokenHandshakeInterceptor가 member.TokenIssuer.verifyGrant로 회원 ID와 토큰 만료 시각(member.AccessGrant(memberId, expiresAt))을 정한다(design-review.md E1, D-110). 앱 → 서버는 진행값과 채팅방 입장 알림(ChatPresence) 둘이다. 서버는 회원마다 연결 하나만 두므로(SocketSessionRegistry.register가 이전 연결을 닫는다) 앱은 대결·크루런·채팅이 한 연결을 함께 쓴다(D-103). 크루 채팅은 새 경로를 만들지 않고 같은 연결에 메시지 종류를 더하며, 채팅 **보내기는 REST**(POST /crews/{id}/chat/messages)이고 실시간 채널은 **받기와 방 입장 알림**만 한다(D-101). **어떤 메시지에도 위도·경도·코스 필드가 없다**(FR-089, FR-149, NFR-021) (v0.11, D-101, D-103, D-110)

REST는 web.battle의 GET /battles/history playedAt, GET /battles/active startAt이 오프셋 없는 LocalDateTime(Spring 기본 직렬화)이고, 그 밖의 web.* 전송 형식(web.record·web.run·web.crew·web.chat·web.avatar·web.admin.report 등)은 OffsetDateTime(`+09:00`)이다. 앱 api.core.ServerTime.parse는 오프셋 있는 값과 없는 값을 모두 읽고, 없는 값은 Asia/Seoul로 본다. 그래서 같은 서울 시간대를 쓰는 지금 앱·서버 사이에서는 어긋나지 않는다.
- MatchFailed(D-210, D-85 대체): `{type: "MatchFailed", code: "MATCH_FAILED", message: "대결을 만들지 못했어요. 다시 시도해 주세요"}`. code·message는 문자열이고 code는 common.ReasonCode 상수 이름이다. battle.live에 MatchFailReason enum이 없다.
- 지연 측정용 sentAt(D-211, D-214, D-65 (1) 대체): OpponentProgress와 CrewRunRelay 줄에 sentAt이 없다. 받는 기기가 메시지로 끝-끝 지연(수신 시각 − 상대 sentAt)을 잴 수 없다. 서버는 받은 ProgressReport.sentAt을 어디에도 쓰지 않는다(battle LiveBattleSession.Runner와 crew LiveProgress는 받은 시각 lastSeen·seenAt만 둔다). NFR-005·NFR-039 측정 방법은 메시지 밖(시험 방법)에서 정한다.
- CrewRunRelay 줄(D-214, D-65 (2) 보완): {name, distance, rank, connection, memberId, mine}. 모든 줄에 회원 ID가 실린다(D-65 대안에서 버렸던 "다른 참가자의 회원 ID가 모든 기기로 퍼진다"가 지금 코드다). 앱은 mine을 먼저 보고, mine이 없을 때만 memberId를 자기 회원 ID와 비교한다(D-178 (2)).
- CrewRunEnded(D-215, D-65 (4)·D-66 앱 동작·D-86 (1) 대체): postId 하나다. 앱은 정상 종료와 삭제를 가르지 않고 측정을 끝낸다(5.7.2 표).
- 연결과 크기(D-216, D-217): 핸드셰이크 인증 실패는 TokenHandshakeInterceptor가 HTTP 401로 업그레이드를 거부한다(앱은 OkHttp TokenAuthenticator로 갱신해 한 번 다시 보내고, 그래도 401이면 Unauthorized). 1008 POLICY_VIOLATION은 세션 속성이 없을 때(인터셉터 없이 연결) LiveSocketHandler가 헤더를 다시 확인해 실패한 방어 경로에서만 쓴다. 앱 → 서버 메시지가 1,024바이트를 넘으면 읽지 않고 버린다. CrewRunCancelled.reason은 화면 문구 문자열이다.

서버 → 앱 메시지 record는 만드는 패키지에 둔다. 대결 메시지 7종(MatchFound, MatchFailed, BattleStart, OpponentProgress, BattleGuidance, CountdownStarted, BattleEnded, v0.8)은 battle.live에서 BattleMessage를, 크루런 메시지 4종(CrewRunStart, CrewRunCancelled, CrewRunRelay, CrewRunEnded)은 crew.live에서 CrewRunMessage를, 채팅 메시지 3종(CrewChatPosted, CrewChatRemoved, CrewChatReactionChanged, v0.11)은 crew.chat.live에서 crew.chat.CrewChatSignal을 구현한다. 세 인터페이스는 `String type()` 하나만 가진다. realtime의 RealtimeMessageSerializer는 type() 값을 JSON의 type 필드로 쓰고 나머지 항목을 그대로 직렬화하므로 메시지 클래스 목록을 알 필요가 없다(sealed 미사용, D-06). crew.chat.live도 13.1 규칙 (7)(*.live는 상위 패키지와 common만 import)을 따른다. ##### 5.7.3.4 실시간 메시지

| 메시지 | 바뀜 | 새 항목 |
|---|---|---|
| `MatchFound` (battle.live.MatchFound, 서버 → 앱) | 항목 1개 추가 | **placementRound** Integer, null 가능. 배치고사 대결이면 판 번호. 이때 `opponentTier`는 `UNRANKED`이고 앱은 상대 티어를 보이지 않으며 상대를 점선 원 「?」로 그린다(J24-3). `opponentName`은 가상 닉네임, `opponentGender`는 무작위 `MALE`·`FEMALE`, `opponentBest`는 상대 완주 시간(초). 배치고사가 아닌 MatchFound에도 `"placementRound": null`이 실린다(battle.live는 Jackson 비의존이라 생략하지 않음, v0.32 D-540) |

##### 5.7.3.6 계약 시험 순서

`android/contract/`(dto-records.json, enums, policy)는 서버에서 뽑는 파일이라 **BE만 고친다**. BE는 첫 커밋(BE-0, 05-21 10절)에서 web DTO record·enum을 이 표대로 더하고 `python android/contract/sync_from_server.py`로 계약 파일을 다시 뽑아 통합 브랜치에 먼저 넣는다. AN 단위는 그 뒤에 시작하거나, 먼저 시작했으면 합치기 전에 BE-0을 받아 계약 시험(앱 `android/data` api.contract `ServerContractTest`·`TierPlacementContractTest`, 서버 `AppContractSnapshotTest`·`web.PlacementContractTest`. v0.31까지 적은 ServerDtoContractTest·ContractEnumsTest는 코드에 없는 이름이라 v0.32 D-530으로 바꿈)을 통과시킨다.
