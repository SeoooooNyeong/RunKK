# 5.31 설계: 실기기 수정 요청 ①~⑧ (다음 판 신규)

> 작성: 2026-11-14 | 버전: 다음 판 변경(design-oo v0.39 기준) | 담당: 이성현(브랜치 `feature/S15P31A207-306-device-fix-requests`) | 입력: srs [03-10-실기기수정-성](../srs/03-10-실기기수정-성.md)([임시:FR-성-24]~[임시:FR-성-38], [임시:NFR-성-7]·[임시:NFR-성-8]), 유지보수 기록 [2026-11-14_실기기수정-성](../maintenance/2026-11-14_실기기수정-성.md)(결정 U-1~U-14, 영향 범위), develop 15d7ab3d 코드 읽기(백엔드 `ArchitectureTest` 허용표, 앱 `ArchitectureTest` 허용표, Flyway 최신 V65), 피그마 NMTtVMWIT22D0CwOU2y0I9 제안 섹션 62431:1918

이 조각은 실기기 수정 요청 ①~⑧의 설계 결정 [임시:D-성-226]~[임시:D-성-314]와 [임시:D-성-322]~[임시:D-성-343], 클래스·파일 변경, 경계 계약 변경, 상태도, 순서, 의존 영향, 시험 목록을 둔다. 세 묶음으로 나눈다: A 크루 아바타 얼굴과 크루 초대(요청 ①, ⑧), B 기록런·대결·크루런·자유런 진행 화면과 매칭 대기(요청 ②, ③, ④). C는 러닝 결과·기록 카드·가이드(요청 ⑤, ⑥, ⑦)다. D절은 뒤에 확정한 정정이고 A~C절보다 우선한다. 코드를 읽어 확인한 것만 사실로 적었고 확인하지 못한 것은 「미확인」으로 표시했다. 구현 언어는 서버 Java 21, 앱 Kotlin이다(절차적 언어로 옮기지 않는다).

객체 모델에서 새로 생기는 값과 객체는 `AvatarLook`(서버, 아바타 모습), `RunnerLook`(앱), `TrackLayout`(트랙 배치), `CrewRunStanding`(크루런 순위), `ResultStageLayout`(결과 무대 배치), `GuideReplay`(가이드 다시 보기 신호), `ChatAuthorFaces`(채팅 작성자 얼굴)다. 상태가 바뀌는 대상은 매칭 대기 화면(확인 창), 보기 모드(트랙, 지도, 지도 불가), 가이드(숨김, 시작 카드, 단계)이고 각 묶음에 상태도를 두었다. 기능 모델은 srs의 DFD 번호(5.5.1, 5.8, 4.1, 4.2, 4.4, 4.5, 4.6, 2.2, 2.5, 3.2, 3.5, 1.4, 5.1.1, 5.3.1, 5.7.3)에 대응하는 연산을 각 묶음의 클래스 변경 표가 담는다.

PM 결정 U-14에 따라 박재영 리뷰 없이 진행한다. 그래서 대결, 러닝 기록 쪽 서버 DTO와 실시간 메시지는 필드 추가만 하고 이름이나 형을 바꾸지 않는다.

## A. 크루 아바타 얼굴과 크루 초대 (요청 ①, ⑧)

(코드 확인 기준. 확인 못 한 것은 미확인. 경로 줄임: BE=`backend/src/main/java/com/a207/runkk/`, AND=`android/`)

##### 먼저 알릴 것: PM 결정과 코드의 어긋남
`DisclosureLevel`(BE `member/DisclosureLevel.java`)은 v0.14 D-241 이후 `SELF`, `WITHDRAWN`, `PUBLIC`만 있고 `showsProfile()`이 거짓인 경우는 탈퇴뿐이다. 나이대·성별만 항목별로 감춘다. 즉 "프로필 비공개 크루원은 기본 얼굴"을 `disclosedMemberIds`에 걸면 지금은 탈퇴 외에 걸러지는 사람이 없다. 현재 코드에는 프로필 전체를 숨기는 설정이 없다. 설계는 판정 위치를 `DisclosureLevel.showsProfile()` 한 곳으로 고정해 규칙이 바뀌면 같이 따라가게 한다. 성별 비공개는 `shownGendersOf`의 대체 성별이 처리한다. "프로필 비공개"가 무엇을 가리키는지는 PM 확인이 필요하다(8절).

##### 8. 위험과 열린 점
- "프로필 비공개" 정의가 코드에 없다(맨 앞). PM이 항목별(나이대·성별) 비공개를 뜻하면 현재 설계로 충분하고, 프로필 전체 비공개 설정을 새로 만들려면 member 변경이 필요하다.
- 크루 초대 대기 수명(`PendingInvite`)의 값은 미정이다. 임시로 30분~1시간 중에서 정해야 한다.
- `KakaoLinkSharer`와 `KakaoInviteSharer`가 한동안 중복된다. 합치려면 battle→share 의존이 필요해 이번엔 미룬다.
- 얼굴 조회 비용: 목록 1회에 최대 10명(`faceKeysOf`는 회원마다 읽음), 채팅은 메시지 한 쪽당 작성자 수만큼이다. 성능 영향은 미측정이다.
- 0.12.0 앱은 크루 링크를 앱으로 열지 못한다(스토어 안내 페이지). 카카오 버튼 실행 인자는 옛 앱이 `invite`가 아니라서 무시한다. 릴리스 안내가 필요하다.
- "이미 구성원" 판정이 `myCrew()` 추가 호출에 기대고, 미리보기 응답에는 정보가 없다. 서버 응답에 `isMember`를 넣는 편이 더 단순할 수 있으나 이번 범위 밖으로 두었다.

#### 4. 상태도

매칭 대기 확인(화면 상태: Waiting, Confirm):

| 상태 | 이벤트 | 다음 | 부수 효과 |
|---|---|---|---|
| Waiting (REQUESTING, WAITING, INVITING) | 시스템 뒤로 가기 | Confirm | `isLeaveConfirmVisible = true` |
| Waiting | 하단 「매칭 취소」 | (기존 `onCancel`) | 확인 창 없이 취소 |
| Waiting | 앱이 뒤로 감 | (기존 `onBackgrounded`) | 확인 창 없이 취소 |
| Confirm | 「나가기」 | Waiting → 취소 중(CANCELLING) → Exit | `onCancel()` 호출 |
| Confirm | 「계속 기다리기」 또는 바깥 누름 | Waiting | 창 닫기 |
| Confirm | 상대가 정해짐(MATCHED) | MATCHED | 창을 자동으로 닫는다 |
| CONFIRMING, INVITE_ENDED | 뒤로 가기 | Exit | 확인 없음(기존) |
| CANCELLING, JOINING, MATCHED | 뒤로 가기 | 변화 없음 | 기존 |

보기 모드(TRACK, MAP, MAP_UNAVAILABLE):
- TRACK에서 「지도」를 누르면 MAP이 되고 `saveRunViewMode(MAP)`을 호출한다. MAP에서 「트랙」은 반대다.
- MAP에서 `onMapError`가 오면 MAP_UNAVAILABLE이 된다. 이때는 전환을 숨기고 트랙만 그린다. 저장값은 건드리지 않는다.
- 시작 값은 `runViewMode()`(없으면 TRACK)다. 지도를 띄울 수 없는 환경(`canShowKakaoMap` false)은 처음부터 MAP_UNAVAILABLE이다.

#### 3. 가이드 상태도

상태는 `HIDDEN`, `START_CARD`, `STEPS(index)`다. 첫 안내와 다시 보기는 `isReplay`로만 갈린다.

| 지금 상태 | 이벤트 | 다음 상태와 동작 |
|---|---|---|
| HIDDEN | 로그인 참이고 `FirstRunGuide.shouldShow`가 참 | START_CARD (`isReplay=false`) |
| HIDDEN | `shouldShow`가 거짓 | HIDDEN 유지 |
| HIDDEN | `GuideReplay` 신호(`consume()`이 참) | STEPS(0), `isReplay=true`. 시작 카드는 건너뛴다 |
| START_CARD | `onStartTour` | STEPS(0) |
| START_CARD | `onSkip` 또는 `onBack` | `finish()`: HIDDEN, `isFinished=true`, `guide.complete()` |
| STEPS(i) | `onNext`, i가 마지막이 아님 | STEPS(i+1) |
| STEPS(i) | `onNext`(마지막, 「시작하기」) | 첫 안내면 `finish()`, 다시 보기면 HIDDEN만 |
| STEPS(i) | `onPrevious`, i>0 | STEPS(i−1). i=0에서는 단추가 없다 |
| STEPS(i) | `onBack` | 첫 안내면 `finish()`, 다시 보기면 HIDDEN만 |
| (아무 때나) | 로그인 상태가 다시 참 | 보이는 중이면 진행을 유지하고, 끝낸 뒤면 판정하지 않는다(기존 규칙) |

다시 보기는 `GuideCopy`·서버 seen을 건드리지 않고 `isFinished`도 바꾸지 않는다. 끝나면 홈에 남는다.

#### 4. 순서 설명

1. **자유런 종료→결과 화면**
   1. `RunResultRoute`가 `viewModel.load(recordId, …)`로 기록과 `readMyAvatar()`(`AccountRepository.myAvatar()`)를 읽는다.
   2. `RunResultScreen`이 `ResultStage(state.myAvatar?.backgroundKey, avatar = { AvatarStillSlot(AvatarStillSubject.MINE, it) { 기본서기 } })`를 부른다.
   3. `ResultStage`가 `LocalConfiguration`의 폭(W)과 `painter.intrinsicSize`로 `ResultStageLayout.forResult`를 계산해 배경, 그림자, 아바타 칸을 놓는다. 배경은 `avatarStageBackdropRes(key, null, isDark)`다.
   4. `AvatarStillSlotContent`가 `RiveAvatarStill`로 내 모습을 읽어 그린다. 시트는 그 아래에 올라간다.
2. **기록 카드 열기와 공유**
   1. `RecordCardRoute`가 `viewModel.load`를 부른다. `records.card`와 `avatars.backgroundChoice()`를 읽어 `backgroundKey`를 상태에 담는다.
   2. `RecordCardFront`가 `ResultStageLayout.forCard`로 무대와 내 아바타를 그린다.
   3. 「공유」를 누르면 `onShareStep(true)`로 `ShareStep`에 들어간다. `AvatarStillSlot(onReady)`가 참이 될 때까지 단추를 막는다.
   4. 단추를 누르면 `capture.capture(isDark)`가 `CapturedCard`를 만든다. `onShare(kind, captured)`가 `ShareImageFramer.frame(captured)`로 워드마크를 붙이고 `CardSharer.share`로 보낸다.
3. **첫 홈 입장**
   1. `FirstRunGuideViewModel` init에서 `session.loggedIn`을 collect해 `FirstRunGuide.shouldShow`로 START_CARD를 정한다.
   2. `HomeFeatureEntry.Overlay`가 홈이 맨 위일 때 `FirstRunGuideRoute`를 그린다. `onStartTour`로 STEPS에 들어가고 `GuideStep.visibleIn(LocalReleaseScope.current)`의 앵커(`LocalGuideAnchors`)로 구멍과 말풍선을 놓는다.
   3. 마지막 「시작하기」나 뒤로 가기가 `finish()`로 `FirstRunGuide.complete()`(기기 사본 SEEN_UNSENT→서버 PUT→SEEN)를 부른다.
4. **설정→다시 보기**
   1. 「가이드 다시 보기」 줄을 누르면 `SettingsViewModel.onReplayGuide()`가 `GuideReplay.request()`를 부르고, `navigator.selectTab(Routes.HOME)`이 홈만 남긴다.
   2. 홈 `FirstRunGuideViewModel`이 신호를 소비해 `onReplay()`로 STEPS(0)을 시작한다. 서버는 부르지 않는다.

- 새 import 간선이 없다. `ArchitectureTest`의 ALLOWED 표(폰 181개)와 Fan-Out 7 이하는 그대로다.

  - `GuideReplay`는 `domain.settings`이고 `javax.inject`와 `kotlinx.coroutines.flow`만 쓴다. `ui.me`·`ui.home`은 이미 `domain.settings`를 쓴다.

화면 → `core.navigation`은 대상과 자세 값, `ui.avatar` → `core.avatar`는 렌더 값, 크루/채팅 → 디자인 시스템은 성별과 얼굴 층을 넘긴다. 서버 `infra.avatar` → `avatar`는 기존 Repository 구현 방향이다. 새 양방향 패키지 의존은 확인되지 않았다. 값 형식의 읽기 전용 속성과 enum을 사용한다. 상속 구조 변경은 없다. 전체 Fan-Out 재집계와 `sw-design review` 재수행은 미실시이며, 29장 이후 변경의 재검증을 pending으로 요청한다.

시험 순서는 단위(`FemaleBuiltInFaceTest`, `HeadPlacementTest`, `SideNeckRegistrationTest`, `LobbySeatCharacterTest`) → 사용 기반 통합(머리 합성, 슬롯, JPA 두 조회) → 스레드 검증(홈, 트랙, 대기실, 반응자 시트) → 시스템(실제 화면 크기, 바탕별 접합부, 새 셀카, 실제 대결)이다. 실제 시험 이름과 미실시는 [시험 10절](../test/실기기수정-성.md)에 둔다. 이 보충은 소스 복원이며 설계 검증 합격이나 PM 승인 기록이 아니다.

## E. 모든 러닝의 절전 모드 안내 (2026-11-16, 다음 판 변경)

작성자 이성현(성). 입력은 SRS의 U-40~U-42, [임시:FR-성-380]~[임시:FR-성-382], [임시:NFR-성-20], [임시:CR-성-230]다. 기존 D-성-876 다음부터 배정한다.

### 객체 모델과 공개 계약

| 파일, 함수 | 책임과 시그니처 |
|------------|------------------|
| `core:ui/core.designsystem/RunPowerSaveSettings.kt` | 기기 판정 `fun shouldOfferRunPowerSaveSettings(context: Context): Boolean`. `PowerManager.isPowerSaveMode == true`만 읽음 |
| 같은 파일 | 설정 열기 `fun openRunPowerSaveSettings(context: Context): Boolean`. 열었으면 true, 세 후보 모두 없거나 접근이 거부되면 false |
| `core:ui/core.designsystem/RunPowerSaveStart.kt` | 화면 세션 안내 `@Composable fun rememberRunPowerSaveStart(onCancel: () -> Unit = {}, onStart: () -> Unit): () -> Unit`. 원래 동작을 보류할 시작 콜백을 돌려줌. 시작 전 매칭 화면의 취소는 앞 화면으로 돌아감 |
| 같은 파일 | `@Composable fun RunPowerSaveDialog(onSettings: () -> Unit, onStart: () -> Unit, onDismissRequest: () -> Unit)`가 `RunkkConfirmDialog`와 공용 문자열을 사용 |

안내 한 인스턴스는 화면 세션 하나와 시작 콜백 하나를 가진다. `isBatteryPromptShown`, `isBatteryPromptVisible`은 private Compose saveable 상태다. 원래 시작 처리는 `rememberUpdatedState`로 최신 콜백을 사용하며 저장 가능한 상태에 람다를 넣지 않는다. 상속, 싱글턴과 도메인 의존을 추가하지 않는다.

### 설계 결정과 화면 연결

| 번호 | 결정과 연결 지점 |
|------|------------------|
| [임시:D-성-900] | `RunPowerSaveSettings`는 `Settings.ACTION_BATTERY_SAVER_SETTINGS` → `Intent.ACTION_POWER_USAGE_SUMMARY` → `Settings.ACTION_APPLICATION_DETAILS_SETTINGS`와 `package:` URI 순으로 시도한다. 성공하면 뒤 후보는 열지 않는다. `ActivityNotFoundException`, `SecurityException`만 대체 처리하며 모든 Intent에 NEW_TASK를 붙인다. 배터리 사용량 화면 액션의 선언 위치는 [Android Intent 공식 문서](https://developer.android.com/reference/android/content/Intent#ACTION_POWER_USAGE_SUMMARY)로 확인 |
| [임시:D-성-901] | `rememberRunPowerSaveStart`는 요청 시 절전 상태를 읽고 안내가 필요하면 원래 행동을 보류한다. 중복 요청은 무시한다. 「그냥 시작」은 안내를 닫고 정확히 한 번 원래 행동을 실행한다. 화면 회전에도 안내를 본 상태를 보존한다. 설정을 여는 동안 안내를 유지하고 `LifecycleResumeEffect`에서 절전 해제를 확인하면 원래 행동을 이어 간다. 설정이 여전히 켜져 있으면 두 단추를 유지한다. 모든 설정이 없으면 원래 행동을 이어 간다. 바깥/뒤로가기는 닫기만 한다 |
| [임시:D-성-902] | `HomeRoute`의 `HomeEvent.StartRun` → 공용 콜백 → 기존 위치 권한/내비게이션. `MatchRoute` 초기 Quick/Invite → 공용 콜백 → `startQuick`/`startInvite`. Join의 조회 `startJoin`은 그대로 하고 참가하기 → 공용 콜백 → 기존 위치 권한 → `onAccept`. `SelfBattleRoute`와 `CelebBattleRoute`의 onStart → 공용 콜백 → VM.onStart. `CrewRunRoute`의 미준비 onReady → 공용 콜백 → onReadyToggle. 준비 해제는 직접 실행하며 이미 준비한 LOBBY 재진입은 공용 콜백으로 확인하되 준비 상태를 뒤집지 않음 |

`MatchEvent.Started`, `RecordBattleEvent.Start`는 측정 예약 후 사건이므로 안내 연결점이 아니다. 매칭 요청 전에 설정을 열어 `OnAppBackgrounded`의 기존 매칭 취소와 충돌하지 않게 한다. 크루런의 준비를 풀 때는 안내하지 않는다.

### 동적 모델과 의존

`출발 요청 → 절전 판정 → [꺼짐/이미 안내함: 원래 행동] 또는 [켜짐: 안내 보류] → 그냥 시작/설정 해제 복귀: 원래 행동, 닫기: 보류 취소`다. 안내 표시 시 이미 본 상태로 기록하여 기존 홈 동작을 유지한다. 기능 모델은 기존 DFD 2.2, 4.1, 4.6, 5.7.2에 출발 전 판정을 대응시킨다. 새 외부 단말이나 저장 자료가 없다.

`feature:home/battle/crew → core:ui`는 시작 람다만 전달한다. `core:ui → Android Settings/PowerManager`는 Intent와 절전 상태를 주고받는다. `core:ui`는 feature나 domain을 import하지 않는다. 기존 Gradle 의존과 구조 시험으로 의존 방향을 확인한다.

### 시험 먼저와 구현 순서

1. 기존 홈 시험에 절전 on/off와 세 단계 설정 기대값을 먼저 넣어 기존 동작의 실패를 확인한다.
2. 판정과 설정 시험을 공용 모듈로 옮기고, Compose 시험으로 보류/즉시 시작/재안내 방지/설정 복귀/닫기를 검증한다.
3. 실제 Route와 기존 VM/fake 저장소로 홈, 랜덤, 초대자, 수신자, 셀프, 셀럽, 크루 준비 호출 전에 안내가 오는지 시험한다. 절전 off와 준비 해제도 확인한다.
4. 공용 안내 문자열에 금지 표현과 줄바꿈이 없고 기존 홈 문자열이 제거됐는지 시험한다. 안내의 라이트/다크 기준 그림을 추가한다.
5. 판정/설정 → 공용 안내 → 각 Route 연결 순서로 구현한다. 지정 `ktlintFormat`, `ktlintCheck lintLocalDebug testLocalDebugUnitTest verifyRoborazziLocalDebug`를 실행한다. 새 안내 기준 그림은 `core:ui`만 기록하고 이유를 시험 11절에 남긴다.

자동 시험과 실제 제조사 설정 동작은 구분한다. 실기기에서 설정 제공 여부, 설정 복귀, 화면 꺼짐 상태 기록을 확인할 때까지 그것을 검증 완료로 쓰지 않는다.
