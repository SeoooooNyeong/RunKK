## 1. 결정 표

| ID | 출처 | 결정 |
|----|------|------|
| D-564 | CR-155, 272 AC-3·AC-9 | **코치 요청의 취소 구분.** CoachChatViewModel.ask는 일반 예외 복구 앞에서 `currentCoroutineContext().ensureActive()`로 요청 Job이 살아 있는지 본다. 실제 Job 취소(화면 종료·새 대화)는 상태를 쓰지 않고 전파하고, 흐름 자체의 CancellationException·내부 시간 초과는 기존 RETRY 복구(부분 답·대화 ID 유지)로 보낸다. D-453·D-474 보완이며 CoachRepository·CoachEvent·동의 판 계약은 그대로다 |
| D-565 | CR-156 | **매칭 이탈.** 랜덤 매칭 요청 중·대기 중·취소 중(REQUESTING·WAITING·CANCELLING)이나 성사 뒤 측정 시작 전(MATCHED)에 Activity가 멈추면(ON_STOP, 구성 변경 제외) 매칭을 접고 홈으로 간다. 홈 이동은 ON_STOP 안에서 바로 한다(이벤트로 미루면 그 사이 저장된 백스택에 매칭 화면이 남아 프로세스 종료 뒤 복원되며 매칭을 다시 요청한다). 대기열 취소가 ALREADY_MATCHED면 진행 중인 랜덤·고스트 대결을 찾아(1·2초 재시도) 기권하고, 성사 뒤면 회를 기록 없이 닫고 기권한다. 기권은 기기에 먼저 남기고 보내며 못 보내면 앱 시작·앞으로 올 때·새 매칭 요청 전에 다시 보낸다(1시간 기한). 친구 초대 대기는 제외(D-271) |
| D-566 | CR-157 | **대결 복귀.** 진행 화면이 앱 범위 OpenBattleScreen에 자기 키(Routes.BattleRunning)를 적는다. 앱 위 ActiveBattleViewModel은 앞으로 올 때와 맨 위 화면이 바뀔 때 열린 회의 키가 있고 맨 위가 그 화면이 아니면 「대결로 돌아가기」 안내를 띄운다. 대결 진행 알림은 대결 ID를 실은 PendingIntent로 MainActivity를 열고, 같은 회면 안내 없이 진행 화면을 연다 |
| D-567 | CR-158 | **워치 표시 요청.** 워치 → 폰 MessageClient 경로 `WearPaths.DISPLAY_REQUEST = "/runkk/display-request"`(본문 없음, 경로 13 → 14, DataClient 항목 아님). 워치 PhoneLink.start와 WatchFlowViewModel.onScreenShown(true)가 요청하고, 폰에 닿은 요청 뒤 2초 안의 요청은 건너뛴다(못 닿았으면 다음 요청에서 바로 다시). 폰은 매니페스트의 PhoneWatchListenerService가 받아(앱이 꺼져 있어도 깨움) WatchLink.onDisplayRequested가 그 노드를 닿는 노드로 등록하고 마지막 표시를 다시 보낸다(없으면 기본 대기 표시). 앱 안 리스너로 온 요청은 다시 보내지 않는다(중복 방지) |

## 4. 남은 위험

- D-565: 화면 꺼짐·다른 Activity가 위에 뜨는 것도 이탈로 본다. 재전송 기권이 출발 뒤에 도착하면 서버는 패배로 판정한다. Android 16 백그라운드 네트워크 제한으로 이탈 직후 기권은 자주 다음 복귀로 미뤄진다.
- D-566: 성사 뒤 진행 화면에 들어가기 전(카운트다운)에 밀어 닫으면 키가 없어 돌아가지 못한다.
- D-567: 근접·역전처럼 한 번만 오는 메시지는 다시 보내지 않는다. 폰 앱이 꺼져 있을 때 서비스가 깨어나는지는 실기기 확인(TC-4897)이 남았다.
