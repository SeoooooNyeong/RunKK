## 2. 배치와 망

```
브라우저 ─ nginx :443 /grafana/ ─ grafana ─┬─ 망 runkk_default ─ prometheus ─ api-<환경>:8081 (기존)
                                            ├─ 망 runkk_db-prod (internal)    ─ postgres-prod:5432    (프로젝트 runkk-prod의 postgres)
                                            └─ 망 runkk_db-develop (internal) ─ postgres-develop:5432 (프로젝트 runkk-develop의 postgres)
환경 스택 망(그대로): api ─ postgres ─ redis ─ ai ─ backup (runkk-<환경>_default), ai ─ avatar (runkk-<환경>_avatar)
```

| 망 | 만드는 스택 | 붙는 컨테이너 | 성격 |
|----|-------------|---------------|------|
| `runkk_db-prod` | 에지(`docker-compose.edge.yml`, 키 `db-prod`) | grafana, runkk-prod postgres(별칭 `postgres-prod`) | internal |
| `runkk_db-develop` | 에지(키 `db-develop`) | grafana, runkk-develop postgres(별칭 `postgres-develop`) | internal |

- 환경 스택(`docker-compose.yml`)은 망 키 `grafana-db`를 `name: runkk_db-${RUNKK_ENV}`, `external: true`로 둔다. 에지 배포가 늘 먼저 돌므로 망이 있다. 에지 스택에 이 변경이 들어가지 않은 브랜치(예: 이 변경 전의 main)로 에지를 맞추면 grafana가 DB 망에서 떨어진다. 에지 설정은 마지막으로 배포한 브랜치의 것이므로(README 3절) 운영 반영은 main까지 들어간 뒤다(7절).
- 이 변경이 처음 배포될 때 postgres 컨테이너는 망이 바뀌어 다시 만들어진다(볼륨 그대로). deploy.sh의 배포 직전 덤프 단계(`up -d --no-deps postgres backup`)에서 몇 초 끊긴다.

## 3. 구성 요소 명세

##### docker-compose.edge.yml (고침)
grafana에 `networks: [default, db-develop, db-prod]`와 환경 변수 `GRAFANA_DB_READONLY_PASSWORD`(기본 빈 값), `GRAFANA_DB_NAME_PROD`, `GRAFANA_DB_NAME_DEVELOP`(기본 `runkk`, 환경 .env의 DB_NAME과 같아야 함)을 더한다. 최상위 `networks`에 두 internal 망을 둔다. 기본 망 이름은 `runkk_default` 그대로다(compose config로 확인).

##### docker-compose.yml (고침)
postgres에 `networks: {default, grafana-db(aliases: postgres-${RUNKK_ENV})}`, 최상위 `grafana-db: {name: runkk_db-${RUNKK_ENV}, external: true}`. 다른 서비스는 바꾸지 않는다. postgres에 ports는 없다.

##### monitoring/grafana/runkk-db/readonly-role.sql (새 파일)
psql 스크립트. `\getenv`로 비밀번호를 읽고, 계정이 없으면 `\gexec`로 만들고, `ALTER ROLE`로 특권 없음과 연결 3개, 비밀번호, 계정 기본 설정(읽기 전용, 15초, 30초)을 맞춘다. 한 트랜잭션 안에서 이 계정의 표·열 권한을 모두 거두고 아래 목록을 준다. 몇 번 돌려도 결과가 같다.

| 표 | 열 | 쓰는 곳 |
|----|----|---------|
| event | 전체(개인정보 없음) | 이벤트 목록, 기간, 설정 |
| event_point_grant | 전체(회원 ID, 금액, 시각) | 지급 건수, 합계, 일별 |
| battle | id, type, status, opponent_kind, opponent_record_id, judged_at, winner_member_id | 셀럽 대결, 승리, 첫 승리 |
| run_record | record_id, member_id, started_at, distance_meters, valid | 거리 이벤트 응모 |
| member | id, nickname, status | 탈퇴 제외, 명단 닉네임 |
| celebrity_record | id, anonymous_name | 코치 가림 이름 |
| flyway_schema_history | version, success | 시각 자동 보정(V48 여부) |

스키마 public USAGE와 DB CONNECT만 더 준다. analytics 스키마(ai)는 USAGE가 없어 닿지 않는다. (다음 판 변경, 코드 리뷰 [임시:GF-성-3], [임시:GF-성-4]) 다시 맞출 때는 표·열 권한과 함께 이 계정의 역할 멤버십 전부(pg_read_all_data 같은 기본 역할 포함, 준 사람마다 `GRANTED BY`), 사용자 스키마 전부의 시퀀스 권한, 스키마 USAGE와 CREATE, 데이터베이스 권한을 거둔 뒤 위 목록과 public USAGE, CONNECT만 다시 준다. 손으로 준 권한이 배포 한 번으로 사라진다. 비밀번호 문장이 서버 로그에 남지 않게 스크립트 첫 부분에서 이 세션만 `log_min_error_statement = panic`, `log_statement = none`, `log_min_duration_statement = -1`로 둔다.

##### monitoring/grafana/runkk-db/datasources.yml, datasources-off.yml (새 파일)

### 4.2 공통 판정 SQL

모든 응모 패널이 같은 CTE를 쓴다(대시보드 JSON이 원본이고 아래는 그 사본). 주석은 대응하는 서버 코드다.

```sql
WITH cfg AS (
  -- 표시 보정 시간: 숫자가 아닌 값(auto)은 NULL이 되어 V48 여부로 정한다
  SELECT coalesce(CAST(NULLIF(regexp_replace('${tzfix}', '[^0-9]', '', 'g'), '') AS integer),
                  CASE WHEN EXISTS (SELECT 1 FROM flyway_schema_history WHERE version = '48' AND success) THEN 0 ELSE 9 END) AS shift_hours
),
ev AS (
  SELECT e.id, e.slug, e.title, e.kind, e.published, e.sort_order, e.starts_at, e.ends_at, e.config::jsonb AS cfg
  FROM event e WHERE e.id IN ($event)
),
coach_win AS (  -- BattleRepository.findCelebrityWinners: (회원, 셀럽)마다 첫 판정 시각
  SELECT ev.id AS event_id, b.winner_member_id AS member_id, b.opponent_record_id AS celebrity_id, min(b.judged_at) AS won_at
  FROM ev JOIN battle b
    ON b.status = 'FINISHED' AND b.type = 'CELEBRITY' AND b.opponent_kind = 'CELEBRITY'
   AND b.winner_member_id IS NOT NULL
   AND b.opponent_record_id IN (SELECT jsonb_array_elements_text(ev.cfg -> 'celebrityIds'))
   AND b.judged_at BETWEEN ev.starts_at AND ev.ends_at
  WHERE ev.kind = 'COACH_CELEB' GROUP BY 1, 2, 3
),
run_first AS (  -- RunQueryService.earliestValidRunsAtLeast: 기준 거리 이상 첫 유효 기록
  SELECT ev.id AS event_id, r.member_id, min(r.started_at) AS run_at
  FROM ev JOIN run_record r
    ON r.valid AND r.distance_meters >= CAST(ev.cfg ->> 'minDistanceMeters' AS bigint)
   AND r.started_at BETWEEN ev.starts_at AND ev.ends_at
  WHERE ev.kind = 'RUN_DISTANCE' GROUP BY 1, 2
),
entrant AS (  -- MemberQueryService.activeNicknames: ACTIVE이고 닉네임이 있는 회원만
  SELECT x.event_id, x.member_id, m.nickname, x.items, x.first_at
  FROM (SELECT event_id, member_id, count(*) AS items, min(won_at) AS first_at FROM coach_win GROUP BY 1, 2
        UNION ALL SELECT event_id, member_id, 1, run_at FROM run_first) x
  JOIN member m ON m.id = x.member_id AND m.status = 'ACTIVE' AND m.nickname IS NOT NULL
)
```

- 셀럽 기록 ID는 battle.opponent_record_id가 문자열이라 이벤트설정 배열을 `jsonb_array_elements_text`로 문자열로 펼쳐 비교한다(서버도 `String::valueOf`로 비교).
- 상태는 `(now() AT TIME ZONE 'Asia/Seoul') + 보정 시간`(저장 기준의 지금)을 저장된 기간과 비교한다. 연결 세션 시간대와 관계없다.
- 일별 패널은 `CAST(시각 - 보정 AS date)`로 한국 날짜를 정하고 `날짜 AT TIME ZONE 'Asia/Seoul'`(timestamptz)을 time 열로 돌려준다. 매크로 `$__timeFilter`에는 괄호 없는 열 이름(`days.t`)만 넘긴다.
- 대결과 승리(패널 5, 7)는 같은 회원의 여러 판을 모두 센다. 패널 7은 이벤트 둘이 같은 셀럽을 지정해도 대결마다 한 번 센다.
- 변수 값은 Grafana가 SQL에 그대로 넣는다. URL로 `tzfix`나 `event`에 다른 글자를 넣으면 SQL이 바뀔 수 있으나, 실행 계정이 읽기 전용 목록 권한이라 영향은 그 범위 안이다(6절).

| DB 상태 | 저장 값 | 개수, 응모 판정 | 자동 보정 | 화면 |
|---------|---------|------------------|-----------|------|
| develop(V48 적용, 2026-11-09) | 한국 시각 | 저장 값끼리 비교, 맞음 | 0시간 | 그대로 |
| 운영(2차 배포 V48 전) | 서버가 쓴 값과 이벤트 기간(임시 보정)이 모두 +9시간 | 저장 값끼리 비교, 맞음 | 9시간 빼기 | 한국 시각 |
| 운영(2차 배포 V48 뒤) | 한국 시각 | 맞음 | 0시간(저절로) | 그대로 |

한계: (1) 운영 V48 전에 운영자가 SQL로 한국 시각 그대로 넣은 값(+9를 하지 않은 값)이 있으면 그 행은 9시간 어긋나게 비교된다. 이벤트 기간은 임시 보정으로 +9가 되어 있어 해당하지 않는다. (2) event_point_grant.granted_at, battle.judged_at, run_record.started_at은 모두 서버가 JPA로 쓴 값이라 같은 기준이다. (3) 2차 배포 중 V48 적용과 대시보드 새로 고침이 겹치면 한 번은 이전 기준으로 보일 수 있다(5분 뒤 바로잡힘).

## 7. 배포와 운영 적용 절차

1. 사용자가 GitLab **Settings › CI/CD › Variables**에 `GRAFANA_DB_READONLY_PASSWORD`(Variable, masked, protected, 영숫자 16자 이상, 예: `openssl rand -hex 24`)를 넣는다. 이 MR 병합 전에 넣어 두면 병합 뒤 develop 자동 배포에서 바로 켜진다.
2. 이 MR을 develop에 병합한다 → develop 배포가 에지(DB 망 두 개, 데이터소스 두 개)와 develop postgres(망, 한 번 재생성)를 맞추고 develop DB에 계정을 만든다. 이때 `runkk-db-develop`만 붙고 `runkk-db-prod`는 연결 오류(운영 postgres가 아직 망에 없음)로 보인다.
3. 운영: 이 변경이 release를 거쳐 main에 들어간 뒤 prod 배포(수동 승인) 때 운영 postgres가 망에 붙고 운영 DB에 계정이 생긴다. 2차 배포(11/13, V36~V49)와 같은 배포면 V48 적용 뒤 자동 보정이 0시간이 된다. 그 전에 따로 운영에 넣으려면 hotfix로 main에 넣는 별도 결정이 필요하다(서버 이미지 변경이 없어 V48과 무관하다).
4. 주의: 이 변경이 main에 들어가기 전에 main(prod) 배포가 돌면 옛 에지 설정으로 grafana가 DB 망에서 떨어진다(develop 데이터소스도 끊김). 다음 develop 배포가 되돌린다. release/* 도 같다(다음 판 변경, 코드 리뷰 [임시:GF-성-6]): release/* 는 develop 환경(8443)에 자동 배포되므로 이 MR 병합 뒤에 자른다. 병합 전에 갈라진 release/* 에 push하면 옛 compose로 develop postgres가 다시 만들어져 DB 전용 망에서 떨어지고(재시작), grafana도 DB 망에서 떨어지며, 다음 develop 배포가 다시 만든다. 그 파이프라인의 옛 restore-check.sh는 develop 덤프 복구 시험에서 멈춘다(코드 리뷰 [임시:GF-성-1]).
5. 확인: Grafana 데이터소스 **Save & test**, 대시보드 이벤트별 응모자 수와 관리 API 응모자 명단(FR-319) 전체 수 비교.

## 9. 구현 지침과 남은 것

- 대시보드 SQL은 JSON 안에 있다. 응모 판정(EventService, EventEntrantService, FR-310, FR-319)을 바꾸는 변경 요청은 `runkk-event.json`의 공통 CTE와 3.3 권한 목록을 함께 고친다. 새 표나 열을 읽으면 readonly-role.sql에 더한다.
- develop 배포 뒤 확인(사용자 또는 다음 작업): develop DB에서 `BEGIN READ ONLY`로 4.2 쿼리를 실행하거나 Grafana 화면에서 숫자를 보고, 관리 API 응모자 명단 전체 수와 비교한다.
- 후속 후보: pg_hba로 DB 전용 망 대역은 runkk_grafana_ro만 받기, Grafana Viewer 계정 분리, 응모자 명단 CSV 내려받기(현재는 표 패널의 Inspect › Data).
