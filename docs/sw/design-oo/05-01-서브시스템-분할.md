## 5. 시스템 설계

### 5.1 서브시스템(패키지) 분할

분석 모델의 클래스를 같은 엔티티 생애주기끼리 묶었다(통신적 응집 이상). 서버 패키지 이름은 `com.a207.runkk.<패키지>`다.

#### 5.1.1 서버 패키지

v0.4는 design-review.md v0.3의 4차 개선(10.6)을 따른다. 핵심 패키지(조립·응용+도메인·도메인 공통) 14개에 표현·구동 하위 패키지 23개(web.* 14개, realtime, batch.* 8개), 인프라 하위 패키지 15개, 시작 패키지 1개를 더해 53개다. 핵심 14개와 그 사이 화살표는 v0.2와 같다. v0.3에서 바뀐 것은 web.admin을 운영자 확인(web.admin)과 기능별 관리 요청(web.admin.celebrity·setting·audit)으로 나눈 것(D-50)과, 구동 패키지를 실행 시각이 아니라 부르는 응용 패키지마다 하나씩 둔 것(D-39)이다. 구조를 이해할 때는 핵심 14개만 보면 되고, web.*·infra.*는 도메인 패키지를 따라가는 하위 패키지다.

v0.11은 61개다. 코드(feature/runkk-impl 45d33ae)는 위 53개에 batch.reward(리워드 적립 일 단위 보정, 코드 리뷰 2차 M4 결정)를 더한 54개이고, v0.11은 크루 채팅 crew.chat(D-101)과 신고 report(D-104) 두 응용+도메인 패키지, 그 표현·인프라 하위 패키지 web.chat·web.report·web.admin.report·infra.chat·infra.report 다섯을 더한다. 핵심 패키지(조립·응용+도메인·도메인 공통)는 16개(common을 빼면 15개), 표현·구동 하위 패키지는 27개(web.* 17개, realtime, batch.* 9개), 인프라 하위 패키지는 17개, 시작 패키지는 1개다. crew.chat의 실시간 메시지 record는 하위 이름 crew.chat.live에 두고 battle.live·crew.live처럼 상위 패키지로 합쳐 센다. 화살표는 12.2에 다시 셌다(140개 → 167개) (v0.11, CR34-02, D-101, D-104). 설계 검증(design-review.md 17장)에서 web.attempt(D-132), report.target(D-135), web.admin.ranking(D-136)을 더해 64개다: 핵심 17개(조립 profile·operator·report.target), 표현·구동 하위 29개(web.* 19개, realtime, batch.* 9개), 인프라 17개, 시작 1개. 화살표는 174개다 (v0.11 검증, D-132, D-135, D-136)

v0.34는 68개다. v0.14의 65개(batch.runimal)에 탈퇴 ai 자료 파기의 aiprivacy(응용+도메인), infra.aiprivacy, batch.aiprivacy 셋을 더했다(코드 develop 60c3385f ArchitectureTest PACKAGES 68과 같음). 05-19의 aicoach·runbody·aimodel·web.coach·web.runbody·web.admin.model은 아직 코드에 없어 세지 않는다. 얼굴 비동기(CR-154)는 기존 avatar·web.avatar·infra.avatar·infra.integration.ai 안의 변경이라 패키지 수가 그대로다 (v0.34, D-447 보정)

(다음 판 변경, [05-26](05-26-설계-이벤트-성.md) [임시:D-성-16]) 이벤트 기능이 응용+도메인 event와 그 하위 infra.event, web.event, web.admin.event 넷을 더해 72개다(핫픽스 main 기준 65 → 69, develop 68 → 72). 핵심 패키지에 event가 든다. 새 화살표는 event → battle, running, reward, audit와 하위 셋 → event다(12.4).

묶은 기준과 검토할 점:
- 응용 서비스와 도메인 객체를 같은 패키지에 두되 클래스 역할로 구분한다. 패키지를 엔티티별로 자르면 "회원을 바꾸는 일"이 한 패키지에 모인다.
- 표현·구동·인프라 계층도 기능(도메인)별 하위 패키지로 나눴다. "모두 컨트롤러라서", "모두 JPA 구현이라서" 묶으면 논리적 응집이 되어 한 도메인의 변경이 다른 도메인의 재시험으로 번진다(design-review.md 3.1). 설정 클래스는 그것이 설정하는 패키지에 둔다(SecurityConfig → web.auth, WebSocketConfig → realtime, 스케줄 설정 → batch.*). bootstrap은 컴포넌트 탐색 진입점이고 common.DomainEventPublisher를 Spring 사건 발행기로 구현하며, 개발·시험 프로필의 내장 Redis(EmbeddedRedisConfig)처럼 특정 도메인에 속하지 않는 프로세스 기반만 둔다. 도메인 시작 작업은 넣지 않는다(D-55). import는 common과 외부 라이브러리뿐이라 12.2 화살표는 그대로다(design-review.md E2, v0.8 CR-U08).
- 표현·구동 하위 패키지는 앱 탭, 클라이언트, 실행 시각이 아니라 부르는 응용 패키지 기준으로 나눈다(5.6 D-39). v0.2는 캐릭터 탭의 세 기능(Runimal, 아바타, 상점), "나" 탭의 알림함, 0시·20시 작업을 각각 한 패키지에 두어 논리적 응집이었다(design-review.md 9.3 V2·V7·V12). v0.3은 탭 단위 묶음을 풀었으나 web.admin(관리툴 클라이언트 단위)과 batch.tick·midnight·cleanup(시각 단위)이 남아 논리적·시간적 응집이었다(design-review.md 10.3 V8·V11·V12a·V13). v0.4는 web.admin을 운영자 확인만 하는 web.admin과 web.admin.celebrity·setting·audit으로(D-50), 구동 패키지를 batch.battle·crew·analysis·avatar·running·member·audit·notification으로 나눴다. 아바타와 상점은 보유 아이템·잔액을 함께 다뤄 web.avatar 하나에 둔다. 여러 패키지를 한 탭에 보이는 일은 앱 내비게이션이 맡는다.
- v0.1의 캐릭터 패키지는 runimal·avatar·reward로, 관리툴 패키지는 operator와 battle.CelebrityRecordService·policy.OperationSettingService로 나눴다(D-33, D-34). 구동 패키지 batch.<응용>은 그 응용 패키지의 시각 작업만 가진다. 작업 클래스는 응용 서비스 호출 하나만 가지고, 대상 선택 같은 업무 규칙은 응용 서비스가 갖는다(D-39, D-47). 실행 시각은 각 패키지의 …SchedulingConfig가 갖는다. 한 응용 패키지에 시각이 다른 작업이 여럿이면(batch.crew 1초·1분·0시 10분·0시 30분·3시, batch.member 3시 셋, batch.analysis 0시·20시) 같은 패키지 안에 작업 클래스를 따로 둔다. v0.11의 보정 작업(RewardReconcileJob·CrewRunLinkReconcileJob·TierReconcileJob·BackgroundReconcileJob, 모두 0시 10분)도 같은 규칙이라 batch.reward 하나만 새로 생겼다 (v0.11, CR34-02, D-107, D-108)
- web.admin.celebrity·setting·audit·report·ranking은 web.admin을 import하지 않는다. web.admin의 OperatorCheckInterceptor가 확인한 운영자 계정 문자열을 요청 속성 `actorId`로 붙이고, 다섯 컨트롤러는 `@RequestAttribute("actorId") String actorId`로 받는다(D-50). 속성 이름 "actorId"가 둘 사이의 계약이다 (v0.11, D-104) (v0.11 검증, D-136)
- crew 패키지가 가장 크다(v0.11에서 100개 가까이). 모두 Crew 엔티티의 생애주기(소속, 신청, 게시글·일정·공지·투표·사진, 크루런, 주간 거리·공동 목표)를 다룬다. 크루런을 나누면 crewrun ↔ crew 양방향 의존이 생겨 나누지 않는다(design-review.md 3.1 P9). 크루 채팅은 생애주기가 다른 고빈도 객체라 crew.chat으로 뗐다(D-101). crew.chat → crew 한 방향이고(CrewMembershipReader.relationOf·activeMemberIds), crew는 crew.chat을 import하지 않는다: 크루 삭제는 DB FK CASCADE로, 탈퇴는 crew.chat의 ChatWithdrawalListener가 MemberWithdrawn을 직접 받는다. 신고는 report에 두고, 조립 패키지 report.target이 crew·crew.chat의 신고용 공개 연산으로 report.ReportedContentPort를 구현한다. report는 crew·crew.chat을 모르고 crew·crew.chat도 report를 모른다(crew Fan-Out 8 → 7) (D-104, F.6.3) (v0.11, D-101, D-104) (v0.11 검증, D-135)
- profile과 operator는 도메인 객체를 갖지 않는 조립 패키지다(operator는 OperatorId 값 하나만 가진다). 다른 패키지를 읽기만 하고, 다른 도메인 패키지가 이 둘을 import하지 않는다. member가 crew·runimal·avatar를 import하면 순환이 생기기 때문에 프로필 조립을 member에서 뺐다. 공개 수준 판정(열람자와 대상의 관계 → SELF·PUBLIC·PRIVATE·WITHDRAWN)은 profile과 crew가 함께 쓰므로 member의 MemberQueryService.disclosureOf에 두고, profile은 수준별 항목 거르기만 한다(D-52). 관리툴 서비스는 operator를 import하지 않고, web.admin이 확인한 운영자 계정 문자열(actorId)만 받는다.
- common은 변경이 드문 불변 기본 형식(값 객체, 열거형, 오류 형식)만 둔다. 사건·포트·유틸 함수·설정을 넣지 않는다(쓰레기통 패키지 방지). DomainEvent·DomainEventPublisher는 형식 정의라 예외다. 이 조건이 깨지면 common은 다시 논리적 응집의 쓰레기통이 된다(design-review.md 6.3). v0.3에서 조건을 다시 점검했다(D-48): Timestamps는 불변 record로 두고 엔티티가 바꿔 끼운다. #### 5.1.2 앱·워치·ai 서버 모듈

v0.5부터 앱은 Clean Architecture 계층으로 나눈다(D-56). **domain.\*은 순수 Kotlin**(Android·Retrofit·Room·Hilt 애너테이션 import 0)이고 업무 규칙, 도메인 모델, 포트(Repository·Gateway 인터페이스), UseCase를 가진다. **데이터 계층(api.\*, data.\*)**은 domain이 정의한 포트를 구현하고 DTO·엔티티를 도메인 모델로 바꾼다. **표현 계층(ui.\*)**은 domain의 UseCase·포트만 부르고 api.\*·data.\*를 import하지 않는다. **app**은 조립 루트(Hilt)다. 의존은 ui·data → domain → core.model 한 방향이다. v0.4의 앱 모듈(app.run, app.store …)은 아래 표의 "v0.4" 열처럼 옮겼다.

v0.1의 app.ui(화면 30종)와 app.api(모든 REST 인터페이스)는 "종류가 같아서" 모인 논리적 응집이었다(design-review.md 8.2). 화면은 기능별 ui.\*로, REST는 기능별 api.\<기능\>과 공통 연결 api.core로 나눈 뒤 v0.5에서 api.\<기능\>이 그 기능의 도메인 포트 구현을 맡는다. 도메인 포트를 계층별 단일 패키지(domain 하나에 모든 포트)로 모으지 않고 기능별 domain.\<기능\>으로 둔 이유도 같다. Gradle 빌드 단위(13.2)는 이와 따로 정하고, 패키지 사이 방향은 아래 표를 Konsist 구조 시험으로 지킨다. 한 탭에 여러 모듈의 화면을 보이는 일은 app의 RunkkNavHost가 맡는다. 각 ui.\* 모듈이 FeatureEntry를 Hilt @IntoSet으로 등록하고 RunkkNavHost는 Set\<FeatureEntry\>만 받으므로 app의 코드는 ui.\*를 import하지 않는다. 화면 사이 이동은 core.navigation.Routes의 경로 이름으로 한다(design-review.md M35).

앱 모듈 사이 의존(주고받는 것)과 Fan-Out. 표는 코드 import 기준이다. Gradle의 implementation 선언(조립 루트 app이 Hilt 집계를 위해 모든 모듈을 가진다)은 빌드 배선이라 세지 않는다.

설계 규칙:
- 포트가 하나뿐인 단순 조회(대시보드, 기록 목록, 상점 등)는 ViewModel이 domain의 Repository 인터페이스를 직접 부른다. 두 개 이상의 포트를 순서대로 묶는 흐름만 UseCase로 둔다(로그인, 로그아웃, 탈퇴, 설정 변경, 보관 기록 전송, 파기 지시 동기화). UseCase를 기계적으로 만들지 않는다.
- 화면은 DTO·Room 엔티티를 받지 않는다. api.\<기능\>·data.store가 도메인 모델로 바꿔 넘긴다.
- 화면용 도메인 모델의 이름은 서버 조회 결과 이름에서 `View` 접미어를 뺀 것이다(DashboardView → Dashboard, GrowthView → Growth). 서버에 같은 이름이 없거나 앱 안에서 이미 쓰는 이름과 겹치면(서버 RunDetail ↔ 앱 RecordDetail) 화면 기준 이름을 쓰고 api 매퍼 KDoc에 서버 형식 이름을 적는다(v0.8, CR-U22, D-78).
- 앱 쪽 거부 사유 코드 상수는 그 사유를 내는 domain.\<기능\>에 둔다(예: 늦은 심박 RECORD_NOT_FOUND는 domain.run의 포트 계약). 서버 사유 코드는 문자열 그대로 Rejected(code)에 담고 상수로 다시 정의하지 않는다. 여러 기능이 함께 내는 사유(LOCATION_CONSENT, RUN_IN_PROGRESS, SIGN_UP_REQUIRED)만 core.model.AppError.Rejected에 둔다(v0.8, CR-U21).
- 오류는 Outcome\<T\>/AppError로 올라온다. ApiErrorMapper가 HTTP·네트워크 오류를, 각 Repository 구현이 저장 오류를 AppError로 바꾼다.
- 코루틴 범위: ViewModel은 viewModelScope, MeasurementService는 LifecycleService의 lifecycleScope, 앱 시작 작업은 app의 applicationScope(SupervisorJob)에서 돈다. 대결·크루런 조정자는 매칭(onMatched)·기록 대결 시작(onRecordBattleStart)·크루런 대기 진입 때 주입받은 applicationScope 아래에 자기 범위(SupervisorJob)를 만들고 endRun 뒤 취소한다. 그래서 화면 회전·화면 이탈에 끊기지 않고, 측정 서비스가 시작되기 전(매칭 화면)부터 동작한다. MeasurementService는 측정 중 프로세스를 살려 두는 일만 한다(design-review.md M44). GlobalScope를 쓰지 않는다.
- 바인딩: 포트 ↔ 구현 바인딩(Hilt @Binds·@Provides)은 구현이 있는 모듈의 Hilt 모듈(`@Module @InstallIn(SingletonComponent::class)`)이 한다. 예: api.account의 AccountBindings, data.store의 StoreBindings. app은 포트 ↔ 구현 바인딩을 갖지 않으므로 데이터 모듈을 import하지 않는다. app이 내주는 것은 applicationScope(AppScopeModule, 처리되지 않은 예외를 기록하는 CoroutineExceptionHandler 포함) 하나다. RunTracker·두 조정자가 주입받는 `java.time.Clock`(Clock.systemUTC())은 측정 시각이 기기 기능이라 data.device의 DeviceBindings가 하나만 내준다(v0.8, CR-U13, CR-U24). domain.\*의 UseCase·RunTracker·조정자는 `javax.inject.Inject`(JSR-330, Android·Hilt 아님) 생성자 주입만 쓰고, 상태를 가진 객체(RunTracker, BattleRunCoordinator, CrewRunCoordinator, PushTokenSync)는 `@javax.inject.Singleton`이다. 한정자를 만들어야 하면 domain에 둔다(D-61, design-review.md R30·M49).
