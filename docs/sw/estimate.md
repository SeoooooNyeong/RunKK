판정
- 마감이 외부 사건(11/18 발표, 11/23 본선, 12/01 전시)에 묶여 있다. 기간 압축을 5절에서 따로 계산한다.
- 하드웨어 성능은 비용 결정 요소로 올리지 않는다. 시험 기기·워치 확보는 환경 비용(6절)과 일정 위험으로만 다룬다.
- 생산성 요소에는 개발자 능력, 팀워크, 제품 복잡도만 넣는다. 최종 사용자(러너)의 능력은 넣지 않는다.
- 주 80시간 근무는 비용 결정 요소가 아니라 가용 노력의 조건이다(A-3). 같은 일을 하는 데 드는 노력(PM)은 바뀌지 않고, 이를 소화할 수 있는 기간 안의 인일만 늘어난다.

## 2. 사용 기법

| 역할 | 기법 | 선택 이유 |
|------|------|-----------|
| 규모 산정 1 | 기능 점수(FP) → LOC 환산 | 과거 데이터가 없고 기능 목록(3.1)이 명확하다. 언어가 셋(Kotlin·Java·Python)이라 언어 독립 척도가 필요하다 |
| 규모 산정 2 | LOC 3점 추정 (실행 단위·모듈별) | 기능 점수 환산을 상향식으로 확인한다 |
| 노력 산정 1차 | COCOMO Basic·Intermediate | 공식 모델로 산업 기준 노력을 남긴다. 조직 실측이 없으므로 Intermediate로 인력·도구·일정 요인을 반영한다 |
| 노력 산정 교차 | Effort per Task (기능·단계별 인일 3점 추정) | 마감과 팀 인원이 고정된 프로젝트라 구간별 가용 노력과 바로 비교할 수 있다. `sw-schedule`에 단계·역할별 노력을 넘긴다 |
| 하향식 | 델파이 | plan.md에 전문가 추정이 없어 이번 판에서도 **미실시**. 4.3에 실시 방법과 기록 양식을 둔다 |
| 미사용 | LOC ÷ 조직 생산성, Putnam | 조직 실측 생산성이 없다(A-1). Putnam은 대규모·장기 인력 곡선용이라 7주 6명 프로젝트에는 과하다. 기간 압축의 방향성만 5절에서 인용한다 |

판정 기준(규모 1개 이상, 노력 2개 이상)은 규모 2개(FP, LOC 3점), 노력 2개(COCOMO, Effort per Task)로 충족한다.

### 3.3 재사용 반영

등가 LOC = 재사용 LOC × (0.4 × 설계 수정 비율 + 0.3 × 코드 수정 비율 + 0.3 × 통합 노력 비율)

| 모듈 | 재사용 LOC | 수정 비율 | 등가 LOC |
|------|-----------|-----------|----------|
| 1.6 위치 기반 기록 스파이크 코드(공식 샘플 기반) | 600 (가정) | 설계 20%, 코드 50%, 통합 30% → 32% | 192 |
| 프레임워크·SDK(Spring Boot, Spring WebSocket, Compose, FastAPI, Kakao 지도, Firebase) | LOC 미산입(A-8) | 통합 노력은 4.4 인프라·각 기능 인일에 포함 | 0 |
| 합계 | 600 | | **192** |

3.2 신규 33,650 + 등가 192 = 33,842 LOC ≈ 33.8 KLOC

### 3.4 규모 확정

| 방법 | KLOC |
|------|------|
| 기능 점수 환산 | 29.9 |
| LOC 3점 + 재사용 등가 | 33.8 |
| 차이 | 13.3% (기준 20% 이내) |
| 확정 | **33.8 KLOC** (낙관 21.8 ~ 비관 49.7) |

v0.1에서는 두 값이 22.6% 차이 났다(21.7 대 26.6 KLOC). 이번에는 새로 들어온 기능(크루런, 알림함, 결과·비교 화면, 관리툴)이 대부분 앱과 서버를 모두 거치는 트랜잭션이라 기능 점수가 더 크게 늘어 차이가 줄었다. 남은 차이는 v0.1과 같은 원인(2계층 중복 구현, 플랫폼 코드, Kotlin 계수 가정)이다.

확정은 3점 추정 값으로 한다. 실행 단위별로 분해되어 있어 `sw-schedule`의 역할 배분에 바로 쓸 수 있다. 범위는 3점 추정의 낙관·비관 합에 재사용 등가 192를 더한 값이다.

차이 설명

기법 간 차이가 30%를 크게 넘는다(최소 13.3 대 현대 보정 COCOMO 최소 38.7, 2.9배). 원인은 v0.1과 같은 입력 가정의 차이다.
1. **생산성 가정.** 상향식 13.3 PM이 성립하려면 약 2,540 LOC/PM이 필요하다(4.1). COCOMO는 이 규모의 산업 프로젝트 생산성을 이보다 훨씬 낮게 본다. 어느 쪽이 이 팀에 맞는지는 실측(7.1)으로만 가릴 수 있다.
2. **품질·문서 수준.** COCOMO는 인수 시험과 정식 문서를 갖춘 산업 납품을 전제로 한다. 이 프로젝트는 베타 20명과 발표·전시가 목표이고, 인수 기준(plan.md 8.1)이 산업 납품보다 가볍다.
3. **분석·테스트 과소 가능성.** 상향식의 구현 비율 60%는 40-20-40과 크게 다르다. 같은 구현량을 40-20-40으로 늘리면 36.8 PM이 된다.
4. **앵커링 가능성.** 상향식은 plan.md의 단계 일정을 보고 작업을 나눴다. 그래서 가용 노력과 비슷한 값이 나왔을 수 있다. 이 편향을 걸러내는 것이 4.3 팀 델파이의 목적이다.

확정값 선택: 팀 인원과 기간이 바뀌지 않는 제약이므로, 일정 판정에는 구간·역할별로 나눌 수 있는 상향식 값 13.3 PM을 쓴다. 공식 모델 값(약 37 PM 이상)은 "산업 기준이라면 주 80시간 가용 노력의 2배 이상"이라는 상한 경고로 기록한다. 실측 생산성이 4.1의 필요치에 못 미치면 확정값을 비관 쪽(19.3 PM 이상)으로 옮긴다.

- **예비비 30%의 근거.** plan.md 2.2의 예비비 원칙(합계의 약 30%)을 따른다. 현금 위험은 R-018(예산 초과, 확률 낮음·영향 경미), 아바타 API 단가 불확실성(R-003)과 재생성 허용(A-9), 날씨 API 무료 한도(R-031)다. 상위 위험(R-005, R-008, R-009, R-019, R-023, R-024, R-027, R-028)은 일정·인력 위험이라 현금으로 막을 수 없다. 이들은 5.2의 범위 버퍼와 인력 재배치로 대응한다.
- **plan.md 2.2 합계(70,000~160,000원)와 다른 이유.** plan.md는 아바타 생성 API를 예비비 안에서 흡수했다. 이 산정서는 환경 비용으로 따로 넣고 상한을 올렸으며(A-9) 예비비를 별도로 잡아 비관치가 217,100원으로 높아졌다. 그래도 예산 안이다.
- **확인 필요 항목.** 워치 대여료(개인 기기가 없을 때), 전시 포스터 인쇄비는 plan.md 2.2 표에 없다. 생기면 환경·간접비에 더한다. 비관치 기준 여유는 82,900원이다.
- 기간 압축은 이 프로젝트에서 현금 비용이 아니라 노력 부족과 장시간 근무(5절)로 나타난다. 인건비를 쓰지 않으므로 압축 비용을 돈으로 바꿔 흡수할 수단이 없다.
