# 프로젝트 팀 구성 방식

`sw-schedule` 절차 6에서 읽는다. 팀 구성 계획의 목적은 각 팀원의 역할과 책임, 협력 방식을 명확히 정하는 것이다. 프로젝트 성격과 규모에 따라 방식이 다르다.

## 1. 세 가지 방식 비교

| 항목 | 분산형 (민주적 팀) | 중앙집중형 (책임 프로그래머 팀) | 계층형 |
|------|-------------------|-------------------------------|--------|
| 의사결정 | 모든 구성원 참여 | 책임 프로그래머 1명 | 소그룹 리더 → 프로젝트 리더 |
| 의사소통 구조 | 링(Ring). 모두 동등하게 연결 | 별(Star). 리더 중심 | 트리(Tree) |
| 경로 수 (n명) | n(n−1) ÷ 2 | n − 1 | 그룹별 n−1의 합 + 리더 간 |
| 속도 | 느림 | 빠름 | 중간 |
| 적합 규모 | 소~중, 장기 | 소규모 | 대규모 |
| 적합 상황 | 복잡하고 장기, 구성원 수준 비슷 | 고급 1명 + 중급 여럿, 기한 촉박 | 초급 다수, 단계적 관리 |
| 장점 | 참여도·만족도 높음, 이직률 낮음 | 결정 빠름, 경로 적어 효율적 | 큰 규모를 단계적으로 관리 |
| 단점 | 결정 오래 걸림, 책임 분산 | 리더 1인 능력에 좌우, 팀원 의견 반영 어려움 | 기술 인력이 관리에 묶여 기술력 묻힘 |

## 2. 분산형 (Democratic Team)

- 민주주의식 운영. 의사결정에 모두 참여한다.
- 의사소통 경로 수: n명이면 **n(n−1) ÷ 2**
  - 3명 3개, 4명 6개, 5명 10개, 6명 15개, 8명 28개, 10명 45개
- 경로가 15개(6명)를 넘으면 회의 비용이 급격히 늘어난다. 그 이상이면 계층형으로 소그룹을 나눈다.
- 복잡하고 장기적인 프로젝트에서 구성원의 지속적 참여가 중요할 때 고른다.

## 3. 중앙집중형 (Chief Programmer Team)

책임 프로그래머 1명이 모든 의사결정을 한다. 소규모 프로젝트, 기한이 촉박한 프로젝트에 맞다. 성공이 리더의 능력에 달려 있으므로 리더는 반드시 고급 인력이어야 한다.

### 역할 네 가지

| 역할 | 책임 | 하지 않는 것 |
|------|------|-------------|
| 책임 프로그래머 | 요구분석, 설계, 중요 기술 판단, 작업 지시, 핵심 모듈 구현 | 문서 정리 같은 보조 업무 |
| 프로그래머 | 리더 지시에 따라 코딩, 단위 테스트, 디버깅, 모듈 문서 작성 | 아키텍처 결정 |
| 보조 프로그래머 | 리더 보조, 사용자 의견 수렴·전달, 자문, 리더 부재 시 대행 | 요구분석·설계·기술 판단의 주도 (책임 프로그래머 몫) |
| 프로그램 사서 | 프로그램 목록, 설계 문서, 테스트 계획·결과, 형상 관리, 회의록 관리 | 코딩 |

### 선택 예

"고급 프로그래머 1명과 중급 프로그래머 여러 명"이면 중앙집중형이다. 고급 1명이 지휘하고 중급이 구현한다.

## 4. 계층형 (Hierarchical Team)

- 분산형과 중앙집중형의 혼합.
- 초급 프로그래머를 **5 ~ 7명씩 소그룹**으로 묶고, 각 소그룹을 고급 프로그래머가 관리하며, 전체를 프로젝트 리더가 총괄한다.
- 규모가 큰 프로젝트에서 단계적 관리가 쉽다.
- 단점: 고급 기술 인력이 관리 업무에 집중되어 기술력이 묻힐 위험이 있다. 소그룹 리더에게 기술 시간을 보장한다.

## 5. 선택 절차

1. 팀 규모와 경력 분포를 적는다 (고급 / 중급 / 초급 인원).
2. 프로젝트 기간과 기한 압박을 적는다.
3. 아래 순서로 묻는다.
   - 10명 초과이거나 초급이 과반인가? → 계층형
   - 고급 1명 + 나머지 중급·초급이고 소규모인가? → 중앙집중형
   - 구성원 수준이 비슷하고 장기이며 참여·유지가 중요한가? → 분산형
   - 어느 것도 아니면 → 중앙집중형 (기본값. 소프트웨어 프로젝트 대부분이 소규모·기한 압박)
4. 선택 이유를 한 문장으로 적는다.
5. 역할표를 만들고 WBS 활동 담당과 연결한다.

| 이름 | 역할 | 경력 | 담당 WBS | 비고 |
|------|------|------|----------|------|
| | 책임 프로그래머 | 고급 | | |

## 7. Brooks 법칙과 조직

"지연된 프로젝트에 인력을 추가하면 더 지연된다." 이유는 세 가지다.
1. 새 인원의 적응 기간
2. 기존 인원이 교육에 쓰는 시간
3. 의사소통 경로 증가 (분산형이면 n(n−1)/2로 급증)

조직 계획은 **처음부터** 필요한 인원을 정확히 예측해 투입하는 것이다. 후반 증원은 계획에 넣지 않는다. 지연 대책은 범위 축소 우선순위다.
