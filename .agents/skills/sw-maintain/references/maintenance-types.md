# 유지보수 유형, 절차, 부작용

## 1. 유지보수란

소프트웨어가 인수·설치된 후에 수행되는 **모든 공학적 수정 작업**이다.

- 생명주기 중 가장 길고, **비용이 개발 단계보다 크다**. 전체 생명주기 비용의 과반이 여기서 든다.
- 목적은 소프트웨어의 안정성·신뢰성을 유지하고 장기적으로 쓸 수 있게 하는 것이다.
- 유지보수는 **설계를 다시 만드는 활동이 아니다**. 설계를 바꿔야 하면 그것은 개선 보수이고, 요구사항 단계로 돌아가는 것이다.

## 2. 네 유형

| 유형 | 영어 | 원인 | 요구사항 변화 | 비용 비중 | 예 |
|------|------|------|---------------|-----------|----|
| 수정 보수 | Corrective | 테스트에서 못 잡은 오류가 운영 중 발견 | 없음 | 낮음 (약 20%) | 90점이 B로 표시됨 |
| 적응 보수 | Adaptive | OS·DB·브라우저·하드웨어·연동 시스템 등 **운영 환경** 변화 | 없음 (운영 환경 절만) | 중간 (약 25%) | Windows 11에서 PDF 한글 깨짐 |
| 개선 보수 | Perfective | 사용자 요청에 따른 기능 추가·변경, 성능·사용성 향상 | **있음** | **가장 높음 (약 50%)** | 모바일 성적 조회 추가 |
| 예방 보수 | Preventive | 장래 오류·비용을 줄이기 위한 구조 개선, 문서화, 재공학 | 없음 | 중간, 장기 회수 | 복잡도 15 함수 분할, 역공학 문서화 |

개선 보수가 가장 비싼 이유: 기능 추가·확장은 개발 이후 가장 자주 요청되고, 요구사항 → 설계 → 구현 → 테스트를 다시 거치며, 기존 구조에 끼워 넣어야 해서 신규 개발보다 제약이 많다.

## 3. 분류 질문표

위에서부터 묻고 먼저 "예"가 나오는 것이 유형이다. 순서가 중요하다. 환경이 바뀌어 드러난 잠재 오류는 1번에서 걸려 수정 보수가 되는 것이 맞다 (환경이 아니라 코드가 원인).

| 순서 | 질문 | 유형 |
|------|------|------|
| 1 | 요구사항과 운영 환경은 그대로인데, 동작이 명세(SRS·설계서)와 다른가 | 수정 |
| 2 | 요구사항은 그대로인데, 운영 환경이 바뀌어서 안 되는가 (바뀌기 전에는 됐는가) | 적응 |
| 3 | 요구사항이 바뀌는가 (새 기능, 기능 변경, 성능·사용성 목표 상향) | 개선 |
| 4 | 지금은 문제가 없지만 장래를 위해 구조·문서를 개선하는가 | 예방 |

구분이 어려운 경우:

| 상황 | 판정 | 이유 |
|------|------|------|
| "느려졌어요" (환경 변화 없음, NFR은 원래 만족했음) | 수정 | 성능 저하는 오류 |
| "느려요" (원래부터 NFR 경계였고 더 빠르게 해 달라) | 개선 | 목표 상향 |
| "DB를 Oracle에서 PostgreSQL로 바꿨더니 안 돼요" | 적응 | 환경 변화 |
| "DB를 바꿀 예정이니 미리 DB 종속 코드를 한 곳에 모아 두자" | 예방 | 장래 대비 |
| "오류 메시지가 불친절해요" | 개선 | 사용성 요구 변경 |
| "오류 메시지가 틀린 정보를 보여 줘요" | 수정 | 명세와 다름 |

## 4. 유지보수 절차

```
1. 유지보수 요구 확인 ─▶ 2. 기존 시스템 이해 ─▶ 3. 코드 수정 ─▶ 4. 수정 후 테스트
   CR 접수, 분류, 재현      SRS·설계서·추적표·      최소 범위,       원인 확인 TC +
                            의존 행렬로 영향 범위    변경 통제        회귀 테스트
```

비용은 2번에 가장 많이 든다. 산출물(SRS, 설계서, 추적표, 의존 행렬)이 있으면 2번이 짧아지고, 없으면 코드를 읽어 복원해야 한다. 이것이 개발 단계에서 문서를 만드는 이유이자 역공학이 필요한 이유다.

## 5. 유지보수의 문제점

| 문제 | 결과 | 예방 (개발 단계) | 대응 (유지보수 단계) |
|------|------|------------------|----------------------|
| 개발자 이직, 인수인계 부족 | 코드 의도를 아무도 모름 | 설계서·주석에 "왜" 기록 | 역공학 |
| 문서화 부족 | 코드 해석에 시간 소모 | 추적표 유지 | 재문서화 |
| 잦은 변경으로 구조 혼란 | 결합도 상승, 응집도 하락 | 변경 통제, 설계 기준 준수 | 재구성 |
| 변경의 부작용 | 고친 곳 외의 기능이 깨짐 | 낮은 결합도, 회귀 테스트 | 부작용 3종 점검 |

## 6. 부작용 세 종류

| 부작용 | 정의 | 전형적 사례 | 점검 |
|--------|------|-------------|------|
| 코딩 부작용 | 코드 변경이 다른 코드의 동작에 영향 | 공용 함수의 반환 형식을 바꿔 호출자 3곳이 깨짐 | Fan-In 모듈의 TC 회귀, 비교 검사 |
| 자료 부작용 | 자료 구조·형식·값 범위 변경이 다른 모듈에 영향 | 점수 필드를 정수에서 실수로 바꿔 등급 계산이 틀어짐. 파생 통계가 갱신 안 됨 | 자료사전 대조, 파생 데이터 목록 |
| 문서화 부작용 | 코드는 바뀌었는데 SRS·설계서·매뉴얼·주석이 그대로 | 매뉴얼에는 10자리 학번, 코드는 12자리 | 문서 갱신 체크리스트 |

문서화 부작용은 당장 시스템을 깨뜨리지 않아서 가장 자주 방치된다. 그러나 다음 유지보수의 "기존 시스템 이해" 단계에서 틀린 문서는 문서가 없는 것보다 나쁘다.

## 7. 외계인 코드 (Alien Code)

너무 오래되고 문서가 없어 **누가 만들었는지도 모르고 이해하기도 어려운 코드**다. 통상 15년 이상 된 시스템에서 말하지만, 연차가 기준이 아니라 상태가 기준이다.

판정 (둘 이상 해당):
- 설계 문서·주석이 없거나 코드와 다르다
- 작성자가 불명이거나 퇴사해 물어볼 수 없다
- 장기간 수정되지 않아 현재 팀 누구도 건드려 본 적이 없다

유일한 방지책은 **문서화**다. 이미 외계인 코드가 되었으면 역공학으로 최소한의 설계 정보를 복원한 뒤에 수정한다. 복원 없이 수정하면 부작용을 예측할 수 없다.

## 8. 유형별 버전 번호 규칙

| 유형 | 버전 | SRS 변경 |
|------|------|----------|
| 수정 | PATCH (1.0.0 → 1.0.1) | 없음 |
| 적응 | PATCH 또는 MINOR (지원 환경 목록이 바뀌면 MINOR) | 운영 환경 절만 |
| 개선 | MINOR (1.0 → 1.1). 호환성 깨지면 MAJOR | 요구 항목·추적표 갱신, 버전 올림 |
| 예방 | PATCH | 없음 (역공학 복원분은 "복원" 표시로 추가) |

## 9. 용어 대조

| 강의 표현 | 이 문서 |
|-----------|---------|
| Corrective(수정·하자 보수) / Adaptive(적응) / Perfective(완전화·기능 개선) / Preventive(예방) | 2절 네 유형 |
| CAPP | 네 유형 영어 머리글자 |
| Perfective가 비용 최대 (약 50%) | 2절 |
| 유지보수 요구 확인 → 기존 시스템 이해 → 코드 수정 → 수정 후 테스트 | 4절 |
| 코딩 / 자료 / 문서화 부작용 | 6절 |
| 외계인 코드, 방지는 문서화 | 7절 |
| 유지보수 목적 중 부적절한 것: 설계 보수 | 1절 마지막 |
| 유지보수 비용 > 개발 비용 | 1절 |
