# 재공학(Reengineering)과 역공학(Reverse Engineering)

## 1. 재공학이란

기존 시스템을 **완전히 버리지 않고**, 그 시스템을 기반으로 새로운 요구와 기술 변화에 맞도록 **개선·강화**하는 활동이다. 낡고 비효율적인 시스템을 사라지기 전에 개조해 재활용하고, 유지보수가 쉽고 성능이 나아지고 수명이 연장되도록 만든다.

재공학은 **예방 보수(Preventive Maintenance)** 에 해당한다. 지금 당장의 오류를 고치는 것이 아니라 앞으로의 유지보수를 쉽고 싸게 만들기 위한 투자다.

## 2. 왜 필요한가

| 이유 | 설명 |
|------|------|
| 완전 교체는 더 낫다는 보장이 없다 | 새 시스템이 기존보다 불편하거나 기능이 빠질 수 있다 |
| 사용자 경험이 축적되어 있다 | 기존 시스템에 익숙한 사용자를 재교육하는 비용과 시간 |
| 호환성 보장이 없다 | 새 시스템이 기존 데이터·프로세스·연동 시스템과 완벽히 맞는다는 보장이 없다 |
| 완전 교체 비용이 크다 | 처음부터 다시 만들면 비용·기간·위험 부담이 매우 크다 |
| 유지보수 문제 | 가장 큰 이유. 수정 비용이 계속 오르는 시스템을 살리는 방법 |

소프트웨어 위기를 **개발 생산성**이 아니라 **유지보수 생산성**으로 해결하려는 접근이다.

## 3. 목적

핵심 목적은 하나다: **유지보수를 더 쉽고 싸게 만든다.**

구체적으로:
1. 유지보수성 향상 (코드를 이해하기 쉽게 재구조화)
2. 기술 향상 (더 나은 언어·프레임워크·버전으로 부분 개선)
3. 소프트웨어 수명 연장
4. 유지보수 비용 절감
5. 품질 향상 (오류 감소, 성능 향상)
6. 재사용 가능성 증가 (결과이지 활동이 아님)

재공학의 목표가 **아닌** 것: 기존 시스템의 보안 취약점을 찾아 침입(해킹)하는 것, 개발 생산성 향상 자체, 기능 추가(그것은 개선 보수).

## 4. 특징

- 예방 보수 활동이다
- 자동화 도구(CASE, 정적 분석기, 코드 변환기, 의존도 추출기)를 적극 활용한다
- 기존 시스템을 버리지 않는다
- 기존 기능은 유지하면서 구조를 개선한다
- 장기 전략이며 많은 비용·시간·자원을 요구한다
- 결과적으로 오류가 줄고 성능이 향상되고 수명이 연장된다

## 5. 네 가지 활동

순서가 있다. 역공학은 분석 단계의 도구로 먼저 쓰이기도 하므로 실제로는 1 → 4 → 2 → 3 순서로 돌 때가 많다.

### 5.1 분석 (Analysis)

- 기존 시스템의 동작 방식과 명세를 확인한다
- 현재 시스템이 어떤 기능을 하는지 **이해**한다
- 재공학 대상(개선할 모듈)을 정한다. 기준: 수정 CR 반복 빈도, 외계인 코드 판정, 결합도·복잡도 지표
- 산출물: 대상 모듈 목록, 현재 지표(결합도·응집도·순환 복잡도·CR당 평균 소요)

### 5.2 재구성 (Restructuring)

- **기능은 그대로 두고 내부 구조만 개선**한다. 이것이 재구성의 정의이자 제약이다
- 코드 정리, 들여쓰기, 함수 분리, 변수명 정리, 중복 제거, 결합도 낮추기, 응집도 높이기
- 동작이 바뀌면 재구성이 아니다. 비교 검사(수정 전후 같은 입력 → 같은 출력)로 기능 불변을 **증명**해야 한다
- 산출물: 재구성된 코드, 비교 검사 결과(일치율 100%), 전후 지표

### 5.3 이식 (Migration)

- 운영 환경을 옮긴다: OS(Windows → Linux), 하드웨어, DB(Oracle → PostgreSQL), 언어·프레임워크 버전, 클라우드
- 환경 변화에 맞춰 옮기는 작업이므로 적응 보수와 겹친다. 차이는 재공학의 이식은 **구조 개선과 함께** 계획적으로 수행한다는 점이다
- 이식 전에 환경 종속 코드를 한 곳(인프라 계층)에 모아 두면(재구성) 이식 범위가 그 계층으로 한정된다
- 산출물: 새 환경 실행 결과, 이전 환경과의 비교 검사

### 5.4 역공학 (Reverse Engineering)

- 완성된 프로그램(코드)에서 설계도·명세·구조도를 **거꾸로 복원**한다
- 구현 수준에서 추상화 수준으로 올라간다: 코드 → 모듈 구조 → 설계 → 요구
- 가장 오래된 형태는 **재문서화(Redocumentation)**: 코드를 읽어 문서를 만든다
- 오래된 소프트웨어를 재문서화하는 데 필수다. 외계인 코드를 수정하기 전에 최소한 수행한다
- 기능을 개선하지 않는다. **이해**가 목적이다
- 산출물: 복원된 의존 행렬, 인터페이스 목록, 자료사전, 관찰 기반 요구 목록(FR-R-nnn)

## 6. 재공학 vs 역공학

| 구분 | 재공학 | 역공학 |
|------|--------|--------|
| 목적 | 시스템 개선, 유지보수 용이 | 설계·분석 정보 복구 |
| 방향 | 설계 → 개발 → 운영 흐름의 개선 | 코드 → 설계로 거슬러 올라감 |
| 포함 관계 | 역공학을 활동 중 하나로 포함 | 재공학의 한 활동 |
| 기능 변화 | 구조 개선 (기능 불변), 이식 | 없음 (이해 중심) |
| 산출물 | 개선된 시스템 | 복원된 문서 |

## 7. 재공학이 아닌 것

| 활동 | 왜 아닌가 |
|------|-----------|
| 재사용 (Reuse) | 재공학의 **결과**로 재사용성이 높아질 수 있지만, 재사용 자체는 재공학 활동이 아니다 |
| 기능 추가 | 개선 보수다. 요구사항부터 다시 간다 |
| 완전 재개발 | 기존 시스템을 버리는 것은 재공학이 아니다 |
| 해킹 | 취약점 침입은 목표가 아니다 |

## 8. 재공학 계획에 들어갈 것

| 항목 | 내용 |
|------|------|
| 대상 | 모듈 목록과 선정 근거 (CR 빈도, 외계인 판정, 지표) |
| 활동별 범위 | 분석·재구성·이식·역공학 각각 무엇을 어디까지 |
| 기능 불변 증명 | 비교 검사에 쓸 TC 목록, 입력 데이터 집합, 일치 기준 |
| 전후 지표 | 결합도 등급 분포, 응집도 등급 분포, 최대 순환 복잡도, CR당 평균 소요 시간, 문서 커버리지 |
| 비용·기간 | 인월, 일정. `sw-estimate`·`sw-schedule` 형식 |
| 위험 | 재구성 중 기능 변화, 이식 중 데이터 손실, 운영 중단 시간 |
| 순서 | 수정 CR이 몰리는 모듈부터. 한 번에 전부 하지 않는다 |

## 9. 모델링과 유지보수

모델링은 소프트웨어를 구성하는 모듈들이 어떻게 연결되었는지를 그림(모델)으로 나타내는 것이다. 개발팀이 문제를 정확히 이해하고, 여러 엔지니어가 같은 개념을 공유하고, 문서화와 설계의 기초가 된다.

모델링은 **분석·설계·구현 전반**에 쓰인다. 유지보수 단계에서만 쓰는 것이 아니다. 유지보수는 기존 모델을 **읽는** 단계이고, 모델이 없으면 역공학으로 **만드는** 단계다.

## 10. 용어 대조

| 강의 표현 | 이 문서 |
|-----------|---------|
| 재공학 = 기존 시스템을 버리지 않고 개조·개선 | 1절 |
| 재공학 = 예방 보수 | 1절 |
| 분석 → 재구성(개조) → 이식 → 역공학 | 5절 |
| 재구성은 기능·동작을 바꾸지 않음 | 5.2 |
| 이식 = OS·하드웨어·DB 변경 | 5.3 |
| 역공학 = 코드 → 설계, 가장 오래된 형태는 재문서화 | 5.4 |
| 재사용은 재공학 활동이 아님 | 7절 |
| 해킹은 리엔지니어링 목표가 아님 | 3절, 7절 |
| 개발 생산성이 아닌 유지보수 생산성 | 2절 |
| 모델링은 유지보수 단계에서만 쓰는 것이 아님 | 9절 |
