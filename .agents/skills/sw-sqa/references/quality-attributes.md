# 소프트웨어 품질 표준 11개

품질은 "사용자의 요구사항을 제대로 만족하고, 설계된 대로 정확하게 구현되었는가"다. 두 측면으로 나눈다.

| 측면 | 질문 | 누가 책임지는가 |
|------|------|-----------------|
| 설계 품질 (Design Quality) | 설계자가 정한 기능·성능·구조 기준이 제대로 **정의**되었는가 | 분석가, 설계자 |
| 일치 품질 (Conformance Quality) | 설계서의 내용이 개발 과정에서 제대로 **지켜졌는가** | 개발자, 테스터 |

품질 관리(Quality Control)는 요구사항 문서부터 소스 코드, 테스트 문서, 사용자 설명서까지 **모든 산출물**을 품질 기준에 맞게 관리하는 활동이다.

## 속성별 정의, 점검 질문, 측정 방법

각 속성마다 SRS에 **수치 목표**가 있어야 측정할 수 있다. 목표가 없으면 "목표 미정의"로 기록한다.

### 1. 정확성 (Correctness)

- 정의: 요구한 기능을 정확하게 수행하는 정도
- 점검 질문: 모든 FR에 합격한 테스트 케이스가 있는가. 요구와 다르게 동작하는 기능이 있는가
- 측정: FR 합격률 = 합격 FR 수 / 전체 FR 수. 목표 100%
- 근거 산출물: `test.md` 검증 테스트, 추적표

### 2. 신뢰성 (Reliability)

- 정의: 주어진 시간·조건에서 오류 없이 일관된 결과를 지속적으로 제공하는 능력
- 점검 질문: 같은 입력에 항상 같은 결과가 나오는가. 운영 중 장애 빈도와 복구 시간은
- 측정: 평균 고장 간격(MTBF), 시간당 오류율, 비교 검사 일치율. 목표 예: 월 장애 1건 이하
- 근거 산출물: `test.md` 시스템 테스트(장애·복구), 운영 로그

### 3. 효율성 (Efficiency)

- 정의: CPU·메모리·네트워크 등 자원을 낭비 없이 사용하는 정도
- 점검 질문: 응답 시간·처리량이 NFR을 만족하는가. 자원 사용량이 예산 안인가
- 측정: p95 응답 시간, 초당 처리 건수, 최대 메모리. 목표 예: 응답 2초 이하
- 근거 산출물: `test.md` 성능 테스트

### 4. 무결성 (Integrity)

- 정의: 허가되지 않은 접근이나 데이터 변경을 막는 능력
- 점검 질문: 권한 없는 사용자가 데이터를 읽거나 바꿀 수 있는 경로가 있는가. 동시 수정 시 데이터가 깨지는가
- 측정: 권한 우회 시도 차단율 100%, 동시성 테스트 데이터 손상 0건
- 근거 산출물: `test.md` 보안·동시성 테스트, `code-review.md` 캡슐화 점검

### 5. 사용 용이성 (Usability)

- 정의: 배우기 쉽고 사용하기 쉬운 정도
- 점검 질문: 처음 쓰는 사용자가 매뉴얼 없이 핵심 작업을 끝낼 수 있는가. 오류 메시지가 다음 행동을 알려 주는가
- 측정: 과업 완료율, 과업 소요 시간, 오류 횟수. 목표 예: 교수가 10분 교육 후 성적 입력 완료율 90%
- 근거 산출물: 프로토타입 평가 기록, 확인(Validation) 테스트의 사용자 피드백

### 6. 유지보수성 (Maintainability)

- 정의: 수정·보완·업그레이드가 얼마나 쉽게 가능한가
- 점검 질문: 결함 하나를 고치는 데 평균 몇 시간인가. 수정이 다른 모듈에 영향을 주는가
- 측정: 응집도·결합도 등급, 순환 복잡도 10 초과 함수 수, 평균 수정 시간
- 근거 산출물: `design-review.md`, `code-review.md`

### 7. 유연성 (Flexibility)

- 정의: 요구사항 변화에 따라 소프트웨어를 쉽게 수정할 수 있는가
- 점검 질문: 새 기능(예: 새 등급 체계)을 추가할 때 바뀌는 모듈 수는. 설정으로 바꿀 수 있는 것을 코드에 박아 두지 않았는가
- 측정: 가상의 변경 시나리오에 대해 영향받는 모듈 수. 목표 예: 등급 기준 변경 시 1개 클래스
- 근거 산출물: `design-oo.md` 다형성·추상화 적용, `code-review.md` 매직 넘버 점검

### 8. 시험 용이성 (Testability)

- 정의: 테스트를 수행하기 쉬운가
- 점검 질문: 클래스를 독립적으로 테스트할 수 있는가(의존성 주입, 스텁 가능). 기초 경로 수가 관리 가능한가
- 측정: 단위 테스트 가능 클래스 비율, 평균 순환 복잡도, 테스트 커버리지
- 근거 산출물: `test.md` 단위 테스트 범위, `code-review.md` 복잡도

### 9. 이식성 (Portability)

- 정의: 다른 OS·하드웨어·DB 환경에서 쉽게 수정해 동작시킬 수 있는 능력
- 점검 질문: 목표 환경 전부에서 테스트했는가. 환경 종속 코드가 한 곳에 모여 있는가
- 측정: 지원 환경 목록 대비 합격 환경 수. 환경 종속 모듈 수
- 근거 산출물: `test.md` 설치·호환 테스트, `design-review.md` 외부 결합도

### 10. 재사용성 (Reusability)

- 정의: 전체 또는 일부를 다른 프로그램에 재사용할 수 있는가
- 점검 질문: Fan-In이 높은 모듈이 기능적 응집을 갖는가. 도메인에 종속되지 않은 모듈이 분리되어 있는가
- 측정: 기능적·순차적 응집 모듈 비율, 외부 의존 없는 모듈 수
- 근거 산출물: `design-review.md`

### 11. 상호운용성 (Interoperability)

- 정의: 다른 시스템·외부 소프트웨어와 데이터를 교환하고 함께 동작할 수 있는가
- 점검 질문: 외부 인터페이스가 명세(SRS 5장)대로 구현되었는가. 표준 형식(JSON, CSV 등)을 쓰는가
- 측정: 외부 인터페이스 통합 테스트 합격률 100%
- 근거 산출물: `test.md` 통합·시스템 테스트(외부 연동), `srs.md` 외부 인터페이스 요구

## 점검 양식

| 속성 | 목표 (SRS) | 측정 방법 (test.md) | 측정값 | 판정 |
|------|------------|---------------------|--------|------|
| 정확성 | FR 100% | 검증 테스트 | 3/4 | 미달 |
| … | | | | |

판정 값: 합격 / 미달 / 목표 미정의 / 미측정. "목표 미정의"는 초기 시점(SRS 작성) 누락이고, "미측정"은 최종 시점(테스트) 누락이다. 구분해서 어느 스킬로 돌아갈지 정한다.

## 품질 보증의 네 조건

품질 보증이 되려면 다음 넷이 함께 성립해야 한다. 하나라도 빠지면 분쟁의 원인이 된다.

| 조건 | 내용 | 확인 산출물 |
|------|------|-------------|
| 요구사항 충족 | 사용자가 원하는 기능이 모두 들어감 | 추적표 미구현 0건 |
| 성능 만족 | 속도·안정성·보안 조건 충족 | NFR 측정값 |
| 예산·기간 준수 | 정해진 예산과 일정 안에 완성 | `schedule.md`, `estimate.md` 대비 실적 |
| 유연성 | 수정·보완 가능 | 유지보수성·유연성 속성 |
