# 정형 기술 검토(FTR) 지침과 산출물별 체크리스트

정형 기술 검토(Formal Technical Review)는 개발자가 만든 산출물(설계서, 코드, 문서)을 기술자들이 모여 검토하는 회의다. SQA에서 가장 중요한 활동이다.

## 1. 목적

- 요구사항과 일치하는지 검증한다
- 표준을 준수했는지 확인한다
- 설계·기능·논리의 오류를 발견한다
- 프로젝트 진행을 투명하게 관리한다
- 산출물을 공식 승인해 기준선(baseline)으로 만든다

## 2. 여섯 가지 지침

| 번호 | 지침 | 지키는 방법 | 어겼을 때 |
|------|------|-------------|-----------|
| 1 | 제품 중심으로 검토한다 | 결함 기록에 작성자 이름을 쓰지 않는다. "이 설계는"이라고 말하고 "당신은"이라고 말하지 않는다 | 작성자가 방어적이 되어 결함을 숨긴다 |
| 2 | 의제를 명확히 제한한다 | 검토 범위(파일·절·줄)를 안내문에 적는다. 범위 밖 지적은 "별도 항목"으로 분리 | 회의가 길어지고 핵심 범위가 검토되지 않는다 |
| 3 | 논쟁과 반박을 제한한다 | 결함을 확인만 하고 해결책을 논의하지 않는다. 의견이 갈리면 "확인 필요"로 기록하고 넘어간다 | 설계 토론이 되어 결함 발견이 멈춘다 |
| 4 | 참가자 수를 3~10명으로 제한한다 | 진행자 1, 기록자 1, 검토자 2~7, 작성자 1 | 적으면 시각이 좁고, 많으면 발언 기회가 줄고 준비도가 떨어진다 |
| 5 | 회의 전 준비를 강제한다 | 자료를 최소 1일 전 배포. 검토자는 결함 후보 목록을 가져온다. 준비 없는 검토자는 참석 불가 | 회의가 설명회가 된다 |
| 6 | 체크리스트를 사용한다 | 산출물 유형별 체크리스트로 항목 순서대로 진행 | 검토자의 관심사에만 집중되고 누락이 생긴다 |

추가 운영 규칙:
- 회의 시간 2시간 이내. 넘으면 2차 회의.
- 진행자는 작성자가 아니어야 한다.
- 결함 수정은 회의 후. 수정 결과는 다음 회차에서 확인.
- 판정은 승인 / 조건부 승인 / 재검토 셋 중 하나.

## 3. 요구사항 명세서(SRS) 체크리스트

| 번호 | 항목 | 예/아니오 |
|------|------|-----------|
| S1 | 모든 요구에 고유 ID(FR-/NFR-)가 있다 | |
| S2 | 한 항목에 한 요구만 있다 | |
| S3 | "~해야 한다" 형태이고 "~하면 좋겠다"가 없다 | |
| S4 | "빠르게", "편리하게" 같은 측정 불가 표현이 없다 | |
| S5 | 설계 내용(DB 종류, 언어, 프레임워크)이 섞여 있지 않다 | |
| S6 | 정상 흐름과 예외 흐름이 모두 있다 | |
| S7 | 서로 모순되는 요구가 없다 | |
| S8 | 자료사전 이름과 본문 데이터 이름이 같다 | |
| S9 | DFD의 모든 프로세스가 요구 항목과 연결된다 | |
| S10 | 각 요구를 테스트로 확인할 수 있다 (검증 가능성) | |
| S11 | 각 요구의 출처(인터뷰·시나리오)가 적혀 있다 (추적 가능성) | |
| S12 | 비기능 요구(성능·보안·가용성·유지보수성)에 수치 목표가 있다 | |

## 4. 설계서 체크리스트

| 번호 | 항목 | 예/아니오 |
|------|------|-----------|
| D1 | 모든 FR이 하나 이상의 모듈·클래스에 할당되었다 | |
| D2 | 요구에 없는 모듈·클래스가 없다 | |
| D3 | 데이터·구조·인터페이스·절차 설계가 모두 있다 | |
| D4 | 모듈 간 결합도가 허용 상한(스탬프) 이하다 | |
| D5 | 모듈 응집도가 허용 하한(통신적) 이상이다 | |
| D6 | 순환 의존이 없다 | |
| D7 | 계층 역행(하위가 상위를 참조)이 없다 | |
| D8 | Fan-Out이 7 이하다 | |
| D9 | 내부 구현이 인터페이스 뒤에 숨어 있다 (정보 은닉) | |
| D10 | 객체지향이면 클래스 다이어그램·시퀀스 다이어그램·상태도가 분석 모델과 일치한다 | |
| D11 | 외부 시스템 인터페이스가 SRS 5장과 일치한다 | |
| D12 | 비기능 요구(성능·보안)를 어떤 구조로 만족시키는지 적혀 있다 | |

## 5. 코드 체크리스트

| 번호 | 항목 | 예/아니오 |
|------|------|-----------|
| C1 | 클래스·메소드 이름이 설계서와 같다 | |
| C2 | 메소드 시그니처가 설계서와 같다 | |
| C3 | 설계에 없는 패키지 간 의존이 없다 | |
| C4 | 순차·선택·반복만 사용하고 goto 등가물이 없다 | |
| C5 | 매개변수 4개 이하, 중첩 3단계 이하, 함수 50줄 이하 | |
| C6 | 순환 복잡도 10 초과 함수가 없다 | |
| C7 | 필드가 private이고 setter에 유효성 검사가 있다 | |
| C8 | 다른 객체의 내부 상태를 직접 수정하는 코드가 없다 | |
| C9 | 매직 넘버가 없다 | |
| C10 | 커밋이 요구 ID 또는 변경 요청 ID와 연결된다 | |

## 6. 테스트 계획·케이스 체크리스트

| 번호 | 항목 | 예/아니오 |
|------|------|-----------|
| T1 | 모든 TC에 입력·실행 조건·기대 결과가 있다 | |
| T2 | 모든 FR에 TC가 1개 이상 있다 | |
| T3 | 모든 NFR에 측정 방법과 합격 수치가 있다 | |
| T4 | 기대 결과가 SRS·설계서에서 왔다 (코드 출력 아님) | |
| T5 | 무효 동치 클래스와 경곗값 바깥 값이 있다 | |
| T6 | 우선 대상 함수에 기초 경로 V(G)개 케이스가 있다 | |
| T7 | 순서가 단위 → 통합 → 검증 → 시스템이다 | |
| T8 | 통합 테스트에 스레드·사용 기반 전략이 명시되었다 | |
| T9 | 외부 시스템 스텁의 반환값이 케이스에 적혀 있다 | |
| T10 | 실행 이력에 실패 TC와 수정 커밋이 연결된다 | |

| DF | 위치 | 체크 항목 | 심각도 | 유형 | 설명 | 처리 |
|----|------|-----------|--------|------|------|------|
| DF-001 | design-oo.md 5.3 | D4 | 중 | 오류 | GradeService → Enrollment 내용 결합 | 열림 |

- 심각도: 치명(요구 모순, 데이터 손실, 권한 우회, 기준선 불일치) / 중(기준 위반이나 우회 가능) / 경(가독성, 표기)
- 유형: 누락 / 오류 / 불일치(산출물 간) / 모호 / 표준 위반
- 처리: 열림 / 수정됨 / 확인됨 / 기각(사유)
