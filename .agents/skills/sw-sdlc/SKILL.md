## 인자

`$sw-sdlc` 뒤에 이어 쓴다: `[status|flow|model 폭포수|프로토타입|나선형|team|merge]`

## 목적

사용자가 소프트웨어 개발 생명주기(SDLC) 중 어디에 있는지 알려 주고, 다음에 호출할 스킬 하나를 지목한다.
스스로 산출물을 만들지 않는다. 다만 여러 사람이 `docs/sw/`를 함께 쓸 때는 문서 소유 표를 만들고(`team`) 병합 대기 파일을 반영한다(`merge`). 생명주기 모형(폭포수, 프로토타입, 나선형, 4세대, V)을 고르는 질문에도 답한다.

## 입력

- 인자 없음 또는 `status`: 현재 상태와 다음 스킬 안내
- `flow`: 전체 흐름표 출력
- `model <이름>`: 해당 생명주기 모형에서 어느 구간을 반복하는지 안내. 이름 없이 `model`만 오면 모형 선택 질문을 한다.
- `team`: 두 사람 이상이 도메인을 나눠 쓸 때 `docs/sw/OWNERS.md`(문서 소유 표)를 만든다. 협업 모드가 시작된다.
- `merge`: 공용 담당이 `docs/sw/pending/`의 병합 대기 파일을 반영한다. 정식 번호, 공용 파일, 버전을 여기서만 고친다.

## 절차

### status (기본)

1. `docs/sw/` 아래 파일 목록을 확인한다. 폴더가 없으면 "계획 전"으로 본다.
2. 아래 순서표에서 **존재하지 않는 첫 번째 산출물**을 찾는다. 그 산출물을 만드는 스킬이 다음 단계다.
3. 산출물이 있어도 다음 중 하나면 "미완성"으로 보고 같은 스킬을 다시 권한다.
   - 제목 다음 줄에 `> 작성: … | 버전: … | 입력: …` 헤더가 없다(제목과 헤더 사이의 빈 줄은 건너뛰고 본다)
   - 템플릿의 빈칸 표시(`<`, `>`, `TODO`, `(작성)`)가 남아 있다
   - 본문이 20줄 미만이다
4. `design.md`와 `design-oo.md`는 둘 중 하나만 있어도 설계 단계를 통과한 것으로 본다. 둘 다 없으면 `$sw-design-oo`를 먼저 권한다. (사용자가 구조적 설계를 원한다고 밝혔으면 `$sw-design`)
5. `implementation.md`, `code-review.md`, `test.md`, `sqa.md`는 반복 산출물이다. `implementation.md`는 "0. 문서 상태"의 현재 단계를 함께 보여 주고, 구현이 끝나지 않았으면 `$sw-implement`와 `$sw-code-review`를 번갈아 권한다. 최초 1회는 순서대로 권하고, 이후에는 마지막 작성일을 함께 보여 준다.
6. `maintenance/`에 파일이 있으면 "운영·유지보수 중"으로 판정하고, 가장 최근 요청 파일의 분류(수정·적응·개선·예방)와 상태를 보여 준다. `maintenance/reengineering.md`가 있으면 재공학 진행 중임을 함께 표시한다. 이 파일은 요청 파일이 아니므로 "가장 최근 요청" 판정에서 제외한다.
7. 순서를 건너뛴 파일이 있으면(예: `srs.md` 없이 `design-oo.md` 존재) 경고하고 빠진 것부터 권한다.
8. `docs/sw/OWNERS.md`가 있으면 협업 모드로 표시한다. `docs/sw/pending/` 파일 수와 작성자를 보여 주고, 대기 파일이 있으면 공용 담당에게 `$sw-sdlc merge`를 권한다.

### 순서표

| 순서 | 산출물 | 스킬 | 단계 |
|------|--------|------|------|
| 1 | `plan.md` | `$sw-plan` | 계획 |
| 2 | `estimate.md` | `$sw-estimate` | 계획 |
| 3 | `schedule.md` | `$sw-schedule` | 계획 |
| 4 | `srs.md` | `$sw-srs` | 분석 |
| 5 | `design-oo.md` 또는 `design.md` | `$sw-design-oo` 또는 `$sw-design` | 설계 |
| 6 | `design-review.md` | `$sw-design` | 설계 (검증) |
| 7 | `implementation.md` | `$sw-implement` | 구현 |
| 8 | `code-review.md` | `$sw-code-review` | 구현 (검증) |
| 9 | `test.md` | `$sw-test` | 테스트 |
| 10 | `sqa.md` | `$sw-sqa` | 테스트 (품질 보증) |
| 반복 | `maintenance/YYYY-MM-DD_요청명.md` | `$sw-maintain` | 유지보수 |
| 필요 시 | `maintenance/reengineering.md` | `$sw-maintain --reengineering` | 유지보수 (예방 보수) |

### flow

순서표를 단계별 묶음으로 보여 준다. 각 단계가 답하는 질문을 함께 적는다.

```
[계획]     할 가치가 있는가? 얼마나, 언제까지, 누가?      → plan, estimate, schedule
[분석]     무엇을 만들 것인가? (What)                      → srs
[설계]     어떻게 만들 것인가? (How)                       → design-oo / design, design-review
[구현]     설계대로 코드로 옮겼는가?                        → implement, code-review (반복)
[테스트]   요구대로 동작하는가? 품질 기준을 만족하는가?     → test, sqa
[유지보수] 운영 중 변화에 대응하는가?                       → maintain → (승인 시) srs로 회귀
```

### model

모형 이름이 없으면 아래 질문 4개를 하고 추천 모형을 하나 고른다.

| 질문 | 예 | 아니오 |
|------|----|--------|
| 요구사항이 처음부터 명확하고 바뀔 가능성이 낮은가? | 폭포수 또는 V | 다음 질문 |
| 사용자가 원하는 것을 화면으로 보여 줘야 확정되는가? | 프로토타입 | 다음 질문 |
| 규모가 크고(수십 인월 이상) 기술·일정 위험이 높은가? | 나선형 | 다음 질문 |
| 자동화 도구(CASE, 코드 생성기)로 대부분을 만들 수 있는 중소형인가? | 4세대 기법 | 폭포수 |

모형별 반복 구간:

| 모형 | 반복 구간 | 스킬 흐름에서의 의미 |
|------|-----------|---------------------|
| 폭포수 | 없음. 단계가 끝나야 다음으로 간다 | 순서표를 한 번만 내려간다. 앞 단계 산출물을 고치려면 변경 통제를 거친다 |
| V | 없음. 설계 단계마다 대응 테스트를 미리 정의한다 | `$sw-test`를 설계 직후에 한 번 먼저 호출해 테스트 계획만 만들고, 구현 후 다시 호출해 케이스를 채운다 |
| 프로토타입 | 분석 ↔ 시제품 ↔ 사용자 평가 | `$sw-srs` 안에서 시제품 평가 루프를 돌고 `srs.md` 버전을 올린다. 설계로 넘어간 뒤에는 반복하지 않는다 |
| 나선형 | 계획 → 위험 분석 → 개발 → 고객 평가를 한 바퀴씩 | 한 바퀴마다 `$sw-plan`(위험 목록 갱신) → `$sw-srs` → `$sw-design-oo` → `$sw-test` 를 부분 범위로 반복한다. 위험 분석은 매 바퀴 수행한다 |
| 4세대 기법 | 요구 명세 → 자동 생성 → 검증 | `$sw-srs`를 상세하게 쓰고 `$sw-design`을 생략하거나 간략화한다. 대규모에서는 오히려 분석·설계가 길어지므로 권하지 않는다 |

### team

1. 사람을 묻는다. 이름, 이니셜(한 글자, 임시 번호에 쓴다), `git config user.name`, 맡을 도메인(기능 묶음 권장: 한 사람이 그 기능의 서버·앱·문서를 끝까지 맡는다), 공용 담당 1명.
2. `docs/sw/` 조각 파일을 훑어 파일마다 담당을 정한다.
   - 한 도메인만 다루는 조각은 그 도메인 담당.
   - 여러 도메인이 행을 더하는 조각(추적표, 자료사전, 위험 요약, 변경 결정 부록, 의존도)과 목차 파일, `README.md`는 "공용".
   - 두 도메인이 섞인 조각은 먼저 도메인별로 나눌지 묻는다. 나누지 않으면 "공용"으로 둔다.
   - 경계 계약(API 명세, DTO, ERD, 패키지 인터페이스)은 제공하는 쪽 담당.
3. `templates/owners.md` 양식으로 `docs/sw/OWNERS.md`를 저장하고 `docs/sw/pending/.gitkeep`을 만든다.
4. 저장소 에이전트 규칙(`AGENTS.md` 또는 `CLAUDE.md`)에 "`docs/sw/`는 OWNERS.md를 따른다" 한 줄을 넣도록 권한다.

### merge

공용 담당만 실행한다. `git config user.name`이 OWNERS.md의 공용 담당과 다르면 멈춘다.

1. `docs/sw/pending/*.md`를 작성일 순으로 하나씩 처리한다. 대기 파일의 브랜치가 아직 병합되지 않았으면 건너뛰고 알린다.
2. 정식 번호를 매긴다. 종류마다 `docs/sw/` 전체에서 현재 가장 큰 번호를 찾아 그다음부터 붙인다. 번호는 한 번 붙이면 바꾸지 않는다.
3. `docs/sw/` 전체에서 `[임시:…]`를 정식 번호로 바꾼다. 바꾼 뒤 `[임시:`가 0건인지 확인한다.
4. "공용 파일 반영"의 행·문단을 해당 공용 파일에 넣는다.
5. 고친 산출물마다 목차 파일 머리 헤더의 버전을 한 번 올리고, 입력란에 대기 파일의 입력을 더한다. 조각의 "(다음 판 변경)"을 실제 버전으로 바꾼다. `docs/sw/README.md` 문서 지도의 버전도 고친다.
6. "다른 담당에게 요청"은 반영하지 않고 해당 담당에게 넘긴다(지라 또는 MR 댓글).
7. 처리한 대기 파일을 지운다. 한 번의 병합 결과를 커밋 하나로 남긴다.

## 판정 기준

- 다음 스킬은 **하나만** 지목한다.
- "미완성" 판정은 위 3번의 세 조건 중 하나라도 해당하면 내린다.
- 모형 추천은 위 질문표에서 처음 "예"가 나온 모형이다.

## 출력

터미널에만 출력한다. 형식:

```
[학사관리 시스템]  단계: 분석
완료: plan, estimate, schedule
다음: $sw-srs  (요구사항 명세서: 도출 → 분석 → 명세 → 확인)
모형: 프로토타입 (srs 구간 반복 중, 현재 v1.1)
유지보수: 없음
협업: 없음  (OWNERS.md가 있으면 "이성현·박재영, 병합 대기 2건")
```

`flow`, `model` 인자면 해당 표를 그대로 보여 준다.

## 체크리스트

- [ ] 다음 스킬을 하나만 지목했다
- [ ] 설계 단계는 `design.md`와 `design-oo.md` 중 하나만 있어도 통과로 봤다
- [ ] 건너뛴 산출물이 있으면 경고했다
- [ ] 모형 추천 시 "요구사항이 불명확하면 프로토타입, 위험이 크면 나선형"을 뒤집어 말하지 않았다
- [ ] 폭포수를 "요구사항 변경이 쉽다"거나 "단계 병행이 가능하다"고 설명하지 않았다
- [ ] 협업 모드에서 정식 번호와 버전은 `merge`에서만 고쳤다

## 자주 하는 실수

- 산출물 파일이 있다는 이유만으로 단계를 통과시킨다. 헤더와 분량을 확인한다.
- 설계 산출물이 없는데 코드 리뷰부터 권한다. 설계 없는 코드 리뷰는 설계 일치 점검을 할 수 없다.
- 유지보수 요청이 승인됐는데 `$sw-maintain`만 반복한다. 기능 추가(개선 보수)는 `$sw-srs`로 돌아가 요구사항부터 갱신해야 한다.
