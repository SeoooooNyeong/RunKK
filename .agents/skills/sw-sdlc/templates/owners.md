# <프로젝트명> 문서 소유 표

> 작성: YYYY-MM-DD | 버전: v0.1 | 입력: 팀 구성(schedule.md 조직 절), 도메인 나눔 결정

이 파일이 있으면 `docs/sw/` 산출물은 협업 모드로 쓴다. 모든 `sw-*` 스킬은 저장 전에 이 파일을 읽는다.

## 1. 사람

| 이름 | 이니셜 | git 사용자 이름 | 맡은 도메인 | 공용 담당 |
|------|--------|-----------------|-------------|-----------|
| <이름> | <한 글자> | <git config user.name> | <기능 묶음> | 예 |
| <이름> | <한 글자> | <git config user.name> | <기능 묶음> | |

## 2. 파일 소유

위에서 아래로 처음 맞는 행을 쓴다. 경로는 `docs/sw/` 기준이다.

| 경로 (glob) | 담당 | 비고 |
|-------------|------|------|
| `OWNERS.md` | 공용 | |
| `README.md` | 공용 | 문서 지도 |
| `*.md` (docs/sw 바로 아래 목차 파일) | 공용 | 머리 헤더, 문서 상태, 목차 표 |
| `<산출물>/<조각>.md` | <이름> | <도메인> |
| `pending/*.md` | 작성자 | 브랜치마다 한 파일 |

공용 조각: 추적표, 자료사전, 위험 요약, 변경 결정 부록처럼 모든 도메인이 행을 더하는 조각은 담당을 "공용"으로 둔다.

## 3. 규칙

1. 자기 담당 파일만 고친다. 남의 파일에 고칠 것이 있으면 병합 대기 파일의 "다른 담당에게 요청"에 적는다.
2. 공용 파일은 공용 담당만 고친다. 다른 사람은 넣을 내용을 병합 대기 파일의 "공용 파일 반영"에 적는다.
3. 새 번호(FR, NFR, C, D, R, CR, TC, 결함 번호)는 `[임시:FR-<이니셜>-1]` 형식으로 쓴다. 정식 번호는 병합 때 공용 담당이 매긴다. 임시 번호는 `docs/sw/` 밖(커밋 메시지, 지라, 코드 주석)에 쓰지 않는다.
4. 산출물 버전은 올리지 않는다. 조각 안의 변경 표시는 "(다음 판 변경)"으로 쓴다.
5. 경계 계약(API, DTO, ERD, 패키지 인터페이스)은 제공하는 쪽 담당이 고치고, 쓰는 쪽 담당이 MR에서 승인한다. 기존 동작을 깨는 변경은 변경 요청(CR)으로 적는다.
6. 병합은 공용 담당이 `$sw-sdlc merge`로 한다.

## 4. 병합 대기 파일 양식 (`pending/<브랜치 이름의 / 를 - 로>.md`)

```markdown
# 병합 대기: <브랜치>

> 작성: YYYY-MM-DD | 작성자: <이름> | 스킬: <sw-srs 등>

## 고친 조각
- srs/03-05-크루-관리.md: <한 줄>

## 새 임시 번호
| 임시 번호 | 종류 | 한 줄 설명 | 위치 |
|-----------|------|------------|------|
| [임시:FR-박-1] | FR | <설명> | srs/03-05 |

## 공용 파일 반영
| 파일 | 넣을 내용 |
|------|-----------|
| srs/07-11-추적표-v0.18.md | [임시:FR-박-1] 행 |
| srs.md | 머리 헤더 입력란에 <입력> |

## 다른 담당에게 요청
- <담당>: <파일> <고칠 것>
```
