# 학사관리 시스템 프로젝트 계획서

> 작성: 2026-03-02 | 버전: v1.0 | 입력: OO대학교 교무처 제안요청서(RFP) 2026-02, 교무처장 면담 기록 2026-02-20

## 1. 프로젝트 성격

| 항목 | 내용 |
|------|------|
| 발주 형태 | 주문형 |
| 발주처 | OO대학교 교무처 |
| 최종 사용자 | 교수(성적 입력), 학생(수강신청·성적 조회), 교무처 직원(학적 관리) |
| 계약 문서 | RFP(2026-02), 제안서(2026-02-25), 계약서 초안 |
| 마감 조건 | 2학기 개강(2026-09-01) 2주 전인 2026-08-18 가동. 개강 후 가동 불가 |

### 계약 문서 모호 표현 점검

| 위치 | 표현 | 수치화 요청 | 상태 |
|------|------|-------------|------|
| RFP 3.2 | "빠른 응답 속도를 제공한다" | 조회 화면 응답 2초 이내로 명시 | 반영됨 |
| RFP 3.4 | "수강신청 기간 폭주에 대응하도록 노력한다" | 동시 접속 1,000명, 신청 처리 초당 50건 | 반영됨 |
| 계약서 7조 | "기존 데이터 이관에 적극 협조한다" | 전산실이 학적 DB 스키마와 샘플 데이터를 착수 후 2주 내 제공 | 요청 중 |

## 2. 타당성 검토

| 관점 | 판정 | 근거 |
|------|------|------|
| 법적 | 예 | 개인정보보호법 대상(학번·성적). 교내 개인정보 처리방침에 수집 항목이 이미 포함. 추가 동의 절차 불필요 |
| 경제적 | 예 | 발주 예산 상한 4억 원. 유사 규모 대학 학사관리 구축 사례 3.2~3.8억 원. 상세 비용은 `estimate.md` |
| 기술적 | 예 | 개발사가 동일 구조(웹 + 관계형 DB)의 대학 수강신청 시스템 2건 구축 경험. 미보유 기술 없음. 단, 기존 학적 DB(Oracle 11g) 스키마 문서 부재가 위험 요소 |

종합: 진행

## 3. 범위

### 3.1 기능

| 구분 | 기능 | 주 사용자 |
|------|------|-----------|
| 포함 | 학생 등록·학적 변동(휴학·복학·전과) 관리 | 교무처 직원 |
| 포함 | 성적 입력, 성적 조회, 성적 이의신청·처리 | 교수, 학생 |
| 포함 | 수강신청, 수강 승인·정정, 정원 관리 | 학생, 교수, 교무처 |
| 포함 | 성적표·수강 확인서 출력 | 학생, 교무처 |
| 제외 | 등록금·장학금 등 재정 관리 | (재무처 기존 시스템 유지) |
| 제외 | 강의실 배정 등 시설 관리 | (시설과 기존 시스템 유지) |
| 제외 | 모바일 전용 앱 | (웹 반응형으로 대체. 전용 앱은 2차 과제) |
| 제외 | 기존 학적 데이터의 정제·보정 | (전산실 책임. 개발사는 이관 도구만 제공) |

### 3.2 성능

| 항목 | 목표 수치 |
|------|-----------|
| 응답 시간 | 조회 화면 2초 이내, 성적표 출력 5초 이내 |
| 동시 사용자 | 1,000명 (수강신청 첫날 기준) |
| 처리량 | 수강신청 초당 50건 |

### 3.3 제약 조건

| 항목 | 내용 |
|------|------|
| 운영 환경 | 교내 전산실 기존 Linux 서버 2대, Oracle DB 유지 |
| 예산 상한 | 4억 원 (부가세 포함) |
| 마감 기한 | 2026-08-18 가동, 2026-08-31까지 안정화 |
| 기타 | 교내 통합 인증(SSO) 필수 사용, 외부 클라우드 사용 불가 |

### 3.4 인터페이스

| 분류 | 대상 | 비고 |
|------|------|------|
| 사용자 ↔ 시스템 | 웹 브라우저(PC·모바일 반응형) | 교수·학생·직원 화면 분리 |
| 기존 시스템 | 학적 DB(Oracle 11g) | 스키마 문서 없음. 위험 R-002 |
| 기존 시스템 | 교내 통합 인증 서버 | 전산실이 연동 규격 제공 |
| 외부 시스템 | 없음 | 재정·시설 시스템과 직접 연동하지 않음 |
| 하드웨어 | 성적표 출력용 프린터 | 표준 드라이버 |

### 3.5 신뢰도

| 항목 | 목표 수치 |
|------|-----------|
| 가동률 | 월 99.5% (학기 중), 수강신청 기간 99.9% |
| 복구 목표 시간 | 장애 발생 후 1시간 이내 서비스 복구 |
| 데이터 손실 | 성적·수강 데이터 손실 0건 (일 단위 백업 + 트랜잭션 로그) |

## 4. 이해관계자

| 역할 | 조직·인물 | 관심사 | 연락 창구 |
|------|-----------|--------|-----------|
| 발주자 | 교무처 (교무처장, 학사팀장) | 개강 전 가동, 예산 준수 | 학사팀장 주간 회의 |
| 최종 사용자 | 교수 약 300명 | 성적 입력 편의, 이의신청 처리 | 교수 대표 3명 (프로토타입 평가) |
| 최종 사용자 | 학생 약 8,000명 | 수강신청 안정성, 성적 조회 | 학생회 대표 |
| 최종 사용자 | 교무처 직원 12명 | 학적 변동 처리 효율 | 학사팀 |
| 기존 시스템 담당 | 전산실 (DB 관리자, 인증 담당) | 기존 DB 보존, 서버 부하 | 전산실장 |
| 개발사 | 개발 PM | 범위 고정, 일정 준수 | PM |

## 5. 프로젝트 관리 3요소

| 요소 | 내용 |
|------|------|
| 사람(People) | 책임 프로그래머 1, 분석·설계 겸임 1, 개발자 2, 테스터 겸 문서 담당 1 수준으로 예상. 확정 인원은 `estimate.md` 이후 `schedule.md`에서 결정 |
| 문제(Problem) | 현재 성적은 교수가 엑셀로 제출하고 직원이 수기 입력하여 오류와 지연이 발생한다. 수강신청은 10년 된 시스템이 첫날 접속 폭주로 매 학기 중단된다. 학적 변동은 종이 서류로 처리되어 조회가 어렵다 |
| 프로세스(Process) | 프로토타입 모형. 교수·학생 화면 요구가 불명확하므로 분석 단계에서 시제품으로 요구를 확정한 뒤 설계로 넘어간다. 설계 이후에는 폭포수로 진행한다 (`$sw-sdlc model 프로토타입`) |
