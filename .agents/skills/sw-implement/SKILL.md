## 인자

`$sw-implement` 뒤에 이어 쓴다: `[plan | stage <단위> <단계> | integrate | status]`

## 목적

구현(Implementation)은 설계서의 클래스·패키지·API 계약을 실행 가능한 코드로 옮기는 단계다. 이 스킬은 코드를 직접 쓰기보다 구현 과정을 **나누고, 맡기고, 합치고, 검증하는** 순서를 정한다.

결과는 `docs/sw/implementation.md`에 남는다. 실행 단위·단계 분할, 단계별 커밋과 검증 결과, 결정 목록(설계와 다르게 정한 것), 통합 기록, 리뷰 반복 기록이 들어간다. `sw-code-review`는 이 파일로 리뷰 대상 범위와 기준선 커밋을 찾고, `sw-test`는 "우선 테스트 대상"과 계약 시험 목록을 읽는다.

## 입력

- `docs/sw/design-oo.md` 또는 `docs/sw/design.md`가 필수다. 없으면 `$sw-design-oo`를 먼저 안내하고 중단한다.
- `docs/sw/design-review.md`의 판정이 합격이어야 한다. 조건부·불합격이면 `$sw-design`(review)을 먼저 안내한다.
- `docs/sw/srs.md`(요구 ID·화면 목록), 설계서의 테스트 순서 절(통합 순서)과 의존 행렬.
- 코드 저장소 위치와 상태. 기본 브랜치, 커밋하지 않은 변경, 기존 뼈대, 팀 규칙 파일(AGENTS.md, CLAUDE.md, 코드 컨벤션)을 확인한다.
- 사용자에게 물을 것. 한 번에 묻고 답을 결정 목록에 적는다.
  1. 범위: 설계 전체인가, 일부 단위·단계인가
  2. 기술 스택: 설계서와 저장소가 다르면 어느 쪽을 따르는가
  3. 작업 위치: 새 worktree인가, 현재 작업 트리인가(커밋하지 않은 변경이 있으면 새 worktree를 권한다)
  4. 이슈 키(Jira 등)를 브랜치·커밋·MR에 붙일 것인가
  5. MR 단위: 하나로 모을 것인가, 단위별로 나눌 것인가
  6. 위임 범위: 단계가 끝날 때마다 물을 것인가, 끝까지 맡길 것인가(push·MR 생성은 따로 확인)

## 절차

### 1. 기준 고정

1. 설계서와 저장소의 차이를 표로 만든다(언어·프레임워크 버전, DB, 패키지 이름, 모듈 구조). 차이가 있으면 추측하지 말고 사용자 결정을 받는다.
2. 이름 규칙을 고정한다. 패키지·클래스·메소드 이름은 설계서와 **글자 그대로** 같아야 한다. 다르면 `sw-code-review`가 설계 불일치 결함으로 본다.
3. 검증 명령을 고정한다. 팀 규칙 파일의 포맷·빌드·시험 명령을 그대로 쓴다. 없으면 단위마다 하나씩 정해 `implementation.md` 머리에 적는다.

### 2. 실행 단위와 단계 나누기

1. **실행 단위**는 배포·빌드가 따로 되는 덩어리다(예: api 서버, 모바일 앱, 워치 앱, ai 서버). 단위마다 git worktree와 브랜치를 하나씩 만든다.
2. **단계**는 설계서의 테스트 순서 절과 의존 행렬의 정렬 순서를 따른다. 아래 패키지가 끝나야 위 패키지를 시작한다. 단계 하나는 하위 작업자 한 명이 한 맥락에서 끝낼 크기(패키지 2~4개 + 그 infra·web·batch)로 자른다.
3. 단위 안에서도 계약(포트 인터페이스, DTO, 화면 상태)이 이미 고정된 조각은 별도 worktree로 나눠 병렬로 진행할 수 있다(예: 데이터 계층 ∥ 화면 ∥ 워치). 조건은 서로 다른 폴더만 고치는 것이다.
4. 통합 브랜치 하나와 MR 하나를 만든다. 단위 브랜치는 단계가 끝날 때마다 통합 브랜치로 합친다.

| 상황 | 나누는 방법 |
|------|-------------|
| 단위 사이 계약(REST·실시간 메시지)이 설계서에 고정됨 | 단위별 worktree로 동시에 시작 |
| 단위 안 하위 모듈이 포트로만 연결됨 | 모듈 묶음별 worktree로 동시에 시작 |
| 아래 패키지 클래스를 직접 써야 함 | 같은 worktree에서 순서대로 |
| 공용 디자인 시스템·공용 기반이 필요함 | 기반 단계를 먼저 끝낸 커밋에서 다음 worktree를 딴다 |

### 3. 하위 작업자에게 맡기기

1. 지시서는 `references/agent-brief.md` 양식을 쓴다. 작업 위치, 고칠 폴더와 고치지 말 폴더, 정답 자료(설계서 절·SRS·시안), 사용자 결정, 범위, ECC 흐름, 실행 환경, 정확도 규칙, 커밋 규칙, 보고 형식을 빠짐없이 적는다.
2. 스택별 ECC 흐름은 `references/ecc-workflows.md`를 따른다. 공통 원칙은 **시험 먼저 쓰고 실패를 확인한 뒤 구현**이다.
3. 모델을 배분한다.

| 일의 성격 | 모델 |
|-----------|------|
| 설계를 해석해야 하는 구현(도메인 단계, 데이터 계층, 화면) | 상위 모델 |
| 동시성·정합성 결함 수정 | 상위 모델 |
| 병합·연결, 리뷰, 결과서 정리, 빌드 복구, 기계적 결함 수정 | 중위 모델 |

4. 작업자를 띄우는 방법, 스킬을 불러오는 방법, 상위·중위 모델의 실제 이름은 쓰는 도구에 따라 다르다. Claude Code는 `references/harness-claude.md`, Codex CLI는 `references/harness-codex.md`를 따른다.
5. 앞 단계의 보고에서 다음 단계가 알아야 할 것(조회 서비스·사건·포트 목록, 마이그레이션 번호, 공통 패턴, 남은 지적)을 다음 지시서에 그대로 옮긴다.
6. 사용량 한도로 작업이 멈추면 새 작업자를 띄우지 않는다. 같은 작업자에게 "상태부터 확인하고 멈춘 자리에서 이어서"라고 보낸다.

### 4. 통합과 검증 게이트

`references/integration-gate.md`의 순서를 매번 지킨다.

1. 단계 보고를 받으면 **작업자의 보고를 믿지 말고** 그 worktree에서 검증 명령을 직접 다시 돌린다.
2. 통합 브랜치에 `--no-ff`로 병합한다. 충돌은 양쪽 의도를 살려 풀고, 같은 키가 두 번 생기는 파일(버전 카탈로그 등)을 확인한다.
3. 배포 설정을 따라 맞춘다. 새 환경 변수는 실행 컨테이너의 변수 목록과 예시 파일에 함께 넣는다. 비밀값은 저장소에 넣지 않는다.
4. 통합 브랜치에서 모든 단위의 검증을 다시 돌린다. 통과했을 때만 push한다.
5. push 직전에 현재 브랜치 이름과 `HEAD`가 브랜치 끝과 같은지 확인한다.

### 5. 계약 고정 (단위 사이)

`references/contract-testing.md`를 따른다. 병렬로 만든 단위가 통합에서 깨지는 가장 흔한 원인은 **설계서에 이름만 있고 값이 고정되지 않은 enum·문자열·응답 항목**이다.

1. 실시간 메시지: 받는 쪽이 표본 JSON을 만들고, 보내는 쪽이 같은 파일로 직렬화 결과를 비교한다.
2. 외부·내부 서비스 응답: 응답하는 쪽이 상태 코드별 표본을 고정하고, 부르는 쪽이 그 표본으로 해석을 시험한다.
3. REST enum·요청·응답 항목: 서버 enum 이름과 요청·응답 record 구조를 파일로 뽑아 앱 시험 자료로 고정하고, 서버 쪽에도 같은 파일과 비교하는 시험을 둔다. 한쪽만 바뀌면 빌드가 실패해야 한다.
4. 화면이 계약 전에 가정한 값은 결정 목록에 "가정"으로 표시하고, 서버 단계가 끝나면 전수 대조한다.

### 6. 미리보기로 확인

1. 단위 시험이 통과해도 실제로 붙여 보지 않으면 드러나지 않는 결함이 있다. 단계 묶음이 끝날 때 로컬 서버와 에뮬레이터(또는 브라우저)로 핵심 흐름을 한 번 돌린다.
2. 미리보기는 통합 브랜치를 바꾸지 않는 별도 worktree에서 한다. 외부 키가 없어 막히는 경로(소셜 로그인 등)를 위한 개발용 우회는 미리보기 worktree에만 두고 push하지 않는다. 인증 우회는 사용자 허락을 받는다.
3. 사용자가 테스트 중이면 앱 데이터를 지우거나 서버를 재시작하는 작업을 멈춘다.

### 7. 리뷰 반복

1. 구현이 일정 분량 쌓이면 `$sw-code-review`를 단위별로 병렬 실행하고 결과를 `docs/sw/code-review.md`에 날짜별로 누적한다.
2. 결함은 진행 중인 단계 작업에 넘기거나(같은 worktree), 끝난 단위는 수정 작업자를 따로 띄운다. 같은 worktree에서 두 작업자가 동시에 커밋하지 않게 한다.
3. 구현이 끝나면 "앱–서버 빈 곳 메우기" 단계를 둔다. 화면을 만들며 드러난 포트·응답 공백, 단계별 자가 리뷰가 남긴 지적을 서버 쪽과 앱 쪽으로 나눠 처리한다.
4. 2차 리뷰로 1차 결함 해소를 표로 확인하고, 설계서 갱신 요청을 모아 `$sw-design-oo`로 넘긴다.

### 8. 기록

`docs/sw/implementation.md`가 없으면 `templates/implementation.md`로 만들고, 있으면 단계·통합·리뷰 기록을 해당 절에 덧붙인다. 헤더 둘째 줄의 버전과 날짜를 올린다.

## 판정 기준

| 단계 | 통과 조건 |
|------|-----------|
| 단계 완료 | 작업자 보고 + 같은 worktree에서 직접 돌린 검증 명령 통과, 작업 트리 깨끗함 |
| 통합 | 통합 브랜치에서 모든 단위의 검증 통과(포맷·린트·단위·통합·구조·계약 시험), 실패 시험 0 |
| push | 위 통합 통과 + 현재 브랜치 = 통합 브랜치, `HEAD` = 브랜치 끝 |
| 구조 | 설계 의존 표 밖 import 0, 순환 0(구조 시험으로 확인) |
| 계약 | 실시간·서비스·REST 계약 시험이 양쪽 모두 통과 |
| 구현 완료 | 설계서 패키지가 모두 채워짐(시험으로 확인), API 표 보류 0, `sw-code-review` 판정 합격 또는 조건부(사유가 이슈 키 부재뿐) |

## 출력

- `docs/sw/implementation.md`. 양식은 `templates/implementation.md`.
- 완성 예시는 `examples/implementation.md`(학사관리 시스템).
- 다음 단계: `$sw-code-review`(리뷰 반복), 구현 완료 뒤 `$sw-test`. 설계서 갱신 요청이 있으면 `$sw-design-oo`.
- 협업 모드: `docs/sw/OWNERS.md`가 있으면 저장 전에 그 규칙을 따른다. `git config user.name`으로 작성자를 찾아 그 사람 담당 파일만 고친다. 새 번호는 `[임시:FR-<이니셜>-1]` 형식으로 쓰고 산출물 버전은 올리지 않는다(변경 표시는 "(다음 판 변경)"). 목차 파일의 머리 헤더·문서 상태·목차, `docs/sw/README.md`, 공용 조각(추적표, 자료사전 등)에 들어갈 내용과 남의 파일에 고칠 것은 `docs/sw/pending/<브랜치 이름의 / 를 - 로>.md`에 적는다. 정식 번호와 버전은 공용 담당이 `$sw-sdlc merge`로 매긴다. 규칙 전문은 CONVENTIONS 8절과 OWNERS.md 3절이다.

## 체크리스트

- [ ] 설계서와 저장소의 스택 차이를 사용자 결정으로 고정했다
- [ ] 단계 순서가 설계서의 테스트 순서·의존 행렬과 같다
- [ ] 모든 지시서에 고칠 폴더와 고치지 말 폴더, "브랜치를 바꾸지 말 것"을 적었다
- [ ] 같은 worktree에서 두 작업자가 동시에 커밋하지 않았다
- [ ] 단계마다 작업자 보고와 별개로 검증을 직접 다시 돌렸다
- [ ] 검증과 커밋·push를 한 명령으로 묶을 때 실패가 파이프에 묻히지 않게 했다(`set -o pipefail`)
- [ ] push 전에 브랜치 이름과 `HEAD` 위치를 확인했다
- [ ] 단위 사이 enum·요청·응답 항목을 양쪽 계약 시험으로 고정했다
- [ ] 새 환경 변수를 실행 설정과 예시 파일에 함께 넣었고, 비밀값은 저장소에 없다
- [ ] 미리보기용 우회 코드는 push하지 않았다
- [ ] 설계와 다르게 정한 것을 모두 결정 목록에 적고, 코드 결함과 설계서 갱신 요청을 나눴다

## 자주 하는 실수

- 병렬로 만든 앱과 서버가 enum 이름을 각자 추정한다. 단위 시험은 모두 통과하지만 실제 요청이 400으로 거부된다. 계약 시험을 서버·앱 양쪽에 두고, 계약 전에 가정한 값은 결정 목록에 표시해 전수 대조한다.
- 검증과 커밋을 `test | tail && commit`처럼 묶는다. `tail`의 종료 코드가 남아 실패한 상태가 커밋·push된다. `set -o pipefail`을 켜거나 결과를 확인한 뒤 따로 push한다.
- 작업자가 특정 커밋을 체크아웃한 상태에서 커밋을 쌓는다. 브랜치가 뒤처져 push가 일부만 올라간다. push 전에 `git branch --show-current`와 `git rev-parse HEAD`를 확인한다.
- 한 worktree에서 두 작업자를 동시에 돌린다. 한쪽이 상대의 스테이징 파일을 함께 커밋하거나 빌드·인덱스 잠금이 충돌한다. 폴더가 겹치지 않아도 같은 worktree면 순서대로 돌린다.
- 공용 빌드 캐시의 잠금 시간 초과를 보고 빌드 데몬을 모두 멈춘다. 다른 작업자의 빌드까지 끊긴다. 잠시 뒤 다시 시도한다.
- 단위 시험만 믿는다. 오류 응답 형식, 실패 시 화면 안내 누락, 시각 형식 같은 결함은 실제 서버에 붙여야 드러난다. 단계 묶음마다 미리보기를 돌린다.
- 리뷰 결함을 고치면서 설계서가 낡은 경우까지 코드 결함으로 센다. 설계가 낡았으면 설계서 갱신 요청으로 분리한다.
- 비밀값이 비면 임의 값으로 뜨는 개발 편의 설정을 운영에도 그대로 둔다. 운영 프로필에서는 필수 비밀값이 비면 기동이 실패해야 한다.
