# 통합·검증 게이트

`sw-implement` 4단계. 단계 결과를 통합 브랜치에 합칠 때마다 이 순서를 지킨다.

## 1. 순서

| 순서 | 할 일 | 판정 질문 |
|------|-------|-----------|
| 1 | 작업 worktree에서 검증 명령을 직접 다시 돌린다 | 작업자 보고와 같은 결과인가 |
| 2 | `git status`, `git log`, `git branch --show-current` | 작업 트리가 깨끗하고 브랜치가 맞는가 |
| 3 | 통합 브랜치에 `git merge --no-ff <커밋>` | 충돌이 있는가, 같은 키가 두 번 생겼는가 |
| 4 | 배포 설정·계약 자료 갱신 | 새 환경 변수·계약 변경이 모두 반영됐는가 |
| 5 | 통합 브랜치에서 모든 단위 검증 | 실패 시험 0인가 |
| 6 | 브랜치·HEAD 확인 후 push | `HEAD` = 브랜치 끝인가 |

## 2. 검증 명령을 묶을 때

```bash
set -o pipefail
ok=0
for t in 1 2 3; do
  if ./gradlew build -q > build.log 2>&1; then ok=1; break; fi
  grep -q "Timeout waiting to lock" build.log && { sleep 60; continue; }   # 공용 캐시 잠금만 재시도
  break
done
[ $ok = 1 ] && git push origin <통합 브랜치>
```

- `명령 | tail` 뒤에 `&&`를 붙이면 `tail`의 종료 코드가 남는다. `pipefail` 없이 묶지 않는다.
- 결과를 세는 `grep`·`xargs`도 일치가 없으면 0이 아닌 값을 낸다. 결과 확인과 push를 같은 줄의 종료 코드에 걸지 않는다.

## 3. 충돌이 잦은 파일

| 파일 | 원인 | 처리 |
|------|------|------|
| 버전 카탈로그(`libs.versions.toml` 등) | 여러 worktree가 같은 라이브러리를 추가 | 합집합 후 같은 키는 하나만, 값이 다르면 상위 호환(예: `core` → `core-ktx`) |
| 배포 설정(compose·배포 스크립트·CI) | 단위마다 서비스·변수 추가 | 서비스 블록 추가는 합치고, 같은 줄 수정은 양쪽 의도를 모두 반영 |
| 팀 규칙 파일의 스택 문구 | 스택 전환과 새 단위 추가가 같은 줄 | 통합 때 한 번에 고친다 |

줄바꿈이 CRLF인 파일을 스크립트로 고칠 때는 `\r?\n`을 처리한다.

## 4. 배포 설정

- 컨테이너마다 필요한 환경 변수만 넘긴다(환경 변수 파일 전체 주입 금지). 새 변수가 생기면 실행 설정의 목록과 예시 파일을 함께 고친다.
- 운영에서 필수인 비밀값은 실행 설정에서 필수 표시(`${VAR:?}`)하고, 서버도 운영 프로필에서 비면 기동을 실패시킨다.
- 실시간 연결(WebSocket)은 프록시에 Upgrade 헤더와 긴 읽기 제한을 둔다.
- 설정을 고치면 문법 검사(`docker compose config -q`, `nginx -t`, CI YAML 파싱)를 돌린다.

## 5. 위험 사례

| 사례 | 증상 | 예방 |
|------|------|------|
| 실패가 파이프에 묻힘 | 시험 실패 상태가 push됨 | `set -o pipefail`, push는 결과 확인 뒤 |
| detached HEAD에서 커밋 | 브랜치가 뒤처져 push가 일부만 올라감 | push 전 `git rev-parse HEAD`와 브랜치 끝 비교 |
| 같은 worktree 동시 작업 | 남의 스테이징 파일이 섞여 커밋 | worktree 하나에 작업자 하나 |
| 임시 우회 코드 혼입 | 개발용 로그인 등이 MR에 들어감 | 우회는 미리보기 worktree에만, push 금지 |
| 커밋 메시지와 내용 불일치 | 리뷰·이력 추적 실패 | push 전이면 메시지만 고친다(amend), 내용은 그대로 |
