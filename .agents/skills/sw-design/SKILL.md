## 인자

`$sw-design` 뒤에 이어 쓴다: `[design | review] [대상 파일 경로 (생략 가능)]`

## 목적

두 가지 일을 한다.

- **design**: `srs.md`의 "무엇"을 "어떻게"로 바꾼 **구조적 설계서** `docs/sw/design.md`를 만든다. 데이터 → 구조 → 인터페이스 → 절차 순서로 설계하고, 모듈을 나누고, 모듈 간 관계를 정한다.
- **review**: 설계서(`design.md` 또는 `design-oo.md`)의 모듈·패키지 의존도를 받아 **응집도는 높고 결합도는 낮은지**를 화살표 하나하나, 상자 하나하나에 등급을 매겨 판정하고 개선안을 낸다. 결과는 `docs/sw/design-review.md`.

`sw-code-review`가 설계 일치 점검의 기준으로, `sw-test`가 통합 테스트 순서(의존 방향)의 입력으로, `sw-maintain`이 변경 영향 범위 계산의 기준으로 이 산출물을 읽는다.

좋은 설계의 기준은 하나다. **각 모듈은 안에서 하나의 목적으로 단단히 뭉치고(응집도 높음), 모듈끼리는 느슨하게 연결되어 서로 간섭하지 않는다(결합도 낮음).** 유지보수 비용이 개발 비용보다 크다는 사실 때문에 이 기준은 처음부터 지켜야 한다.

## 입력

### design 모드
- `docs/sw/srs.md`. 없으면 `$sw-srs`를 먼저 안내하고 중단한다. 요구사항 없이 설계하면 "무엇"이 흔들릴 때마다 설계가 다시 바뀐다.
- 사용자에게 물어야 할 것:
  - 구조적 설계인가 객체지향 설계인가. 객체지향이면 `$sw-design-oo`로 안내한다. 이 스킬의 design 모드는 기능 분해 중심의 구조적 설계다.
  - 계층 구조(표현 → 응용 → 도메인 → 인프라)를 쓸 것인가, 단순 모듈 트리로 갈 것인가.
  - 기존 시스템·외부 연동의 인터페이스 규격이 정해져 있는가.

### review 모드
- `docs/sw/design.md` 또는 `docs/sw/design-oo.md`의 모듈/패키지 의존도. 둘 다 없으면 `$sw-design-oo` 또는 `$sw-design design`을 먼저 안내하고 중단한다.
- 사용자가 의존도 그림만 따로 들고 왔으면 그것을 입력으로 받되, 산출물 헤더 입력란에 "설계서 없음, 의존도 직접 입력"이라고 적는다.
- 검증 기준을 사용자와 합의한다. 기본값은 판정 기준 절에 있다.

## 절차 — design 모드

설계는 네 가지 모델을 순서대로 만든다. **데이터 설계 → 구조(아키텍처) 설계 → 인터페이스 설계 → 절차 설계.** 데이터가 먼저인 이유는 구조·인터페이스·절차가 모두 "어떤 데이터를 다루는가"에 따라 결정되기 때문이다. 원리와 지침은 `references/design-principles.md`를 읽는다.

### 1단계. 데이터 설계 (Data Design)

1. `srs.md`의 자료사전과 자료 저장소를 데이터 구조로 바꾼다. 저장소 하나가 보통 테이블(또는 파일) 하나다. 자료사전의 `{ }` 반복은 별도 테이블, `( )` 생략 가능은 NULL 허용, `[ | ]` 선택은 코드 값이 된다.
2. 각 데이터 구조의 키, 속성, 형식, 제약을 정한다. ERD가 있으면 그대로 옮기고, 없으면 여기서 그린다.
3. 자료 추상화를 적용한다. 데이터와 그 데이터에 대한 연산을 함께 묶어 "성적 레코드"처럼 이름 붙인 단위로 다룬다. 설계 전체에서 이 이름을 쓴다.
4. 데이터 접근 모듈을 정한다. 같은 저장소를 여러 모듈이 직접 읽고 쓰면 공통 결합도가 된다. 저장소마다 접근 모듈을 하나 두고 나머지는 그 모듈을 통한다.

판정 질문: 자료사전의 모든 저장소에 대응하는 데이터 구조가 있는가? 저장소마다 접근 모듈이 하나로 정해졌는가?

### 2단계. 구조 설계 (Architectural Design)

1. **단계적 분해**로 시스템을 모듈 트리로 나눈다. 최상위는 시스템 전체, 그 아래는 `srs.md` DFD Level 1의 프로세스, 그 아래는 Level 2 프로세스다. DFD가 하향식으로 그려져 있으므로 모듈 트리는 DFD에서 거의 그대로 나온다.
2. 트리의 모양을 측정한다. `references/design-principles.md`의 프로그램 구조 항목을 본다.
   - 깊이(Depth): 계층 수. 7을 넘으면 중간 계층을 합친다.
   - 넓이(Width): 한 계층의 모듈 수. 한 상위 모듈 아래 7개를 넘으면 묶는다.
   - Fan-Out: 한 모듈이 호출하는 하위 모듈 수. 7 이하로 둔다.
   - Fan-In: 한 모듈을 호출하는 상위 모듈 수. 공용 모듈은 높아도 되지만, 그 모듈은 바뀌면 안 된다.
3. 모듈마다 **책임을 한 문장**으로 쓴다. 문장에 "그리고", "및"이 들어가면 모듈을 나눈다. 이 문장이 review 모드의 응집도 판정 입력이다.
4. 계층을 쓴다면 모듈마다 계층(표현/응용/도메인/인프라)을 적는다. 하위 계층은 상위 계층을 호출하지 않는다.
5. 공용 모듈(여러 곳에서 쓰는 검증, 변환, 로그)을 따로 모으되, "기타", "공통", "유틸"이라는 이름으로 서로 무관한 것을 한 모듈에 넣지 않는다. 날짜 처리와 전역 설정은 다른 모듈이다.

판정 질문: 모든 모듈에 한 문장 책임이 있는가? Fan-Out 7 초과 모듈이 0개인가? 하위 계층 → 상위 계층 호출이 0건인가?

### 3단계. 인터페이스 설계 (Interface Design)

1. 모듈 간 인터페이스를 정한다. 호출하는 모듈, 호출받는 모듈, 넘기는 것(매개변수 이름·형식), 돌려받는 것, 오류 시 동작. **넘기는 것**을 구체적으로 적어야 review 모드에서 결합도를 판정할 수 있다.
2. 넘기는 것은 **필요한 값만**으로 제한한다. 구조체·객체 전체를 넘기면 스탬프 결합도, 제어 플래그를 넘기면 제어 결합도가 된다. 전역 변수로 주고받지 않는다.
3. 정보 은닉을 적용한다. 모듈 내부의 데이터 구조와 알고리즘은 밖에서 모르게 하고 인터페이스만 공개한다. 외부가 알아야 하는 것은 "무엇을 하는가"이지 "어떻게 하는가"가 아니다.
4. 사용자 인터페이스(화면)와 외부 시스템 인터페이스는 `srs.md` 5장을 설계 수준으로 구체화한다. 화면 흐름, 입력 검증 위치, 외부 연동 규격(형식, 빈도, 실패 시 재시도).
5. 인터페이스는 **단순**하게 유지한다. 매개변수는 4개 이하로 유지하고, 5개 이상이 되면 자료 추상화로 묶되, 묶은 구조 전체를 넘기는 것이 스탬프 결합도임을 알고 선택한다.

판정 질문: 모든 모듈 간 호출에 "넘기는 것"이 명시되어 있는가? 전역 변수 공유가 0건인가?

### 4단계. 절차 설계 (Procedural Design)

1. 최하위 모듈마다 처리 절차를 쓴다. `srs.md`의 소단위 명세서를 입력으로, 순차·선택·반복 세 가지 제어 구조만으로 알고리즘을 서술한다. 의사코드, 순서도, N-S 도표 중 하나를 쓴다.
2. **단일 입구·단일 출구.** 모듈은 들어오는 곳 하나, 나가는 곳 하나다. 중간 탈출(goto, 여러 return)을 설계에 넣지 않는다.
3. 입력이 같으면 출력이 같아야 한다(예측 가능). 모듈 안에 숨은 상태(이전 호출 결과를 기억하는 전역 변수)를 두지 않는다.
4. 오류 처리 절차를 함께 쓴다. 어떤 입력을 거부하는지, 거부하면 무엇을 돌려주는지.
5. 모듈 크기를 본다. 한 모듈의 절차가 한 화면(약 50~100줄)을 넘으면 단계적 분해를 한 번 더 한다. 너무 잘게 쪼개 모듈이 수백 개가 되면 인터페이스 비용이 커지므로 합친다.

판정 질문: 모든 최하위 모듈에 절차가 있는가? 세 가지 제어 구조 외의 흐름(goto, 다중 출구)이 0건인가?

### 5단계. 의존도 작성과 자체 점검

1. 모듈(또는 패키지) 의존도를 그린다. 상자 = 모듈/패키지, 화살표 = 호출·참조 방향. 화살표마다 3단계에서 정한 "넘기는 것"을 붙인다.
2. 바로 **review 모드**를 실행해 `design-review.md`를 만든다. 설계서와 검증 결과서는 한 쌍이다.
3. 추적표를 갱신한다. `srs.md` 추적표의 "설계 요소" 열에 FR마다 담당 모듈 이름을 적는다.

## 절차 — review 모드

그림만 보고 "결합도가 낮아 보인다"고 판정하지 않는다. **화살표마다 무엇을 주고받는지 적어야 등급이 나오고, 상자마다 왜 같이 있는지 물어야 응집도가 나온다.** 등급 정의와 질문표는 `references/coupling.md`, `references/cohesion.md`, 구조 결함은 `references/structural-defects.md`를 읽는다.

### 0단계. 입력 정리

1. **패키지(모듈) 목록표**를 만든다. 열: ID(P1…), 이름, 계층, 책임 한 문장, 포함 요소. 책임 문장에 "그리고/및/등"이 있으면 표시해 둔다(3단계 응집도 의심 대상). 이름이 `common`, `util`, `misc`, `base`, `core`면 마찬가지로 표시한다.
2. **의존 화살표 목록표**를 만든다. 다이어그램의 화살표 하나가 한 행이다. 열: No(D1…), From, To, 의존 형태(메서드 호출 / 필드 접근 / 전역 참조 / FK 참조 / 파일 공유 …), **주고받는 것**. 주고받는 것이 설계서에 없으면 사용자에게 묻거나 코드를 보고 채운다. 추정으로 채웠으면 "(추정)"이라고 적는다.
3. 검증 기준을 확정한다. 기본값: 결합도 상한 스탬프(제어는 검토 대상, 외부·공통·내용은 불허), 응집도 하한 통신적, Fan-Out 상한 7, 순환 0.

### 1단계. 의존 행렬과 Fan-In / Fan-Out

1. **의존 행렬**을 만든다. 행 = 의존하는 쪽(From), 열 = 의존받는 쪽(To). 화살표가 있으면 1(또는 화살표 수).
2. 행 합계 = Fan-Out(내가 부르는 수), 열 합계 = Fan-In(나를 부르는 수).
3. **불안정도** `I = Fan-Out / (Fan-In + Fan-Out)`를 계산한다. 0에 가까우면 안정(많이 불리고 적게 부름), 1에 가까우면 불안정. Fan-In과 Fan-Out이 모두 0이면 고립이므로 "-"로 둔다.
4. 해석한다.
   - Fan-In이 높은 모듈 = 재사용되는 공용 모듈 = 바뀌면 영향 범위가 넓다. 안정적이어야 한다.
   - Fan-Out이 높은 모듈 = 조정자 = 복잡도가 높다. 7을 넘으면 4단계 허브 후보.
   - 화살표는 불안정한 쪽 → 안정한 쪽으로 향해야 한다. 반대면 4단계 안정성 위반.

### 2단계. 결합도 판정 (화살표마다)

1. 화살표 하나씩 `references/coupling.md`의 질문표를 **나쁜 것부터** 묻는다. 먼저 "예"가 나오는 것이 그 화살표의 등급이다.

   | 순서 | 질문 | 등급 |
   |------|------|------|
   | 1 | 상대의 내부 필드·private 멤버·내부 구현을 직접 읽거나 고치는가 | 내용 |
   | 2 | 전역 변수·static 가변 상태·싱글턴의 가변 상태를 함께 쓰는가 | 공통 |
   | 3 | 같은 파일·DB 테이블·장치·환경 변수를 직접 공유하는가 | 외부 |
   | 4 | flag·mode·type 같은 제어 신호를 넘겨 상대 내부 분기를 결정하는가 | 제어 |
   | 5 | 구조체·객체·DTO·배열 전체를 넘기는가 (일부 필드만 쓰더라도) | 스탬프 |
   | 6 | 필요한 단순 값만 넘기고 결과만 받는가 | 데이터 |

2. **화살표별 판정표**를 쓴다. 열: No, From → To, 주고받는 것, 등급, 기준 대비(허용/검토/불허), 근거.
3. **패키지 쌍 요약.** 같은 두 패키지 사이에 화살표가 여럿이면 **가장 나쁜 등급**이 그 쌍의 결합도다.
4. 양방향(A→B와 B→A 모두 존재)은 표시해 4단계 순환 의존으로 넘긴다.
5. FK 화살표로 보이지 않는 **숨은 의존**을 찾는다. 다른 패키지 데이터로부터 계산되는 파생 컬럼, 같은 설정 파일 참조, 같은 메시지 큐 토픽. 원본이 바뀌면 함께 바뀌어야 하므로 암묵적 결합이다. 찾으면 목록에 추가하고 갱신 책임을 적게 한다.

### 3단계. 응집도 판정 (패키지마다)

1. 0단계 책임 문장을 다시 본다. "그리고"가 있거나 이름이 `common`류면 의심 대상.
2. 패키지 안의 요소들이 **왜 같이 있는지** `references/cohesion.md`의 질문표를 **좋은 것부터** 묻는다. 먼저 "예"가 나오는 것이 등급이다.

   | 순서 | 질문 | 등급 |
   |------|------|------|
   | 1 | 모든 요소가 하나의 기능만을 위해 존재하는가 | 기능적 |
   | 2 | 한 요소의 출력이 다음 요소의 입력으로 이어지는가 | 순차적 |
   | 3 | 같은 데이터(엔티티)를 다루기 때문에 모였는가 | 통신적 |
   | 4 | 업무 순서상 함께 실행되어서 모였는가 (데이터 공유 없음) | 절차적 |
   | 5 | 같은 시점(초기화·종료)에 실행되어서 모였는가 | 시간적 |
   | 6 | 종류가 비슷해서(출력 함수 모음, 유틸 모음) 모였는가 | 논리적 |
   | 7 | 아무 이유 없이 모였는가 | 우연적 |

3. **패키지별 판정표**를 쓴다. 열: ID, 패키지, 같이 있는 이유, 등급, 기준 대비, 근거.
4. **잘못 배치된 요소**를 찾는다. 패키지 안의 어떤 모듈이 같은 패키지 안의 모듈보다 다른 패키지의 모듈과 더 많이 연결되어 있으면 옮겨야 한다. 내부 연결 수 < 외부 연결 수인 모듈을 이동 후보로 적는다.

### 4단계. 구조 결함 점검

행렬과 판정표에서 전체 그래프 모양의 문제를 찾는다. 정의와 판별법은 `references/structural-defects.md`.

| 결함 | 판별 |
|------|------|
| 순환 의존 | A→B와 B→A, 또는 A→B→C→A 경로 |
| 계층 역행 | 하위 계층(도메인·인프라) → 상위 계층(표현·응용) 화살표 |
| 허브 패키지 | Fan-In과 Fan-Out이 모두 높음(각각 상위 20% 또는 Fan-Out > 7) |
| 쓰레기통 패키지 | Fan-In 높음 + 응집도 논리적 이하 |
| 안정성 위반 | 불안정도 낮은(안정) 패키지가 높은(불안정) 패키지에 의존 |
| 고립 패키지 | Fan-In = 0 이고 Fan-Out = 0 |
| 정보 은닉 위반 | 내용 결합도 화살표 1건 이상 |

결함마다 관련 패키지와 근거 화살표 번호를 적는다.

### 5단계. 판정과 개선안

1. **검증 결과서**에 0~4단계 표를 모으고 항목별 합격/불합격을 표시한다.
2. 발견한 문제마다 개선 기법을 붙인다.

   | 문제 | 개선 기법 |
   |------|-----------|
   | 내용 결합 | 내부 필드를 감추고 공개 메서드로만 접근 (`b.status = X` → `b.markDone()`) |
   | 공통 결합 | 전역 변수 제거. 필요한 값을 인자로 넘기거나 설정 객체 주입 |
   | 외부 결합 | 파일·DB 접근을 인프라 모듈 하나에 몰고 나머지는 인터페이스만 사용 |
   | 제어 결합 | 플래그 대신 별도 메서드로 분리하거나 다형성으로 분기를 호출자 밖으로 |
   | 스탬프 결합 | 실제로 쓰는 값만 넘김 (필요할 때만) |
   | 순환 의존 | 한쪽이 필요로 하는 것을 인터페이스로 뽑아 제3 패키지에 두고 양쪽이 그것에 의존 |
   | 계층 역행 | 하위가 상위를 직접 부르지 않고 이벤트·콜백·인터페이스로 알림 |
   | 논리적·우연적 응집 | 목적별로 분할 (`common` → `dateutil`, `config`) |
   | 잘못 배치 | 가장 많이 연결된 패키지로 이동 |
   | 높은 Fan-Out | 하위 패키지를 묶는 중간 패키지(퍼사드) |

3. 우선순위: **내용·공통 결합도와 순환 의존을 먼저** 없앤다. 이 둘이 남아 있으면 다른 개선이 의미가 없다.
4. 개선안을 반영한 **2차 의존도**를 그린다.

### 6단계. 재검증과 확정

1. 2차 의존도로 0~4단계를 반복한다. 표만 갱신하면 되므로 빠르다.
2. **전후 비교표**를 쓴다. 항목: 내용·공통·외부 결합 화살표 수, 제어 결합 화살표 수, 순환 수, 계층 역행 수, 응집도 통신적 미만 패키지 수, 최대 Fan-Out, 패키지 수.
3. 부작용을 본다. 분할로 Fan-Out이 기준을 넘지 않았는가, 새 인터페이스 패키지가 또 다른 쓰레기통이 되지 않았는가.
4. 최종 판정(합격 / 조건부 합격 / 불합격)을 내리고 설계서 버전을 올린다.

## 판정 기준

### 결합도 (화살표별)

| 등급 | 기준 대비 |
|------|-----------|
| 데이터 | 허용 |
| 스탬프 | 허용 (쓰는 필드가 전체의 절반 미만이면 "검토" 표시) |
| 제어 | 검토. 개선안을 반드시 쓴다 |
| 외부 | 불허 |
| 공통 | 불허 |
| 내용 | 불허 |

### 응집도 (패키지별)

| 등급 | 기준 대비 |
|------|-----------|
| 기능적, 순차적, 통신적 | 허용 |
| 절차적, 시간적 | 검토. 개선안을 쓴다 |
| 논리적 | 불허. 단, 변경이 드문 읽기 전용 참조 데이터(코드 테이블)만 모인 경우 조건부 허용 |
| 우연적 | 불허 |

### 구조

| 항목 | 합격 조건 |
|------|-----------|
| 순환 의존 | 0건 |
| 계층 역행 | 0건 |
| 최대 Fan-Out | 7 이하 |
| 내용 결합도 화살표 | 0건 |
| 고립 패키지 | 0개 (있으면 입력 누락 여부 확인) |

### 최종 판정

| 판정 | 조건 |
|------|------|
| 합격 | 불허 항목 0건, 검토 항목 0건 |
| 조건부 합격 | 불허 항목 0건, 검토 항목 1건 이상이고 각각 개선안이 있음 |
| 불합격 | 불허 항목 1건 이상 |

### design 모드 설계서

| 항목 | 합격 조건 |
|------|-----------|
| 데이터 설계 | 자료사전의 모든 저장소에 데이터 구조 존재, 저장소별 접근 모듈 1개 |
| 구조 설계 | 모든 모듈에 한 문장 책임, Fan-Out ≤ 7, 깊이 ≤ 7 |
| 인터페이스 설계 | 모든 호출에 "넘기는 것" 명시, 전역 변수 공유 0건, 매개변수 ≤ 5 |
| 절차 설계 | 최하위 모듈 100%에 절차, 단일 입구·출구 |
| 추적 | 모든 FR에 담당 모듈 1개 이상 |

## 출력

- design 모드: `docs/sw/design.md`. 양식 `templates/design.md`, 예시 `examples/design.md`.
- review 모드: `docs/sw/design-review.md`. 양식 `templates/design-review.md`, 예시 `examples/design-review.md`.
- 첫 두 줄: `# <프로젝트명> 설계서` 또는 `# <프로젝트명> 설계 검증 결과서` / `> 작성: YYYY-MM-DD | 버전: vX.Y | 입력: srs.md v1.1` (review는 `design-oo.md v1.0` 등).
- design 모드를 마치면 review 모드를 이어서 실행한다. 두 산출물이 모두 있어야 설계 단계가 끝난다.
- 다음 단계: `$sw-code-review` (구현 후) 또는 `$sw-test` (V 모형이면 설계 직후 테스트 계획).
- 협업 모드: `docs/sw/OWNERS.md`가 있으면 저장 전에 그 규칙을 따른다. `git config user.name`으로 작성자를 찾아 그 사람 담당 파일만 고친다. 새 번호는 `[임시:FR-<이니셜>-1]` 형식으로 쓰고 산출물 버전은 올리지 않는다(변경 표시는 "(다음 판 변경)"). 목차 파일의 머리 헤더·문서 상태·목차, `docs/sw/README.md`, 공용 조각(추적표, 자료사전 등)에 들어갈 내용과 남의 파일에 고칠 것은 `docs/sw/pending/<브랜치 이름의 / 를 - 로>.md`에 적는다. 정식 번호와 버전은 공용 담당이 `$sw-sdlc merge`로 매긴다. 규칙 전문은 CONVENTIONS 8절과 OWNERS.md 3절이다.

## 체크리스트

### design 모드
- [ ] 데이터 → 구조 → 인터페이스 → 절차 순서로 작성했다
- [ ] 모든 모듈에 "그리고/및"이 없는 한 문장 책임이 있다
- [ ] `common`, `util`, `misc` 이름의 모듈에 서로 무관한 것을 넣지 않았다
- [ ] 모든 모듈 간 호출에 넘기는 것(매개변수)이 적혀 있다
- [ ] 전역 변수로 모듈 간 자료를 주고받는 설계가 없다
- [ ] 제어 플래그로 하위 모듈의 분기를 결정하는 인터페이스가 없다
- [ ] 저장소마다 접근 모듈이 하나다
- [ ] 절차 설계에 순차·선택·반복 외의 제어 구조(goto)가 없다
- [ ] 모듈은 단일 입구·단일 출구다
- [ ] 추상화 기법으로 기능·제어·자료 세 가지를 썼다 (정보 은닉은 추상화 기법이 아니라 모듈 설계 원리다)
- [ ] 설계를 "전체적으로 통합"하지 않고 모듈로 분리했다
- [ ] 추적표의 설계 요소 열을 채웠다
- [ ] review 모드를 실행해 `design-review.md`를 함께 만들었다

### review 모드
- [ ] 화살표마다 "주고받는 것"을 적었다. 추정이면 (추정) 표시를 했다
- [ ] 결합도를 패키지 단위가 아니라 화살표 단위로 매겼다. 쌍은 최악 등급으로 요약했다
- [ ] 결합도 질문은 나쁜 것부터, 응집도 질문은 좋은 것부터 물었다
- [ ] Fan-In이 높은 `common`을 "재사용성 좋다"로만 해석하지 않고 응집도를 함께 봤다
- [ ] 양방향 화살표를 "협력"으로 넘기지 않고 순환 의존으로 다뤘다
- [ ] 불안정도 방향(불안정 → 안정)을 확인했다
- [ ] 숨은 의존(파생 데이터, 공유 설정)을 찾았다
- [ ] 개선안에 내용·공통 결합과 순환 의존을 최우선으로 두었다
- [ ] 2차 의존도로 재검증하고 전후 비교표를 썼다
- [ ] 최종 판정을 합격 / 조건부 합격 / 불합격 중 하나로 적었다

## 자주 하는 실수

- **그림만 보고 결합도를 판정한다.** 화살표가 적어 보여도 하나가 내용 결합이면 불합격이다. 주고받는 것을 적어야 한다.
- **결합도를 패키지에 하나만 매긴다.** 같은 두 패키지 사이에 데이터 결합 5개와 내용 결합 1개가 있으면 그 쌍은 내용 결합이다.
- **"관련 있어 보인다"로 응집도를 판정한다.** 왜 같이 있는지(같은 기능 / 같은 데이터 / 같은 순서 / 같은 시점 / 비슷한 종류)를 물어야 등급이 나온다.
- **`common`의 높은 Fan-In을 좋은 신호로만 본다.** 응집도가 논리적 이하이면 쓰레기통이다. 하나를 고치면 전부 다시 테스트해야 한다.
- **양방향 의존을 "서로 협력한다"로 넘긴다.** 순환은 한쪽만 수정·테스트·배포할 수 없게 만든다. 사실상 하나의 패키지다.
- **설계서에 인터페이스 매개변수를 안 쓴다.** 그러면 코드 리뷰에서 설계 일치를 확인할 수 없고, 결합도도 판정할 수 없다.
- **데이터 설계 없이 구조부터 그린다.** 나중에 데이터 구조가 바뀌면 모듈 경계가 다 흔들린다.
- **개선 후 재검증을 생략한다.** 분할하면 Fan-Out이 늘고, 인터페이스 패키지를 새로 만들면 그것이 새 쓰레기통이 될 수 있다.
- **정보 은닉을 추상화의 한 종류로 쓴다.** 추상화 기법은 기능·제어·자료 셋이고, 정보 은닉은 모듈 설계 원리다. 용어를 섞으면 설계서 독자가 혼란스럽다.
