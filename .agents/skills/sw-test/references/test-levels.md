# 테스트 수준과 순서

## 1. 테스트의 목적 (Myers)

- 테스트의 목적은 **오류가 존재함을 보이는 것**이다. 오류가 없음을 증명하는 것이 아니다.
- 좋은 테스트 케이스는 **아직 발견되지 않은 오류**를 찾아낼 확률이 높은 케이스다.
- 성공한 테스트는 통과한 테스트가 아니라 **오류를 발견한** 테스트다.
- 테스트는 대표성과 효과가 높은 케이스로 수행한다. 모든 입력을 다 넣을 수는 없다.

이 관점이 케이스 설계를 바꾼다. "잘 되는지 보자"가 아니라 "어디서 깨지는지 보자"로 입력을 고른다.

## 2. 테스트 케이스의 구성

| 요소 | 내용 |
|------|------|
| 입력값 | 데이터와 상태 |
| 실행 조건 | 사전 조건, 권한, 환경 |
| 기대 결과 | 관찰 가능한 출력, 저장, 상태 변화, 메시지 |

기대 결과가 없으면 테스트가 아니라 실행이다. 기대 결과는 SRS와 설계서에서 온다.

## 3. 네 수준

| 수준 | 단위 | 질문 | 기준 문서 (V-모델) |
|------|------|------|--------------------|
| 단위 테스트 | 클래스 (또는 함수) 하나 | 이 클래스가 명세대로 동작하는가 | 상세 설계 (클래스 설계, 알고리즘) |
| 통합 테스트 | 클래스 묶음 | 각각은 되는데 **연결했을 때도** 되는가 | 시스템 설계 (아키텍처, 인터페이스, 시퀀스) |
| 검증 (Validation) | 전체 기능 | 사용자가 원한 **그것**인가 | 요구사항 명세서 (FR) |
| 시스템 테스트 | 운영 환경의 전체 | 성능·보안·장애·운영 시나리오를 견디는가 | 요구사항 명세서 (NFR), 운영 환경 |

객체지향에서 **단위 = 클래스**다. 메소드 하나를 따로 떼면 객체 상태와의 상호작용이 빠지고, 패키지 전체를 묶으면 실패 원인을 좁힐 수 없다.

순서는 단위 → 통합 → 검증 → 시스템이다. 앞 수준이 합격해야 다음으로 간다.

## 4. V-모델 대응

```
요구사항 분석  ─────────────────────────  시스템 테스트 / 검증
    │                                          ▲
    시스템 설계  ───────────────────  통합 테스트
        │                               ▲
        상세 설계  ───────────  단위 테스트
            │                    ▲
            구현  ───────────────┘
```

왼쪽 산출물을 쓸 때 오른쪽 테스트의 합격 기준을 함께 정한다. 그래서 V-모델에서는 `sw-test`를 설계 직후에 한 번(계획만), 구현 후 다시 한 번(케이스 채움) 호출한다.

## 5. 통합 전략

### 스레드 기반 (Thread-based)

하나의 입력·이벤트에 응답하기 위해 협력하는 클래스들을 **한 스레드**로 묶어 테스트한다. 설계서의 시퀀스 다이어그램 하나가 스레드 하나다.

```
"성적 입력" 스레드:
  GradeController → GradeService → GradeCalculator
                                 → StudentRepository (학적 상태 확인)
                                 → GradeRepository (저장)
```

장점: 사용자 시나리오 단위라 빨리 의미 있는 결과를 얻는다. GUI·대화식 시스템에 적합.
단점: 하위 클래스의 결함이 여러 스레드에서 반복 발견된다.

### 사용 기반 (Use-based)

다른 클래스에 의존하지 않는 **독립 클래스**부터 테스트하고, 그것을 사용하는 **종속 클래스**로 한 층씩 올라간다.

```
1층: Grade, Student, Course (엔티티. 의존 없음)
2층: GradeCalculator (Grade만 사용)
3층: GradeRepository, StudentRepository (엔티티 + DB 스텁)
4층: GradeService (2, 3층 사용)
5층: GradeController (4층 사용)
```

장점: 결함 위치가 명확하다. 하위 층이 안정된 뒤 올라가므로 재테스트가 적다.
단점: 상위 시나리오를 확인하기까지 오래 걸린다.

### 혼합

도메인·인프라 계층은 사용 기반으로 바닥을 다지고, 응용·표현 계층은 스레드 기반으로 시나리오를 돌린다. 대부분의 프로젝트가 이렇게 한다.

## 6. 스텁과 드라이버

| 도구 | 역할 | 언제 |
|------|------|------|
| 스텁(stub) | 아직 없거나 외부에 있는 **하위** 모듈을 흉내 냄 | 외부 DB, 외부 API, 미구현 클래스 |
| 드라이버(driver) | 아직 없는 **상위** 모듈 대신 테스트 대상을 호출 | 컨트롤러 없이 서비스를 테스트할 때 |

스텁이 반환하는 값은 테스트 케이스의 입력 칸에 적는다. 스텁이 숨겨진 가정을 가지면 안 된다.

## 7. 검증과 확인의 구분

| 용어 | 질문 | 수행자 |
|------|------|--------|
| 검증 (Verification) | **올바르게** 만들었는가 (설계대로) | 개발자, 리뷰어 |
| 확인 (Validation) | **올바른 것**을 만들었는가 (사용자가 원한 것) | 사용자, 발주자 참여 |

테스트 수준 이름의 "검증 단계"는 요구사항 기반 테스트로 확인(Validation)에 가깝다. 강의 용어를 따라 "검증"으로 부르되, 질문은 "사용자가 원한 그것인가"다. 상세 구분은 `sw-sqa`의 `references/review-types.md`.

## 8. 시스템 테스트 항목

| 항목 | 내용 | 측정 |
|------|------|------|
| 성능 | 응답 시간, 처리량 | 동시 n 세션에서 p95 응답 시간 |
| 부하·스트레스 | 요구 이상의 부하 | 한계 동시 사용자 수, 복구 시간 |
| 보안 | 권한 우회, 주입 | 권한 없는 요청 100% 거부 |
| 장애·복구 | DB 단절, 디스크 가득 참, 프로세스 재시작 | 데이터 손실 0, 복구 시간 |
| 설치·호환 | 목표 OS·브라우저 | 지원 목록 100% |
| 운영 시나리오 | 학기 시작일 수강신청 폭주 등 실제 상황 | 시나리오별 합격 조건 |

NFR마다 측정 방법과 합격 수치를 케이스에 적는다.

## 9. 용어 대조

| 강의 표현 | 이 문서 |
|-----------|---------|
| Glen Myers의 테스트 원칙 | 1절 |
| 단위 테스트 = 클래스 테스트 | 3절 |
| Thread-based / Use-based | 5절 |
| 단위 → 통합 → 검증 → 시스템 | 3절 순서 |
| 요구분석↔시스템, 시스템설계↔통합, 상세설계↔단위 | 4절 V-모델 |
| 할아버지 → 아버지 → 아들 클래스 순 테스트 | 5절 사용 기반 |
