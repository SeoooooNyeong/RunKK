# 형상 관리(Software Configuration Management)

형상 관리는 소프트웨어 개발 전 과정에서 생기는 모든 산출물과 그 변경을 체계적으로 추적·통제·기록하는 활동이다. 한 문장으로는 **"개발 과정의 변경 사항을 관리하는 것"** 이다.

## 1. 형상(Configuration)이란

개발 과정에서 만들어지는 **모든 결과물** 전체다.

| 형상 항목인 것 | 형상 항목이 아닌 것 |
|----------------|---------------------|
| 요구사항 명세서, 설계 문서 | 개발 비용, 예산 |
| 소스 코드, 실행 파일, 라이브러리 | 개발 인력 명단 |
| 테스트 계획·절차·결과 | 회의 일정 |
| 사용자·관리자 매뉴얼 | |
| 데이터 구조, 스키마, 초기 데이터 | |
| 버전 정보, 변경 요청서, 변경 처리 보고서 | |
| 유지보수 문서 | |

비용은 형상 항목이 아니다. 형상 관리의 **효과**가 비용 절감일 수는 있지만 비용 자체를 형상으로 관리하지는 않는다.

## 2. 목적

- 변경을 통제한다. 승인 없는 변경이 기준선에 들어가지 않게 한다.
- 누가, 무엇을, 언제, 왜 바꿨는지 추적한다.
- 버전 혼란(어느 것이 최신인가, 고객에게 나간 것이 어느 것인가)을 막는다.
- 기존 사용자에게 가는 피해를 최소화한다.
- 변경에 드는 전체 비용을 줄인다.
- 유지보수를 쉽게 한다.

형상 관리와 관련 **없는** 것: 개발 인력 관리, 테스트 단계에서 소프트웨어를 통합하는 것(이는 통합 테스트), 책임 프로그래머 팀 구성(이는 조직 계획).

## 3. 다섯 가지 활동

| 활동 | 하는 일 | 코드 리뷰에서 확인하는 것 |
|------|---------|---------------------------|
| 형상 식별 | 모든 형상 항목에 이름·번호·버전을 부여 | 파일이 어느 모듈·버전에 속하는지 식별 가능한가 |
| 버전 제어 | 버전 이력을 보관하고 특정 버전으로 되돌릴 수 있게 함 (Git, SVN) | 커밋 이력, 태그, 버전 번호가 있는가 |
| 변경 통제 | 변경 요청 접수 → 영향 분석 → 승인/기각 → 반영. 기준선(baseline) 중심 | 변경이 승인된 요청·요구사항 ID와 연결되는가 |
| 형상 감사 | 변경이 기준선에 맞게 정확히 반영되었는지 공식 확인 | diff로 기준선 대비 변경을 확인할 수 있는가 |
| 상태 보고 | 식별·변경·감사 내용을 기록하고 보고 | 변경 이력이 사람이 읽을 수 있게 남는가 |

## 4. 기준선(Baseline)

공식 검토를 거쳐 확정된 산출물의 상태다. 기준선이 된 산출물은 변경 통제 절차 없이는 바꿀 수 없다. 전형적인 기준선:

| 기준선 | 확정 시점 | 산출물 |
|--------|-----------|--------|
| 요구사항 기준선 | SRS 승인 | `docs/sw/srs.md` v1.0 |
| 설계 기준선 | 설계 검토 통과 | `docs/sw/design*.md` |
| 제품 기준선 | 시스템 테스트 통과 | 릴리스 태그 |

`sw-srs` 6단계의 승인, `sw-sqa`의 FTR 통과가 기준선을 만드는 사건이다.

## 5. 기본 규칙 (프로젝트 규약이 없을 때)

### 브랜치

| 브랜치 | 용도 | 수명 |
|--------|------|------|
| `main` | 제품 기준선. 릴리스 태그만 붙음 | 영구 |
| `develop` | 통합 브랜치 | 영구 |
| `feature/FR-012-grade-input` | 요구사항 ID + 짧은 설명 | 병합 후 삭제 |
| `fix/CR-007-win11-print` | 변경 요청 ID + 설명 | 병합 후 삭제 |

### 커밋 메시지

```
<유형>(<모듈>): <요약 50자 이내>

<본문: 왜 바꿨는지>

Refs: FR-012, CR-007
```

유형: `feat`(기능), `fix`(수정 보수), `refactor`(동작 불변 재구성), `docs`, `test`, `chore`. 본문에는 "무엇을"이 아니라 "왜"를 쓴다. 무엇을 바꿨는지는 diff가 보여 준다.

### 태그와 버전

`vMAJOR.MINOR.PATCH`. 요구사항이 바뀌는 개선 보수는 MINOR, 수정·적응 보수는 PATCH, 호환성이 깨지면 MAJOR.

### 변경 통제 절차

```
변경 요청서(CR-nnn) 접수
  → 영향 분석: 어느 요구 ID, 어느 설계 모듈, 어느 테스트 케이스가 영향받는가
  → 비용·일정 추정
  → 승인 / 기각 / 보류
  → 승인 시 브랜치 생성 → 구현 → 리뷰 → 테스트 → 병합
  → 버전 갱신, 변경 이력 기록, 관련 문서(SRS·설계서) 갱신
```

## 6. 점검 양식

```
| 활동 | 판정 | 근거 |
| 형상 식별 | 예 | 패키지·클래스가 설계서 모듈 ID와 1:1 |
| 버전 제어 | 예 | Git, 태그 v0.9.0 |
| 변경 통제 | 아니오 | 커밋에 요구 ID 없음. CR 절차 미정의 |
| 형상 감사 | 예 | v0.9.0 대비 diff 확인 가능 |
| 상태 보고 | 아니오 | CHANGELOG 없음. 커밋 메시지 "수정", "update" 다수 |
아니오 2건 → 조건부
```

## 7. 용어 대조

| 강의 표현 | 이 문서 |
|-----------|---------|
| 형상 = 개발 과정의 모든 결과물 | 1절 |
| 형상 식별 / 버전 제어 / 변경 제어(통제) / 형상 감사 / 상태 보고(Status Accounting) | 3절 다섯 활동 |
| 기준선(baseline) | 4절 |
| 형상 관리 대상이 아닌 것: 시스템 개발 비용 | 1절 오른쪽 열 |
| 형상관리팀 ≠ chief programmer team | 2절 마지막 단락 |
