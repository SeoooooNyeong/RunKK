## 인자

`$sw-code-review` 뒤에 이어 쓴다: `[코드 경로 또는 디렉터리] [--style-only]`

## 목적

구현(Implementation)은 설계 명세서를 컴퓨터가 이해할 수 있는 코드로 변환하는 단계다. 이 스킬은 변환이 제대로 되었는지를 네 축으로 점검한다.

1. 설계 일치: 설계서의 클래스·모듈·인터페이스가 코드에 그대로 있는가
2. 코딩 스타일: 읽기 쉽고 유지보수하기 쉬운 코드인가
3. 구조적·객체지향 원칙: 순차·선택·반복만으로 짜였는가, 정보 은닉이 지켜졌는가
4. 형상 관리: 이 코드가 어떤 버전·브랜치·변경 요청에 묶여 있는지 추적되는가

결과는 `docs/sw/code-review.md`에 날짜별 절로 누적되고, `sw-test`가 테스트 대상 모듈과 순환 복잡도 상위 함수를 고를 때 읽는다. `sw-sqa`는 이 결과서의 치명 결함 수를 FTR 합격 조건에 쓴다.

## 입력

- 리뷰할 코드 경로. 인자로 받거나 사용자에게 묻는다. 디렉터리면 소스 파일 전체를 대상으로 하되, 변경된 파일이 있으면(git diff) 그것을 우선한다.
- `docs/sw/design-oo.md` 또는 `docs/sw/design.md` 중 하나. 둘 다 없으면 "설계서가 없어 설계 일치 점검을 생략한다"고 경고하고 **스타일·구조·형상 관리만** 점검한다. 이때 결과서 판정은 "조건부"를 넘지 못한다. 설계서를 만들려면 `$sw-design-oo` 또는 `$sw-design`을 먼저 안내한다.
- `docs/sw/design-review.md`가 있으면 거기서 확정한 결합도·응집도 기준(허용 상한·하한, Fan-Out 상한)을 그대로 쓴다. 없으면 기본값(결합도 스탬프 이하, 응집도 통신적 이상, Fan-Out 7 이하)을 쓴다.
- `docs/sw/srs.md`가 있으면 코딩 스타일 규약(언어, 명명 규칙)이 비기능 요구에 적혀 있는지 확인한다.
- `--style-only` 인자가 오면 설계 일치·형상 관리를 건너뛴다.
- 사용자에게 물을 것: 프로젝트가 정한 코딩 규약 문서가 따로 있는가, 형상 관리 도구(Git, SVN)와 브랜치 전략은 무엇인가. 답이 없으면 `references/coding-style.md`와 `references/scm.md`의 기본 규칙을 적용하고 결과서에 "기본 규칙 적용"이라고 적는다.

## 절차

### 1. 리뷰 범위와 기준 고정

1. 대상 파일 목록을 만들고 파일별 줄 수, 언어, 마지막 수정 커밋을 적는다.
2. 설계서에서 이 파일들이 대응하는 모듈·클래스 목록을 뽑는다. 설계서에 없는 클래스가 코드에 있거나, 설계서에 있는 클래스가 코드에 없으면 **설계 일치 결함 후보**로 표시한다.
3. 기준을 결과서 머리에 적는다. 기준이 없는 리뷰는 취향 싸움이 된다.

   | 항목 | 기본 기준 |
   |------|-----------|
   | 매개변수 수 | 4개 이하 (5개 이상은 결함) |
   | 중첩 깊이 | 3단계 이하 |
   | 함수 길이 | 50줄 이하 (초과는 분리 권고) |
   | 순환 복잡도 | 10 이하 (초과는 `sw-test`에 상위 대상으로 전달) |
   | 결합도 / 응집도 | `design-review.md` 기준, 없으면 스탬프 이하 / 통신적 이상 |

### 2. 언어와 환경 적정성 (최초 리뷰 1회)

처음 리뷰할 때만 수행한다. 언어가 이미 정해져 바꿀 수 없더라도 기록은 남긴다. 유지보수 단계에서 "왜 이 언어였는가"가 자주 필요하다.

1. `references/language-selection.md`의 선정 기준 9개로 현재 언어를 평가한다. 각 기준에 적합 / 보통 / 부적합을 매긴다.
2. "4세대 언어인가"는 선정 기준이 아니다. 누군가 이 이유를 들면 기준표에서 제외한다.
3. 부적합이 3개 이상이면 결과서에 "언어 재검토 권고"를 남기되, 리뷰 판정에는 반영하지 않는다. 언어 교체는 코드 리뷰의 범위가 아니다.

### 3. 설계 일치 점검

설계서가 없으면 이 단계를 건너뛰고 결과서에 "생략"이라고 적는다.

1. **이름 대조**: 설계서의 클래스·메소드·패키지 이름과 코드의 이름을 표로 대조한다. 다르면 어느 쪽이 맞는지 묻지 말고 **설계서가 기준**이라고 적는다. 코드가 더 나은 이름을 썼다면 설계서 갱신 요청으로 분류한다.
2. **인터페이스 대조**: 설계서의 메소드 시그니처(매개변수, 반환형)와 코드를 대조한다. 매개변수가 늘어났으면 왜 늘었는지 확인한다. 대개 스탬프 결합도(객체 전체 전달)나 제어 결합도(플래그 추가)가 새로 생긴 흔적이다.
3. **의존 방향 대조**: 설계서의 패키지 의존도(또는 `design-review.md`의 의존 행렬)와 코드의 import·참조를 대조한다. 설계에 없던 화살표가 코드에 생겼으면 그 화살표의 결합도 등급을 `sw-design`의 판정 질문표(`references/terms.md` 결합도 절 참조)로 매긴다. 내용·공통·외부 결합도면 **치명** 결함이다.
4. **응집도 회귀**: 설계서에서 기능적·순차적 응집으로 판정된 모듈에 관련 없는 메소드가 추가되었는지 본다. 유틸 메소드가 도메인 클래스에 들어가는 것이 전형이다.

### 4. 코딩 스타일 점검

`references/coding-style.md`의 점검 항목을 파일마다 적용한다. 핵심 8개:

| 항목 | 판정 질문 | 위반 시 등급 |
|------|-----------|--------------|
| 변수명 | 이름만 보고 역할을 알 수 있는가 (a, b, tmp, data1 금지) | 경 |
| 들여쓰기 | 블록 구조가 들여쓰기와 일치하는가 | 경 |
| 제어 구조 | if 뒤에 바로 if가 연속되거나 else가 비어 있지 않은가 | 중 |
| 모듈화 | 함수가 한 가지 일만 하고 50줄 이하인가 | 중 |
| 매개변수 | 4개 이하인가 | 중 |
| 임시 변수 | 한 번만 쓰이는 임시 변수가 없는가 | 경 |
| 중첩 깊이 | if/for 중첩이 3단계 이하인가 | 중 |
| 변수 용도 | 한 변수를 두 가지 목적으로 재사용하지 않는가 | 중 |

위반마다 파일명, 줄 번호, 현재 코드 한 줄, 교정 예시 한 줄을 적는다. 교정 예시가 없는 지적은 기록하지 않는다.

### 5. 구조적 프로그래밍 점검

`references/structured-programming.md`를 기준으로 한다.

1. 제어 구조가 **순차·선택·반복** 세 가지만으로 구성되었는가. 함수 호출은 기본 제어 구조가 아니라 추상화 수단이므로 여기서 세지 않는다.
2. **goto**(또는 언어별 등가물: 다중 레벨 break 남용, 예외를 흐름 제어로 사용)가 없는가. 있으면 **치명**.
3. 함수마다 **단일 입구·단일 출구**인가. return이 여러 개여도 모두 함수 끝 근처의 가드 절(guard clause)이면 허용한다. 반복문 한가운데 return은 **중** 결함이다.
4. 흐름이 위에서 아래로 읽히는가. 뒤로 점프하는 흐름은 반복문으로만 표현되어야 한다.

### 6. 객체지향 구현 점검 (객체지향 언어일 때)

1. **캡슐화**: 필드가 private인가. public 필드가 있으면 **중**. 외부가 필드를 직접 수정하는 코드(`obj.status = X`)가 있으면 내용 결합도이므로 **치명**.
2. **접근자**: getter/setter가 있다면 setter에 유효성 검사가 있는가. 검사 없는 setter는 public 필드와 다를 바 없다. **경**.
3. **생성자**: 객체가 생성 직후 유효한 상태인가. 생성 후 setter를 여러 번 불러야 쓸 수 있는 클래스는 생성자로 묶는다. **경**.
4. **this**: 매개변수와 필드 이름이 같을 때 this를 써서 구분했는가. 섀도잉으로 필드가 대입되지 않는 버그가 흔하다. **중**.
5. **상속**: 상속이 "is-a" 관계인가, 코드 재사용만을 위한 상속인가. 후자는 합성으로 바꾼다. 상속 깊이 4 이상이면 **중**.
6. **다형성**: `instanceof`나 타입 분기(switch on type)로 동작을 나누고 있으면 오버라이딩으로 바꿀 수 있는지 본다. **경**.
7. 클래스를 절차적 스타일로 쓴 경우(모든 메소드가 static, 데이터와 처리가 분리됨)는 객체지향 구현이 아니다. 설계가 객체지향이면 **중**.

### 7. 형상 관리 점검

`references/scm.md`의 다섯 활동으로 현재 상태를 본다.

| 활동 | 판정 질문 | 결과 |
|------|-----------|------|
| 형상 식별 | 리뷰 대상 파일이 어떤 형상 항목(모듈·버전)에 속하는지 알 수 있는가 | 예/아니오 |
| 버전 제어 | 커밋 이력이 있고 태그 또는 버전 번호가 붙어 있는가 | 예/아니오 |
| 변경 통제 | 이 변경이 승인된 변경 요청(또는 요구사항 ID)과 연결되는가 | 예/아니오 |
| 형상 감사 | 기준선(baseline) 대비 무엇이 바뀌었는지 diff로 확인할 수 있는가 | 예/아니오 |
| 상태 보고 | 변경 이력(CHANGELOG, 커밋 메시지)이 사람이 읽을 수 있게 기록되는가 | 예/아니오 |

형상 관리 대상은 코드, 설계서, 요구사항 명세서, 테스트 계획·결과, 매뉴얼, 버전 정보, 변경 요청서다. **개발 비용은 형상 항목이 아니다.** 커밋 메시지 규칙, 브랜치 이름 규칙이 없으면 `references/scm.md`의 기본 규칙을 제안한다.

### 8. 결함 집계와 판정

1. 결함을 치명 / 중 / 경으로 집계한다.
2. 순환 복잡도 10 초과 함수 목록을 만들어 `sw-test`에 넘길 "우선 테스트 대상"으로 적는다. 복잡도 계산법은 `sw-test`의 `references/white-box.md`를 따른다. 여기서는 조건문·반복문 수 + 1로 약산해도 된다.
3. 판정 기준(아래)에 따라 합격 / 조건부 / 불합격을 적는다.
4. 설계서 갱신이 필요한 항목(코드가 옳고 설계가 낡은 경우)을 따로 모아 `sw-design` 재호출 목록으로 적는다.

### 9. 저장

`docs/sw/code-review.md`가 없으면 `templates/code-review.md`로 새로 만들고, 있으면 파일 끝에 `## 리뷰 YYYY-MM-DD` 절을 추가한다. 파일 머리의 헤더 줄은 최신 리뷰 날짜와 버전으로 갱신한다.

## 판정 기준

| 판정 | 조건 |
|------|------|
| 합격 | 치명 0, 중 3 이하, 설계 일치 점검 수행됨, 형상 관리 5항목 모두 예 |
| 조건부 | 치명 0, 중 4 이상 10 이하, 또는 설계서 부재로 설계 일치 생략, 또는 형상 관리 1~2항목 아니오 |
| 불합격 | 치명 1 이상, 또는 중 11 이상, 또는 형상 관리 3항목 이상 아니오 |

치명 결함의 정의: goto 또는 등가 흐름 제어, 내용 결합도(다른 모듈 내부 필드 직접 조작), 공통 결합도(전역 가변 상태 공유), 설계서에 없는 패키지 간 양방향 의존.

## 출력

- `docs/sw/code-review.md`. 양식은 `templates/code-review.md`.
- 완성 예시는 `examples/code-review.md` (학사관리 시스템 성적 모듈 리뷰).
- 다음 단계: `$sw-test`. 결과서의 "우선 테스트 대상" 절을 입력으로 넘긴다.
- 설계서 갱신 항목이 있으면 `$sw-design` 또는 `$sw-design-oo`를 함께 안내한다.
- 협업 모드: `docs/sw/OWNERS.md`가 있으면 저장 전에 그 규칙을 따른다. `git config user.name`으로 작성자를 찾아 그 사람 담당 파일만 고친다. 새 번호는 `[임시:FR-<이니셜>-1]` 형식으로 쓰고 산출물 버전은 올리지 않는다(변경 표시는 "(다음 판 변경)"). 목차 파일의 머리 헤더·문서 상태·목차, `docs/sw/README.md`, 공용 조각(추적표, 자료사전 등)에 들어갈 내용과 남의 파일에 고칠 것은 `docs/sw/pending/<브랜치 이름의 / 를 - 로>.md`에 적는다. 정식 번호와 버전은 공용 담당이 `$sw-sdlc merge`로 매긴다. 규칙 전문은 CONVENTIONS 8절과 OWNERS.md 3절이다.

## 체크리스트

- [ ] 리뷰 기준(매개변수·중첩·길이·복잡도·결합도·응집도 상한)을 결과서 머리에 적었다
- [ ] 설계서가 있으면 이름·인터페이스·의존 방향·응집도 네 가지를 모두 대조했다
- [ ] 설계서가 없으면 "생략"을 명시하고 판정을 조건부 이하로 제한했다
- [ ] 모든 지적에 파일명·줄 번호·교정 예시가 있다
- [ ] 함수 호출을 구조적 프로그래밍의 기본 제어 구조로 세지 않았다
- [ ] "4세대 언어 여부"를 언어 선정 기준으로 쓰지 않았다
- [ ] 형상 관리 대상에 개발 비용을 넣지 않았다
- [ ] 순환 복잡도 10 초과 함수를 `sw-test` 전달 목록에 적었다
- [ ] 설계가 낡은 경우를 코드 결함으로 기록하지 않고 설계서 갱신 항목으로 분리했다
- [ ] 산출물 둘째 줄 헤더(`> 작성: … | 버전: … | 입력: …`)를 갱신했다

## 자주 하는 실수

- 스타일 지적만 수십 건 나열하고 설계 일치는 보지 않는다. 설계와 다른 코드는 스타일이 아무리 좋아도 틀린 코드다. 설계 일치를 먼저 본다.
- 결합도 판정을 "느낌"으로 한다. 화살표마다 무엇을 주고받는지 적고 등급표로 매긴다. `design-review.md`와 같은 기준을 써야 설계 검증과 코드 리뷰가 일관된다.
- 매개변수가 많은 함수에 객체 하나를 통째로 넘겨 매개변수 수만 줄인다. 데이터 결합이 스탬프 결합으로 나빠진 것이다. 실제로 쓰는 값만 넘기거나 함수를 분리한다.
- 모든 return을 하나로 합치려고 깊은 중첩을 만든다. 가드 절은 단일 출구 원칙의 예외로 허용한다. 중첩 깊이 3 초과가 더 나쁘다.
- 리뷰 결과를 새 파일로 만든다. 한 파일에 날짜별로 누적해야 `sw-sqa`가 추세(결함이 줄고 있는가)를 볼 수 있다.
- 코드가 더 나은데 설계서가 낡았다고 코드를 고친다. 설계서 갱신 요청으로 분리하고 코드는 둔다.
