# 요구사항 명세서(SRS) 목차와 각 절의 내용

`sw-srs` 5단계에서 읽는다. `templates/srs.md`의 각 절에 무엇을 써야 하는지 설명한다.

## 목차

```
1. 개요
   1.1 목적          1.2 범위          1.3 용어 정의
   1.4 참고 자료      1.5 문서 구성
2. 전체 설명
   2.1 시스템 개요(배경도)    2.2 사용자 특성    2.3 운영 환경
   2.4 제약 조건              2.5 가정과 의존성
3. 기능적 요구사항      FR-001 ~
4. 비기능적 요구사항    NFR-001 ~
   4.1 성능  4.2 가용성  4.3 보안  4.4 사용성  4.5 유지보수성  4.6 데이터 품질
5. 외부 인터페이스 요구사항
   5.1 사용자 인터페이스  5.2 하드웨어  5.3 소프트웨어(연동 시스템)  5.4 통신
6. 분석 모델
   6.1 DFD(Level 0 / 1 / 2)  6.2 자료사전  6.3 소단위 명세서  6.4 ERD / STD
7. 부록
   7.1 요구사항 추적표  7.2 검토 기록  7.3 변경 이력  7.4 승인
```

## 절별 내용

### 1. 개요

- **1.1 목적**: 이 문서가 누구를 위해 무엇을 정하는가. "이 문서는 OO 시스템의 요구사항을 정의하며, 발주자와 개발사 간 인수 기준이 된다"처럼 쓴다.
- **1.2 범위**: 시스템이 하는 일과 **하지 않는 일**. `plan.md`의 범위 정의를 옮기고, 분석 중 바뀐 것이 있으면 반영한다. 하지 않는 일이 없으면 범위가 아니다.
- **1.3 용어 정의**: 사용자와 개발자가 다르게 쓰는 단어, 약어. 자료사전의 이름 규칙과 맞춘다.
- **1.4 참고 자료**: RFP, 인터뷰 기록(날짜·대상), 현행 업무 문서, 관련 법규·표준.
- **1.5 문서 구성**: 이 목차의 요약 한 단락.

### 2. 전체 설명

- **2.1 시스템 개요**: 배경도(Level 0)와 한 단락 설명. 시스템이 누구와 무엇을 주고받는지.
- **2.2 사용자 특성**: 사용자 유형(교수, 학생, 교무처 직원)별 인원, 숙련도, 사용 빈도, 접근 권한.
- **2.3 운영 환경**: 서버·클라이언트 OS, 브라우저, 네트워크, 기존 시스템. 사용자가 이미 정한 것만 쓴다.
- **2.4 제약 조건**: 반드시 지켜야 하는 외부 조건. 법규, 기존 DB 연동, 예산·기간, 발주자가 지정한 기술. **설계 선택이 아니라 주어진 조건만** 쓴다.
- **2.5 가정과 의존성**: 분석 시점에 확인하지 못해 가정한 것(예: "기존 학적 DB의 학번 체계가 유지된다고 가정"). 가정이 깨지면 어느 요구가 영향받는지 적는다.

### 3. 기능적 요구사항

항목 하나의 구성:

| 필드 | 내용 |
|------|------|
| ID | FR-001 형식. 한 번 매기면 바꾸지 않음 |
| 명칭 | 동사+목적어 ("성적 입력") |
| 설명 | "누가 무엇을 할 수 있어야 한다" 한 문장 |
| 입력 | 들어오는 자료(자료사전 이름) |
| 처리 | 규칙, 검증, 예외 처리 |
| 출력 | 나가는 자료, 화면 메시지 |
| 우선순위 | 필수 / 권장 / 선택 |
| 출처 | 인터뷰(날짜·대상), 시나리오 번호, RFP 절 |
| DFD | 관련 프로세스 번호 |

기능 묶음(학적 관리, 성적 관리, 수강신청)별로 소절을 나눈다. 묶음 순서는 DFD Level 1 프로세스 순서와 같게 한다.

### 4. 비기능적 요구사항

각 항목에 **측정 방법**이 있어야 한다.

| 분류 | 예 | 측정 방법 예 |
|------|----|-------------|
| 성능 | 성적 조회 응답 2초 이내 | 동시 접속 1,000명 조건에서 100회 측정, 95% 이상 2초 이내 |
| 가용성 | 수강신청 기간 중 24시간 가동 | 기간 중 계획 외 중단 누적 1시간 이하 |
| 보안 | 성적은 본인과 담당 교수만 조회 | 권한 없는 계정으로 조회 시도 → 100% 거부 |
| 사용성 | 성적 입력은 3단계 화면 이내 | 화면 전환 수 측정 |
| 유지보수성 | 등급 기준 변경 시 코드 수정 없이 설정으로 | 설정 변경 후 재배포 없이 반영 확인 |
| 데이터 품질 | 성적은 0~100 정수만 저장 | 범위 밖 입력 시도 → 100% 거부 |

### 5. 외부 인터페이스 요구사항

- **5.1 사용자 인터페이스**: 화면 종류와 각 화면의 입출력. 화면 설계(레이아웃)는 하지 않는다. 프로토타입을 만들었다면 화면 흐름도를 붙인다.
- **5.2 하드웨어**: 바코드 리더, 프린터 등 연결 장치.
- **5.3 소프트웨어**: 연동하는 외부 시스템(기존 학적 DB, 통합 인증)과 주고받는 자료, 방향, 빈도. 배경도의 외부 시스템 단말과 일치해야 한다.
- **5.4 통신**: 프로토콜·형식 요구가 있으면 쓴다.

### 6. 분석 모델

- **6.1 DFD**: 배경도, Level 1, 필요한 Level 2. 각 그림 아래 한 단락 설명.
- **6.2 자료사전**: 가나다순.
- **6.3 소단위 명세서**: 최하위 프로세스마다. 번호는 DFD 프로세스 번호.
- **6.4 ERD / STD**: 필요할 때만.

### 7. 부록

- **7.1 추적표**: 요구 ID → 출처 → DFD 프로세스 → 설계 요소(비움) → 테스트 케이스(비움).
- **7.2 검토 기록**: 검토 회의 날짜, 참석자, 지적 사항 번호와 반영 여부.
- **7.3 변경 이력**: 버전, 날짜, 변경 내용, 영향받은 FR/NFR, 승인자.
- **7.4 승인**: 발주자, 프로젝트 관리자, 분석 담당의 이름·날짜. 미승인이면 "미승인(초안)".

## 요구 항목 작성 규칙 요약

1. 한 항목에 한 요구.
2. "~해야 한다"로 끝낸다.
3. 수치로 쓸 수 있는 것은 수치로.
4. 설계 결정(DB, 언어, 프레임워크, 화면 배치)을 쓰지 않는다.
5. 주어를 쓴다. "교수는", "시스템은".
6. 부정문보다 긍정문. "~하면 안 된다"보다 "~인 경우 거부해야 한다".
