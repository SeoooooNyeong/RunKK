# 객체지향 기본 개념

`sw-design-oo` 0단계와 6단계에서 읽는다.

## 1. 객체지향이란

세상을 구성하는 모든 것을 **객체**로 보고, 객체들을 조합해 프로그램을 만드는 방식. 현실 세계의 사물·개념(학생, 자동차, 계좌)을 그대로 프로그램 안으로 옮긴다.

### 절차지향과의 차이

| 구분 | 절차지향 | 객체지향 |
|------|----------|----------|
| 주인공 | 함수(절차) | 객체 |
| 데이터와 함수 | 따로 있음. 데이터가 함수 사이를 돌아다님 | 한 객체 안에 묶임 |
| 프로그램 구성 | 순서대로 실행되는 함수 호출 | 객체들이 메시지를 주고받으며 협력 |
| 재사용 | 함수 복사 | 클래스 재사용, 상속 |
| 유지보수 | 데이터 변경이 모든 함수에 영향 | 클래스 단위로 수정 |
| 대표 언어 | C, Fortran, COBOL | Java, C++, Python, C#, Kotlin, Smalltalk |

절차지향의 문제: 같은 데이터를 여러 함수가 동시에 접근·변경하면 프로그램이 꼬인다. 객체지향은 데이터와 그것을 다루는 함수를 한 덩어리로 묶어 이 문제를 줄인다.

객체지향의 장점은 재사용성, 유지보수성, 확장성, 현실 모델링 용이성이다. **실행 속도가 빨라지는 것은 장점이 아니다.** 구조가 좋아도 속도는 느릴 수 있다.

## 2. 네 가지 구성 요소

### 객체 (Object)

실제로 일을 하는 주체. 현실의 사물 하나를 프로그램 단위로 표현한 것.

- **속성(Attribute)**: 객체가 가진 정보. 이름, 학번, 학과.
- **메소드(Method)**: 객체가 할 수 있는 일. 수강신청하기(), 시험보기().

객체 = 데이터(속성) + 기능(메소드). 객체의 **상태**는 특정 시점의 속성 값 집합이다. 상태는 속성으로 파악한다.

### 클래스 (Class)

객체를 만들기 위한 **틀(template)**, 설계도. 속성과 메소드를 정의해 둔다. 클래스만 있으면 실행되지 않는다. 붕어빵틀만 있고 빵을 안 구운 상태.

하나 이상의 유사한 객체를 묶어 공통 속성·연산을 정의한 것이 클래스다. **모든 객체는 어떤 클래스의 인스턴스**다.

### 메소드 (Method)

객체가 **메시지를 받아 실행하는 구체적인 연산**. 절차지향의 함수와 비슷하지만 객체 안에 포함되어 있고, 그 객체의 속성을 읽거나 바꾼다. 연산(Operation)은 속성을 변화시킨다.

**메소드는 언제 시작되는가:** 객체가 메시지를 받을 때. 운영체제 인터럽트나 입력 장치가 메소드를 직접 실행하지 않는다.

### 메시지 (Message)

객체 간 상호작용의 수단. 한 객체가 다른 객체에게 "이 메소드를 실행하라"고 요청하는 것. `teacher.ask(student)` 안에서 `student.answer()`를 호출하면 Teacher 객체가 Student 객체에 메시지를 보낸 것이다.

### 인스턴스 (Instance)

클래스로부터 만들어진 객체. 객체와 같은 말이되 "클래스에서 나왔다"는 점을 강조. 클래스에서 객체를 만드는 행위가 **인스턴스화(Instantiation)**. `Student s1 = new Student();`에서 `s1`이 Student의 인스턴스다.

| 용어 | 비유 |
|------|------|
| 클래스 | 붕어빵틀 |
| 객체 / 인스턴스 | 붕어빵 |
| 인스턴스화 | 붕어빵을 찍어내는 행위 |
| 메소드 | "팥 넣기", "굽기" |
| 메시지 | "붕어빵 하나 구워 줘" |

## 3. 네 가지 원리

### 캡슐화 (Encapsulation)

데이터(속성)와 그 데이터를 다루는 메소드를 **하나의 단위(객체)로 묶고 내부를 외부로부터 감춘다.** 정보 은닉(Information Hiding)을 실현하는 수단.

```java
class Account {
    private int balance = 0;              // 외부 접근 불가

    public void deposit(int amount) {     // 공개 인터페이스
        if (amount > 0) balance += amount;
    }
    public int getBalance() { return balance; }
}
```

감기약 캡슐: 사용자는 "감기에 좋다"만 알면 되고, 안의 성분 조합은 몰라도 된다. **무엇을(what)만 보여 주고 어떻게(how)는 숨긴다.**

효과: 데이터 보호(잘못된 값 차단), 내부 구조가 바뀌어도 외부 사용법 유지, 재사용성, **결합도 감소**·응집도 증가, 고려되지 않은 영향(side effect) 축소. 캡슐화로 객체 간 결합도가 높아지지 않는다. 낮아진다.

### 추상화 (Abstraction)

복잡한 현실에서 **필요한 정보만 남기고 불필요한 것은 생략**한다. 객체의 성질을 분해해 **공통된 성질을 상위 클래스**로 만드는 것도 추상화다(자동차 + 말 → "탈것", 축구 + 야구 + 배구 → "운동경기").

```java
abstract class Sports {
    abstract void attack();      // 구체적 내용은 하위 클래스가
    abstract void defense();
}
```

추상 클래스는 "아직 완성되지 않은 설계도"이며 직접 인스턴스를 만들 수 없다. 하위 클래스가 상속받아 추상 메소드를 구현한다. 설계 수준의 공통화.

### 상속 (Inheritance)

상위 클래스(Super Class, 부모)의 속성과 메소드를 하위 클래스(Sub Class, 자식)가 **그대로 물려받고**, 거기에 자기 것을 더한다. 할아버지 → 아버지 → 아들.

```java
class Person { String name; void introduce() {...} }
class Student extends Person { String major; void study() {...} }
```

Student는 name, introduce()를 물려받고 major, study()를 추가한다.

목적: 중복 제거, 공통 기능 재사용, 확장 용이. 절차지향에서는 구조체를 복사해 다시 써야 했던 것을 `extends` 한 줄로 해결한다.

**단일 상속:** Java는 한 클래스가 하나의 부모만 가진다. 두 부모가 같은 이름의 메소드를 가지면 어느 것을 따를지 모호해지기 때문이다. 다중 상속의 효과가 필요하면 **인터페이스**로 푼다. 상속은 한 단계씩 이어지며 할아버지를 건너뛰어 직접 상속하지 않는다.

하위 클래스는 물려받은 메소드를 **재정의(오버라이딩)** 할 수 있다.

### 다형성 (Polymorphism)

**하나의 메시지에 객체가 각자 다르게 반응하는 능력.** poly(여러) + morphism(형태). 많은 상이한 클래스가 동일한 메소드 이름을 쓰고, 상위 클래스 타입 변수가 하위 클래스 객체를 참조할 수 있어서 가능하다.

```java
Sports[] games = { new Soccer(), new Baseball(), new Volleyball() };
for (Sports g : games) g.attack();     // 슛 / 타격 / 스파이크
```

효과: 새 종목(농구)을 추가해도 기존 코드를 거의 고치지 않는다. 유연성·확장성. 상속 관계(또는 인터페이스)가 없는 객체끼리는 다형성이 성립하지 않는다.

`A`가 integer면 `int_func()`, float면 `float_func()`를 호출하는 것도 다형성의 한 형태(형태에 따라 다르게 반응).

### 원리 요약

| 원리 | 본질 | 키워드 | 비유 |
|------|------|--------|------|
| 캡슐화 | 보호와 은닉 | private, public | 감기약 캡슐 |
| 추상화 | 단순화, 공통화 | abstract | 운동경기 ← 축구·야구 |
| 상속 | 재사용과 확장 | extends | 부모 → 자식 |
| 다형성 | 행동의 다양화 | override | attack() → 슛/타격/스파이크 |

추상화는 **설계 수준의 공통화**, 다형성은 **실행 수준의 다양화**다. 추상 클래스 → 하위 클래스들이 오버라이딩, 이 둘이 함께 쓰인다.

## 4. 정보 은닉 (Information Hiding)

캡슐화의 핵심 목표. 외부 객체가 특정 객체의 내부 데이터를 직접 접근·변경하지 못하게 막는다. `private String password;` → 외부는 `setPassword()`로만 바꾼다. 잘못된 입력과 보안 사고를 막고 side effect를 줄인다.

구조적 설계의 정보 은닉과 객체지향의 캡슐화는 같은 원리다.

## 5. 모듈화는 객체지향 고유 개념이 아니다

캡슐화·상속·다형성은 객체지향의 특징이다. **모듈화**는 구조적 프로그래밍 등 기존 소프트웨어공학에서도 쓰던 개념이다. "객체지향이라서 모듈화한다"고 쓰지 않는다. 객체지향에서 모듈 단위는 클래스·패키지·서브시스템이고, 응집도·결합도 기준도 그대로 적용된다.

## 6. 객체지향 생명주기

계획 → 분석 → 설계 → 구현 → 테스트 → 유지보수. 폭포수처럼 단계가 뚜렷이 끊어지지 않고 상호 피드백으로 반복될 수 있지만, 기본 흐름은 **분석 → 설계 → 구현**이다.

핵심은 세 단계에서 **같은 객체 개념**을 쓴다는 것이다.

| 단계 | 객체 개념의 쓰임 |
|------|-----------------|
| 분석(OOA) | 객체의 상태·행위 파악. 클래스 후보, 관계, 상태 변화 |
| 설계(OOD) | 속성·연산 확정, 인터페이스, 패키지, 알고리즘 |
| 구현(OOP) | 클래스 단위로 코드 작성. **객체지향 언어** 사용 (절차적 언어가 아님) |
| 테스트(OOT) | 클래스 단위 테스트 → 통합 → 검증 → 시스템 |

분석의 Student 클래스가 설계의 Student 클래스이고 구현의 `class Student`다. 이 일관성이 객체지향 개발법의 가장 큰 장점이다.

## 7. 메타클래스

클래스를 만드는 클래스. 클래스 계층 트리의 **최상단**에 있다. 설계에서 직접 다루는 일은 드물지만 "모든 것은 객체"라는 원칙을 끝까지 밀면 클래스도 객체이고 그 클래스가 메타클래스다.
