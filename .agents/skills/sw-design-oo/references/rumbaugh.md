# 럼바우(Rumbaugh) 기법 — 분석 3모델과 설계 2층

`sw-design-oo` 1~3단계(분석)와 5~6단계(설계)에서 읽는다. 럼바우의 OMT(Object Modeling Technique)는 UML의 뿌리 중 하나다.

## 1. 분석: 세 가지 모델

분석을 **객체 모델 → 동적 모델 → 기능 모델** 세 모델로 나눠 진행한다. 순서가 중요하다.

| 모델 | 보는 것 | 핵심 질문 | 산출물 |
|------|---------|-----------|--------|
| 객체 모델 (Object) | 구조 | 무엇이 있고 서로 어떤 관계인가 | 클래스 다이어그램, 객체 다이어그램 |
| 동적 모델 (Dynamic) | 시간 | 언제 어떤 사건으로 상태가 바뀌는가 | 상태도, 시퀀스(사건 추적도) |
| 기능 모델 (Functional) | 변환 | 입력이 어떤 처리를 거쳐 출력이 되는가 | 자료 흐름도(DFD) |

### 1.1 객체 모델 — 가장 먼저

객체지향 시스템은 "객체"라는 기반 위에서 모든 기능이 정의되기 때문에 가장 먼저 한다.

절차:
1. **객체·클래스 식별.** 요구 명세의 명사에서 후보를 뽑고 거른다.
2. **자료 사전 작성.** 클래스마다 속성·연산을 명세한다.
3. **관계 정의.** 연관(association), 집합(aggregation), 상속(inheritance).
4. **속성·메시지·연결 관계 정의.**
5. **클래스 계층화.** 공통 속성·연산을 상위 클래스로 올려 상속 구조를 만든다.
6. **모듈 정의.** 기능 단위로 패키지 구조를 잡는다.
7. **모델 검증.** 반복적으로.

#### 명사·동사 추출 요령

| 문장 성분 | 후보 | 예 |
|-----------|------|-----|
| 명사 | 클래스 또는 속성 | 학생, 교수, 과목, 성적, 수강신청 / 학번, 점수, 학과 |
| 동사 | 연산(메소드) | 등록하다, 입력하다, 조회하다, 승인하다, 계산하다 |
| 형용사·소유격 | 속성 또는 관계 | "학생의 성적" → Student–Grade 연관 |

명사가 객체·클래스 후보이고 동사가 연산 후보다. 반대가 아니다.

#### 명사 거르기

| 제외 | 이유 | 처리 |
|------|------|------|
| 교무처, 교수(행위자로서) | 시스템 밖 | 유스케이스 액터. 단, 시스템이 교수 정보를 저장하면 Professor 클래스도 둔다 |
| 학번, 점수, 성명 | 다른 것의 속성 | Student.studentId, Grade.score |
| 수강생, 재학생 | 학생의 다른 이름·역할 | Student 하나. 역할은 상태 속성이나 관계로 |
| 화면, 버튼, DB | 구현 세부 | 설계 단계의 표현·인프라 계층에서 |
| 시스템 | 전체 | 클래스가 아님 |

#### 관계

| 관계 | 뜻 | 예 | 다중성 예 |
|------|----|-----|-----------|
| 연관 | 알고 있다, 참조한다 | Student – Enrollment – Course | Student 1 : Enrollment 0..* |
| 집합 | 전체–부분, 부분은 독립 존재 가능 | Department ◇– Professor | 학과가 없어져도 교수는 존재 |
| 합성 | 전체–부분, 부분은 전체에 종속 | Grade ◆– GradeHistory | 성적이 삭제되면 이력도 삭제 |
| 상속 | ~의 한 종류 (is-a) | Person ◁– Student, Professor | |

상속은 **공통 기능 재사용과 중복 제거**를 위해 공통 성질을 상위 클래스로 추상화하는 것이다. is-a가 아닌 곳에 쓰지 않는다.

### 1.2 동적 모델

"움직임", 시간에 따른 변화를 다룬다.

핵심 요소:
- **상태(State)**: 특정 시점의 객체 속성 값 집합. 수강신청의 {신청, 승인대기, 확정, 반려, 취소}.
- **사건(Event)**: 사용자 입력, 시스템 내부 이벤트, 메시지, 시간 경과. 전이를 일으킨다.
- **상태 전이(Transition)**: 사건이 발생하면 객체가 다른 상태로 이동.

절차:
1. **사건 시나리오 작성.** "마우스 클릭 → 창이 열린다"처럼 사건과 결과를 쓴다. SRS 시나리오를 객체 관점으로.
2. **사건 추적도(Event Trace) 작성.** 어떤 객체가 어떤 객체를 어떤 순서로 호출하는지. 시퀀스 다이어그램의 원형.
3. **사건 흐름도(Event Flow) 작성.** 모든 시나리오의 사건을 모아 객체 간 흐름을 한 장에.
4. **상태도(State Diagram) 작성.** 사건에 따라 상태가 어떻게 바뀌는지 시각화.

상태도의 모든 사건은 어떤 클래스의 연산에 대응해야 한다. 대응이 없으면 연산이 빠진 것이다.

### 1.3 기능 모델

자료 흐름 중심. 어떤 입력이 들어와 어떤 출력이 나오는가.

핵심 도구: **자료 흐름도(DFD)**. 프로세스, 자료 흐름, 자료 저장소, 외부 엔티티.

절차:
1. **입출력 자료 정의.**
2. **자료 흐름도 작성.** (핵심)
3. **기능 상세 기술.** 프로세스마다 처리 내용.
4. **제약 사항 분석과 최적화.**

객체지향 분석에서도 기능 모델은 DFD로 그린다. SRS에 DFD가 있으면 재사용하고, 각 프로세스를 클래스 연산에 대응시킨다.

### 1.4 세 모델의 교차 검증

| 대응 | 확인 |
|------|------|
| 클래스 연산 ↔ 상태도 사건 | 상태도의 사건마다 그것을 처리하는 연산이 있는가 |
| 클래스 연산 ↔ DFD 프로세스 | 최하위 프로세스마다 대응 연산이 있는가 |
| DFD 자료 흐름 ↔ 메시지 매개변수 | 프로세스 입력이 연산 매개변수, 출력이 반환값인가 |
| DFD 저장소 ↔ 클래스 | 저장소마다 영속 클래스(또는 저장소 접근 클래스)가 있는가 |
| 시퀀스 참여자 ↔ 클래스 | 시퀀스에 등장하는 객체가 모두 클래스 다이어그램에 있는가 |

## 2. 설계: 두 층

### 2.1 시스템 설계 (System Design)

전체 시스템을 서브시스템으로 나누고 뼈대를 정한다.

| 작업 | 내용 |
|------|------|
| 서브시스템 분할 | 분석 모델의 클래스를 적당한 크기의 서브시스템(패키지)으로. 같은 엔티티를 다루는 클래스끼리 |
| 계층 구조 정의 | 표현 → 응용 → 도메인 → 인프라 |
| 성능 최적화 방안 | 자주 조회되는 경로, 캐시, 인덱스 |
| 자원 분해 | 서버, 디스크, 네트워크. 어느 서브시스템이 어디서 도는가 |
| 하드웨어·태스크 할당 | 프로세스·스레드 배치 |
| 자원 공유와 동시성 | 여러 사용자가 동시에 바꾸는 객체의 잠금·트랜잭션 |
| 제어 방식 | 요청-응답, 이벤트 구동, 배치 |
| 경계 조건 | 시작, 종료, 장애 시 동작 |

"큰 시스템을 적당한 크기의 서브시스템 단위로 나눠라." 이것이 설계와 유지보수에 직접 영향을 준다.

### 2.2 객체 설계 (Object Design)

분석의 클래스·속성·관계·메시지를 **구체적인 자료 구조와 알고리즘**으로.

| 작업 | 내용 |
|------|------|
| 정보와 처리를 모듈화 | 데이터 + 메소드를 한 클래스에 캡슐화 |
| 추상화·정보 은닉·모듈화 원칙 적용 | private 속성, public 인터페이스 |
| 연산 알고리즘 설계 | 연산마다 입력·처리·출력 |
| 데이터 접근 경로 최적화 | 참조 방향, 컬렉션 선택 |
| 상속 구조 재정비 | 공통을 올리고(일반화), 상속성을 극대화해 재사용성 향상 |
| 클래스와 관계를 모듈 단위로 구성 | 패키지 안 배치 확정 |
| 문서화 | 클래스 명세표 갱신 |

요약: "분석에서 나온 클래스·객체 모델을 실제 코드 수준에 가깝게 구체화하는 단계."

## 3. 일반 OOD 절차

방법론과 무관한 공통 순서:

1. **문제 정의** — 범위와 목표
2. **요구 명세화** — 입력·출력·제약을 정형화 (SRS)
3. **객체 연산 정의** — 클래스마다 어떤 기능을 수행하는가
4. **객체 인터페이스 결정** — 외부에서 호출할 수 있는 메소드, 매개변수, 반환, 예외, 접근 제한자. 이것이 계약
5. **객체 구현** — 실제 코드. **항상 마지막**

## 4. 다른 설계 기법 요약

| 기법 | 특징 |
|------|------|
| 부치(Booch) | 자료 흐름도로 객체를 분해하고, 객체 간 인터페이스를 정의해 Ada 프로그램으로 변환 |
| Wirfs-Brock / Smalltalk 계열 | 서브시스템별 자료 추상화 식별 → 속성 식별 → 연산 식별 → 객체 간 메시지 식별 → 시나리오로 설계 검토 → 적절한 곳에 상속 도입 |
| 제이콥슨(Jacobson) | 유스케이스 중심. 사용자 목표에서 출발 |

세 기법과 럼바우가 합쳐진 것이 UML이다. 근본은 모두 "객체를 중심으로 시스템을 나눈다".

## 5. 현대적 흐름 (실무 확장)

1. 요구사항 분석 — 유스케이스 식별 (제이콥슨)
2. 도메인 모델 — 핵심 업무 객체 식별 (객체 모델)
3. 상태·시퀀스 모델 — 이벤트 흐름 (동적 모델)
4. 서비스·데이터 흐름 — (기능 모델)
5. 클래스 설계 — 속성·메소드·관계 구체화
6. 구현 — Java, C++, Python
7. 테스트 — 단위(클래스) → 통합 → 검증 → 시스템

## 6. 객체지향 테스트 순서

| 순서 | 단계 | 내용 |
|------|------|------|
| 1 | 단위 테스트 | **클래스 테스트.** 캡슐화된 클래스 하나를 독립적으로. 메소드 동작, 경계 조건, 예외 |
| 2 | 통합 테스트 | 여러 클래스를 결합. **스레드 기반**(한 입력·사건에 응답하는 클래스 묶음) 또는 **사용 기반**(독립 클래스 먼저, 종속 클래스 다음) |
| 3 | 검증(Validation) | 사용자 요구를 만족하는가. SRS 기준 |
| 4 | 시스템 테스트 | 전체 통합 상태에서 성능·보안·장애·운영 시나리오 |

사용 기반 통합의 순서는 패키지 의존도의 역순이다. 아무도 의존하지 않는 패키지(repo, rules)를 먼저, 그것을 쓰는 패키지(grade, enrollment)를 다음에, 마지막에 ui.
