## 인자

`$sw-design-oo` 뒤에 이어 쓴다: `[프로젝트명 | analysis (분석만) | design (설계만) | uml <다이어그램 종류>]`

## 목적

`srs.md`의 "무엇"을 **객체·클래스·메시지·관계**의 관점으로 다시 읽어 구현 가능한 설계로 바꾼다. 산출물 `docs/sw/design-oo.md`는 객체지향 분석(OOA)과 객체지향 설계(OOD)를 한 문서에 담는다. 분석과 설계가 같은 개념(객체, 클래스, 메시지)을 쓰기 때문에 둘을 나누면 오히려 중복이 생긴다.

이 산출물을 `sw-design review`가 패키지 의존도 검증의 입력으로, `sw-code-review`가 클래스·메서드 이름 일치 점검의 기준으로, `sw-test`가 단위 테스트(클래스) 단위와 통합 테스트 순서의 입력으로, `sw-maintain`이 변경 영향 범위 계산의 기준으로 읽는다.

객체지향 개발의 가장 큰 장점은 **분석에서 쓴 객체 개념이 설계와 구현(Java 클래스)까지 끊기지 않고 같은 개념으로 이어진다**는 것이다. 이 스킬은 그 일관성을 지키는 것을 최우선으로 한다.

## 입력

- `docs/sw/srs.md`. 없으면 `$sw-srs`를 먼저 안내하고 중단한다. 요구사항 없이 클래스를 뽑으면 명사 후보의 출처가 없어 추적표가 끊긴다.
- 사용자에게 물어야 할 것:
  - 구현 언어. 기본은 Java로 가정하고 `references/java-implementation.md`의 지침을 쓴다. 다른 객체지향 언어면 문법 예만 바꾼다.
  - 기존 클래스·라이브러리·프레임워크 제약이 있는가.
  - 이 시스템이 **대화식·사용자 중심**(화면이 많고 상호작용이 많음)인가. 그렇다면 객체지향 설계가 잘 맞는다. 배치 처리 중심이면 `$sw-design design`(구조적)도 검토하라고 알린다.
- 인자 `analysis`면 1~4단계(OOA)까지만, `design`이면 분석 결과가 이미 있다고 보고 5~8단계만, `uml <종류>`면 해당 다이어그램만 작성·갱신한다.

## 절차

전체 흐름: **객체지향 개념 확인 → 럼바우 분석(객체 → 동적 → 기능) → 객체지향 설계(시스템 설계 → 객체 설계) → UML 정리 → 패키지 의존도 → 구현 지침 → 테스트 순서.** 개념 정의는 `references/oo-concepts.md`, 럼바우 절차는 `references/rumbaugh.md`, 다이어그램 표기는 `references/uml-diagrams.md`를 읽는다.

### 0단계. 관점 고정

객체지향은 세상의 모든 것을 **속성(데이터)과 행동(메소드)을 함께 가진 객체**로 보고, 객체들이 **메시지**를 주고받으며 협력해 문제를 푸는 방식이다. 절차지향(함수가 주인공, 데이터가 함수 사이를 돌아다님)과 다르다. 설계 내내 다음 네 가지를 같은 뜻으로 쓴다.

| 용어 | 뜻 | 비유 |
|------|----|------|
| 객체(Object) | 속성 + 메소드를 가진 실체 | 붕어빵 |
| 클래스(Class) | 객체를 만드는 틀. 속성·메소드의 정의 | 붕어빵틀 |
| 인스턴스(Instance) | 클래스로부터 만들어진 객체. 객체와 같은 말이되 "틀에서 나왔다"를 강조 | 구워진 붕어빵 하나 |
| 메시지(Message) | 객체가 다른 객체의 메소드를 호출하는 요청. 메소드는 **메시지를 받을 때** 실행된다 | "시험 봐라" |

네 가지 원리(캡슐화·상속·다형성·추상화)와 정보 은닉은 설계 판단마다 근거로 쓴다. 모듈화는 객체지향 고유 개념이 아니라 구조적 설계에서도 쓰던 것이므로 "객체지향이라서 모듈화한다"고 쓰지 않는다.

### 1단계. 객체 모델 (Object Model) — 가장 먼저

객체지향 시스템은 객체라는 기반 위에 모든 기능이 정의되므로 **객체 모델을 가장 먼저** 만든다.

1. `srs.md`의 기능 요구 설명문, 시나리오, 자료사전에서 **명사**를 모두 뽑는다. 명사가 클래스 후보다. **동사**는 연산(메소드) 후보로 따로 모은다. (명사가 연산, 동사가 객체가 아니다.)
2. 명사 후보를 거른다.

   | 제외 기준 | 예 |
   |-----------|-----|
   | 시스템 밖의 것 | 교무처(액터로 남김), 기존 학적 DB(외부 시스템) |
   | 다른 클래스의 속성에 불과 | 학번, 점수, 성명 → Student, Grade의 속성 |
   | 같은 것의 다른 이름 | 학생 = 수강생 = 재학생 → Student 하나 |
   | 구현 세부 | 화면, 버튼, 테이블, 파일 |
   | 역할일 뿐 | 발주자, 관리자 → Actor 또는 권한 속성 |

3. 남은 클래스마다 **속성**(자료사전에서)과 **연산**(동사 후보에서)을 붙인다. 연산은 그 클래스의 속성을 바꾸거나 읽는 것이어야 한다. 객체의 상태는 속성 값의 집합이고, 연산은 속성을 변화시킨다.
4. 클래스 간 **관계**를 정한다.

   | 관계 | 판별 질문 | 표기 |
   |------|-----------|------|
   | 연관(Association) | A가 B를 알아야 하는가 (참조) | 실선, 다중성(1, 0..*, 1..*) |
   | 집합(Aggregation) | A가 B를 부분으로 가지지만 B는 A 없이도 존재하는가 | 빈 마름모 |
   | 합성(Composition) | A가 없어지면 B도 없어지는가 | 채운 마름모 |
   | 상속(Inheritance) | B는 A의 한 종류인가 (is-a) | 빈 삼각형 화살표 |

   상속은 공통 속성·연산을 상위 클래스로 올려 **중복을 없애고 재사용**할 때 쓴다. "~의 한 종류"가 아닌데 코드 재사용만을 위해 상속하지 않는다. 단일 상속을 전제로 하고(Java), 두 부모가 필요하면 인터페이스로 푼다.
5. **클래스 다이어그램**을 그린다. 자료사전 항목 ↔ 클래스 속성의 대응표를 만든다.
6. 자료 사전(클래스 명세)을 쓴다. 클래스마다 책임 한 문장, 속성(이름·형·제약), 연산(이름·매개변수·반환·전후 조건).

판정 질문: 모든 FR의 명사가 클래스 또는 속성으로 흡수되었는가? 책임 문장에 "그리고"가 있는 클래스가 0개인가? 모든 연산이 자기 클래스의 속성을 다루는가?

### 2단계. 동적 모델 (Dynamic Model)

시간에 따른 **상태 변화와 객체 간 상호작용**을 다룬다.

1. **사건 시나리오**를 쓴다. `srs.md`의 시나리오를 객체 관점으로 다시 쓴다. "교수가 성적 입력 버튼을 누른다" → "GradeScreen이 GradeService에 enterGrades 메시지를 보낸다".
2. **사건 추적도(Event Trace)** 를 그린다. 어떤 객체가 어떤 객체에 어떤 순서로 메시지를 보내는지. 이것이 시퀀스 다이어그램의 원형이다. 시나리오마다 하나씩, 핵심 시나리오 3~7개.
3. **사건 흐름도(Event Flow)** 를 그린다. 모든 시나리오의 사건을 모아 객체 간 사건 흐름을 한 장에 정리한다.
4. **상태도(State Diagram)** 를 그린다. 상태가 2개 이상 바뀌는 클래스마다. 상태 = 특정 시점의 속성 값 집합, 사건 = 전이를 일으키는 입력·메시지·시간, 전이 = 사건 발생 시 상태 이동. 시작 상태와 종료 상태를 명시한다.
   - 상태도가 필요한 클래스: 수강신청(신청 → 승인대기 → 확정/반려), 이의신청(접수 → 처리중 → 완료), 결제·주문처럼 생애주기가 있는 것.
   - 상태도가 필요 없는 클래스: 상태가 바뀌지 않는 참조 데이터(Course 기본 정보, 등급 기준표).
5. 상태도의 사건이 1단계 클래스의 연산과 대응하는지 확인한다. 상태도에 있는 사건인데 연산이 없으면 연산을 추가한다.

판정 질문: 핵심 시나리오마다 사건 추적도가 있는가? 상태가 바뀌는 클래스마다 상태도가 있는가? 상태도의 모든 사건이 어떤 클래스의 연산에 대응하는가?

### 3단계. 기능 모델 (Functional Model)

**자료 흐름** 관점이다. 입력이 어떤 처리를 거쳐 출력이 되는가.

1. `srs.md` 6.1의 **DFD를 재사용**한다. 객체지향 분석에서 기능 모델의 핵심 도구는 DFD다. 새로 그리지 않고 SRS의 것을 가져온다.
2. DFD의 각 프로세스를 1단계의 **클래스 연산에 대응**시킨다. 프로세스 "2.3 등급 계산" → `Grade.calculateLetter()` 또는 `GradePolicy.toLetter()`. 대응이 안 되는 프로세스가 있으면 클래스나 연산이 빠진 것이다.
3. 입출력 자료(자료 흐름)를 메시지의 매개변수·반환값에 대응시킨다.
4. 제약 사항(기간, 범위, 권한)을 어느 클래스의 어느 연산이 검사하는지 정한다.

판정 질문: DFD 최하위 프로세스 100%가 클래스 연산에 대응하는가?

세 모델의 관계: 객체 모델은 **구조**(무엇이 있는가), 동적 모델은 **시간**(언제 어떻게 바뀌는가), 기능 모델은 **변환**(입력이 어떻게 출력이 되는가)을 본다. 셋이 서로 모순되지 않아야 한다. 반복적으로 검증한다.

### 4단계. 분석 모델 검증

1. 세 모델의 교차 확인: 클래스 연산 ↔ 상태도 사건 ↔ DFD 프로세스가 서로 빠짐없이 대응하는가.
2. `srs.md` 추적표의 "설계 요소" 열에 FR마다 담당 클래스·연산을 채운다. 비는 FR이 있으면 클래스가 빠진 것이다.
3. 이해관계자에게 **유스케이스 다이어그램**과 핵심 **시퀀스 다이어그램**으로 설명하고 확인받는다. 클래스 다이어그램은 개발자용이고, 사용자 확인에는 유스케이스와 시퀀스가 낫다.

### 5단계. 객체지향 설계 절차와 시스템 설계

OOD는 분석에서 "무엇을 해야 하는지" 정리한 것을 "어떻게 구현할지"로 구체화한다. 일반 절차는 **문제 정의 → 요구 명세화 → 객체 연산 정의 → 객체 인터페이스 결정 → 객체 구현** 순이며, 구현은 항상 마지막이다. 이 스킬에서 문제 정의와 요구 명세화는 `plan.md`·`srs.md`가 이미 했으므로 연산 정의부터 시작한다.

럼바우 설계는 두 층이다. 먼저 **시스템 설계**:

1. **서브시스템 분할.** 분석 모델의 클래스들을 서브시스템(패키지)으로 묶는다. 묶는 기준은 같은 엔티티를 다루는가(통신적 응집 이상). 규모가 크면 적당한 크기의 서브시스템으로 나누는 것이 설계와 유지보수에 직접 영향을 준다.
2. **계층 구조.** 표현(화면) → 응용(서비스) → 도메인(엔티티·규칙) → 인프라(저장소·외부 연동). 하위가 상위를 모르게 한다.
3. **동시성.** 여러 사용자가 동시에 같은 객체를 바꾸는 곳(수강신청 정원, 성적 입력)을 찾아 잠금·트랜잭션 경계를 정한다. 객체는 순차적으로도, 동시적으로도 구현될 수 있다.
4. **자원·배치.** 어느 서브시스템이 어느 프로세스·서버에서 도는가. 외부 시스템 연결은 어디서 하는가.
5. **제어 방식과 경계 조건.** 요청-응답인가 이벤트 구동인가. 시작·종료·장애 시 동작.
6. **패키지 의존도**를 그린다. 상자 = 패키지, 화살표 = import·호출 방향, 화살표마다 **무엇을 넘기는지** 적는다. 이 그림이 `sw-design review`의 입력이다.

### 6단계. 객체 설계

분석에서 정의한 클래스·속성·관계·메시지를 **코드 수준에 가깝게** 구체화한다.

1. **정보와 처리를 모듈화.** 데이터와 그 데이터를 다루는 메소드를 한 클래스에 **캡슐화**한다. 속성은 private, 접근은 public 메소드로. 외부가 알 것은 "무엇을 하는가"이지 "어떻게 하는가"가 아니다(정보 은닉).
2. **연산의 알고리즘과 자료구조**를 정한다. 1단계 연산마다 입력·출력·처리 단계를 쓴다. 컬렉션 선택(목록인가, 키 조회인가), 정렬·검색 방식.
3. **데이터 접근 경로 최적화.** 자주 함께 조회되는 객체는 참조를 직접 두고, 드문 조회는 저장소를 거친다. 조회 경로가 3단계 이상(a.getB().getC().getD())이면 메소드를 올려 줄인다.
4. **상속 구조 재정비.** 공통 속성·연산이 두 클래스 이상에 있으면 상위 클래스로 올린다(일반화). 상위 클래스에만 쓰이는 연산을 하위가 억지로 가지고 있으면 내린다(특수화). 추상 클래스(`abstract`)는 직접 인스턴스를 만들지 않는 상위 개념에 쓴다.
5. **다형성 적용 지점.** 같은 메시지에 객체마다 다르게 반응해야 하는 곳(절대평가/상대평가 등급 계산, 알림 채널)에 상위 타입 + 오버라이딩을 쓴다. `if type == A then … else if type == B` 분기가 세 곳 이상 반복되면 다형성 후보다.
6. **인터페이스 결정.** 클래스마다 public 메소드의 시그니처(이름, 매개변수, 반환, 예외)를 확정한다. 이것이 클래스 간 계약이다. 매개변수는 필요한 값만 넘긴다(결합도).
7. **클래스와 관계를 모듈 단위로 구성.** 5단계 서브시스템 안에서 클래스 배치를 확정한다.
8. 설계 내용을 문서화한다. 클래스 명세표를 설계 수준으로 갱신한다.

부치(Booch) 설계는 DFD로 객체를 분해하고 인터페이스를 정의해 Ada로 옮기는 기법, Wirfs-Brock 계열은 서브시스템별로 자료 추상화 → 속성 → 연산 → 메시지 → 시나리오 검토 → 상속 도입 순으로 가는 기법이다. 핵심은 모두 같다. 객체를 중심으로 나누고, 인터페이스를 정하고, 시나리오로 검증하고, 상속으로 재사용한다.

판정 질문: 모든 속성이 private인가? public 메소드마다 시그니처가 확정되었는가? 같은 코드가 두 클래스에 중복된 곳이 0개인가?

### 7단계. UML 다이어그램 정리

UML(Unified Modeling Language)은 럼바우(OMT)·부치·제이콥슨의 방법론을 하나로 통합한 **표준 모델링 언어**이며 OMG(Object Management Group)가 표준으로 지정했다. 요구사항을 정확히 명세하고, 설계 결정을 눈에 보이게 하고, 분석–설계–구현의 간격을 줄이고, 이해관계자 간 의사소통을 돕는다. 실시간·분산 시스템을 포함해 어떤 시스템에도 쓸 수 있다.

다섯 가지를 쓴다. 언제 그리는지가 중요하다.

| 다이어그램 | 보여 주는 것 | 모델링 종류 | 언제 |
|-----------|-------------|------------|------|
| 유스케이스 | 액터가 시스템으로 무엇을 하는가 | 기능(사용자 요구) | 분석 초기. 사용자 확인용 |
| 클래스 | 클래스·속성·연산·관계 | 정적(구조) | 1단계 객체 모델. 설계의 뼈대 |
| 시퀀스 | 객체 간 메시지의 시간 순서 | 동적 | 2단계 사건 추적도. 핵심 시나리오마다 |
| 상태 | 한 객체의 상태 변화 | 동적 | 2단계. 생애주기가 있는 클래스마다 |
| 활동 | 처리 흐름(분기·병렬) | 동적 | 복잡한 업무 흐름. DFD와 비슷한 역할 |

표기법과 예는 `references/uml-diagrams.md`. 유스케이스 다이어그램의 구성 요소는 액터·유스케이스·관계 셋이고 객체(Object)는 들어가지 않는다. 유스케이스 이름은 동사구("성적을 입력한다")로 쓴다.

mermaid로 그린다. 텍스트 저장소에서 diff가 보이고 코드 리뷰에서 함께 검토할 수 있다.

### 8단계. 구현 지침과 테스트 순서

1. **구현 지침.** 설계 → Java 코드 변환 규칙을 적는다. 클래스 → `class`, 속성 → `private` 필드 + getter/setter(필요한 것만), 생성자로 필수 속성 초기화, `this`로 필드와 매개변수 구분, 상속 → `extends`, 다형성 → 오버라이딩, 추상 개념 → `abstract class` 또는 `interface`. 상세는 `references/java-implementation.md`. 클래스를 **절차적 언어로 기술하지 않는다.** 객체지향 언어(Java, C++, Python 등)로 구현한다.
2. **테스트 순서**를 적어 `sw-test`에 넘긴다. 객체지향 테스트는 **단위 테스트(= 클래스 테스트) → 통합 테스트 → 검증 → 시스템 테스트** 순이다. 통합 테스트는 두 가지 중 고른다.
   - 스레드 기반: 하나의 입력·사건에 응답하는 데 필요한 클래스들을 묶어 한 스레드로 테스트 (예: "성적 입력" 요청 → GradeScreen, GradeService, Grade, GradePolicy, GradeRepository).
   - 사용 기반: 독립 클래스(아무도 의존하지 않는 것)를 먼저, 그것을 쓰는 종속 클래스를 다음에. 패키지 의존도의 역순.
3. `srs.md` 추적표의 "설계 요소" 열을 최종 확정한다.
4. **`$sw-design review`를 실행**해 패키지 의존도를 검증한다. 결과가 불합격이면 5~6단계로 돌아온다.

| 항목 | 합격 조건 |

## 체크리스트

- [ ] 객체 모델을 가장 먼저 만들었다 (동적·기능 모델보다 앞)
- [ ] 명사를 클래스 후보로, 동사를 연산 후보로 뽑았다 (반대가 아니다)
- [ ] 제외한 명사마다 사유를 적었다
- [ ] 모든 클래스에 "그리고/및" 없는 한 문장 책임이 있다
- [ ] 상속은 "~의 한 종류"인 곳에만 썼다. 코드 재사용만을 위한 상속이 없다
- [ ] 다중 상속을 쓰지 않았다. 필요한 곳은 인터페이스로 풀었다
- [ ] 상태가 바뀌는 클래스마다 상태도가 있고, 시작·종료 상태가 있다
- [ ] 상태도의 사건이 모두 어떤 클래스의 연산과 대응한다
- [ ] 기능 모델은 SRS의 DFD를 재사용했고, 프로세스마다 연산이 대응한다
- [ ] 모든 속성이 private이고 접근은 public 메소드로만 한다
- [ ] 메소드는 객체가 메시지를 받을 때 실행된다는 전제로 시퀀스를 그렸다 (인터럽트나 입력 장치가 메소드를 직접 실행하지 않는다)
- [ ] public 메소드마다 시그니처가 있다
- [ ] 타입 분기가 반복되는 곳을 다형성으로 바꿨다
- [ ] 유스케이스 다이어그램에 객체(Object)를 넣지 않았다. 유스케이스 이름이 동사구다
- [ ] 클래스 다이어그램이 객체 모델(정적)을, 시퀀스·상태·활동이 동적 모델을 담당한다
- [ ] 패키지 의존도에 화살표마다 넘기는 것을 적었다
- [ ] 하위 계층이 상위 계층을 모른다
- [ ] "모듈화는 객체지향 고유 개념"이라고 쓰지 않았다
- [ ] 구현 지침에서 클래스를 절차적 언어가 아니라 객체지향 언어로 구현한다고 명시했다
- [ ] 테스트 순서를 단위(클래스) → 통합 → 검증 → 시스템으로 적었다
- [ ] 추적표의 설계 요소 열을 채웠다
- [ ] `$sw-design review`를 실행했거나 다음 단계로 명시했다

## 자주 하는 실수

- **동적 모델부터 그린다.** 객체가 정해지기 전에 시퀀스를 그리면 참여자 이름이 계속 바뀐다. 객체 모델이 먼저다.
- **명사를 전부 클래스로 만든다.** "학번", "점수"는 속성이다. 클래스가 50개를 넘으면 속성을 클래스로 만든 것이 없는지 본다.
- **데이터만 있는 클래스와 메소드만 있는 클래스로 갈라진다.** `StudentData` + `StudentManager`는 절차지향이다. 데이터와 그것을 다루는 메소드를 한 클래스에 둔다.
- **상속을 코드 재사용 도구로만 쓴다.** `Student extends Person`은 맞지만 `Grade extends Student`(학생의 속성을 쓰려고)는 틀렸다. is-a가 아니면 연관이다.
- **상태도를 모든 클래스에 그린다.** 상태가 안 바뀌는 참조 클래스에는 필요 없다. 반대로 생애주기가 있는 클래스(수강신청)에 안 그리면 전이 조건이 코드에서 제각각이 된다.
- **DFD를 버리고 기능 모델을 새로 그린다.** SRS의 DFD가 기능 모델이다. 재사용하고 연산에 대응시킨다.
- **유스케이스에 시스템 내부 동작을 쓴다.** 유스케이스는 액터가 시스템으로 얻는 가치("성적을 조회한다")이지 내부 단계("DB에서 성적을 읽는다")가 아니다.
- **시퀀스 다이어그램의 메시지 이름이 클래스 연산과 다르다.** 시퀀스의 `saveGrade()`와 클래스의 `enterGrades()`가 따로 놀면 구현자가 어느 쪽을 따를지 모른다.
- **getter/setter를 모든 속성에 기계적으로 만든다.** 캡슐화가 깨진다. 외부가 정말 바꿔야 하는 속성에만, 검증을 넣어서 만든다.
- **패키지 의존도를 안 그리고 끝낸다.** 클래스 다이어그램만으로는 순환 의존과 쓰레기통 패키지를 못 찾는다.
- **E-R 다이어그램만으로 객체 모델을 대신한다.** ERD는 데이터 관계만 보여 주고 연산·메시지·다형성을 표현하지 못한다. 데이터 설계의 입력으로는 쓰되 객체 모델은 클래스 다이어그램으로 그린다.
