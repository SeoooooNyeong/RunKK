## 인자

`$sw-estimate` 뒤에 이어 쓴다: `[docs/sw/plan.md 경로 (생략 가능)]`

## 목적

"이 프로젝트에 돈·시간·사람이 얼마나 드는가"를 근거가 있는 숫자로 고정한다.
산출물 `docs/sw/estimate.md`의 노력(인월)과 기간은 `sw-schedule`이 인원 배치와 일정의 입력으로 쓰고, 비용은 계획서의 예산 상한과 비교해 계약 여부를 판단하는 근거가 된다.
너무 적게 잡으면 기간 내에 끝낼 수 없고 품질이 떨어진다. 너무 많이 잡으면 계약을 따지 못한다. 그래서 한 기법으로 끝내지 않고 반드시 교차 검증한다.

## 입력

- `docs/sw/plan.md` (없으면 `$sw-plan`을 먼저 안내하고 중단). 사용할 절: 3.1 기능 목록(포함·제외), 3.2 성능, 3.5 신뢰도, 3.3 제약 조건의 예산 상한과 마감 기한, 7절 재사용 가능 소프트웨어.
- 사용자에게 물어야 할 정보
  - 조직의 과거 프로젝트 데이터가 있는가 (생산성 LOC/인월, 유사 프로젝트 실적 인월)
  - 사용 언어·프레임워크 (기능 점수를 LOC로 환산할 때 필요)
  - 1인월 인건비 (직급별 평균)
  - 내부 전문가 2명 이상에게 의견을 받을 수 있는가 (하향식 기법 가능 여부)

## 절차

### 1. 비용 결정 요소 정리

계산에 앞서 이 프로젝트의 비용을 움직이는 요소를 계획서에서 뽑아 적는다. 이 표가 기법 선택과 보정의 근거가 된다.

| 요소군 | 항목 | 계획서 출처 | 비용에 미치는 방향 |
|--------|------|-------------|-------------------|
| 제품 | 복잡도 | 3.1 기능, 3.4 인터페이스 수 | 복잡할수록 증가 |
| 제품 | 규모 | 3.1 기능 수 | 클수록 증가 (비례 이상) |
| 제품 | 신뢰도 | 3.5 신뢰도 | 높을수록 증가 |
| 자원 | 인적 자원 능력·경험 | 7절 인적 | 높을수록 감소. 인건비가 비용의 대부분 |
| 자원 | 하드웨어·소프트웨어 도구 | 7절 환경, 재사용 SW | 도구·재사용이 많을수록 감소. 하드웨어 성능 자체는 영향이 작다 |
| 기간 | 개발 기간 | 3.3 마감 기한 | 같은 일을 짧게 끝낼수록 증가 (인력·장비 추가 투입) |

판정 질문
- 마감 기한이 외부 사건에 묶여 있는가? 그렇다면 기간 압축 비용을 뒤에서 별도로 계산한다.
- 유지보수 비용은 여기서 추정하지 않는다. 개발 전에는 개발 기간·노력·인원만 추정한다.
- 산정 기법을 바꾼다고 실제 비용이 바뀌지 않는다. 기법은 계산 도구일 뿐이다. 기법마다 값이 다르면 그 차이의 원인(입력 가정)을 찾는다.

### 2. 기법 선택

상황에 따라 **최소 두 가지**를 고른다. 하나는 규모 기반(상향식 또는 수학적), 하나는 경험 기반(하향식)이 되도록 한다.

| 상황 | 1차 기법 | 교차 검증 기법 |
|------|----------|----------------|
| 과거 유사 프로젝트 데이터가 있다 | LOC(조직 생산성 적용) | 전문가 감정 또는 델파이 |
| 과거 데이터가 없고 기능 목록은 명확하다 | 기능 점수(FP) → LOC 환산 → COCOMO | 델파이 |
| 요구가 아직 모호하다 (제안 단계) | 전문가 감정 (예비 추정) | 기능 점수 상·하한 |
| 대규모·장기, 인력 투입 곡선이 중요하다 | COCOMO Intermediate | Putnam |
| 언어가 여러 개이거나 아직 정해지지 않았다 | 기능 점수 | 델파이 |
| 단계별 인원 배치까지 필요하다 | Effort per Task | LOC 또는 COCOMO |

기법별 상세 절차와 공식은 다음을 읽는다.
- 하향식(전문가 감정, 델파이): `references/top-down.md`
- LOC, 생산성·노력·비용·기간 공식, Effort per Task: `references/loc-and-formulas.md`
- COCOMO(Basic, Intermediate, Detailed, 유형별 상수): `references/cocomo.md`
- 기능 점수(5요소, 가중치, 영향도 보정, LOC 환산), Putnam: `references/function-point.md`

### 3. 규모 산정

1. 기능 점수를 쓰는 경우: 계획서 3.1 기능 목록을 입력·출력·질의·내부 파일·외부 인터페이스로 분해하고 복잡도별 가중치를 곱해 미조정 기능 점수를 구한 뒤 영향도 보정 계수를 곱한다. 언어별 환산 계수로 LOC를 구한다.
2. LOC를 직접 추정하는 경우: 모듈별로 낙관치(a), 기대치(m), 비관치(b)를 받아 `E = (a + 4m + b) / 6`으로 모듈 LOC를 구하고 합산한다.
3. 재사용 모듈이 있으면 신규 개발 LOC와 재사용 LOC를 분리한다. 재사용분은 수정 비율만큼만 신규 환산 LOC에 더한다.
4. 판정 질문: 두 방법의 규모가 20% 이상 차이 나는가? 그렇다면 기능 분해가 빠졌거나 환산 계수가 잘못된 것이다. 차이의 원인을 찾아 적는다.
5. 중간 결과: 규모(KLOC), 산정 근거표.

### 4. 노력 산정

1. LOC 기반: `노력(인월) = 총 LOC ÷ 1인당 월 생산성(LOC/인월)`. 생산성은 조직의 과거 실적을 쓴다. 없으면 COCOMO로 간다.
2. COCOMO: 규모와 신뢰도·복잡도로 프로젝트 유형(Organic / Semi-detached / Embedded)을 정하고 `노력 = a × (KLOC)^b`를 계산한다. 비용 영향 요인이 뚜렷하면 Intermediate로 보정한다.
3. 하향식: 전문가 2명 이상의 추정을 받는다. 편차가 크면 델파이로 수렴시킨다.
4. 세 값을 나란히 놓고 차이를 설명한다. 조직 실측 데이터가 있으면 그것을 우선하되, 공식 모델이 크게 높게 나오면 그 차이를 예비 노력 또는 위험으로 기록한다.
5. 중간 결과: 노력(인월) 확정값, 기법별 비교표.

인월(Person-Month, PM)은 **작업량**이다. 기간이 아니다. 1명이 10개월 하면 10 PM, 2명이 5개월 해도 10 PM이다. "개발 기간 5개월"과 "24 PM"을 직접 비교하지 않는다.

### 5. 기간과 인원

1. `기간(개월) = 노력(인월) ÷ 투입 인원`. 마감이 고정되어 있으면 `인원 = 노력 ÷ 기간`으로 거꾸로 구한다.
2. COCOMO 명목 기간 `기간 = c × (노력)^d`와 비교한다. 요구 기간이 명목 기간보다 짧으면 기간 압축이다. 압축 비율을 적고, 인력 추가에 따른 의사소통 비용 증가를 예비비에 반영한다.
3. 판정 질문: 인원이 소수점으로 나오는가? 올림한다. 올림으로 생긴 여유는 테스트·문서 작업에 배정한다(`sw-schedule`에 전달).
4. 중간 결과: 기간, 인원.

### 6. 비용 계산

1. `인건비 = 노력(인월) × 1인월 평균 인건비`.
2. 환경 비용(서버·도구·라이선스), 간접비(관리·교육·회의), 예비비(위험·압축)를 더한다. 예비비는 `plan.md` 위험표의 상위 위험을 근거로 비율을 정한다.
3. 계획서 3.3 예산 상한과 비교한다. 초과하면 범위 축소 후보(계획서 제외 목록 인접 기능)를 적어 `sw-plan` 재검토를 권한다.
4. 중간 결과: 비용 내역표, 예산 대비 판정.

### 7. 교차 검증과 확정

1. 기법별 노력 비교표를 만든다. 최솟값과 최댓값의 비율을 적는다.
2. 확정값을 고르고 그 이유를 한 문단으로 쓴다. 보통 조직 실측 데이터 기반 값을 고른다.
3. 확정값 ± 범위(낙관·비관)를 함께 적는다. 단일 숫자만 쓰지 않는다.
4. `templates/estimate.md` 양식으로 `docs/sw/estimate.md`에 저장한다.

## 판정 기준

- 규모 산정 기법 1개 이상, 노력 산정 기법 2개 이상을 썼다.
- 기법 간 노력 추정 차이가 30% 이내이거나, 초과 시 원인이 문서에 적혀 있다.
- 노력 단위는 인월(PM)이고, 기간(개월)과 혼용하지 않았다.
- 기간 = 노력 ÷ 인원 계산이 맞다 (소수점은 올림).
- 비용 = 인건비 + 환경 + 간접 + 예비비 네 항목이 모두 있다.
- 예산 상한 대비 판정(이내 / 초과)이 적혀 있다.
- 확정값에 낙관·비관 범위가 붙어 있다.
- 유지보수 비용이 산정 항목에 없다.

## 출력

- `docs/sw/estimate.md`. 양식은 `templates/estimate.md`.
- 완성 예시는 `examples/estimate.md` (학사관리 시스템: 약 9 KLOC, COCOMO Organic 2.4 × 9^1.05 ≈ 24 PM, 5명, 기간 = 24 ÷ 5 ≈ 5개월).
- 다음 단계: `$sw-schedule`. 노력(인월), 인원, 기간, 단계별 노력 배분(Effort per Task)이 일정과 조직 계획의 입력이 된다.
- 협업 모드: `docs/sw/OWNERS.md`가 있으면 저장 전에 그 규칙을 따른다. `git config user.name`으로 작성자를 찾아 그 사람 담당 파일만 고친다. 새 번호는 `[임시:FR-<이니셜>-1]` 형식으로 쓰고 산출물 버전은 올리지 않는다(변경 표시는 "(다음 판 변경)"). 목차 파일의 머리 헤더·문서 상태·목차, `docs/sw/README.md`, 공용 조각(추적표, 자료사전 등)에 들어갈 내용과 남의 파일에 고칠 것은 `docs/sw/pending/<브랜치 이름의 / 를 - 로>.md`에 적는다. 정식 번호와 버전은 공용 담당이 `$sw-sdlc merge`로 매긴다. 규칙 전문은 `docs/sw/OWNERS.md` 3절이다.

## 체크리스트

- [ ] 비용 결정 요소표에서 하드웨어 성능을 주요 요소로 올리지 않았다
- [ ] 사용자의 능력을 생산성 요소에 넣지 않았다 (개발자 능력, 팀워크, 제품 복잡도만 해당)
- [ ] 유지보수 비용을 추정하지 않았다
- [ ] 문서화·관리 비용을 LOC 산정 요소에 섞지 않았다 (간접비로 따로 계산)
- [ ] LOC 3점 추정 공식이 (a + 4m + b) / 6 이고 기대치에 가중치 4를 줬다
- [ ] COCOMO 유형이 Organic / Semi-detached / Embedded 셋 중 하나다 (medium, object, dynamic 같은 유형은 없다)
- [ ] COCOMO 규모 경계(Organic 50 KLOC 이하, Semi-detached 300 KLOC 이하, Embedded 300 KLOC 이상)와 선택이 맞는다
- [ ] COCOMO 결과 단위를 인월로 적었다
- [ ] 기능 점수 5요소(입력·출력·질의·내부 파일·외부 인터페이스)를 모두 셌다. 클래스 인터페이스 같은 항목은 요소가 아니다
- [ ] Putnam을 쓴 경우 Rayleigh-Norden 곡선과 SLIM 도구를, 기능 점수에는 ESTIMACS를 혼동 없이 연결했다
- [ ] "비용 산정을 나중으로 미룬다"는 선택지를 두지 않았다
- [ ] 기간을 짧게 잡으면 비용이 늘어난다는 방향으로 압축 비용을 계산했다 (반대로 쓰지 않았다)
- [ ] 둘째 줄 헤더 형식을 지켰다

## 자주 하는 실수

- 기법 하나로 숫자 하나만 낸다. 비용 추정은 소프트웨어공학에서 오차가 가장 큰 작업이다. 범위 없는 단일 값은 틀릴 확률이 거의 100%다.
- COCOMO 공식 결과를 그대로 쓴다. 1981년 상수는 프레임워크·도구·재사용이 없던 시절 생산성이다. 조직 실측 데이터가 있으면 그것을 우선하고, COCOMO는 상한 참고치로 쓴다.
- 인월을 기간으로 읽는다. "24 PM이니 24개월"이 아니다. 5명이면 약 5개월이다.
- 마감이 고정된 프로젝트에서 인원을 뒤늦게 늘려 기간을 맞추려 한다. 말기 인력 투입은 오히려 지연을 키운다(`sw-schedule`의 Brooks 법칙). 압축은 처음부터 인원과 예비비에 반영한다.
- 기능 점수를 셀 때 화면 수를 입력 수로 센다. 입력은 "시스템에 데이터를 넣어 내부 파일을 바꾸는 트랜잭션" 단위다. 화면 하나에 입력이 여러 개일 수도, 없을 수도 있다.
- 재사용 모듈을 신규 개발과 똑같이 LOC에 넣는다. 재사용분은 수정 비율만큼만 센다. 반대로 재사용을 0으로 치면 통합·적응 비용이 빠진다.
- 예비비 없이 예산 상한에 딱 맞춘다. 위험표 상위 3건이 모두 발생해도 버틸 수 있는 예비비 비율을 적는다.

## 근거
